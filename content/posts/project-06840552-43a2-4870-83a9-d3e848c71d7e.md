## 개발 배경과 핵심 문제

포트폴리오를 정리하면서 프로젝트 경험과 학습 기록이 GitHub·개인 노트 등 여러 곳에 흩어져 있어, 정리할 때마다 자료를 다시 모아야 했음. 기록을 한곳에 모아 다시 찾고, 에이전트와 함께 쓰고 고칠 수 있는 블로그를 직접 만듦.

설계 제약은 세 가지.

- **서버 자원**: OCI 일본 리전의 ARM 1코어·약 4GB 단일 VM. 주요 독자는 한국에 있으며 독자 기준 왕복 지연은 약 38ms.
- **운영 인력**: 설계·구현·운영을 1인이 담당.
- **작성 방식**: 사람과 에이전트가 같은 원고를 수정.

이 제약에서 다음 세 문제를 핵심 문제로 정의함.

- **P1 변경 추적성**: 사람과 에이전트가 함께 고치는 원고의 변경 내용을 검토하고 이력을 추적할 수 있어야 함.
- **P2 열람 성능**: 해외 리전의 소형 서버에서도 글을 열 때 본문이 빠르게 보이고, 독자 요청이 서버 부하로 이어지지 않아야 함.
- **P3 발행 일관성**: Git의 원고, DB의 글 정보, 디스크의 이미지를 결합한 공개 결과가 서로 다른 시점의 자료로 섞이지 않아야 함.

### 인프라·시스템 통합 구성도

```mermaid
architecture-beta
  %% layout: ken-blog-infrastructure
  group people[Users]
  group github[GitHub]
  group site[Pages workflow] in github
  group ci[API workflow] in github
  group ops[Manual operation]
  group oci[OCI ARM VM]
  group compose(ken:docker)[Docker Compose] in oci
  group data[External database]

  service writer(ken:user)[Author and agent] in people
  service repo(ken:git)[Git repository] in github
  service sitebuild(ken:github-actions)[Site build] in site
  service pages(ken:github)[GitHub Pages] in site
  service apibuild(ken:github-actions)[API CI] in ci
  service archive(ken:docker)[JVM image] in ci
  service operator(ken:user)[Operator] in ops
  service reader(ken:user)[Reader] in people
  service admin(ken:user)[Admin] in people
  service caddy(ken:caddy)[Caddy] in compose
  service api(ken:spring)[Java Spring Boot API] in compose
  service disk(ken:disk)[Image disk] in oci
  service db(ken:mysql)[MySQL] in data

  writer:R -[Push]-> L:repo
  repo:R -[Web changes]-> L:sitebuild
  repo:B -[API changes]-> L:apibuild
  sitebuild:R -[Publish]-> L:pages
  sitebuild:B -[Public API]-> T:caddy
  apibuild:R -[Archive]-> L:archive
  archive:B -[Review]-> R:operator
  operator:B -[Manual deploy]-> T:api
  reader:R -[Read]-> R:pages
  admin:T -[Manage UI]-> B:pages
  admin:R -[Admin API]-> L:caddy
  caddy:R -[HTTP]-> L:api
  api:R -[JDBC]-> L:db
  api:B -[Read only]-> T:disk
```

실선은 요청·데이터 접근, 초록 점선은 빌드·산출물 전달, 보라 점선은 검토 후 수동 운영 반영. API 응답은 요청의 반대 경로로 전달.

배포 경계는 GitHub(원고 저장·사이트 빌드·Pages 호스팅), OCI ARM VM(Caddy·API·이미지 디스크), 관리형 MySQL의 세 영역. 공개 화면은 GitHub Pages가 제공하고, API는 인증·메타데이터 관리와 빌드용 공개 데이터 제공을 담당함. 원고는 Git, 글 정보·관계·세션은 MySQL, 이미지 원본은 VM의 영속 디스크에 두고, 빌드 단계의 Node 빌더가 이 자료를 결합해 공개 페이지를 생성함.

## 핵심 문제별 설계와 검증

### P1. Git Markdown을 원고의 정본으로

**문제.** 초기에는 Next.js 화면의 웹 블록 편집기로 본문을 작성해 DB에 저장했음. 원고가 바뀐 내용을 diff로 검토하거나 수정 이력을 추적하기 어려웠고, 사람과 에이전트가 같은 원고를 같은 방식으로 다루기 어려웠음.

**검토한 대안.**

| 대안 | 판단 |
| --- | --- |
| 웹 편집기와 DB 저장 유지 | 변경 검토와 이력 추적 문제가 그대로 남음 |
| DB에 버전 이력 테이블 추가 | 이력 저장은 가능하지만 diff 검토 화면과 되돌리기 기능을 별도로 구현해야 함 |
| **Git 저장소의 Markdown을 정본으로 사용 (채택)** | diff·검토·되돌리기를 Git이 제공하고, 사람과 에이전트가 같은 파일을 같은 도구로 수정함 |

아키텍처·ERD 도식도 Mermaid 원문으로 원고에 포함해 설명과 같은 커밋으로 관리함.

**대가.** 본문(Git)과 글 정보(DB)가 서로 다른 저장소에 있게 되었고, 둘을 일관되게 발행하는 문제가 P3로 이어짐.

**검증.** 현재 API에는 본문을 저장하거나 조회하는 경로가 없음. 본문 변경은 모두 Git 커밋으로만 발생하며, 이 프로젝트 문서들의 개정도 커밋 단위로 검토함.

[기술적 의사결정과 검증](/ken-blog/post/doc-267e2237-7f38-4ea1-b04b-7c51d456c2b4/)

### P2. 빌드 시 정적 생성으로 열람 경로에서 API 제거

**문제.** 옛 구조에서는 브라우저가 화면 스크립트를 받은 뒤 API를 호출해 본문을 받아 그렸음. 프로젝트 문서 하나를 열 때 로그인 상태 확인 → 프로젝트 조회 → 문서 조회의 세 단계가 앞 단계 응답을 기다리는 순차 호출이었고, 이미지를 빼고도 글 한 편에 API 요청이 6회(로그인 상태·프로젝트·문서·역링크·CSRF 토큰·조회수 기록) 발생했음. 응답은 모두 캐시 금지(`no-store`)라 재방문에도 같은 요청이 반복됨. 순차 단계마다 왕복 지연(약 38ms)과 1코어 서버의 처리 시간이 더해지는 구조.

**검토한 대안.**

| 대안 | 판단 |
| --- | --- |
| 브라우저의 API 호출(CSR) 유지 | 순차 3단계 왕복과 요청 6회가 열람마다 반복됨 |
| Redis 캐시로 본문 조회 가속 | 실측에서 외부 Redis 조회가 DB 직접 조회보다 느렸음(본문 약 1KB 기준 중앙값 20.51ms 대 12.26ms, 각 10회). 서버 처리 시간을 줄여도 순차 왕복은 남음 |
| 요청마다 서버에서 렌더링(SSR) | 순차 왕복은 서버 안으로 옮겨지지만 모든 열람 요청이 1코어 서버의 렌더링 부하가 됨 |
| **빌드 시 정적 생성 (채택)** | 본문을 포함한 HTML 한 번의 응답으로 열람이 끝나고, 독자 요청이 API 서버에 도달하지 않음 |

**대가.** 글과 공개 상태의 변경은 Pages 재배포 후 반영되며, 발행 취소 후 재배포 전까지 이전 페이지가 남음.

**검증.** 현재 공개 페이지의 본문·이미지·목록·역링크는 모두 빌드 시 HTML에 포함되어 열람 중 API 요청이 없음. 본문이 초기 HTML에 있어 검색엔진이 본문을 수집할 때 스크립트 실행과 추가 API 호출을 기다리지 않아도 됨. [Google의 JavaScript SEO 가이드](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

### P3. revision 재검증으로 서로 다른 시점의 자료 혼합 방지

**문제.** 공개 페이지는 Git의 원고, DB의 글 정보, 디스크의 이미지를 빌드 시 결합해 만듦. 빌드가 자료를 수집하는 동안 관리자가 글 정보를 바꾸면 서로 다른 시점의 자료가 섞인 사이트가 발행될 수 있고, 원고 누락이나 손상된 이미지가 있으면 일부만 깨진 사이트가 배포될 수 있음.

**검토한 대안.**

| 대안 | 판단 |
| --- | --- |
| 검증 없이 수집한 그대로 빌드 | 서로 다른 시점의 자료가 섞이거나 일부가 깨진 사이트가 배포될 수 있음 |
| 빌드하는 동안 DB 쓰기 잠금 | 빌드 시간 동안 관리 기능이 멈추고, 빌드 실패 시 잠금 해제를 따로 보장해야 함 |
| **revision 기반 낙관적 검증 (채택)** | 관리 기능을 멈추지 않고, 수집 도중의 변경을 빌드 결과 확정 전에 감지함 |

API가 공개 메타데이터와 첨부 상태의 SHA-256 revision을 제공하고, 빌더가 수집 시작 때와 페이지 생성 후의 revision을 비교해 다르면 결과를 폐기함. Git 쪽은 배포 직전 `main`의 사이트 입력 변경 여부를 다시 확인함. 페이지는 임시 디렉터리에서 생성·검사하고, 수집·생성·검증 중 하나라도 실패하면 새 결과를 확정하지 않고 Pages 배포도 진행하지 않아 공개 중인 사이트가 그대로 유지됨.

**대가.** 빌드 중 관리자 변경이 있으면 빌드를 다시 실행해야 하며, 마지막 검증부터 배포 완료까지의 구간은 원자적으로 묶이지 않음.

**검증.** 빌드 파이프라인 회귀 검사에서 원고 누락, 수집 중 revision 변경, 첨부 접근 거부, 잘못된 MIME·이미지 시그니처, 리다이렉트 응답의 경우 새 결과를 확정하지 않고 기존 산출물을 유지하는지 확인함.
