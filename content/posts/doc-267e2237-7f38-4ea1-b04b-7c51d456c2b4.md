P3는 P1·P2를 택한 결과로 생긴 문제를 푸는 결정임. 본문(Git)과 글 정보(DB)를 빌드 때 합치기 때문에, 빌드 도중 관리자가 글 정보를 바꾸면 한 사이트에 서로 다른 시점의 자료가 섞일 수 있음.

## P1. Git Markdown을 원고의 정본으로

### 문제

초기에는 Next.js 화면의 웹 블록 편집기로 본문을 작성해 DB에 저장했음. 원고가 바뀐 내용을 diff로 검토하거나 수정 이력을 추적하기 어려웠고, 사람과 에이전트가 같은 원고를 같은 방식으로 다루기 어려웠음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 웹 편집기와 DB 저장 유지 | 변경 검토와 이력 추적 문제가 그대로 남음 |
| DB에 버전 이력 테이블 추가 | 이력 저장은 가능하지만 diff 검토 화면과 되돌리기 기능을 별도로 구현해야 함 |
| **Git 저장소의 Markdown을 정본으로 사용 (채택)** | diff·검토·되돌리기를 Git이 제공하고, 사람과 에이전트가 같은 파일을 같은 도구로 수정함 |

### 대가

본문(Git)과 글 정보(DB)가 서로 다른 저장소에 있게 되었고, 둘을 일관되게 발행하는 문제가 P3로 이어짐.

### 검증

현재 API에는 본문을 저장하거나 조회하는 경로가 없어 본문 변경은 모두 Git 커밋으로 남음. 2026-10-08 기준 원고 디렉터리의 변경 커밋은 41개이고, 이 중 아키텍처 문서 한 편만 20번 고쳤으며 개정마다 diff로 검토하고 되돌릴 수 있음.[* [아키텍처 문서의 커밋 이력](https://github.com/gjaku1031/ken-blog/commits/main/content/posts/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8.md)] 아키텍처·ERD 도식도 Mermaid 원문으로 원고에 들어 있어 설명과 같은 커밋에서 바뀜. 본문이 담긴 키를 보낸 요청은 400으로 거부됨([API 설계](/ken-blog/post/doc-6bf82223-5b13-49ae-894b-5da5a0de6ddf/) 참조).

## P2. 빌드 시 정적 생성으로 열람 경로에서 API 제거

### 문제

옛 구조에서는 브라우저가 화면 스크립트를 받은 뒤 API를 호출해 본문을 받아 그렸음. 프로젝트 문서 하나를 열 때 로그인 상태 확인 → 프로젝트 조회 → 문서 조회가 앞 단계 응답을 기다리는 순차 호출로 이어졌고, 이미지를 빼고도 문서 한 편에 API 요청이 6~9회(로그인 상태·프로젝트·문서·역링크·CSRF 토큰·조회수 기록 등) 발생했음. 응답은 모두 캐시 금지(`no-store`)라 재방문에도 같은 요청이 반복됨. 순차 단계마다 왕복 지연(약 38ms)과 1코어 서버의 처리 시간이 더해지는 구조.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 브라우저의 API 호출(CSR) 유지 | 순차 3단계 왕복과 요청 6회가 열람마다 반복됨 |
| Redis 캐시로 본문 조회 가속 | 실측에서 외부 Redis 조회가 DB 직접 조회보다 느렸음[* 본문 약 1KB 기준 중앙값 Redis 20.51ms, DB 12.26ms, 각 10회. 전환 전 격리 환경 측정]. 서버 처리 시간을 줄여도 순차 왕복은 남음 |
| 요청마다 서버에서 렌더링(SSR) | 순차 왕복은 서버 안으로 옮겨지지만 모든 열람 요청이 1코어 서버의 렌더링 부하가 됨 |
| **빌드 시 정적 생성 (채택)** | 본문을 포함한 HTML 한 번의 응답으로 열람이 끝나고, 독자 요청이 API 서버에 도달하지 않음 |

### 대가

글과 공개 상태의 변경은 Pages 재배포 후 반영되며, 발행 취소 후 재배포 전까지 이전 페이지가 남음. 재배포는 최근 성공한 20회 기준 중앙값 67초, 최대 345초 걸리고, 배포 뒤에도 Pages 캐시 때문에 최대 10분 동안 이전 페이지가 보일 수 있음.[* 2026-10-08 기준 Pages 워크플로 실행 시간. 캐시는 GitHub Pages의 `max-age=600`]

### 검증

같은 데이터를 넣은 세 구조를 로컬에 재구성해 비교함. 비교 대상은 본문을 API로만 받는 순수 CSR, 본문을 HTML에 미리 넣고 API도 호출하는 전환 직전의 하이브리드, 현재 정적 생성. 맥에서 잰 실제 왕복 지연(38.6ms)과 처리량을 브라우저에 적용하고, 세 구조 모두 GitHub Pages와 같은 캐시 정책으로 제공함. 시나리오 5개 × 캐시 2조건 × 네트워크 2조건의 20개 조합에서 각 15회 측정한 결과, 정적 구조가 모든 조합에서 본문 표시가 가장 빨랐음.

| 측정 항목(중앙값) | 순수 CSR | 하이브리드 | 정적 생성 |
| --- | ---: | ---: | ---: |
| ERD 문서 첫 방문, 본문 표시 | 747ms | 625ms | 463ms |
| 같은 조건, 모바일 네트워크(150ms·1.6Mbps) | 3,536ms | 1,582ms | 869ms |
| 대문에서 ERD 문서로 이동, 클릭 후 본문 표시 | 414ms | 701ms | 216ms |
| ERD 문서 한 번 열 때 서버 API 요청 | 6회 | 9회 | 0회 |
| 초당 5회 ERD 열람 60초, API 서버 CPU 평균/최대 | 17.1% / 42.2% | 25.6% / 66.0% | 요청 없음 |

> 정적 생성은 첫 방문 전송량이 가장 컸지만, API 응답을 기다리는 순차 단계가 없어 모든 조합에서 본문이 가장 빨리 보였음.

로컬 재구성 환경의 브라우저 측정이며, 네트워크 지연은 브라우저의 요청 단위 지연 주입[* Chromium DevTools Protocol의 네트워크 조건 에뮬레이션. TCP·TLS 핸드셰이크 왕복은 정확히 재현하지 않음]으로 근사함. 측정 방법과 전체 결과는 [정적 생성 전환 전후의 글 열람 지연 측정](/ken-blog/post/post-c342d140-8026-4137-8761-b5c3eecddc2c/) 참조.

## P3. revision 재검증으로 서로 다른 시점의 자료 혼합 방지

### 문제

공개 페이지는 Git의 원고, DB의 글 정보, 디스크의 이미지를 빌드 시 결합해 만듦. 빌드가 자료를 수집하는 동안 관리자가 글 정보를 바꾸면 서로 다른 시점의 자료가 섞인 사이트가 발행될 수 있고, 원고 누락이나 손상된 이미지가 있으면 일부만 깨진 사이트가 배포될 수 있음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 검증 없이 수집한 그대로 빌드 | 서로 다른 시점의 자료가 섞이거나 일부가 깨진 사이트가 배포될 수 있음 |
| 빌드하는 동안 DB 쓰기 잠금 | 빌드 시간 동안 관리 기능이 멈추고, 빌드 실패 시 잠금 해제를 따로 보장해야 함 |
| DB에 단조 증가 버전 번호를 두고 비교 | 모든 쓰기 경로에서 번호를 올려야 하고 하나라도 빠지면 감지하지 못함. 운영자가 SQL로 직접 고친 변경은 DB 트리거 없이는 놓치고, 초안 편집처럼 공개 결과와 무관한 변경에도 번호가 올라 불필요한 재빌드가 생김 |
| **공개 자료 해시(revision) 기반 낙관적 검증 (채택)** | 관리 기능을 멈추지 않고, 수집 도중의 변경을 빌드 결과 확정 전에 감지함. 공개 결과 자체로 계산하므로 어떤 경로로 바뀌어도 감지하고, 공개와 무관한 변경에는 값이 그대로임 |

revision은 공개 사이트에 들어갈 DB 자료 전체로 계산한 SHA-256 지문으로, 자료가 바뀌면 값이 바뀜.[* 공개 스냅샷 JSON과 공개 글의 첨부 연결 행(글 ID·첨부 ID·object_key·형식·크기·상태·수정 시각)을 합쳐 계산함. Git 원고는 포함하지 않으며, 원고 쪽 변경은 배포 직전 `main` 재확인으로 검사] API가 이 값을 공개 스냅샷과 함께 제공하고, 빌더가 수집 시작 때와 페이지 생성 후의 revision을 비교해 다르면 결과를 폐기함. Git 쪽은 배포 직전 `main`의 사이트 입력 변경 여부를 다시 확인함. 페이지는 임시 디렉터리에서 생성·검사하고, 수집·생성·검증 중 하나라도 실패하면 새 결과를 확정하지 않고 Pages 배포도 진행하지 않아 공개 중인 사이트가 그대로 유지됨.

### 대가

- 빌드 중 관리자 변경이 있으면 빌드를 다시 실행해야 함.
- 확인할 때마다 공개 자료 전체를 읽어 해시를 계산하므로, 글 수에 비례해 비용이 늚. 스냅샷 응답의 상한은 글 10,000건·약 8MB.
- 이미지 파일 바이트는 해시에 들어가지 않아, 같은 키로 파일을 덮어쓰면 감지하지 못함. 파일 교체는 항상 새 키로 함.[* [인프라 ADR](https://github.com/gjaku1031/ken-blog/blob/3074d80/docs/ADR/ADR_infra.md)의 기술 아이콘 직접 관리 절차]
- 마지막 검증부터 배포 완료까지의 구간은 원자적으로 묶이지 않음.

### 검증

빌드 파이프라인 회귀 검사에서 아래 실패 상황마다 새 결과를 확정하지 않고 기존 산출물을 유지하는지 확인함. 수집·검증 순서와 보장하지 않는 구간은 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)의 일관성 모델 절에서 다룸.[* [파이프라인 검사](https://github.com/gjaku1031/ken-blog/blob/3074d80/.github/pages/pipeline.test.mjs)]
