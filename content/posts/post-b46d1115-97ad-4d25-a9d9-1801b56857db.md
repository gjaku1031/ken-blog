핵심 문제 P2(제한된 자원에서의 열람 성능)에 관한 측정과 테스트 통과 기준을 모아 둔 목록임. 실험은 글마다 따로 있고 여기에는 결과 요약과 링크만 둠. 테스트 통과 기준은 이 글이 원본임. 분류는 설계(실험·평가·관찰)와 목적(확증·탐색)의 두 축으로 적음.

## 공개 스냅샷 회귀 기준

운영 실측이 아니라 격리 MySQL 통합 검사 `largeSnapshotsAreBoundedAndConsistent`의 통과 조건. 같은 분류의 공개 글 300개로 스냅샷을 만들어, 탐색 목록을 글마다 중복 직렬화하거나 조회가 글 수에 비례해 늘어나는 퇴행을 감시함.[* 조회 계수는 Hibernate `prepareStatementCount`와 jOOQ SELECT 리스너를 합산. 서비스의 실제 응답 상한은 공개 스냅샷 7,999,800바이트, 관리자 스냅샷 8,000,000바이트로 이 통과 조건과 별개]

| 검증 대상 | 입력과 통과 조건 | 해석 범위 |
| --- | --- | --- |
| 공개 글 수 | 한 분류에 공개 글 300개 | 다양한 실사용 분류·태그 조합까지 대표하지 않음 |
| 조회 계수 | Hibernate `prepareStatementCount` + jOOQ SELECT 계수 ≤ 10 | 해당 snapshot 호출 구간의 DB 접근 기준. HTTP 지연 기준 아님 |
| 응답 형식 | `version == 3` | 현재 서버 스냅샷 계약 확인 |
| 탐색 중복 | `navigation` 그룹 1개, 해당 그룹 항목 300개 | 300개 그룹을 만드는 검사가 아님 |
| 응답 크기 | 전체 payload의 JSON 직렬화 결과 < 500,000바이트 | 네트워크 압축 전 바이트. 실제 반환 크기의 측정 보고서와 구분 |
| 관리자 읽기 | REPEATABLE_READ 안에서 외부 변경 전후 두 조회가 동일 | 한 읽기 트랜잭션의 일관성 확인 |
| 커밋 후 재조회 | 글 300개를 유지하고 외부에서 바꾼 제목을 확인 | 이전 트랜잭션 밖에서는 새 결과를 읽는지 확인 |

큰 그룹 하나를 쓰는 fixture라 모든 그룹·문자열·관계 조합에서 같은 크기를 보장하지 않음. ## 측정하지 않은 것

- 현재 운영 이미지의 JVM 부하.
- 스냅샷의 글 수·그룹 수·문자열 길이를 바꾼 조회 수·응답 크기·지연.
- 정적 빌드의 원고·이미지 수와 번들 캐시 상태별 수집·렌더링·자산 생성 시간.
