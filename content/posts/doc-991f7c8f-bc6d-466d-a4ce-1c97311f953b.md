기능은 업무일지, 자료실, 권한 관리의 세 묶음이고, 누가 어떤 기능을 쓰는지는 코드가 정하지 않고 학원이 구성한 역할의 권한이 정함.

## 기능 범위

| 모듈 | 기능 묶음 | 필요한 권한 |
| --- | --- | --- |
| 업무일지 | 업무 배정과 전체 진행 조회 | `worklog.task.manage` |
| 업무일지 | 배정받은 업무 처리, 텍스트 보고와 첨부 | `worklog.task.perform` |
| 업무일지 | 상담 작성과 외부 ERP 전송 | `worklog.counsel.write` |
| 업무일지 | 날짜별 일일보고 항목과 설정 관리 | `worklog.journal.manage` |
| 업무일지 | 일일보고 작성과 제출 / 제출 현황 조회와 확인 | `worklog.report.write` / `worklog.report.review` |
| 업무일지 | 공지, 팀 일정, 담당 반 연결과 태그 | `worklog.notice.manage`, `worklog.event.manage`, `worklog.staff.manage` |
| 업무일지 | 캘린더와 개인일정, 알림장, 본인 반 직접 관리 | `worklog.calendar.use`, `worklog.notebook.write`, `worklog.selfclass.manage` |
| 자료실 | 폴더 열기, 만들기, 파일 올리기와 내려받기 | `storage.folder.list`, `storage.folder.create`, `storage.file.write`, `storage.file.read` + 그 폴더의 허용 |
| 자료실 | 이름 변경, 이동, 휴지통, 복원 / 영구 삭제 | `storage.node.modify` / `storage.node.delete` + 그 폴더의 허용 |
| 자료실 | 폴더 허용 목록 조회와 변경 | `storage.acl.read`, `storage.acl.manage` + 그 폴더의 허용 |
| 권한 관리 | 직원 등록과 소속 종료, 역할과 권한 편집, 역할 배정, 감사 기록 조회 | `access.membership.*`, `access.role.*`, `access.assignment.*`, `access.audit.read` |

권한 키는 코드가 정하고 배포로만 늘어남. 학원은 역할을 만들어 이 키를 고르고 직원에게 배정함. 자료실의 기능은 역할의 권한에 더해 대상 폴더의 허용 목록이 맞아야 열림.

## 역할 구성의 예

팀장·강사·다른 팀이라는 세 역할을 권한 조합으로 구성하면 아래와 같음. 역할 이름과 조합은 학원이 화면에서 바꿀 수 있음.

| 권한 묶음 | 팀장 | 강사 | 다른 팀 |
| --- | --- | --- | --- |
| 업무 배정, 일일보고 관리와 검토, 공지, 팀 일정, 담당 반 연결 | ○ | | |
| 업무 처리, 일일보고 작성 | | ○ | |
| 상담 작성, 알림장 | | ○ | ○ |
| 본인 반 직접 관리, 개인 상담일정 | | | ○ |
| 캘린더 | ○ | ○ | ○ |
| 자료실 목록·읽기 | ○ | ○ | ○ |
| 자료실 올리기 | ○ | ○ | |
| 자료실 관리, 권한 관리, 감사 기록 | ○ | | |

팀장에게는 업무 처리와 일일보고 작성 권한을 주지 않았음. 이 두 권한을 가진 사람이 "업무를 받는 사람"과 "일일보고를 쓰는 사람"의 집합이 되므로, 팀장이 가지면 전원 배정 업무의 담당자와 제출 현황의 분모에 팀장이 들어감.

## 업무의 종류와 완료 판정

| 종류 | 담당자 | 완료로 보는 조건 |
| --- | --- | --- |
| 일반 | 전원 또는 고른 사람 | 담당자가 완료로 표시. 텍스트 보고 필수나 첨부 필수를 걸었으면 그것이 있어야 표시됨 |
| MT | 전원 또는 고른 사람 | 월수금과 화목토를 모두 체크 |
| 전체 상담 | 전원 또는 고른 사람 | 가져온 명단의 학생 전원에게 상담을 보냄. 명단을 가져오기 전에는 완료가 아님 |
| 특강상담 | 만들 때 고정 | 만들 때 고정한 학생 전원에게 보냄. 맡은 학생이 없는 담당자는 완료로 봄 |
| 개인 상담일정 | 만든 사람 | 본인 담당 반의 학생 전원에게 보냄. 만든 사람만 봄 |

전원에게 배정한 업무의 담당자는 저장하지 않고 조회할 때 "업무를 받는 사람" 집합으로 계산함. 특강상담만 만들 때의 담당자와 학생 명단을 함께 고정함.

## 상태와 전이

### 일일보고

```mermaid caption="일일보고는 작성 중, 제출, 확인 순으로만 나아가고, 작성자는 확인 전까지만 제출을 되돌릴 수 있음"
stateDiagram-v2
    [*] --> DRAFT: 임시저장
    DRAFT --> DRAFT: 임시저장
    DRAFT --> SUBMITTED: 제출(다섯 단계 완료)
    SUBMITTED --> DRAFT: 작성자가 되돌림
    SUBMITTED --> CONFIRMED: 검토자가 확인
    CONFIRMED --> [*]
```

확인은 별도 상태가 아니고 제출 상태에 붙는 표시임. 제출하지 않은 보고는 확인할 수 없고, 다시 제출하면 확인 표시가 지워짐. DB의 CHECK 제약도 확인 표시가 제출 상태에만 붙도록 막음.

### 상담 전송

```mermaid caption="전송 중 표시가 커밋된 뒤에만 외부 ERP에 씀. 결과를 모르는 상담은 대조를 거쳐 둘 중 하나로 정리됨"
stateDiagram-v2
    [*] --> IDLE: 명단에서 생성
    IDLE --> IDLE: 주제·내용 저장
    IDLE --> PENDING: 보내기(내용 저장과 선점을 커밋)
    PENDING --> SENT: 외부 ERP가 기록함
    PENDING --> IDLE: 외부 ERP가 거부함
    PENDING --> SENT: 대조 결과 기록이 있음
    PENDING --> IDLE: 대조 결과 기록이 없음
    SENT --> [*]
```

`PENDING`과 `SENT`인 상담은 고치거나 다시 보낼 수 없음. 명단을 다시 가져올 때 써 둔 주제와 내용은 남기고, 명단에서 빠진 학생은 보내기 전인 상담만 지움. 가져온 명단이 비어 있으면 조회 실패일 수 있으므로 아무것도 지우지 않음.

## 대표 유저 플로우

### 일일보고 제출

```mermaid caption="다섯 단계의 완료 여부는 서버가 저장된 답, 외부 ERP, 업무 원장을 읽어 계산함. 화면이 보낸 완료 표시는 받지 않음"
flowchart TD
    %% legend: color:#fff7ed:#ea580c=강사 행동; color:#eff6ff:#2563eb=팀장 행동; color:#f1f5f9:#64748b=시스템 처리; round=시작·끝; diamond=판단
    start([강사가 작성 화면을 엶]) --> exists{그 날짜의 일일보고가 만들어져 있는가}
    exists -->|아니요| wait([팀장이 만들 때까지 작성 불가])
    exists -->|예| fill[체크리스트 답, 알림장 게시, 상담·출결 확인, 업무 표시]
    fill --> submit[제출 요청]
    submit --> gate[서버가 다섯 단계를 다시 계산]
    gate --> complete{모두 마쳤는가}
    complete -->|아니요| reject[남은 단계 이름과 함께 거부]
    reject --> fill
    complete -->|예| snapshot[그 순간의 담당 반, 알림장 게시 여부, 업무 상태를 보고에 적고 제출로 기록]
    snapshot --> review[팀장이 보고를 읽음]
    review --> confirmed{확인 처리}
    confirmed -->|확인| done([확인 완료. 더 고칠 수 없음])
    confirmed -->|아직| reopen{작성자가 되돌림}
    reopen -->|예| fill
    reopen -->|아니요| review
    classDef teacher fill:#fff7ed,stroke:#ea580c,color:#7c2d12,stroke-width:2px
    classDef lead fill:#eff6ff,stroke:#2563eb,color:#172554,stroke-width:2px
    classDef system fill:#f1f5f9,stroke:#64748b,color:#0f172a,stroke-width:2px
    class fill,submit teacher
    class review lead
    class gate,reject,snapshot system
```

| 단계 | 완료 조건 | 서버가 읽는 곳 |
| --- | --- | --- |
| 체크리스트 | 항목이 하나 이상이고 전부 체크, 필수 항목에는 확인 결과가 있음 | 저장된 답 |
| 알림장 | 그날 담당 반이 없거나 모든 반에 게시함 | 외부 ERP |
| 상담 확인, 출결 확인 | 확인 표시 | 저장된 답 |
| 업무 확인 | 그날이 기간에 드는 일반 업무를 모두 완료나 미완료로 표시함 | 업무 원장 |

MT와 상담 업무는 제출을 막지 않음. 담당 반이 없는 사람은 알림장 단계가 자동으로 통과됨. 제출한 뒤에 담당 반을 다시 가져오거나 업무 상태가 바뀌어도 낸 보고에 적힌 내용은 달라지지 않음.

### 자료실에 파일 올리기

```mermaid caption="올리기는 역할의 권한과 폴더의 쓰기 허용이 둘 다 있어야 통과하고, 통과한 뒤에는 작업 원장을 거쳐 저장소에 씀"
flowchart TD
    %% legend: color:#fff7ed:#ea580c=사용자 행동; color:#f1f5f9:#64748b=시스템 처리; round=시작·끝; diamond=판단
    start([폴더에서 파일을 고름]) --> locate[폴더와 조상을 원장에서 읽음]
    locate --> member{학원에 활성 소속이 있는가}
    member -->|아니요| denied([거부, 감사 기록])
    member -->|예| permission{역할에 올리기 권한이 있는가}
    permission -->|아니요| denied
    permission -->|예| acl{이 폴더나 조상에 쓰기 허용이 있는가}
    acl -->|아니요| denied
    acl -->|예| ledger[작업 원장에 기록하고 노드를 준비 상태로 만듦]
    ledger --> write[트랜잭션 밖에서 임시 이름으로 받아 크기와 해시 확인]
    write --> result{성공했는가}
    result -->|예| activate([최종 이름으로 확정, 노드 활성화])
    result -->|아니요| revert([노드를 실패로 정리, 원장에 오류 기록])
    classDef user fill:#fff7ed,stroke:#ea580c,color:#7c2d12,stroke-width:2px
    classDef system fill:#f1f5f9,stroke:#64748b,color:#0f172a,stroke-width:2px
    class start user
    class locate,ledger,write system
```

조상의 허용은 "하위 항목까지"로 준 것만 적용됨. 시연 구성에서 강사 역할은 올리기 권한을 가지지만 쓰기 허용은 교재 폴더에만 있어서, 시험지 폴더에는 올릴 수 없고 운영 문서 폴더는 목록에도 보이지 않음.

## 본인의 것만 다루는 규칙

| 대상 | 규칙 | 확인하는 곳 |
| --- | --- | --- |
| 업무 | 담당자가 아니면 처리하거나 보고할 수 없음 | 업무일지 |
| 다른 담당자의 보고와 첨부 | 담당자에게 내려가는 업무에는 본인 것만 들어 있음 | 업무일지가 응답을 만들 때 뺌 |
| 상담, 알림장, 출결 | 가져온 본인 담당 반 안에서만 열림 | 업무일지 |
| 개인일정, 개인 상담일정 | 만든 사람만 봄. 업무 관리 권한으로도 고치거나 지울 수 없음 | 업무일지와 컨트롤러 |
| 첨부 내려받기 | 올린 본인, 또는 업무 보고의 것이면 업무 관리 권한, 일일보고의 것이면 검토 권한 | 컨트롤러 → 권한 엔진 |
