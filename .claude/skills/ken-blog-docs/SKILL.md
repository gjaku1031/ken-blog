# ken-blog 문서 작성

ken-blog 문서는 대학원 진학용 포트폴리오이자, 이후 다른 프로젝트 문서의 템플릿이다. 이 스킬의 규칙은 ken-blog에서 사용자와 합의해 확정한 것이며, 결정의 근거와 이력은 [references/decisions.md](references/decisions.md)에 있다.

## 먼저 읽을 것

| 상황 | 읽을 파일 |
| --- | --- |
| 어떤 문서든 쓰거나 고칠 때 | 이 파일 전체, [decisions.md](references/decisions.md) |
| 문서 유형별 구성(넣을 절·넣지 않을 것) | [document-types.md](references/document-types.md) |
| 새 프로젝트 대문 | [landing-template.md](references/landing-template.md) |
| 다이어그램 | `docs/guide/mermaid.md`, ERD는 `docs/guide/erd.md`, 아키텍처는 `docs/guide/mermaid-architecture.md` (AGENTS.md 지침) |
| ken-blog 원고 대응표·인터뷰 기록 | `temp/review-notes.md` (있을 때) |

## 독자와 목표

- 독자는 컴퓨터공학 교수와 시니어 개발자다. "잘 만든 서비스 소개"가 아니라 "기술적 문제를 정의하고, 대안을 비교해 결정하고, 근거로 검증한 사람"으로 읽혀야 한다.
- 대문은 흥미를 주고 상세 문서로 보내는 입구다. 상세의 원본은 각 상세 문서 한 곳에 둔다.
- 문서를 고치기 전에 아래 기준으로 구조부터 검토하고, 재구성안을 사용자와 합의한 뒤 문장을 쓴다.

| 기준 | 확인할 질문 |
| --- | --- |
| 문제 정의 | 다루는 기술적 문제가 무엇인가. 대문의 핵심 문제(P1~Pn)와 연결되는가 |
| 기여 | 본인의 판단·결정·검증이 드러나는가. 에이전트·팀원이 한 일과 구분되는가 |
| 근거 | 주장마다 측정·테스트·코드 근거가 있는가. 수치에 대상·환경·표본·시점이 있는가 |
| 대안과 대가 | 검토한 대안, 선택 이유, 받아들인 비용이 있는가 |
| 정확한 용어 | 일관성·동시성·실패 처리를 표준 용어로 쓰고 보장 범위와 불일치 구간을 밝히는가 |
| 깊이 | 조작 절차보다 설계 판단의 비중이 큰가 |
| 한계 | 확인하지 못한 것과 구조적 한계를 숨기지 않는가 |
| 연결 | 상세 원본은 한 곳, 다른 문서는 요약과 링크인가 |

## 진행 절차

1. **검토**: 문서와 관련 코드를 읽고, 위 기준의 진단·코드와 다른 사실·재구성안·사용자에게 물을 질문(3~5개, 추천안 포함)을 제시한다.
2. **합의**: 개인 경험·담당 범위·선택 이유·측정하지 않은 성과는 사용자 답 전까지 쓰지 않는다. 사용자가 직접 결정하지 않은 설계는 이유를 지어내지 않고 사실만 쓴다.
3. **작성**: 편집 원본(`temp/NN-*.md`가 있으면 그것, 없으면 게시 원고)을 고친다.
4. **확인**: 아래 '배포 절차'의 사실 확인과 미리보기.
5. **배포**: 합의한 수정은 매번 게시 원고·커밋·push·Pages 배포·공개 화면 확인까지 한다.
6. **기록**: 확정 사항은 `temp/review-notes.md`에, 다른 프로젝트에도 적용할 규칙은 [decisions.md](references/decisions.md)에 새 번호로 추가하고 이 파일·document-types.md에 반영한다.

## 문체

- 문서 본문은 `~했음`, `~임`, `~함` 간결체. 존댓말·감상적 수사 금지. 사용자에게 하는 답변은 해요체.
- 메타 문장 금지: "이 문서는 ~를 다룸", "아래에서 설명함", 작성 경위·자료 수집 과정.
- 문서 첫머리는 그 문서의 핵심 주장 한 줄로 시작한다. 요약 문단을 반복하지 않되, 대제목 바로 아래에 중제목이 오지 않게 한 줄은 둔다.
- 판단 기록(문제·결정·대가·검증 같은 반복 구조)은 굵은 머리말 문단을 나열하지 않고 목록으로 쓴다. 비교한 대안·선택 이유·세부 조건은 한 단계 들여쓴 하위 목록으로 내린다.

```markdown
- **문제**: 웹 편집기와 DB 저장 구조에서는 원고 변경을 diff로 검토하기 어려웠음
- **결정**: Git 저장소의 Markdown을 본문 정본으로 삼음
  - 비교한 대안: 웹 편집기 유지, DB 이력 테이블 추가
  - 선택 이유: diff·검토·되돌리기를 Git이 제공함
- **대가**: 본문과 글 정보가 다른 저장소로 나뉨
- **검증**: API에 본문 저장 경로가 없음
```

- 일관성·동시성은 표준 용어로: 갱신 손실(lost update), 낙관적·비관적 동시성 제어, 최종적 일관성, TOCTOU, 확장-축소(expand/contract) 이관.
- 현재 구현·과거 기록·예정 기능을 구분한다. 수치는 대상·환경·표본·시점과 함께 쓰고, 측정 조건은 주석으로 뺀다.

## 블로그 표현 요소

본문만으로 쓰지 않고 용도에 맞게 쓴다. 렌더러는 HTML 태그(`<br>`, 외부 이미지)를 허용하지 않는다.

| 요소 | 문법 | 쓰는 곳 |
| --- | --- | --- |
| 캡션 | 이미지 `![설명\|dark=ID\|w=100\|a=center](attachment:ID)`, 도식 `` ```mermaid caption="설명" `` | 그림 설명과 범례. 그림 아래 설명 문단을 따로 두지 않음 |
| 인용 | `> 문장` | 절·문서의 핵심 결론. 문서당 1~2회 |
| 주석 | `[* 내용]` | 측정 조건·용어 정의·출처·세부 수치. 표 셀·표 머리글에도 사용 가능 |
| 접기 | `<details><summary>제목</summary>…</details>` | 원자료에 가까운 긴 표·필드 계약 |
| 위키 링크 | `[[글 제목]]` | 블로그 안의 다른 글 |
| 목록 들여쓰기 | `  - 하위 항목` | 판단 기록의 세부(대안·이유·조건) |

- 표 셀 안 줄바꿈은 렌더링되지 않는다. 여러 줄이 필요하면 표 아래 목록으로 뺀다. 표 셀의 `|`는 `\|`로 이스케이프한다.
- 스크린샷은 페이지와 반대 테마의 캡처를 쓴다(기본 이미지는 어두운 캡처, `dark=`에 밝은 캡처). 모의 데이터가 보이면 캡션에 밝힌다.

## 다이어그램

- Mermaid만 쓴다. 노드 ID에 `link`, `click`, `style`, `linkStyle`, `classDef` 같은 지시어 이름을 쓰지 않는다(렌더러가 거부).
- 도식은 원래 크기보다 확대되지 않는다(기준 글자 14px, ERD는 0.85배). 원래 폭이 본문(약 800px)의 두 배를 넘는 가로 흐름도는 글자가 7px 이하로 줄어드므로 `flowchart TD`로 그린다.
- 선 색은 지정할 수 없다(`linkStyle` 금지). 경로 구분은 선 모양(`==>` 굵은 선, `-->` 실선, `-.->` 점선)과 캡션 범례로 한다. 노드 색은 `classDef`의 6자리 HEX만.
- 아키텍처·시스템 도식의 라벨은 영어, 기능 흐름도는 한국어를 쓴다.
- 작성 후 `node .claude/skills/ken-blog-docs/scripts/check-mermaid.mts <원고.md>`로 렌더러 검사를 통과시키고, 미리보기로 실제 크기를 확인한다.

## ken-blog에서 쓰지 않는 내용

- 백엔드 언어 전환(Kotlin → Java) 이력과 이유. 현재 언어를 처음부터 쓴 것처럼 쓴다.
- 서버 리전을 고른 사정(무료 티어 등).
- 폐기·삭제한 기능: MCP, RAG·에이전트용 본문 조회 API, 관리자 위키 선언.
- 사용자가 직접 정하지 않은 설계의 "선택 이유"(DB 설계 세부, 편집 버전 방식, MySQL TLS 구성 등).

## 배포 절차

원고 위치는 `content/posts/{slug}.md`, 편집 원본은 `temp/NN-*.md`(대응표: `temp/review-notes.md`). 둘을 같은 내용으로 유지한다.

1. **사실 확인**: 경로·메서드·상태 코드·필드·테스트 이름·수치·설정값을 현재 코드와 대조한다. 운영 DB 관련 서술은 `.claude/skills/ken-blog-stack-badges/scripts/db.sh`로 읽기 전용 조회해 대조한다. 다른 곳이 있으면 배포하지 않는다.
2. **도식 검사**: `check-mermaid.mts`.
3. **테스트**: `npm test` (필요하면 `npm run test:browser`).
4. **미리보기**: `.claude/skills/ken-blog-docs/scripts/preview.sh <scratchpad>` 후 `node .claude/skills/ken-blog-docs/scripts/preview-shots.cjs <slug> <저장 디렉터리>`. 출력된 도식 크기와 캡처를 직접 본다.
5. **커밋·push·배포 요청**: 배포 전담 pane `deployment`가 있으면 직접 커밋하지 않고 `herdr agent prompt deployment`로 요청한다. 요청에는 요청자 이름, 커밋할 파일 목록(정확한 경로), 커밋 메시지, 확인할 공개 주소를 적는다. deployment가 없을 때만 직접 한다: 바뀐 게시 원고만 스테이징하고 `git push https://github.com/gjaku1031/ken-blog.git main`(SSH 원격은 호스트 키 문제로 실패, force 금지), 커밋 메시지 끝에 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
6. **Pages 확인**: 해당 커밋의 Pages 실행 결과를 확인한다. 배포 직전 `main`이 바뀌면 Pages가 의도적으로 실패하고 다음 실행이 반영하므로 최신 실행을 본다. 공개 주소 `https://gjaku1031.github.io/ken-blog/post/{slug}/`에서 바뀐 문구를 확인하고 주소를 사용자에게 알린다.

## 글 메타데이터(DB)

- 제목·요약·분류·소속·문서 순서·발행 상태는 DB에 있다. 단순 열 변경은 SQL, 편집 버전·연결 관계가 걸린 변경은 관리자 API(비밀번호는 사용자에게 받고 파일·커밋에 남기지 않음).
- 실행 전에 변경 전 값을 조회해 기록하고, SQL·요청을 사용자에게 보여 준 뒤 실행한다. DB 변경은 Pages를 다시 배포해야 공개 화면에 반영된다.
- 본문 이미지는 첨부로만 넣는다: 디스크 `{KEN_BLOG_ASSETS_DIR}/ken-blog/live/attachments/{UUID}.png`(소유자 10001:1001, 0640)에 두고 `attachments` 행(READY)과 `post_attachments` 연결을 만든다. 형식·권한 규칙은 `docs/ADR/ADR_infra.md`의 '기술 이름·아이콘의 직접 관리'와 같다.
