팀장이 업무와 체크리스트를 한 번 정해 두면, 강사의 일일보고와 상담이 그 정의를 따라 날마다 채워짐.

## 기능 범위

| 역할 | 기능 묶음 | 내용 |
| --- | --- | --- |
| 팀장 | 업무 배정 | 업무를 내고 기간·담당자·완료 조건을 정함. 업무별 진행률과 강사별 보고를 봄 |
| 팀장 | 일일보고 관리 | 날짜별 체크리스트를 만들고, 특강기간과 주간테스트 날짜를 정함. 제출 현황을 보고 확인 처리함 |
| 팀장 | 강사 현황 | 강사를 등록하고 담당 반을 정함. 팀장 권한과 다른 팀 권한을 켜고 끔 |
| 팀장 | 공지·일정·유틸리티 | 강사 화면에 띄울 공지, 팀 일정, 주간테스트 우수 학생 PPT·PDF 만들기 |
| 강사 | 일일보고 | 다섯 단계를 마치고 하루 한 번 제출함. 지난 날짜의 보고도 씀 |
| 강사 | 내 업무 | 받은 업무를 완료·미완료로 표시하고 보고와 첨부를 남김. 상담 업무는 학생별로 상담을 써서 외부 ERP로 보냄 |
| 다른 팀 | 본인 반·상담일정·알림장 | 본인 계정으로 담당 반을 불러오고, 본인만 보는 상담일정과 알림장을 씀. 일일보고 대상이 아님 |

팀장 권한을 받은 강사는 팀장 화면과 강사 화면을 오가며 씀. 강사에게는 본인이 담당인 업무와 본인의 처리 상태만 내려가고, 다른 팀에게는 본인이 만든 상담일정과 본인 반만 내려감.[* 역할별 화면 상태(`src/api/store.service.ts`의 `getState`)]

## 업무의 종류와 완료 판정

| 종류 | 담당자 | 완료로 보는 조건 |
| --- | --- | --- |
| 일반 | 전원 또는 고른 사람 | 담당자가 완료로 표시. 텍스트 보고 필수나 첨부 필수를 걸었으면 그것이 있어야 서버가 표시를 받음 |
| MT | 전원 또는 고른 사람 | 월수금(M)과 화목토(T)를 모두 체크 |
| 전체 상담 | 전원 또는 고른 사람 | 가져온 명단의 학생 전원에게 상담을 보내 외부 ERP에서 확인됨. 명단을 가져오기 전에는 완료가 아님 |
| 특강상담 | 만들 때 고정 | 만들 때 고정한 학생 전원에게 보냄. 맡은 학생이 없는 담당자는 완료로 봄 |
| 개인 상담일정 | 만든 사람(다른 팀) | 본인 반의 학생에게 상담을 쓰고 보냄. 만든 사람만 봄 |

전원에게 배정한 업무의 담당자는 저장하지 않고, 조회할 때 일일보고 대상 강사 전체로 계산함. 특강상담만 만들 때의 담당자와 학생 명단을 업무에 복사해 고정함(P3).[* 완료 판정(`docs/requirements.md` 4.1절)]

## 일일보고의 다섯 단계

일일보고는 팀장이 그 날짜를 만들어야 열림. 날짜를 만들 때 오늘의 체크리스트를 복사하고, 오늘 것이 없으면 그 날짜 직전의 체크리스트를 복사함.[* 체크리스트 복사(`src/api/store.service.ts`의 `createJournal`)]

| 단계 | 하는 일 | 완료 조건 |
| --- | --- | --- |
| 1 체크리스트 | 항목을 체크하고 확인 결과와 파일을 남김 | 모든 항목을 체크하고, 보고 필수 항목에 보고를 씀 |
| 2 알림장 | 담당 반마다 외부 ERP의 알림장을 불러와 새로 쓰거나 고쳐 게시함 | 담당 반 전부 게시함. 담당 반이 없으면 통과 |
| 3 상담 확인 | 외부 ERP에서 그날의 상담 기록을 불러와 읽음 | 확인했다고 표시 |
| 4 출결 확인 | 반별 출결과 과제 이행, 주간테스트 성적을 불러와 봄 | 확인했다고 표시 |
| 5 업무 확인 | 그날이 기간에 드는 업무를 완료·미완료로 표시함 | 기간 안의 일반 업무에 모두 표시함. MT와 상담 업무는 제출을 막지 않음 |

단계 사이는 자유롭게 오갈 수 있고, 다섯 단계를 모두 마쳐야 제출 버튼이 열림. 이 판정은 화면에서 하며, 서버는 제출할 때 단계별 조건을 다시 검사하지 않음. 그날의 보고를 처음 저장할 때 화면이 계산한 반 목록과 특강 여부가 서버의 계산과 같은지만 확인하고, 다르면 새로고침을 요구함(409).[* 단계 판정(`components/screens/Wizard.tsx`의 `stepDone`, `wizard-task-gate.test.cjs`), 제출 처리(`src/api/store.service.ts`의 `submitReport`)]

특강기간에 만든 날짜는 그날의 알림장·출결 단계에서 일반 반과 같은 요일의 특강 반을 함께 다룸. 제출한 보고에는 그날 실제로 다룬 반 목록이 함께 저장돼, 나중에 반을 다시 동기화해도 지난 보고의 반 목록은 바뀌지 않음(P3).

## 상태와 전이

### 일일보고

```mermaid caption="일일보고는 강사와 날짜마다 하나이고, 팀장의 확인은 제출된 보고에만 붙는 표시임. 확인된 보고는 강사가 되돌릴 수 없음"
stateDiagram-v2
    [*] --> draft: 임시저장
    draft --> draft: 임시저장
    draft --> submitted: 제출(다섯 단계 완료)
    submitted --> draft: 강사가 되돌림(확인 전)
    submitted --> confirmed: 팀장이 확인
    confirmed --> [*]
```

`confirmed`는 별도 상태가 아니라 제출 상태에 붙는 표시임. 제출하지 않은 보고는 확인할 수 없고, 다시 제출하면 확인 표시가 지워짐.[* 제출·확인·되돌리기(`src/api/store.service.ts`의 `submitReport`·`confirmReport`·`reopenReport`)]

### 상담 전송

```mermaid caption="상담 하나의 전송 상태. 보내기 전 단계(claimed)는 외부 ERP에 닿지 않았음이 확실한 구간이고, 보내는 단계(posting)에 들어간 뒤에는 대조나 사람의 판단으로만 끝남"
stateDiagram-v2
    [*] --> idle: 명단에서 생성
    idle --> claimed: 보내기(선점)
    claimed --> idle: 보내기 전 중단
    claimed --> posting: 보내기 전 건수 기록
    posting --> confirmed: 건수가 늘었음
    posting --> confirmed: 담당자가 찾음
    posting --> idle: 담당자가 없음을 확인
    confirmed --> claimed: 고쳐서 다시 보냄
```

보내기 전에는 주제와 내용을 몇 번이든 저장할 수 있음. 선점한 요청이 3분 안에 다음 단계로 가지 못하면 다른 요청이 선점을 회수해 `idle`로 되돌림. 보낸 뒤 다시 읽어 건수가 늘지 않으면 담당 강사가 외부 ERP를 직접 보고, 찾았으면 보낸 것으로 종결하고 없으면 다시 보낼 수 있게 되돌림. `claimed`와 `posting`은 DB에서 "전송 결과 확인 중"(`pending`) 하나로 묶여 있고, 이 동안에는 내용을 고치거나 다시 보낼 수 없음. 같은 내용으로 다시 보내기를 누르면 외부 ERP를 부르지 않고 지금 상태를 돌려줌. 팀장은 강사의 상담 전송을 대신 종결하지 못함.[* 상태 기계와 사람 종결(`counsel-delivery-store.test.cjs`, `counsel-api-reconcile.test.cjs`)]

![강사의 상담 업무 화면. 학생마다 상담 전송 상태(전송 완료, 미전송)와 부재·문자 기록이 있고, 보낸 상담은 고쳐서 다시 보낼 수 있음. 이름과 연락처는 모의 데이터이고 외부 ERP의 이름은 가렸음|dark=267|w=100|a=center](attachment:266)

전화 부재나 문자 안내는 한 학생에게 여러 번 남길 수 있어서, 상담과 따로 한 건씩 기록함. 한 건마다 같은 선점과 대조를 거치고, 같은 요청 식별자로 다시 오면 새로 만들지 않음.[* 부재·문자 기록(`counsel-absence-api.test.cjs`)]

### 상담 업무 처리

```mermaid caption="강사가 반 명단을 외부 ERP에서 가져와 학생별로 상담을 쓰고 보냄. 결과를 모르는 상담은 다시 보내지 않고 결과 확인을 거침"
flowchart TD
    %% legend: color:#eff6ff:#2563eb=강사; color:#f1f5f9:#64748b=시스템; round=시작·끝; diamond=판단
    start([상담 업무를 받음]) --> roster[반 명단 가져오기]
    roster --> merge[새 학생 추가, 빠진 학생은 대상에서 제외]
    merge --> write[학생별 상담 작성]
    write --> send[보내기]
    send --> result{외부 ERP에서 확인됨?}
    result -->|예| sent[전송 완료]
    result -->|모름| check[전송 결과 확인]
    check --> again{다시 읽어 확인됨?}
    again -->|예| sent
    again -->|아니요| human[담당자가 외부 ERP를 보고 종결 또는 한 번 다시 보내기]
    human --> sent
    sent --> all{모든 학생 전송?}
    all -->|아니요| write
    all -->|예| done([업무 완료])
    classDef teacher fill:#eff6ff,stroke:#2563eb,color:#172554,stroke-width:2px
    classDef sys fill:#f1f5f9,stroke:#64748b,color:#1e293b,stroke-width:2px
    class start,roster,write,send,check,human,done teacher
    class merge,result,sent,again,all sys
```

명단을 다시 가져와도 써 둔 주제와 내용, 전송 상태는 남음. 가져온 명단이 비어 있으면 조회 실패일 수 있으므로 아무것도 바꾸지 않음. 명단에서 빠진 학생의 행은 지우지 않고 대상에서만 빼므로, 다시 들어오면 써 둔 상담이 되살아남. 전송 결과를 확인 중인 학생은 명단에서 빠져도 행과 식별 정보를 바꾸지 않음.[* 명단 반영(`counsel-roster-reconcile.test.cjs`)]
