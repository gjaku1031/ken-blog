공개 화면은 GitHub Pages의 정적 파일이라 요청마다 권한을 검사할 서버가 없음. 그래서 권한이 필요한 작업은 모두 OCI VM의 API에서 검사하고, 공개 산출물에는 공개 조건을 통과한 자료만 넣음. 배포 경계는 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)에서 정의함.

## 배포 구조가 만든 보안 설계

### HTTPS 진입점

API 앞에는 Caddy를 두고 HTTPS를 종료함.[* [보안 설정](https://github.com/gjaku1031/ken-blog/blob/951bf54/src/main/java/io/github/gjaku1031/kenblog/global/config/SecurityConfig.java) · [Caddy 설정](https://github.com/gjaku1031/ken-blog/blob/951bf54/deploy/Caddyfile) · [운영 Compose](https://github.com/gjaku1031/ken-blog/blob/3074d80/deploy/compose.production.yaml)] 운영을 단순하게 하려고 별도 웹 서버 없이 Spring Boot 내장 서버만 두려 했으나, 공인 IP용 단기 ACME 인증서의 발급·갱신을 자동화하려고 Caddy를 둠. Caddy는 허용한 경로와 메서드만 API로 전달하고, 클라이언트가 보낸 전달 헤더를 지운 뒤 실제 접속 주소와 공유 키를 붙임. API는 공유 키가 맞을 때만 이 주소를 로그인 출처로 믿음. API의 호스트 포트는 loopback에만 열려 있음.

### 교차 사이트 쿠키와 CORS

관리 화면은 Pages(`https://gjaku1031.github.io`)의 정적 파일이고 API는 다른 출처에 있음. 그래서 관리 화면이 보내는 요청은 사이트 간 요청이 되고, 세션 쿠키가 출처를 넘어가야 함.

```mermaid caption="관리 화면과 API의 출처가 달라 세션 쿠키를 SameSite=None으로 보내고, CORS는 Pages 출처에만 자격 증명을 허용함"
sequenceDiagram
    %% legend: solid=요청; dotted=응답
    participant UI as 관리 화면(Pages 출처)
    participant Caddy as Caddy(API 출처)
    participant API as Spring Boot API
    UI->>Caddy: 사전 요청(OPTIONS)
    Caddy->>API: 허용 메서드면 전달
    API-->>UI: Pages 출처만 자격 증명 허용
    UI->>Caddy: 변경 요청 + 세션 쿠키 + CSRF 헤더
    Caddy->>API: 전달 헤더 교체 후 전달
    Note over API: CSRF 토큰, 세션, ADMIN 권한 확인
    API-->>UI: 결과
```

| 대상 | 설정 |
| --- | --- |
| 세션 쿠키 | `HttpOnly`, `Secure`, `SameSite=None`, `Partitioned` |
| 공개 조회(스냅샷·이미지) | `GET`·`HEAD`만 허용. 요청 출처가 인증 출처 목록에 있으면 자격 증명을 허용하고, 공개 출처 목록에만 있으면 자격 증명 없이 허용[* 운영은 공개·인증 출처 목록이 모두 Pages 출처 하나라, Pages에서 온 공개 조회도 자격 증명 허용 정책을 받음. 관리 화면의 스냅샷 조회는 쿠키를 싣지 않음(`credentials: omit`)] |
| 인증·관리 요청 | 인증 출처(운영: Pages)에만 자격 증명 허용. 관리 경로 메서드는 `GET`, `POST`, `PUT`, `DELETE` |

CORS를 통과해도 인증은 생기지 않으며, 관리 경로는 별도로 ADMIN 권한을 검사함. 허용 메서드는 실제로 쓰는 `GET`·`POST`·`PUT`·`DELETE`만 API와 Caddy에 둠. 이 구조의 대가로 관리 기능이 사이트 간 쿠키를 받아들이는 브라우저 정책에 의존함.

## 관리자 인증과 세션

계정은 운영자가 DB에 직접 등록한 관리자 한 명뿐이고 회원가입 API는 없음. 로그인은 서버 설정의 계정 이름과 저장된 비밀번호 해시를 비교하며, 폼 로그인과 HTTP Basic은 꺼져 있음. 세션 방식을 쓰는 이유는 [API 설계](/ken-blog/post/doc-6bf82223-5b13-49ae-894b-5da5a0de6ddf/)의 설계 원칙 절에서 다룸.

로그인에 성공하면 세션 ID를 바꾸고 기존 CSRF 토큰을 폐기함. 이후 요청마다 계정의 존재·활성·권한과 세션에 담은 인증 버전을 다시 확인함. 관리자 비밀번호나 설정이 바뀌면 인증 버전이 올라 이전 세션은 모두 거부됨. 세션 저장소인 DB가 장애이면 메모리 세션으로 우회하지 않고 503으로 응답함.

| 항목 | 계약 |
| --- | --- |
| 세션 저장 | Spring Session JDBC(MySQL) |
| 일반 로그인 | 비활동 8시간 |
| 로그인 유지 | 비활동 30일, 쿠키 수명 30일 |
| 로그아웃 | 세션·인증 정보·CSRF 토큰 폐기 |
| 인증 상태 행 누락 | 기존 세션 거부, 새 로그인 중단 |
| 비밀번호 입력 | 앞뒤 공백 보존, 빈 값과 UTF-8 72바이트 초과 거부 |

## 로그인 반복 시도 제한

`admin_auth_state`의 단일 행을 잠근 안에서 출처별 실패 상태와 전체 검증 예산을 함께 갱신해, 동시에 들어온 로그인 시도도 순서대로 셈.

| 제한 | 동작 |
| --- | --- |
| 출처별 실패 | 첫 실패부터 60초 고정 창 안에 5회 실패하면 차단. 차단 중의 요청으로 창을 연장하지 않음 |
| 전체 검증 예산 | 60초당 비밀번호 검증 30회 |
| 출처 저장 | 주소 원문 대신 해시, IPv6는 /64 단위로 묶음. 최대 4,096개 |

출처별 제한은 한 출처의 반복 시도를 막고, 전체 예산은 여러 출처에서 오는 시도가 비밀번호 해시 검증으로 서버 자원을 소진하는 것을 막음. 다만 분산된 출처가 전체 예산을 먼저 쓰면 정상 관리자도 잠시 로그인할 수 없음.[* [로그인 제한](https://github.com/gjaku1031/ken-blog/blob/3074d80/src/main/java/io/github/gjaku1031/kenblog/auth/service/AdminLoginAttemptService.java)]

## 공개 자료 경계

공개 스냅샷과 첨부 전달은 관리자 세션이 있어도 공개 조건을 생략하지 않음. 공개 조건은 [기능과 사용자 흐름](/ken-blog/post/doc-4cfccbd2-1972-4ad8-893a-6a8bf45744e1/)에서 다룸. 첨부는 공개 글과의 연결, READY 상태, PNG·JPEG 형식, 1바이트~10MiB 크기를 확인하고 실제 파일 크기와 대조한 뒤 전송함. 존재하지 않는 첨부와 접근할 수 없는 첨부는 같은 404로 응답해 비공개 첨부의 존재를 드러내지 않음.

오류 응답에는 내부 경로·SQL·예외 원문을 담지 않음. 예상하지 못한 오류는 운영 기록과 대조할 `eventId`만 응답에 붙임.[* [첨부 전달](https://github.com/gjaku1031/ken-blog/blob/3074d80/src/main/java/io/github/gjaku1031/kenblog/attachment/service/PostAttachmentDeliveryService.java)]

## 한계

- 공개 산출물 전체에 계정·세션 정보가 없음을 확인하는 별도 테스트는 없음.
- 관리 기능이 브라우저의 사이트 간 쿠키 정책에 의존함.
- 분산된 출처의 로그인 시도가 전체 예산을 소진하는 경우까지는 막지 못함.
- 발행 취소로 공개 저장소의 원고와 이미 배포된 정적 사본을 회수할 수 없음.
