| 항목 | 내용 |
| --- | --- |
| 소개 | 팀장이 정한 업무와 날짜별 체크리스트를 강사가 다섯 단계로 확인해 제출하고, 상담 기록을 외부 ERP로 보내는 학원 사내 웹앱 |
| 목적 | 날마다 다시 적던 업무 지시와 보고를 한 번 정해 두고 쓰게 하고, 외부 ERP와 주고받는 기록이 중복되거나 어긋나지 않게 함 |
| 개발 형태 | 개발 1인, 기획 1인. 요구사항은 운영진과 각 팀의 팀장에게서 받음 |

| 링크 | [![GitHub\|dark=61\|w=20\|a=center](attachment:60) GitHub](https://github.com/gjaku1031/npr-erp) |

Next.js 하나에 화면과 API를 함께 두고 Vercel의 서버리스 함수에서 돌리는 시스템임. 데이터의 원본은 Turso의 원격 DB이고, 함수 인스턴스마다 그 리플리카를 파일로 둠. 반·학생·출결의 원장은 학원이 쓰던 외부 ERP이며, 공개 저장소에서는 외부 ERP 연동을 포트와 모의 구현으로 대체했음.

## 담당 범위

- **요구사항 정리와 운영**: 시제품을 먼저 만들어 기획 담당자와 1차로 다듬고, 팀장이나 원장의 확인을 거쳐 요구사항을 정함. 강사로 일하며 직접 쓰면서 운영함
- **업무·일일보고 모델**: 업무 종류와 완료 판정, 날짜별 체크리스트, 다섯 단계 작성 흐름, 특강기간을 보고에 고정하는 규칙
- **직접 정한 설계**: 외부 ERP에 상담을 보낼 때의 선점과 대조, 서버리스 인스턴스 사이의 읽기 일관성과 갱신 손실 방지, 기술 스택(한 언어 풀스택, 관리형 플랫폼, SQLite 계열 DB)

## 개발 배경과 핵심 문제

학원은 기존 ERP에 딸린 업무일지를 쓰고 있었음. 표 하나로 된 화면이라 상담일지 쓰기처럼 날마다 반복되는 업무도 매번 다시 적어야 했고, 상담일지를 쓴 뒤에 상담한 학생의 이름을 업무일지에 한 번 더 적어야 했음. 팀장은 그날 확인할 사항을 퇴근 전후로 손으로 적었는데, 월요일부터 목요일까지 이어지는 업무는 나흘 모두 적어야 했음. 팀장이 항목을 빠뜨리면 그 업무를 하지 않는 사람이 생겼고, 작성이 늦어지면 팀의 퇴근이 늦어졌음.

업무일지를 새로 만들면서 세 가지를 바꿈.

| 불편 | 바꾼 것 |
| --- | --- |
| 날마다 반복되는 업무를 매번 다시 적음 | 일일보고의 체크리스트로 옮김. 날짜별 체크리스트는 오늘(없으면 직전 날짜)의 항목을 복사해 만듦 |
| 상담일지를 쓴 뒤 업무일지에 학생 이름을 다시 적음 | 일일보고가 그날의 상담 기록을 외부 ERP에서 불러와 보여 주고, 강사는 확인만 함 |
| 여러 날 이어지는 업무를 팀장이 날마다 적음 | 업무에 시작일과 마감일을 두면 그 기간의 일일보고에 자동으로 나타남 |

새 업무일지는 기존 업무일지를 완전히 대체했음. 퇴근 전에 업무일지를 마치는 데 필요한 클릭은 평균 50번쯤에서 10번 안으로 줄었음.

| 운영 기록 | 값 |
| --- | ---: |
| 참여 인원 | 13명[* 일일보고 대상 10명, 일일보고 없이 상담·알림장 기능만 쓰는 다른 팀 3명] |
| 일일보고를 연 날 | 55일[* 2026-07-13 ~ 2026-09-23. 운영은 이 기간으로 끝났음] |
| 제출된 일일보고 | 493건 |
| 하루 제출 수(중앙값) | 10건 |

설계 제약은 3가지.

- **반·학생·출결의 원장이 외부 ERP임**: 학원이 이미 쓰는 시스템이라 바꿀 수 없고, 응답이 늦거나 끊길 수 있음. 상담과 알림장은 그쪽에 써야 하는데, 상담 쓰기는 멱등하지 않고 쓴 기록을 가리킬 식별자를 돌려주지 않음
- **서버리스 함수와 관리형 DB 위에서 돎**: 사용자가 100명 안쪽이라 서버를 직접 꾸리지 않고 관리형 플랫폼을 씀. 요청마다 다른 함수 인스턴스가 처리할 수 있고, 인스턴스마다 DB 리플리카를 따로 가짐
- **개발과 운영을 거의 한 사람이 맡음**: 화면과 API를 한 언어로 두고, 별도 작업 서버나 메시지 큐 없이 요청 안에서 처리함

이 제약에서 다음 3개 문제를 핵심 문제로 정의함.

- **P1 외부 쓰기의 중복 방지**: 이 시스템이 같은 상담을 외부 ERP에 두 번 보내지 않고, 결과를 모르는 전송은 다시 보내지 않은 채 확인될 때까지 남아 있어야 함
- **P2 인스턴스 사이의 일관성**: 다른 인스턴스가 방금 쓴 변경이 다음 조회에서 사라져 보이지 않고, 긴 외부 조회를 낀 갱신이 그사이 다른 요청의 변경을 덮어쓰지 않아야 함
- **P3 시점 고정**: 외부 ERP의 반과 명단이 바뀌어도, 이미 만든 일일보고와 상담 업무의 대상이 바뀌지 않아야 함

## 주요 기능

| 기능 | 사용자가 할 수 있는 일 |
| --- | --- |
| 업무 | 팀장이 기간과 완료 조건(텍스트 보고, 첨부)을 걸어 업무를 내면, 강사가 처리하고 보고함. 기간에 드는 날의 일일보고에 자동으로 나타남 |

| 반 관리 | 외부 ERP의 반 목록을 불러와 강사마다 담당 반을 고름. 다른 팀은 본인 반과 상담일정, 알림장만 씀 |

### 주요 흐름

강사의 화면은 브라우저에서 돌고, 바꾸는 요청을 보내면 API가 변경 결과와 함께 갱신된 화면 상태를 돌려줘 다시 조회하지 않음. 일일보고 작성 중 알림장·상담·출결 단계는 API가 외부 ERP 포트로 그날의 기록을 읽어 보여 줌. 상담 전송은 원본 DB에서 선점한 요청 하나만 외부 ERP에 쓰고, 결과를 다시 읽어 확인한 뒤에 완료로 바꿈. 흐름별 경로와 실패 시 동작은 [아키텍처](/ken-blog/post/doc-c2513d8a-31f4-49df-a99a-675fca3305a3/)에서 다룸.

## 핵심 문제별 설계와 검증

문제마다 결정과 대표 근거만 요약함. 검토한 대안 표, 대가, 검증 상세는 [주요 기술적 의사결정](/ken-blog/post/doc-f47c5aab-4b47-412a-a28c-db6f0c36a314/)에서 다룸.

### P1. 선점과 건수 대조로 같은 상담을 두 번 보내지 않음

- **문제**: 외부 ERP의 상담 쓰기는 멱등하지 않아, 응답이 늦어 다시 누르거나 두 인스턴스가 같은 상담을 동시에 보내면 두 번 기록될 수 있었음
- **결정**: 원본 DB에서 읽은 상태를 조건에 넣은 갱신으로 전송을 선점하고, 보내기 직전에 외부 ERP의 같은 상담 수를 기록한 뒤 보내고, 다시 읽어 수가 늘었을 때만 완료로 바꿈
- **대가**: 결과를 모르는 상담은 재전송하지 않고 남겨 두므로, 담당 강사가 외부 ERP를 확인해 종결해야 함
- **검증**: 두 연결이 같은 상담을 동시에 선점하면 하나만 성공하고, 결과를 모르는 상담의 재확인은 외부 ERP에 다시 쓰지 않음을 테스트로 확인함[* 선점과 사람 종결(`counsel-delivery-store.test.cjs`), 결과 확인 경로(`counsel-api-reconcile.test.cjs`)]

### P2. 겨루는 변경은 원본 DB에서 처리함

- **문제**: 인스턴스마다 리플리카를 가지므로, 다른 인스턴스가 만든 업무가 다음 조회에서 사라져 보이거나 두 요청이 같은 강사의 반 정보를 서로 덮어쓸 수 있었음
- **결정**: 상태·보고 조회와 로그인 전에 원본을 당겨 오고 실패하면 요청을 실패시킴. 선점·특강상담 생성·명단 반영은 원본 DB의 트랜잭션에서, 강사 반 정보를 고치는 요청은 원본의 잠금 행으로 줄 세움
- **대가**: 조회마다 원본과 한 번 더 왕복하고, 반 정보를 고치는 요청은 동시에 하나만 진행됨
- **검증**: 원본을 당기지 못한 조회가 오래된 상태를 돌려주지 않고, 외부 조회 뒤에 바뀐 강사 정보가 있으면 반 전체 교체가 거부됨을 테스트로 확인함[* 읽기 일관성(`read-consistency-api.test.cjs`), 반 교체의 지문 검사와 잠금(`regular-class-sync.test.cjs`)]

### P3. 만든 시점의 대상을 복사해 고정함

- **문제**: 반과 명단의 원장이 외부 ERP라 달마다 바뀌는데, 지난 일일보고나 진행 중인 특강상담이 지금의 명단을 따라 바뀌면 진행률과 기록이 달라짐
- **결정**: 일일보고 날짜를 만들 때 특강기간 여부를, 특강상담을 만들 때 대상 월·담당자·학생 명단을 함께 저장함
- **대가**: 같은 명단을 업무마다 복사해 저장하고, 만든 뒤에 들어온 학생은 그 업무에 들어가지 않음
- **검증**: 반을 다시 동기화하거나 강사를 추가해도 특강상담의 명단·대상 월·진행률이 그대로이고, 강사 16명·학생 270명의 명단을 한 트랜잭션으로 고정함을 테스트로 확인함[* `special-feature.test.cjs`]

> 외부 ERP에 쓰는 일은 되돌릴 수 없으므로, 결과를 모르면 다시 보내지 않고 사람이 확인할 때까지 남겨 둠.
