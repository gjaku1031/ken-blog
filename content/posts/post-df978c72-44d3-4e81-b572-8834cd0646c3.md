Spring으로 API를 만들어 봤지만, 내가 아는 건 컨트롤러 메서드가 불린 다음부터였다. 주소창에 주소를 치고 엔터를 누른 순간부터 그 메서드가 불리기까지 무슨 일이 일어나는지는 설명하지 못했다. 그래서 요청 하나가 서버에 닿기까지의 길을 처음부터 따라가 보기로 했고, 이 글에서는 먼저 그 길 전체를 한 장으로 그려 봤다.

## 학습 목표

- 요청 하나가 브라우저에서 서버 코드까지 거치는 단계를 순서대로 말할 수 있다
- 각 단계가 무슨 일을 하는지 한 문장으로, 비유를 곁들여 설명할 수 있다
- `curl` 출력에서 각 단계의 흔적을 찾을 수 있다

## 택배로 비유하면

처음엔 단계 이름만 늘어놓으니 머리에 남지 않았다. 요청 하나를 "답장을 받아 오는 택배"로 바꿔 생각하니 각 단계가 왜 필요한지 보이기 시작했다.

| 단계 | 택배로 치면 | 실제로 하는 일 | 자세히 |
| --- | --- | --- | --- |

| 리버스 프록시 | 회사 대표 접수처 | 서버 앞에서 요청을 대신 받아 뒤쪽 서버로 넘김 | [7편](/ken-blog/post/post-ca04bdf2-91f9-4bf6-abff-b422dc854eb4/) |

| 응답 | 답장 택배 | 상태 코드, 헤더, 본문이 같은 길을 거꾸로 돌아옴 | [2편](/ken-blog/post/post-3afb11d0-e0ac-40ec-b062-a66775e3264b/) |

비유가 딱 맞지 않는 곳도 있다. 실제 택배와 달리 TCP 연결은 한 번 열어 두면 같은 서버로 가는 다음 요청에 다시 쓸 수 있다.[* HTTP/1.1의 keep-alive, HTTP/2의 한 연결 위 여러 요청이 그런 경우다. 이미 열린 연결이 있으면 DNS, TCP, TLS 단계를 건너뛴다]

### 헷갈렸던 것 두 가지

**연결을 맺는 상대가 원 서버가 아닐 수 있다.** CDN을 쓰는 사이트에서는 DNS가 원 서버가 아니라 CDN 서버의 IP를 알려 준다. 그래서 TCP 연결도, TLS의 자물쇠도 CDN 서버와 맺는다. 나는 브라우저가 늘 "그 회사 서버"와 직접 이야기한다고 생각했는데, 실제로는 동네 물류 센터에 맡기는 셈이었다.[* CDN(Content Delivery Network): 여러 지역에 서버를 두고 원 서버의 응답 사본을 나눠 들고 있는 전달망. 사본이 없을 때만 원 서버(origin)에 따로 요청한다]

**서버가 보는 "상대방"은 바로 앞 칸이다.** 리버스 프록시 뒤의 서버 입장에서 연결을 맺은 상대는 프록시다. 그래서 원래 요청한 사람의 IP는 프록시가 `X-Forwarded-For` 같은 헤더에 적어 넘겨줘야 알 수 있다. 접수처를 거쳐 들어온 서류에 "원래 보낸 사람"을 따로 적어 주는 것과 같다.[* 리버스 프록시: 서버 쪽에 놓여 여러 서버를 대신해 요청을 받는 중간 서버. 사용자 쪽에 놓여 사용자를 대신하는 포워드 프록시와 구분한다]

여기까지는 요청 하나에 응답 하나가 짝을 이룬다. 채팅이나 알림처럼 서버가 먼저 말을 걸어야 하는 기능은 이 짝으로는 만들기 어려워서, 요청을 계속 반복하거나(폴링) 연결을 열어 둔 채 주고받는 방법(SSE, WebSocket)을 쓴다. 지도 맨 아래 점선이 그 이야기이고, [10편](/ken-blog/post/post-faadfcd9-8851-488b-b485-253aee1b297c/)에서 다룬다.

## 직접 확인해 보기

말로만 봐서는 감이 안 와서 `curl -v`로 example.com에 요청을 보내 봤다. `-v`를 붙이면 각 단계에서 한 일을 출력해 준다. `*`로 시작하는 줄은 curl의 진행 기록, `>`는 내가 보낸 요청, `<`는 받은 응답이다.[* 2026-10-23, Linux VM에서 curl 8.18.0(OpenSSL 3.5.5)으로 실행했다. 인증서 세부, TLS 내부 메시지, IPv6 시도 줄은 생략하고 로컬 내부 주소는 지웠다]

```bash
curl -v -o /dev/null https://example.com/
```

```text
* Host example.com:443 was resolved.
* IPv4: 104.20.23.154, 172.66.147.243
*   Trying 104.20.23.154:443...
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / X25519MLKEM768 / id-ecPublicKey
* Server certificate:
*   subject: CN=example.com
*   issuer: C=US; O=SSL Corporation; CN=Cloudflare TLS Issuing ECC CA 3
* Established connection to example.com (104.20.23.154 port 443)
* using HTTP/2
> GET / HTTP/2
> Host: example.com
> User-Agent: curl/8.18.0
> Accept: */*
>
< HTTP/2 200
< content-type: text/html; charset=utf-8
< server: cloudflare
< age: 6
< cf-cache-status: HIT
```

| 출력 | 지도에서 |
| --- | --- |
| `was resolved`, `IPv4: …` | DNS가 IP 주소를 알려 줌 |
| `Trying 104.20.23.154:443` | TCP 연결 |
| `SSL connection using TLSv1.3`, `Server certificate` | TLS 암호화 |
| `> GET / HTTP/2`부터 빈 `>` 줄까지 | 요청 메시지 |
| `< HTTP/2 200`과 그 아래 헤더 | 응답 메시지 |
| `server: cloudflare`, `cf-cache-status: HIT`, `age: 6` | CDN이 사본으로 응답함 |

위에서 헷갈렸던 첫 번째가 그대로 보였다. 인증서 발급자도 `server` 헤더도 Cloudflare다. 내가 연결한 상대는 example.com의 원 서버가 아니라 CDN 서버였고, `cf-cache-status: HIT`와 `age: 6`을 보면 CDN이 6초 전에 저장해 둔 사본을 돌려줬다.[* `age`는 응답이 중간 저장소에 머문 초다. `cf-cache-status`는 이 CDN이 붙이는 자체 헤더로, 표준 헤더는 아니다]

단계마다 시간이 얼마나 걸리는지도 궁금해서 `-w`로 찍어 봤다. 각 변수는 요청을 시작한 때부터 그 단계가 끝날 때까지의 누적 시간(초)이다.

```bash
curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com/
```

```text
dns=0.000845 tcp=0.002546 tls=0.016051 ttfb=0.021655 total=0.021767
```

| 단계 | 계산 | 걸린 시간 |
| --- | --- | --- |
| DNS 조회 | `time_namelookup` | 0.8ms |
| TCP 연결 | `time_connect` − `time_namelookup` | 1.7ms |
| TLS 핸드셰이크 | `time_appconnect` − `time_connect` | 13.5ms |
| 요청을 보내고 응답 첫 바이트를 받기까지 | `time_starttransfer` − `time_appconnect` | 5.6ms |

세 번 실행해 첫 번째를 적었고, 세 번 모두 합계가 21\~25ms였다. DNS가 1ms도 안 걸린 건 직전 실행의 조회 결과가 저장돼 있어서다.[* 이보다 앞서 처음 실행했을 때는 DNS 조회에 4.7ms가 걸렸다] TCP 연결은 한 번 왕복하면 끝나니까 CDN 서버까지 왕복은 2ms 남짓이다. 그런데 TLS 핸드셰이크는 그 몇 배가 걸렸다. 이 경우 TLS 시간의 대부분은 네트워크를 기다린 시간이 아니라 키를 주고받고 인증서를 검증하는 계산에 쓰인 것으로 보인다. 자물쇠를 다는 데 드는 비용이 생각보다 컸다.

> 요청 하나는 이름을 주소로 바꾸고, 연결을 열고, 자물쇠를 채우고, 메시지를 보내는 단계를 차례로 거친다. 그리고 그 메시지는 서버 코드에 닿기 전에 CDN이나 프록시 같은 중간 서버를 먼저 만난다.

## 확인 질문

**1. 주소창에 주소를 넣고 엔터를 눌렀는데 네트워크로 요청이 하나도 나가지 않을 수 있을까?**

<details><summary>답</summary>

있다. 같은 주소의 응답을 브라우저가 저장해 두었고, 그 응답의 `Cache-Control`이 정한 유효 기간이 아직 남아 있으면 브라우저는 서버에 묻지 않고 저장된 응답을 쓴다. 집에 지난번 물건이 있으면 택배를 다시 부르지 않는 것과 같다([5편](/ken-blog/post/post-69de2eba-53bf-4cf2-9c86-fdd0aa3dadc5/)).

</details>

**2. CDN을 쓰는 사이트에 접속할 때 브라우저가 TCP 연결을 맺는 상대는 누구일까?**

<details><summary>답</summary>

CDN 서버다. DNS가 원 서버가 아닌 CDN 서버의 IP를 알려 주기 때문이다. 위 `curl -v` 출력에서 인증서 발급자와 `server` 헤더가 CDN 회사인 것으로 확인할 수 있다([6편](/ken-blog/post/post-5b5ec693-9a31-4a67-9053-0381b98c9ddf/)).

</details>

**3. 요청의 `Cookie` 헤더는 누가 넣을까?**

<details><summary>답</summary>

브라우저다. 서버는 응답의 `Set-Cookie` 헤더로 "이 번호표를 가지고 있어"라고 줄 뿐이고, 이후 요청마다 그 사이트에 해당하는 쿠키를 브라우저가 알아서 실어 보낸다([4편](/ken-blog/post/post-3af3de8c-228f-45d9-b316-c16924e45bd9/)).

</details>

**4. 리버스 프록시 뒤의 애플리케이션 서버가 연결 상대의 IP를 읽으면 누구의 IP가 나올까?**

<details><summary>답</summary>

프록시의 IP다. 서버와 직접 연결을 맺은 상대가 프록시이기 때문이다. 실제 사용자의 IP는 프록시가 `X-Forwarded-For` 같은 헤더에 적어 넘겨줘야 알 수 있고, 그 헤더를 어디까지 믿을지도 따로 정해야 한다([7편](/ken-blog/post/post-ca04bdf2-91f9-4bf6-abff-b422dc854eb4/)).

</details>

**5. `curl -w`의 `time_appconnect`에서 `time_connect`를 빼면 무엇을 잰 값이 될까?**

<details><summary>답</summary>

TLS 핸드셰이크에 걸린 시간이다. `time_connect`는 TCP 연결이 끝난 시점, `time_appconnect`는 TLS 핸드셰이크가 끝난 시점까지의 누적 시간이기 때문이다([8편](/ken-blog/post/post-fe24a8b3-892f-4e3f-aeb6-13437ed47aaa/)).

</details>
