## 문제와 순서 조정

현재 게시글은 내부 Service에서 초안을 저장하거나 ID·slug로 찾을 수 있는 단계. 관리자가 HTTP 요청으로 목록을 보거나 내용을 고치고 삭제하는 기능은 없음. 공개 여부·출간 시각·공개 글 API도 없음.

로드맵의 Redis Cloud 캐시를 바로 구현하면 무엇을 공개 데이터로 보관할지 먼저 임의로 정해야 하는 문제. 다음 순서 제안.

1. **P1-04A: 관리자 초안 작성·조회·수정·삭제** — 이번 승인 대상.
2. P1-04B: 출간 상태와 공개 목록·상세 조회 — 별도 계획 대상. 기존 P1-05의 공개 범위 일부를 먼저 설계.
3. P1-04: 확정된 공개 조회에 Redis Cloud 캐시 적용 — 별도 계획 대상.

Redis Cloud 사용 계획은 유지. 이번에는 Redis 연결·키·TTL·캐시 코드를 추가하지 않음. 관리자 초안 내용은 후속 공개 데이터 캐시 대상에서 제외.

## 이번에 사용할 수 있게 되는 기능

관리자로 로그인한 뒤 Swagger나 HTTP 도구로 초안을 작성하고, 목록과 상세 내용을 확인하고, 제목·주소·본문을 수정하거나 삭제할 수 있는 상태. 웹 에디터나 공개 방문자 화면은 이번 결과에 포함하지 않음.

### HTTP 계약

기준 경로 `/api/v1/admin/posts`. 모든 요청은 ADMIN 세션 필요, POST·PUT·DELETE는 기존 CSRF 토큰 필요. 목록·상세·쓰기 응답에 `Cache-Control: no-store` 적용.

| 요청 | 입력 | 성공 결과 |
| --- | --- | --- |
| POST `/api/v1/admin/posts` | JSON `title`, `slug`, `body` 필수 | 201, 상세 DTO와 생성된 관리자 조회 경로의 Location |
| GET `/api/v1/admin/posts` | `page=0`, `size=20` 기본 | 200, 본문 없는 요약 목록과 페이지 정보 |
| GET `/api/v1/admin/posts/{id}` | 양수 ID | 200, 상세 DTO |
| PUT `/api/v1/admin/posts/{id}` | JSON `title`, `slug`, `body` 모두 필수 | 200, 변경 후 상세 DTO |
| DELETE `/api/v1/admin/posts/{id}` | 양수 ID | 204, 본문 없음 |

- 상세 DTO: `id`, `title`, `slug`, `body`, `createdAt`, `updatedAt`. 목록의 각 항목은 상세 DTO에서 `body` 제외. JPA 엔티티·Spring Page 구현체를 그대로 JSON으로 노출하지 않음.
- 목록은 `createdAt DESC, id DESC` 고정 정렬. `page`는 0 이상, `size`는 1~100. 응답은 `items`, `page`, `size`, `totalElements`, `totalPages`. 빈 결과·범위 밖 페이지는 빈 목록. 잘못된 페이지 입력은 400. JPA 조회 오프셋의 정수 범위를 넘는 `page × size > 2,147,483,647`도 400으로 거부하여 내부 500 방지.
- 목록 SQL은 요약에 필요한 열만 조회해 최대 1 MiB 본문을 페이지마다 읽지 않도록 구성. Spring Data 쿼리와 구체 DTO 사용, 불필요한 Custom Repository·인터페이스 투영 추가 없음.
- 없는 양수 ID의 조회·수정·삭제는 404. 0·음수 ID는 400. 삭제 후 같은 ID의 재요청은 404.
- 생성/수정 시 기존 규칙 유지: 제목 trim 후 1~200 코드포인트, slug trim·소문자 정규화 후 ASCII 영숫자/단일 하이픈 1~160자, 본문 UTF-8 최대 1 MiB. 빈 초안 본문은 기존처럼 허용.
- 초안 slug 수정 허용, 중복은 409. 자기 자신의 slug를 유지하는 수정은 허용. 출간 후 주소 정책은 후속 계획에서 결정.
- 본문은 원문 문자열로 저장·반환. HTML 렌더링·Markdown 변환·블록 에디터 형식을 이번에 확정하지 않음.

### 오류·인증 계약

기존 ProblemDetail 처리에 게시글 오류만 연결. 입력 400, 미인증 401, ADMIN/CSRF 부족 403, 없는 글 404, slug 충돌 409, DB 연결 장애 503, 예상 밖 내부 오류 500. DB 원문·입력 본문·세션/비밀값을 오류 응답에 노출하지 않음.

401과 403의 순서는 기존 Spring Security 필터 계약 유지. 특히 CSRF 없는 쓰기 요청은 로그인 여부보다 먼저 403일 수 있으므로 미인증 검증은 유효한 익명 CSRF를 준비해 구분.

기존 로그인·로그아웃·세션 ID 교체·현재 사용자·첨부 API의 권한과 ProblemDetail 변경 없음. 브라우저 관리자 CORS 허용 확대·공개 HTTPS·쿠키 정책 변경 없음. 이번 검증은 격리 환경에서 직접 HTTP 요청으로 진행.
