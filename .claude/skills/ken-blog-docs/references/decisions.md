# 문서 작성 결정 기록

ken-blog 문서를 사용자와 검토하며 확정한 결정. 새 결정은 다음 번호로 추가하고, 바뀐 결정은 지우지 않고 '대체됨'으로 표시한 뒤 새 번호를 붙인다. 적용 범위가 '공통'인 결정은 다른 프로젝트 문서에도 그대로 적용한다.

## 주요 결정과 Posts의 분배

대문과 06에 올리는 주요 결정은 아래를 만족한다. 누가 결정했는지, 사용자가 지금 설명할 수 있는지는 기준이 아니다(D-028). 개수는 정하지 않지만 보통 2~4개이며, 많으면 영향이 큰 순서로 고르고 나머지는 Posts로 보낸다.

1. **핵심 제약·특징에서 나옴**: 개발 배경의 설계 제약(자원·인력·작성 방식 등)이나 프로젝트의 존재 이유·대표 특징에서 직접 나온 결정
2. **구조 전체에 영향**: 여러 구성 요소·문서에 걸치고, 되돌리기 비용이 큼
3. **트레이드오프가 분명**: 얻은 것과 받아들인 대가를 한 문장씩 말할 수 있음
4. **근거가 있음**: 측정·테스트·코드로 확인한 결과가 있음. 부족하면 확인한 범위까지만 쓰고 '보완 필요'로 사용자에게 알린 뒤 학습 목록에 올림(D-029)

Posts(ADR형 결정 글·실험·트러블슈팅)로 보내는 것:

- 한 구성 요소 안에서 끝나는 결정, 라이브러리·도구 선택(예: jOOQ)
- 주요 결정의 상세 검증·측정 원자료(06은 요약과 링크만)
- 운영 사고와 문제 해결 기록

## 비공개 학습 목록

- 위치: `docs/study/<프로젝트>-learning.md` (`.gitignore` 대상, 공개 저장소에 올라가지 않음)
- 올리는 것: 인터뷰에서 사용자가 잘 모르는 것으로 보인 설계·기술(D-028), 근거가 부족한 주장(D-029)
- 항목 형식: 주제 / 관련 문서·절 / 왜 올렸나(모름·근거 부족) / 공부·보완할 것 / 상태(대기·진행·완료)
- 공부를 마치면 상태를 완료로 바꾸고, 해당 문서의 설명이나 근거를 보강한다.

ken-blog 적용: P1 Git 정본(작성 방식 제약), P2 정적 생성(자원 제약, 측정 근거), P3 revision 검증(P1·P2가 만든 저장소 분리의 결과, 회귀 검사 근거)이 주요 결정. 편집 충돌과 jOOQ 선택은 Posts 글로 게시함(관리 화면 동시 편집의 갱신 손실 방지, jOOQ vs QueryDSL). 반영 시점은 03 발행 흐름에 둠.
