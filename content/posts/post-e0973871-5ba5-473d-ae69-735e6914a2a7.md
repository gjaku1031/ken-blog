ken-blog는 쓰기와 단건 조회, 행 잠금은 JPA로, 목록과 집계, 공개 스냅샷 조회는 jOOQ로 처리한다. 처음부터 둘을 함께 쓴 것은 아니다. 공개 글 목록을 JPQL 문자열 하나로 쓰다 보니 선택 조건과 정렬이 문자열 안에서 갈라졌고, 더 큰 문제는 "무엇이 공개 글인가"라는 조건이 쿼리마다 따로 적혀 있다는 것이었다. Criteria API, QueryDSL, jOOQ를 비교해 jOOQ로 옮겼고, 공개 조건은 한곳에 모았다.

## 계기: 조건이 문자열 안에서 갈라졌다

당시 공개 글 목록은 발행 상태, 공개 범위, 구획, 분류, 태그 조건을 골라서 걸고, 시리즈 순서와 최신순 중 하나로 정렬해야 했다.[* 공개 범위(`visibility`)와 구획(`section`)은 나중에 값이 하나로 고정되어 열을 지웠다. 지금 공개 조건은 발행 상태 하나다] 이것을 JPQL 문자열 하나로 쓰면 아래처럼 된다.[* JPQL은 테이블 대신 JPA 엔티티를 대상으로 쓰는 질의 언어다. Hibernate가 SQL로 바꿔 실행한다]

<details><summary>jOOQ로 옮기기 전의 공개 글 목록 JPQL</summary>

```sql
select new PublishedPostRow(p.id, p.title, p.slug, p.publishedAt, p.categoryId)
from PostEntity p
where p.section = PostSection.TECH
  and p.status = :published
  and (:includePrivate = true or p.visibility = :publicVisibility)
  and (:categoryPath is null or exists (
        select c.id from CategoryEntity c
        where c.id = p.categoryId and (c.path = :categoryPath or c.path like :descendantPath)))
  and (:tag is null or exists (
        select t.id from PostTagEntity t where t.postId = p.id and t.name = :tag))
order by case when :seriesOrder = true and p.techSeriesOrder is null then 0
              when :seriesOrder = true then 1 else null end asc,
         case when :seriesOrder = true then p.techSeriesOrder else null end asc,
         case when :seriesOrder = true then p.publishedAt else null end asc,
         case when :seriesOrder = true then p.id else null end asc,
         case when :seriesOrder = false then p.publishedAt else null end desc,
         case when :seriesOrder = false then p.id else null end desc
```

</details>

조건을 걸지 말지가 `(:값 is null or ...)`로 쿼리 문자열 안에서 갈라졌다. 정렬 기준 하나를 바꾸려고 `CASE`를 여섯 번 되풀이했고, 같은 `where` 조건을 건수 조회 쿼리에 한 번 더 복사해야 했다.

## 더 큰 문제: 공개 조건이 쿼리마다 따로 있었다

당시 공개 글의 조건은 발행, 공개 범위, 구획 세 가지였다. 이 조건이 목록, 건수, 단건, 첨부 조회마다 따로 적혀 있어서, 한 곳만 바뀌어 기준이 어긋나도 알아채기 어려웠다.

![전환 전의 공개 조건. 목록, 건수, 단건·첨부 조회가 공개 조건을 각자 따로 적고 있어서, 하나만 바뀌면 기준이 어긋나도 알아채기 어렵다|dark=235|w=100|a=center](attachment:236)

문자열 분기보다 이쪽이 더 컸다. 공개 사이트는 공개 스냅샷과 첨부 전달이 같은 공개 기준을 써야 일관되게 만들어지기 때문이다([아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/) 참조). 조건을 코드 값으로 만들어 여러 쿼리가 나눠 쓸 수 있는 도구가 필요했다.

## 고른 방법

JPQL을 그대로 두는 것 말고 세 가지를 비교했다.

| 도구 | 조건 조립과 표현 범위 | 판단 |
|---|---|---|
| Criteria API | Java 코드로 조립한다. JPQL 범위 안이다 | 조건 하나에도 빌더 호출이 길게 이어져 유지보수가 어렵다고 보고 뺐다[* Spring Data JPA의 Specification도 Criteria API 위에서 조건을 조합하는 방식이다] |
| QueryDSL(JPA 모듈) | SQL과 비슷한 문장으로 조립한다. JPQL로 바뀌므로 그 범위 안이다 | 원 저장소의 릴리스가 멈춰 있어 뺐다[* 2026-10 확인. QueryDSL 원 저장소의 마지막 릴리스는 5.1.0(2024-01)이고, 이후 OpenFeign 조직의 포크가 릴리스를 이어 가고 있다. JPQL을 거치지 않는 SQL 모듈도 있지만 유지 상태는 같다. jOOQ는 이 프로젝트가 쓰는 3.21 계열까지 정기 릴리스가 나오고, Spring Boot가 `spring-boot-starter-jooq`를 제공한다] |
| jOOQ(고른 쪽) | SQL과 비슷한 문장으로 조립한다. SQL을 그대로 쓰므로 `FOR UPDATE`나 방언별 기능도 쓸 수 있다 | 스키마에서 테이블 타입을 만들어야 하고, 영속 기술이 두 개가 된다 |

QueryDSL은 OpenFeign 포크가 릴리스를 이어 가고 있지만 원 저장소 조직의 릴리스가 아니어서, 핵심 조회 계층을 맡기기에는 유지 주체가 불확실하다고 봤다. 또 JPQL로 복잡한 조회를 쓰기 어려웠던 문제는 JPQL로 바뀌는 도구를 써도 그 범위에 머문다. 그래서 SQL을 직접 다루는 jOOQ를 골랐다. 쓰기와 단건 조회, 잠금은 JPA에 남겼고, 두 기술은 같은 데이터 소스와 Spring 트랜잭션을 공유한다.

## 옮긴 뒤의 조회

공개 조건은 `Condition` 하나로 정의했다.[* `Condition`은 jOOQ에서 `where` 절의 조건을 값으로 다루는 타입이다. `and`, `or`로 이어 붙일 수 있다] 공개 스냅샷의 글 목록, 시리즈 문서 목록, 첨부 전달, 첨부 revision 계산이 모두 이 조건을 쓴다.[* revision은 공개 데이터가 바뀌었는지 판단하려고 계산하는 해시 값이다]

```java
public Condition readable() {
    return p.STATUS.eq("PUBLISHED");
}

public AttachmentDeliveryRow readableAttachment(long postId, long attachmentId) {
    return sql.select(ATTACHMENTS.OBJECT_KEY, ATTACHMENTS.CONTENT_TYPE, ATTACHMENTS.BYTE_SIZE)
            .from(joined().join(POST_ATTACHMENTS).on(POST_ATTACHMENTS.POST_ID.eq(p.ID))
                    .join(ATTACHMENTS).on(ATTACHMENTS.ID.eq(POST_ATTACHMENTS.ATTACHMENT_ID)))
            .where(readable().and(p.ID.eq(postId)).and(ATTACHMENTS.ID.eq(attachmentId)))
            .fetchOne(...);
}
```

![전환 후의 공개 조건. readable() 하나를 공개 스냅샷의 글 목록, 시리즈 문서 목록, 첨부 전달, 첨부 revision 계산이 함께 쓰므로, 기준을 바꾸면 네 조회가 함께 바뀐다|dark=231|w=100|a=center](attachment:232)

조건과 정렬을 `Condition`과 `SortField` 값으로 조합하니 옛 JPQL의 null 분기와 `CASE` 정렬이 사라졌다. 첨부 연결을 바꿀 때 첨부 행을 ID 순서로 잠그는 `SELECT ... FOR UPDATE`도 같은 조회 계층에서 쓴다.[* 조회 코드(`PostQueries.java`)]

## 받아들인 비용

- 영속 기술 두 개와 코드 생성 단계를 함께 유지해야 한다. 스키마 정의를 두 곳에 두지 않으려고 jOOQ 타입은 JPA 엔티티에서 만든 DDL로 생성한다. 그 순서는 [jOOQ 타입을 JPA 엔티티에서 만들려다 풀어야 했던 컴파일 순서](/ken-blog/post/post-f69cf0bb-68a1-4b72-b6c9-6aea1ed04db9/)에서 다룬다.
- 상태 열은 DDL에서 문자열 열로 만들어지므로, `"PUBLISHED"` 같은 값은 컴파일러가 검사하지 않는다. 열 이름과 타입은 컴파일 때 검사되지만 값의 오타는 테스트로만 잡힌다(예: 초안이 공개 목록에서 빠지는지 보는 `secondLevelNavigationKeepsOrderAndExcludesDrafts`).
- 같은 트랜잭션에서 JPA로 쓰고 jOOQ로 읽으면, JPA가 아직 flush하지 않은 변경은 jOOQ 조회에 보이지 않는다.[* flush는 JPA가 영속성 컨텍스트에 모아 둔 변경을 SQL로 DB에 보내는 일이다. 영속성 컨텍스트는 JPA가 트랜잭션 동안 엔티티를 들고 있는 작업 공간이다] 두 기술을 섞는 메서드에서는 flush 시점을 챙겨야 한다.

![JPA와 jOOQ를 한 트랜잭션에서 섞을 때. JPA로 바꾼 값은 flush하기 전까지 영속성 컨텍스트에만 있고, jOOQ는 SQL을 DB에 바로 보내므로 옛 값을 받는다|dark=233|w=100|a=center](attachment:234)

- 속도를 비교해 내린 결정은 아니다. JPQL과 jOOQ의 조회 성능은 재지 않았다.

## 확인

공개 스냅샷 회귀 검사는 Hibernate의 쿼리 수와 jOOQ SELECT 리스너의 횟수를 합쳐, 글 300개에서 조회가 10번 이하인지 본다. jOOQ로 옮긴 뒤에도 조회 수가 글 수에 비례해 늘지 않는다는 기준이다.[* [측정과 회귀 기준](/ken-blog/post/post-b46d1115-97ad-4d25-a9d9-1801b56857db/), 조회 횟수 설정(`SqlCountConfig.java`)]

## 남은 위험

- 공개 조건은 한곳에 모았지만, 상태 값의 오타는 여전히 테스트가 막아야 한다.
- 두 기술을 섞는 메서드가 늘수록 flush 시점을 놓칠 자리도 는다.
- 조회 성능을 비교하지 않았으므로, jOOQ로 옮겨 빨라졌거나 느려졌다고 말할 근거는 없다.
