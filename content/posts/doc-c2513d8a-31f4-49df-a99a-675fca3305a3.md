모든 요청은 Vercel의 API 함수 하나가 받고, 함수 인스턴스는 각자의 리플리카로 일하되 인스턴스끼리 겨루는 변경만 Turso의 원본 DB에서 직접 처리함.

## 품질 요구사항

| 품질 속성 | 요구 | 관련 문제 | 구조적 대응 |
| --- | --- | --- | --- |
| 외부 쓰기의 중복 방지 | 같은 상담을 외부 ERP에 두 번 보내지 않고, 결과를 모르는 전송은 다시 보내지 않음 | P1 | 원본 DB의 조건부 갱신으로 선점, 보내기 전 건수 기록, 보낸 뒤 건수 대조 |
| 인스턴스 사이의 일관성 | 다른 인스턴스가 쓴 변경이 조회에서 사라지지 않고, 동시 갱신이 서로를 덮어쓰지 않음 | P2 | 조회 전 원본 당겨 오기, 겨루는 변경은 원본 DB에서 처리, 잠금 행과 상태 지문 |
| 시점 고정 | 외부 명단이 바뀌어도 만든 보고·업무의 대상이 유지됨 | P3 | 만들 때 특강기간 여부와 대상 명단을 복사해 저장 |

## 일관성 모델과 보장 범위

함수 인스턴스는 요청마다 다를 수 있고 각자 리플리카 파일을 가짐. 한 인스턴스의 리플리카에서 커밋한 트랜잭션은 다른 인스턴스의 동시 요청을 막지 못하므로, 겨루는 변경은 원본 DB에서 판정함. 보장은 Turso를 쓰는 운영 구성 기준이며, 로컬 개발에서는 두 연결이 같은 파일을 가리킴.

| 경계 | 보장 | 방법 | 보장하지 않는 구간 |
| --- | --- | --- | --- |
| 다른 인스턴스의 쓰기 ↔ 화면 조회 | 조회 직전까지 원본에 반영된 변경을 읽음 | 상태·보고·로그인 전 엄격 당겨 오기, 실패하면 요청 실패. 상담 상세는 원본에서 직접 읽음 | 응답 뒤에 생긴 변경은 다음 조회까지 보이지 않음 |
| 동시 상담 전송 | 같은 상담의 외부 쓰기는 선점한 요청 하나만 함 | 원본의 조건부 갱신(compare-and-set). 선점 뒤 3분 동안은 다른 요청이 회수하지 못함 | 외부 ERP에서 사람이 직접 쓴 같은 내용의 상담은 대조에서 구분하지 못함 |
| 외부 쓰기 ↔ 원본 반영 | 외부 쓰기가 확인된 뒤의 저장 실패를 전송 실패로 보고하지 않음 | 저장이 늦어졌다는 별도 상태로 응답 | 반영이 늦는 동안 그 상담은 "확인 중"으로 보임 |
| 강사 반 정보의 동시 갱신 | 갱신 손실(lost update)이 없음 | 원본 잠금 행으로 요청을 줄 세움. 반 전체 교체는 외부 조회 전에 잰 상태 지문(SHA-256)을 원본 트랜잭션에서 다시 비교(낙관적 동시성 제어) | 잠금이 걸린 동안의 다른 요청은 409로 거부되고, 다시 시도는 사람이 함 |
| 명단 재동기화 ↔ 작성 중 상담 | 작성한 내용과 전송 중인 상담 행을 지우지 않음 | 명단에서 빠진 학생은 대상 여부만 끔. 전송 중인 행은 식별 정보도 바꾸지 않음 | — |

> 원본 DB에서 판정하는 것은 인스턴스끼리 겨루는 변경뿐이고, 나머지는 요청 앞뒤의 동기화로 맞춤.

상담 전송은 이 시스템에서 유일하게 되돌릴 수 없는 외부 쓰기라서, 외부 ERP에 닿기 전과 후를 원본 DB의 단계로 나눠 기록함. 선택 이유와 대안은 [주요 기술적 의사결정](/ken-blog/post/doc-f47c5aab-4b47-412a-a28c-db6f0c36a314/)의 P1에 있음.

```mermaid caption="상담 전송의 실행 순서. 보내기 전 단계(claimed)에서 끊긴 요청은 보내지 않았음이 확실해 선점을 풀고, 보내는 단계(posting)에 들어간 뒤의 실패는 결과를 다시 읽어 확인할 때까지 남김"
sequenceDiagram
    %% legend: solid=요청; dotted=응답
    participant T as 강사 화면
    participant API as API 함수
    participant Pri as 원본 DB
    participant ERP as 외부 ERP 포트
    T->>API: 상담 보내기(날짜·주제·내용)
    API->>Pri: 조건부 갱신으로 선점(claimed)
    alt 같은 내용이 이미 확인 중이거나 완료
        API-->>T: 현재 상태(외부 호출 없음)
    else 선점 성공
        API->>ERP: 같은 상담 수 조회
        API->>Pri: 보내기 전 건수 기록(posting)
        API->>ERP: 상담 쓰기
        API->>ERP: 다시 조회
        alt 수가 늘었음
            API->>Pri: 완료(confirmed)
            API-->>T: 완료
        else 늘지 않았거나 응답이 없음
            API-->>T: 결과 확인 중(다시 보내지 않음)
        end
    end
```

결과 확인 중인 상담은 화면의 "전송 결과 확인"이 외부 ERP를 읽기만 해서 다시 대조함. 그래도 확인되지 않으면 담당 강사가 외부 ERP를 직접 보고 "보낸 것으로 종결"하거나 "한 번 다시 보내기"를 고름.[* 결과 확인과 사람 종결(`counsel-api-reconcile.test.cjs`)]
