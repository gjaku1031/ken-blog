애플리케이션은 운영 VM에서 배포 스크립트 한 개로 빌드·백업·마이그레이션·전환·검사를 차례로 실행하고, 검사에 실패하면 이전 릴리스로 자동으로 돌아감. 외부 연동(문자·시트·학생 원천)은 코드 배포와 따로, 사람이 확인한 뒤 하나씩 켬(P3). 배포 경계와 구성 요소는 [아키텍처](/ken-blog/post/doc-71ac4b10-9f99-4251-893d-a57dd46ad334/)에서 정의함.

## 릴리스 배포와 롤백

릴리스마다 UTC 시각 이름의 디렉터리를 만들고, `current`·`previous` 심볼릭 링크를 원자적으로 바꿔 전환함. 실행 프로세스는 릴리스 디렉터리를 읽을 수만 있음.

- **빌드 도구 고정**: 호스트의 Corepack을 믿지 않고, 무결성 해시를 고정한 Corepack을 내려받아 저장소가 지정한 pnpm 버전만 씀. 호스트에 깔린 도구 버전에 따라 빌드 결과가 달라지는 것을 막음
- **프로세스별 환경 파일**: 하나의 운영 설정에서 API·worker·웹·마이그레이션용 파일을 따로 만들고(root 전용 0600), API 파일에 worker·마이그레이션 DB 주소나 Google 인증 경로가 있으면 중단함. 한 프로세스가 탈취되어도 다른 프로세스의 비밀값이 함께 새지 않게 함

그 밖의 단계는 데이터 저장소 권한·시간대 검사, 백업 후 마이그레이션과 worker 권한 재설정, 전환 후 준비 상태·수신 포트·공개 HTTPS 검사 순서임.

전환 후 검사에 실패하면 이전 릴리스의 링크로 되돌리고 다시 시작함. 마이그레이션은 되돌리지 않으므로 모든 운영 마이그레이션은 직전 릴리스 코드와 호환되어야 함. 수동 롤백은 `rollback` 명령으로 직전 릴리스나 지정한 릴리스로 함.

## 스키마 변경을 동반한 전환

API와 스키마가 함께 바뀔 때는 확장-축소(expand/contract) 순서를 따름. 배포 스크립트가 마이그레이션을 먼저 적용한 뒤 프로세스를 바꾸므로, 마이그레이션이 이전 코드가 쓰는 테이블을 지우면 전환 직전과 롤백 구간에 이전 코드가 실패함.

회차 정원 테이블 제거가 사례. 정원을 없앤 새 코드는 예약·입장을 회차 행 잠금으로 직렬화하고 정원 테이블을 읽지 않음. 이 릴리스를 먼저 배포해 정상임을 확인한 뒤, 이전 릴리스로 돌아갈 가능성이 없을 때 정원 테이블 삭제 SQL을 따로 실행함. 이 SQL은 Prisma 마이그레이션 체인 밖에 두어 배포 스크립트가 자동으로 실행하지 않게 함.[* [정원 테이블 삭제 SQL](https://github.com/gjaku1031/npr-seminar/blob/92598e6/ops/pve-release/migrations/post-capacity-code-cutover.sql) · [API 운영 안내](https://github.com/gjaku1031/npr-seminar/blob/92598e6/apps/api/README.md)]

기존 행을 대량으로 바꾸는 이관은 별도 확인을 둠. 학생 반 배정 제약을 바꾸는 마이그레이션은 잠금 대기 5초, 문장 실행 120초 제한을 걸어, 제한을 넘으면 검사를 끄지 않고 배포 실패로 처리함.

## 운영 실적

설명회를 마친 뒤 운영 명단 사본의 가족 예약 행을 집계한 결과임.[* 사본은 DB에서 한 방향으로 만든 명단이라 DB와 같은 시점의 값이며, 학생·연락처 열은 쓰지 않음]

| 항목 | 값 |
| --- | ---: |
| 가족 예약(취소 포함) | 650건 |
| 취소 | 58건 |
| 유효 예약 | 592가족, 학부모 686명 |
| 웹앱으로 받은 유효 예약 | 583건(98.5%) |
| 담임·전화·현장 예약 | 1·1·7건 |
| 설명회 당일 입장 | 281가족, 유효 예약의 47.5% |
| 입장 시간대 | 10:17~11:46, 10:40~11:10에 214건(76%) |
| 분당 최대 입장 | 15건(11:00) |

현장 예약 7건은 모두 당일 현장에서 만들어 바로 입장 처리된 가족임. 입장률이 절반에 못 미친 것은 예약만 하고 오지 않은 가족이 많았기 때문이며, 시스템이 입장을 거절한 건수는 이 사본으로 알 수 없음.

## 운영 사례

### 입장 사건의 CHECK 제약 누락으로 인한 입장 500

2026-08-16, 실제 입장 인원을 묻는 기능을 넣은 뒤 2명 예약을 스캔하자 입장 요청이 500을 반환함. 새 결과 코드 `PARTY_SELECTION_REQUIRED`를 계약과 코드에는 추가했지만, `check_in_events.result`의 허용 값 CHECK 제약은 넓히지 않아 입장 사건 INSERT가 거절됨. 타입 검사·계약 검사·배포 검사를 모두 통과한 뒤 첫 스캔에서 드러남. 계약 검사는 계약과 컨트롤러만 대조하고 DB 제약은 보지 않았기 때문이며, 각 검사가 보는 범위는 아래 검사의 의미 절에 정리함.

- **영향과 복구**: 설명회 전 입장 리허설에서 발견해 학부모 영향은 없었고, 당일 바로 고침
- **담당**: 백엔드·인프라 담당(본인)

원인을 찾는 데 시간이 걸린 이유는 오류 필터가 5xx를 로그 없이 고정 문구로만 응답했기 때문임.

- 5xx는 추적 ID·메서드·경로·스택만 로그에 남기도록 바꿈. 요청 본문·헤더·쿼리는 남기지 않음[* [오류 필터](https://github.com/gjaku1031/npr-seminar/blob/92598e6/apps/api/src/common/errors/problem-details.filter.ts)]
- 제약에 새 값을 추가하고, 계약 검증기가 마이그레이션의 마지막 CHECK 정의를 읽어 계약의 결과 코드 목록과 대조하게 함. 마이그레이션에서 값을 빼 보면 검증기가 실패하는 것을 확인함[* [계약 검증기](https://github.com/gjaku1031/npr-seminar/blob/92598e6/packages/contracts/scripts/validate_openapi.py)]

### 대량 문자 발송 중 worker 반복 재시작

2026-08-20, 한 캠퍼스 전체 학부모 대상 문자 332건을 넣자 worker가 33회 재시작함. 244건이 대기에 묶이고 77건이 `DELIVERY_UNKNOWN`으로 남음.[* 수치는 [수정 커밋](https://github.com/gjaku1031/npr-seminar/commit/c9563cd) 기록]

- **원인**: worker의 DB 연결이 모두 소진됨. worker DB 역할의 연결 한도는 8인데, 연결 풀의 기본 상한은 10이었음. worker는 한 번에 최대 10건을 집어 동시에 처리하므로, 대기열이 9건을 넘자 연결이 한도를 넘어 PostgreSQL이 연결을 끊음. worker 루프가 이 오류를 잡지 않아 프로세스가 그대로 종료됨
- **피해가 커진 이유**: 종료되는 동안 잡고 있던 작업의 lease가 만료됨. 외부 호출 전(`CLAIMED`)이던 139건은 대기열로 돌아갔지만, 호출 중(`SENDING`)이던 77건은 발송 여부를 알 수 없어 재전송하지 않음. 설계대로 중복 발송 대신 누락 가능성 쪽으로 멈춘 것임
- **조치**: 운영에서는 역할 연결 한도를 24로 올려 남은 발송을 마침(255건 발송 완료). 코드에는 풀 상한(16)을 명시하고 배포 스크립트의 역할 한도(24)와 서로를 가리키게 함. worker 루프는 한 바퀴가 실패해도 계속 돌고, 실패가 이어지면 최대 30초까지 간격을 늘림
- **영향과 복구**: 실제 학부모 대상 발송이었음. 결과 불명 77건은 자동 재전송 대신 사람이 판단해 다시 보냄
- **담당**: 백엔드·인프라 담당(본인)

### PostgreSQL 세션 시간대와 timestamptz 저장

PrismaPg 드라이버는 JavaScript `Date`를 오프셋 없는 UTC 시각 문자열로 보내므로, DB 세션 시간대가 `Asia/Seoul`이면 `timestamptz` 값이 9시간 어긋나게 저장됨. 서버·DB·모든 역할의 시간대를 UTC로 바꾸고, 배포 스크립트가 세션 시간대가 UTC가 아니면 배포를 거부하게 함. 화면과 시트는 계속 `Asia/Seoul`로 표시함.

이전에 저장된 행은 일괄 수정하지 않고, 읽기 전용 점검 SQL로 정확히 9시간 어긋난 후보만 찾음. 같은 트랜잭션의 DB 생성 시각처럼 독립된 기준이 있는 값만 고칠 수 있다고 정함.[* [시간대 점검 SQL](https://github.com/gjaku1031/npr-seminar/blob/92598e6/ops/pve-release/audit-timestamptz-offset.sql)] 영향받은 행 수와 수정 여부는 기록이 남아 있지 않음.

### 에이전트의 운영 DB 삭제와 백업 복구

예약 접수를 시작한 첫날, Google Sheets 명단과 DB가 맞지 않아 에이전트에게 둘을 맞추라고 지시함. 그런데 시트는 누군가 내용을 모두 지운 상태였고, 에이전트는 빈 시트를 기준으로 DB의 예약자 테이블을 모두 지움. 서버의 정기 백업을 학원 NAS로 복사해 둔 사본으로 복구해 운영을 이어 감.

- **원인**: 기준의 방향이 거꾸로 적용됨. 시트는 DB에서 시트로만 쓰는 대체 명단인데(P3), 에이전트가 시트를 기준으로 DB를 고쳤고, 지시에도 어느 쪽이 기준인지 적지 않았음
- **영향과 복구**: 백업 이후의 손실 범위와 복구에 걸린 시간은 기록이 남아 있지 않음
- **재발 방지**: 에이전트가 운영 DB를 바꿀 때는 먼저 백업이 있는지 확인하고 본인의 허락을 받게 함
- **담당**: 백엔드·인프라 담당(본인)

## 검사의 의미

CI 서버는 없음. 검사는 개발 환경의 명령과 배포 스크립트 안에서 실행됨.

| 검사 | 확인하는 범위 | 운영에서 추가로 확인할 것 |
| --- | --- | --- |
| `pnpm typecheck`·`lint`·`test` | 타입, 경계 규칙, API 단위 테스트 | 실제 DB 제약과 외부 서비스 |
| `test:integration` | Testcontainers의 PostgreSQL·Redis에서 동시성·마이그레이션·회로 | 운영 데이터 규모 |
| 계약 검증·경로 대조 | OpenAPI 문법, 컨트롤러 경로 일치, 결과 코드와 DB 제약 일치 | — |
| 배포 스크립트 검사 | 빌드 산출물, 데이터 저장소 권한·시간대, 수신 포트, 공개 HTTPS | 화면의 실제 흐름 |

같은 프로젝트의 QA 스택을 운영과 다른 VM에 따로 두고, 합성 데이터와 별도 비밀값을 씀. 학생 원천 연동은 꺼 두고, 문자·시트는 QA 전용 계정과 시트로만 켬. 일반 배포는 QA 데이터를 지우지 않고, 다시 채우려면 두 개의 확인 문구를 함께 넣어야 함.[* [QA 스택](https://github.com/gjaku1031/npr-seminar/blob/92598e6/ops/pve-dev/README.md)]
