# P1-04: Redis Cloud 공개 본문 캐시

상태: 구현·격리 검증·main·CI·Pages 완료 — P1-04B main·CI·Pages 성공 확인. 2026-09-26 전체 잔여 작업 자율 진행 지시 적용.

## 목적과 판단

공개 조회 계약이 확정되어 Redis Cloud를 공개 글 본문의 선택적 캐시로 연결할 수 있는 상태. MySQL은 원본과 권한 판단을 계속 담당하며 Redis 장애로 로그인이나 글 조회를 중단하지 않는 구성이 목적. 작은 블로그에서는 외부 Redis가 로컬 MySQL보다 빠르다고 보장하지 않으며 실제 지연과 SQL 선택 열을 측정해 효과를 기록.

공개 목록은 이미 본문 없는 작은 투영이므로 이번에는 캐시하지 않음. 익명의 PUBLIC 출간 글 상세 본문만 캐시. USER/ADMIN 상세·초안·PRIVATE 잠금·세션·CSRF·계정·첨부는 제외. 목록까지 캐시하여 공개 범위 변경 후 예전 글 목록이 노출되는 문제를 만들지 않음.

## 원본 확인과 캐시 흐름

1. 비활성 기본값에서는 기존 DB 조회 그대로 사용, Redis 연결·추가 조회 없음.
2. 활성 상태의 익명 상세는 MySQL에서 PUBLISHED/PUBLIC 메타데이터를 먼저 조회. id·제목·slug·출간 시각·본문 SHA-256만 선택하고 본문 열 제외.
3. 공개가 아니면 기존 잠금/404 계약 사용, Redis 조회 없음. 공개이면 `prefix:v1:post-body:{id}:{bodySha256}` 키 조회.
4. 값이 있으면 크기·SHA-256을 현재 DB 해시와 비교한 뒤 본문으로 사용. 손상/오염/예전 값은 버리고 원본 DB에서 조회. 제목·출간일은 언제나 DB 메타데이터 사용.
5. miss·Redis 오류이면 DB 본문 반환. 성공한 공개 본문 중 UTF-8 256 KiB 이하만 TTL 300초로 저장. 빈 본문도 유효한 값. 기존 최대 1 MiB API 계약은 유지하며 큰 본문은 캐시 생략.
6. 본문 변경은 새 해시로 키가 달라져 이전 값을 읽지 않음. 수정·공개 범위 변경·철회·삭제 후 이전 키는 트랜잭션 커밋 뒤 best-effort 제거. Redis 장애로 삭제가 실패해도 DB 공개 판단과 현재 해시가 이전 본문 사용을 막고 TTL이 잔여 키 정리.

DB 공개 판단을 건너뛰는 TTL 기반 권한 캐시는 없음. DB 장애는 캐시가 있어도 기존 503 유지. 읽기 트랜잭션의 스냅샷 경계 안에서 시작된 요청과 동시 공개 변경은 기존 DB 읽기 일관성 기준 적용.

## 구현 범위

- V6 `posts.body_sha256` 추가와 기존 본문 SHA2 backfill. Kotlin 생성·수정에서도 UTF-8 SHA-256 계산, 엔티티/마이그레이션 정합성 유지. DB는 해시를 포함한 원본 판단 근거.
- 기본 CRUD/Swagger/공개 DTO/ProblemDetail/JDBC 세션 유지. 새 HTTP 엔드포인트 없음. Service 구체 클래스·JpaRepository 인터페이스·KDoc 유지.
- Lettuce core만 필요한 범위로 도입해 Spring Session Data Redis나 Redis 저장소 자동 구성을 재도입하지 않음. 공통 캐시 추상화/Service 인터페이스 추가 없음.
- `CACHE_REDIS_ENABLED=false` 기본, host/port/username/password/TLS·prefix·TTL·짧은 연결/명령 timeout 외부 설정. URL에 비밀번호를 포함해 로그에 흘리지 않음. TLS 인증서 검증 우회 없음. 기존 외부 설정은 읽기만 가능하며 기존 배포 env 수정 없음.
- 단일 재사용 연결, 제한된 대기열, 끊긴 연결의 명령 무한 적재 금지. 최초 네트워크 초기화는 단일 백그라운드 연결 준비로 분리하고 준비 중 HTTP 요청은 DB로 바로 우회. 연결 실패는 요청당 장시간 재시도하지 않고 짧은 재연결 유예 후 DB fallback. Redis 오류 원문·비밀번호·본문 로깅 없음. 앱 종료 시 연결 자원 정리.
- 키는 전용 prefix 사용. FLUSHDB/FLUSHALL/전체 KEYS, 외부 Redis 설정 변경·비소유 키 삭제 없음. 모든 캐시 키에 TTL.
- Compose는 Redis 서비스 추가 없이 선택적 외부 캐시 환경변수만 전달. CI 기본 캐시 비활성, 기존 MySQL/JDBC 검사 유지. 실제 운영 Compose나 Redis 컨테이너 조작 없음.
- `.env.example`, README·실행/캐시 안내·계획·도면 갱신. Redis Cloud는 이미 도면에 존재하므로 계획/사용 상태와 선 의미만 실제 구성에 맞게 변경. 학습 문서 추가/갱신 없음.

## 검증

신규 테스트 코드 없음. 기존 Flyway 기대 버전만 필요한 만큼 수정. 기존 검사·빌드 및 격리 HTTP/SQL/Redis 명령으로 확인.

- 비활성 상태와 Redis 없이 기동, JDBC 로그인·공개 API 정상.
- 격리 MySQL/API/검증 전용 Redis에서 공개 miss→저장→hit, TTL·본문 해시·빈 본문·256 KiB 경계 확인. hit 시 실제 본문 SQL 제외, 메타데이터 권한 SQL은 유지.
- USER/PRIVATE/초안/목록/잘못된 slug에서 캐시 생성·본문 노출 없음.
- 내용 수정·slug 변경·공개→비공개·철회·삭제 후 이전 키를 인위적으로 남겨도 오래된 본문 반환 없음. 공개 복귀/새 본문 키 일치.
- 캐시 키에 틀린 값 삽입 후 DB 원문 fallback, 대용량/오류 값 거부. 전용 키에만 검증 데이터 삽입.
- 검증 Redis 중단/연결 거부/복구·앱 재시작 후 DB 조회와 JDBC 세션 정상, DB 중단은 기존 503.
- 사용자가 제공한 Redis Cloud 계정은 전용 무작위 prefix의 임시 데이터로 연결·TTL·캐시 흐름과 실제 지연만 확인. 실 계정의 무료 한도·연결 정책을 변경하지 않음. 권한/접속이 막히면 로컬 검증과 외부 미확인을 분리 기록.
- Buildpacks·격리 Compose 확인, 생성한 키/컨테이너/볼륨 정리, 기존 VM ID/시작 시각 대조. 기능별 커밋·main 정상 push·CI/Pages 확인.
