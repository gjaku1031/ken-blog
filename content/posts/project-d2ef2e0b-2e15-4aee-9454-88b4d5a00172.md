## 개발 배경과 핵심 문제

학원은 송파·위례·광진 세 캠퍼스의 재원생 가정을 대상으로 대입 설명회를 열고, 예약은 구글폼이나 전화로 받았음. 당일에는 직원들이 종이 명단에서 참석자를 찾아 확인했고, 한 명이 종이 기록을 스프레드시트로 옮겼음. 재원생 정보는 학원 관리 서비스(통통통)에, 학부모 연락은 문자에 있어, 예약을 받는 시스템이 이 두 곳과 함께 움직여야 했음.

설계 제약은 네 가지.

- **개인정보**: 미성년 학생의 이름·반·학교와 학부모 연락처를 다룸. 학부모는 계정 없이 예약하므로, 로그인 대신 연락처 소유를 증명할 방법이 필요함.
- **현장 입장**: 행사 당일 한 회차에 입장이 몰리고, 여러 입구의 iPad가 같은 명단을 동시에 처리함. 모바일 네트워크에서는 응답을 받지 못한 요청이 다시 전송될 수 있음.
- **외부 시스템**: 학생 원천(통통통)은 세 캠퍼스가 공유하는 계정 하나로 로그인한 뒤 캠퍼스를 바꿔 가며 관리 화면의 표 데이터를 읽어야 하고, 로그인 실패 횟수가 원천 쪽에 누적됨[* 원천의 실패 횟수는 운영자가 따로 초기화해야 함. [동기화 운영 절차](https://github.com/gjaku1031/npr-seminar/blob/e74a2a2/ops/pve-release/README.md)]. 문자(Aligo)와 Google Sheets도 응답이 늦거나 결과를 알 수 없는 경우가 있음.
- **일정과 인력**: 2026-07-16 착수, 2026-08-21 설명회까지 약 5주. 3인 팀이 기획·화면·백엔드를 나눠 맡음.

이 제약에서 다음 세 문제를 핵심 문제로 정의함.

- **P1 예약·입장 정합성**: 동시 예약, 재전송, 입장과 취소·회차 이동의 경합에서도 한 가족 예약은 하나의 최종 상태만 가지고, 같은 요청은 한 번만 반영되어야 함.
- **P2 개인정보 최소 노출**: 로그인 없는 공개 예약에서도 본인 예약만 다룰 수 있어야 하고, 연락처·QR 원문이 DB·URL·로그·시트에 남지 않아야 함.
- **P3 외부 연동 실패 격리**: 문자·시트·학생 원천이 실패하거나 결과가 불명확해도 예약·입장 처리가 멈추거나 깨지지 않고, 외부에 같은 작업을 중복으로 실행하지 않아야 함.

## 핵심 문제별 설계와 검증

검토한 대안 표와 검증 상세는 [주요 기술적 의사결정](/ken-blog/post/doc-faeef8eb-3ab9-4a39-840f-bfb6b01adbda/)에 있음.

### P1. 회차 잠금과 멱등 키로 예약·입장을 한 번만 반영

- **문제**: 한 가족이 두 기기에서 동시에 예약하거나, 스캐너가 응답을 받지 못해 같은 QR을 다시 보내거나, 입장 처리와 학부모의 취소·회차 이동이 같은 순간에 일어날 수 있음
- **결정**: 변경 경로마다 행 잠금 순서(멱등 키 → 스캐너 → 회차 ID 오름차순 → 예약 → QR)를 고정하고, DB의 부분 유니크 인덱스가 회차당 연락처 하나·학생 하나의 활성 예약만 허용함
  - 비교한 대안: 애플리케이션 선조회만으로 중복 차단
  - 선택 이유: 잠금 순서가 정해져 있어 교착이 생기지 않고, 선조회를 지나친 경합도 DB 제약이 막음
- **대가**: 같은 회차의 예약·입장 변경이 회차 행에서 한 줄로 대기함
- **검증**: 입장과 취소, 회차 이동과 취소가 경합할 때 최종 결과가 하나만 남는지, 같은 연락처의 동시 예약이 한 건만 생기는지를 통합 테스트로 검사함[* [예약 통합 테스트](https://github.com/gjaku1031/npr-seminar/blob/e74a2a2/apps/api/test/integration/family-bookings.spec.ts). 2026-10-09 재실행에서는 입장 인원 선택 도입(2026-08-17) 뒤 테스트 기대값을 고치지 않아 일부가 실패함. 결과와 원인은 [주요 기술적 의사결정](/ken-blog/post/doc-faeef8eb-3ab9-4a39-840f-bfb6b01adbda/)에 있음]

### P2. 연락처를 암호문과 다이제스트로만 저장

- **문제**: 학부모는 계정 없이 예약하므로 연락처가 곧 신원이고, 예약 링크·QR이 문자로 전달되어 URL과 메시지에 비밀값이 실리기 쉬움
- **결정**: 연락처는 AES-256-GCM 암호문, 키를 쓴 HMAC-SHA256 다이제스트, 끝 네 자리로 나눠 저장하고, 조회는 다이제스트 일치로만 함. 문자 인증을 통과하면 한 번만 쓸 수 있는 예약 증명을 발급하고, QR과 증명은 SHA-256 다이제스트로만 대조함
  - 처음부터 원문을 저장하지 않는 방식으로 정했고, 평문 저장이나 학부모 가입과는 비교하지 않았음
  - 선택 이유: DB가 유출되어도 연락처 원문이 드러나지 않고, 학부모는 가입 없이 예약할 수 있음
- **대가**
  - 연락처로 부분 검색을 할 수 없어 현장에서는 끝 네 자리 후보 목록으로 찾음
  - 암호화·HMAC 키를 서버 설정으로 따로 관리해야 함
- **검증**: 예약 링크의 예약 ID는 권한으로 쓰이지 않고, 연락처 다이제스트가 그 예약과 일치해야 읽기 세션이 열림. 재생 응답에 QR·증명 원문이 없는지는 통합 테스트로 검사함[* [비재원생 공개 예약 HTTP 테스트](https://github.com/gjaku1031/npr-seminar/blob/e74a2a2/apps/api/test/integration/guest-public-http.spec.ts)]

### P3. outbox와 회로로 외부 실패를 예약에서 분리

- **문제**: 예약 트랜잭션 안에서 문자·시트를 직접 호출하면 외부 지연이 예약을 붙잡고, 커밋 전후로 실패하면 예약과 문자가 어긋남. 학생 원천에 로그인을 반복하면 공유 계정의 실패 횟수가 쌓임
- **결정**: 예약·입장과 같은 트랜잭션에 문자·시트 outbox 행을 기록하고, 별도 프로세스의 worker가 lease를 잡아 전송함. 학생 원천은 실행당 로그인 1회만 시도하고, 결과가 불명확하면 회로를 열어 자동 재시도를 막음
  - 비교한 대안: 요청 처리 중 외부 직접 호출, 별도 메시지 큐(Kafka·BullMQ)
  - 선택 이유: 원장과 같은 DB 트랜잭션이라 예약이 커밋되면 발송 작업도 반드시 남음. 큐 인프라를 따로 운영하지 않아도 됨
- **대가**
  - 문자·시트는 비동기로 반영됨
  - Aligo에는 요청 중복을 막는 멱등 토큰이 없어, 전송 중 연결이 끊겨 결과를 모르는 문자는 `DELIVERY_UNKNOWN`으로 두고 다시 보내지 않음. 중복 발송 대신 누락 가능성을 받아들임[* [문자 연동 결정 기록](https://github.com/gjaku1031/npr-seminar/blob/e74a2a2/docs/specs/aligo-sms-implementation-decisions-20260717.md)]
- **검증**: 여러 worker가 동시에 돌 때 각 행을 한 번만 집고 결과 불명 행을 재시도하지 않는지, 회로가 열린 뒤 외부 호출 없이 실행이 거절되는지를 통합 테스트로 검사함[* [문자 관리 테스트](https://github.com/gjaku1031/npr-seminar/blob/e74a2a2/apps/api/test/integration/sms-admin.spec.ts) · [학생 동기화 회로 테스트](https://github.com/gjaku1031/npr-seminar/blob/e74a2a2/apps/api/test/integration/student-sync-circuit.spec.ts)]. 2026-08-20 대량 발송 중 worker가 반복 재시작했을 때도 전송 중이던 77건을 다시 보내지 않고 멈췄음([배포와 운영](/ken-blog/post/doc-5fe55659-a943-4c64-aed1-481462f32c56/)의 운영 사례)
