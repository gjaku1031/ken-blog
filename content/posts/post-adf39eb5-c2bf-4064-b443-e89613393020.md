IP 주소와 포트가 뭔지, DNS가 이름을 IP 주소로 바꿔 준다는 것까지는 안다. 그런데 [0편](/ken-blog/post/post-df978c72-44d3-4e81-b572-8834cd0646c3/)에서 curl이 `example.com`을 `104.20.23.154`로 바꾸고 443번 포트에 연결하는 걸 보면서, 그 답을 DNS가 어디서 가져오는지, "연결을 연다"는 게 정확히 무슨 일인지는 설명하지 못한다는 걸 알았다.

## 지도에서 이번 구간

![0편 지도에서 이번 편이 다루는 구간을 초록으로 표시했다. 브라우저가 DNS에 이름을 물어 IP 주소를 받고, 그 주소와 TCP 연결을 연다|dark=154|w=100|a=center](attachment:153)

## 학습 목표

- DNS의 답이 리졸버를 거쳐 어떤 순서로 모이는지, 그 답의 TTL이 어떻게 줄어드는지 설명할 수 있다
- TCP 연결을 맺는 3-way handshake와, 순서 번호로 데이터를 빠짐없이 전하는 방식을 설명할 수 있다
- 연결 하나가 어떤 값으로 구분되는지 설명할 수 있다

## DNS: 답은 누가 모아 오나

내가 아는 건 "DNS에 물으면 IP 주소가 온다"까지였다. 실제로 내 컴퓨터가 묻는 상대는 리졸버 하나뿐이고, 리졸버가 루트 서버 → `.com` 서버 → `example.com`의 권한 서버 순서로 물어 답을 모아 온다. 사무실 안내 데스크에 "그 회사 주소 좀 알아봐 주세요" 하면, 데스크가 여기저기 전화를 돌려 알아 와 주는 것과 같다.[* 이렇게 대신 끝까지 물어 주는 것을 재귀 질의, 리졸버가 각 서버에 차례로 묻는 것을 반복 질의라고 한다. DNS의 기본 규약은 RFC 1034, RFC 1035다] 아래 실습의 `dig +trace`가 이 순서를 그대로 보여 준다.

### 헷갈렸던 것: DNS 답의 유통기한은 계속 줄어든다

TTL이 "이 답을 몇 초 동안 써도 되는지"라는 건 알았다. 헷갈린 건 `dig`에 찍힌 TTL이 매번 다르다는 점이었다. 권한 서버가 정한 TTL은 고정값이지만, 리졸버는 답을 저장해 둔 뒤 남은 시간을 TTL 자리에 적어 준다. 그래서 같은 질문을 몇 초 간격으로 하면 숫자가 줄어든다. 유통기한이 아니라 남은 유통기한을 보고 있었던 셈이다.

그래서 서버의 IP 주소를 바꿔도 모든 사용자가 바로 새 주소로 가지는 않는다. 옛 답을 저장해 둔 리졸버는 남은 시간이 끝날 때까지 옛 주소를 알려 준다.

## TCP: 연결을 연다는 것

IP는 패킷을 목적지 쪽으로 보내 줄 뿐, 도착을 보장하지 않는다. 중간에 사라질 수도 있고, 늦게 보낸 패킷이 먼저 도착할 수도 있다. HTTP 요청을 이런 패킷 여러 개로 쪼개 보낸다면, 받는 쪽은 빠진 조각이 있는지, 순서가 맞는지 알 길이 없다.

TCP는 이 문제를 번호로 푼다. 보내는 바이트마다 순서 번호(sequence number)를 매기고, 받는 쪽은 "여기까지 받았으니 다음엔 이 번호를 보내 줘"라고 확인 응답(ACK)을 돌려준다. 확인이 오지 않으면 보낸 쪽이 그 조각을 다시 보낸다. 책을 한 장씩 우편으로 보내면서 쪽 번호를 매기고, 받는 사람이 "37쪽까지 받았어"라고 엽서를 보내는 것과 같다.[* TCP의 현재 표준은 RFC 9293이다. 실제로는 확인을 한 조각마다 기다리지 않고 여러 조각을 한꺼번에 보낸 뒤 확인을 받는다]

이 번호를 쓰려면 양쪽이 서로의 시작 번호를 먼저 알아야 한다. 그 약속이 3-way handshake다. 전화를 걸 때 "여보세요?", "네, 들려요. 제 목소리도 들리세요?", "네, 들려요" 하고 나서야 본론을 꺼내는 것과 비슷하다.

![실습에서 캡처한 handshake. 내 컴퓨터가 SYN으로 시작 번호를 알리고, 서버가 SYN-ACK로 자기 시작 번호와 "다음엔 3044999081번을 보내라"는 확인을 돌려주고, 내 컴퓨터가 ACK로 답하면 연결이 열린다. 시각은 내 컴퓨터 기준|dark=174|w=100|a=center](attachment:173)

1. **SYN**: 내 컴퓨터가 "연결하고 싶다, 내 시작 번호는 3044999080이다"라고 보낸다.
2. **SYN-ACK**: 서버가 "좋다, 내 시작 번호는 1064500982이고, 네 다음 번호인 3044999081을 기다린다"라고 답한다.
3. **ACK**: 내 컴퓨터가 "네 다음 번호인 1064500983을 기다린다"라고 답한다. 이제 양쪽이 서로의 번호를 안다.

이렇게 열린 연결 하나는 내 IP, 내 포트, 서버 IP, 서버 포트 네 값으로 구분된다. 내 쪽 포트는 운영체제가 남는 번호를 임시로 골라 붙인다(아래 실습에서는 54108번이었다). 같은 컴퓨터에서 탭 두 개가 같은 서버의 443번에 붙어도 서버가 둘을 헷갈리지 않는 건 이 내 쪽 포트가 다르기 때문이다.[* 이 네 값에 프로토콜(TCP, UDP)을 더해 5-tuple이라고 부르기도 한다. 임시 포트는 ephemeral port라고 한다]

비유가 틀리는 지점도 있다. 전화는 통화하는 동안 교환망이 회선을 붙잡고 있지만, TCP 연결은 양 끝의 운영체제만 기억한다. 중간의 라우터들은 연결이 있는지 모르고 패킷을 하나씩 옮길 뿐이다.

## 직접 확인해 보기

먼저 `dig`로 DNS에 직접 물어봤다.[* 2026-10-23, Linux VM에서 DiG 9.20.24, tcpdump 4.99.6, curl 8.18.0으로 실행했다. 출력의 일부 줄은 생략했다]

```bash
dig example.com A
```

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 48648
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; QUESTION SECTION:
;example.com.			IN	A

;; ANSWER SECTION:
example.com.		52	IN	A	172.66.147.243
example.com.		52	IN	A	104.20.23.154

;; Query time: 2 msec
;; SERVER: 127.0.0.53#53(127.0.0.53) (UDP)
```

| 출력 | 뜻 |
| --- | --- |
| `QUESTION SECTION` | `example.com`의 A 레코드(IPv4 주소)를 물었다 |
| `ANSWER SECTION`의 두 줄 | 답이 IP 주소 두 개다. 어느 쪽으로 연결해도 된다 |
| 두 번째 열 `52` | TTL. 이 답을 앞으로 52초 더 써도 된다 |
| `SERVER: 127.0.0.53` | 내가 물은 상대. 이 VM 안에서 도는 로컬 리졸버다[* Ubuntu의 systemd-resolved가 127.0.0.53에서 질의를 받아 바깥 리졸버로 넘기고, 답을 저장해 둔다] |
| `(UDP)` | DNS 질의는 TCP 연결 없이 UDP로 오갔다 |

6초쯤 뒤에 같은 질문을 다시 했다.

```bash
dig example.com A +noall +answer
```

```text
example.com.		46	IN	A	104.20.23.154
example.com.		46	IN	A	172.66.147.243
```

TTL이 52에서 46으로 줄었다. 리졸버가 다시 물어본 게 아니라, 저장해 둔 답을 남은 유통기한과 함께 그대로 준 것이다.

리졸버가 대신 해 주는 일을 직접 해 보려고 `dig +trace`를 썼다. 루트 서버부터 차례로 묻는 옵션이다.[* 루트 서버(13개)와 `.com` 서버(13개) 목록은 두 줄씩만 남겼다. 서명 레코드(RRSIG, DS) 줄과, 이 VM에 IPv6 경로가 없어 실패한 시도 줄도 지웠다]

```bash
dig +trace example.com A
```

```text
.			518399	IN	NS	a.root-servers.net.
.			518399	IN	NS	m.root-servers.net.
;; Received 239 bytes from 127.0.0.53#53(127.0.0.53) in 1 ms

com.			172800	IN	NS	a.gtld-servers.net.
com.			172800	IN	NS	b.gtld-servers.net.
;; Received 1199 bytes from 192.112.36.4#53(g.root-servers.net) in 3 ms

example.com.		172800	IN	NS	hera.ns.cloudflare.com.
example.com.		172800	IN	NS	elliott.ns.cloudflare.com.
;; Received 506 bytes from 192.52.178.30#53(k.gtld-servers.net) in 108 ms

example.com.		300	IN	A	104.20.23.154
example.com.		300	IN	A	172.66.147.243
;; Received 179 bytes from 108.162.192.162#53(hera.ns.cloudflare.com) in 2 ms
```

| 단계 | 물은 곳 | 받은 답 |
| --- | --- | --- |
| 1 | 로컬 리졸버 | 루트 서버 목록 |
| 2 | 루트 서버(`g.root-servers.net`) | `.com`을 맡은 TLD 서버 목록 |
| 3 | TLD 서버(`k.gtld-servers.net`) | `example.com`을 맡은 권한 서버 목록(Cloudflare) |
| 4 | 권한 서버(`hera.ns.cloudflare.com`) | IP 주소 두 개, TTL 300 |

권한 서버가 준 원래 TTL은 300초였다. 앞에서 본 52, 46은 리졸버가 이 답을 저장해 둔 뒤 남은 시간이다. 루트와 `.com` 단계의 TTL은 172800초(2일)로 훨씬 길었다. 위층일수록 잘 바뀌지 않으니 오래 저장해도 되는 셈이다.

다음은 TCP handshake를 눈으로 보려고 `tcpdump`를 켜 둔 채 curl로 요청 하나를 보냈다. DNS 조회가 섞이지 않게 `--resolve`로 IP를 미리 정해 줬다.[* 내 컴퓨터의 사설 IP는 `내IP`로 바꿨고, 각 줄의 `win`, `options` 부분과 이후 패킷은 지웠다. `-S`는 순서 번호를 상대값이 아닌 실제 값으로 보여 주는 옵션이다]

```bash
sudo tcpdump -i <인터페이스> -nn -S 'host 104.20.23.154 and tcp port 443'
curl -s -o /dev/null --resolve example.com:443:104.20.23.154 -w 'tcp=%{time_connect}\n' https://example.com/
```

```text
tcp=0.001960

20:53:44.181670 IP 내IP.54108 > 104.20.23.154.443: Flags [S], seq 3044999080, length 0
20:53:44.183344 IP 104.20.23.154.443 > 내IP.54108: Flags [S.], seq 1064500982, ack 3044999081, length 0
20:53:44.183401 IP 내IP.54108 > 104.20.23.154.443: Flags [.], ack 1064500983, length 0
20:53:44.186292 IP 내IP.54108 > 104.20.23.154.443: Flags [P.], seq 3044999081:3045000652, ack 1064500983, length 1571
20:53:44.187862 IP 104.20.23.154.443 > 내IP.54108: Flags [.], ack 3045000652, length 0
```

| 줄 | 플래그[* `S`는 SYN, `.`은 ACK, `P`는 PUSH(받은 데이터를 바로 프로그램에 넘기라는 표시)다] | 뜻 |
| --- | --- | --- |
| 1 | `[S]` | SYN. 내 시작 번호 3044999080 |
| 2 | `[S.]` | SYN-ACK. 서버 시작 번호 1064500982, "다음엔 3044999081을 보내라" |
| 3 | `[.]` | ACK. "다음엔 1064500983을 보내라". 여기서 연결이 열린다 |
| 4 | `[P.]` | 첫 데이터 1571바이트. 번호 3044999081부터 3045000652 전까지. 내용은 HTTP 요청이 아니라 TLS 핸드셰이크의 첫 메시지다([8편](/ken-blog/post/post-fe24a8b3-892f-4e3f-aeb6-13437ed47aaa/)) |
| 5 | `[.]` | 서버의 확인. "3045000652 전까지 다 받았다" |

이 출력에서 세 가지를 알게 됐다.

- SYN을 보낸 뒤 SYN-ACK가 오기까지 1.67ms가 걸렸다. 한 번 왕복한 시간이고, curl이 잰 연결 시간(1.96ms)과 거의 같다. TCP 연결에는 데이터를 보내기 전에 왕복 한 번이 꼭 든다.
- SYN의 번호는 3044999080인데 서버는 3044999081을 기다린다고 답했고, 실제 첫 데이터도 3044999081부터 시작했다. SYN 자체가 번호 하나를 차지하기 때문이다.
- 첫 데이터가 1571바이트였고 서버는 3044999081 + 1571 = 3045000652를 확인 번호로 돌려줬다. "다음에 받을 번호"로 어디까지 받았는지 알리는 방식이 그대로 보였다.

> DNS는 이름을 IP 주소로 바꿔 주고, 그 답은 TTL 동안 저장돼 재사용된다. TCP는 handshake로 서로의 시작 번호를 맞춘 뒤, 바이트마다 번호를 매기고 확인을 주고받아 순서대로 빠짐없이 전한다.

## 확인 질문

**1. 같은 컴퓨터의 브라우저 탭 두 개가 같은 서버의 443번 포트에 연결했다. 서버는 두 연결을 어떻게 구분할까?**

<details><summary>답</summary>

내 쪽 포트가 다르다. 운영체제가 연결마다 다른 임시 포트를 붙이기 때문에, 내 IP, 내 포트, 서버 IP, 서버 포트 네 값 중 내 포트가 달라져 서로 다른 연결이 된다.

</details>

**2. 서버를 옮기면서 DNS의 IP 주소를 바꿨는데, 한동안 일부 사용자는 옛 서버로 접속한다. 왜 그럴까?**

<details><summary>답</summary>

리졸버나 브라우저, 운영체제가 옛 답을 저장해 두고 TTL이 끝날 때까지 쓰기 때문이다. TTL이 300초라면 길게는 5분 정도 옛 주소로 갈 수 있다. 그래서 주소를 바꾸기 전에 TTL을 미리 짧게 줄여 두기도 한다.

</details>

**3. 내 SYN의 순서 번호가 3044999080이었다. 서버가 돌려준 SYN-ACK의 ack 번호는 얼마이고, 왜 그 값일까?**

<details><summary>답</summary>

3044999081이다. ack 번호는 "다음에 받을 번호"를 뜻하고, SYN 자체가 번호 하나를 차지하기 때문에 하나 늘어난 값이 된다.

</details>

**4. `dig` 출력에는 `(UDP)`라고 나왔다. DNS 질의는 왜 TCP 연결 없이 보낼까?**

<details><summary>답</summary>

질문 하나, 답 하나로 끝나는 짧은 대화라서 handshake로 왕복을 한 번 더 쓰는 게 아깝기 때문이다. 답이 사라지면 리졸버가 다시 물으면 된다. 다만 답이 너무 크거나 할 때는 DNS도 TCP를 쓴다.

</details>

**5. TCP는 보낸 조각이 중간에 사라졌다는 걸 어떻게 알아챌까?**

<details><summary>답</summary>

확인 응답으로 안다. 받는 쪽은 "다음에 받을 번호"를 ACK로 돌려주는데, 일정 시간 안에 확인이 오지 않거나 같은 번호의 확인만 계속 오면 그 번호부터 다시 보낸다.

</details>
