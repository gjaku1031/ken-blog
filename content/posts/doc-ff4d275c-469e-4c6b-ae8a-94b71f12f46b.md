API는 Next.js 웹이 같은 출처의 `/api`로 부르는 JSON API 하나임. 방문자, 회원, 운영자의 요청을 모두 이 API가 받고, 운영자만 쓰는 요청은 `/api/admin` 아래로 모음. 주문 요청의 모양은 P1을, 사진 응답의 캐시 지시는 P2와 P3을 받침. 경로와 필드 제약의 기준은 코드임.[* 주문 컨트롤러(`OrderController.java`) · 주문 입력(`CreateOrderRequest.java`) · 오류 변환(`GlobalExceptionHandler.java`) · 사진 컨트롤러(`StorageController.java`)]

## 설계 원칙

| 결정 | 내용 | 이유·대가 |
| --- | --- | --- |
| 서버가 정하는 값은 받지 않음 | 주문 요청에는 옵션, 수량, 연락처, 배송지만 있고 가격, 주문자, 상태, 입금 기한이 없음. 선언하지 않은 필드가 오면 400으로 거부하고, 숫자를 문자열로 보내는 식의 타입 변환도 받지 않음 | 화면이 보낸 값으로 금액이나 주문자가 바뀌지 않고, 잘못 보낸 필드가 조용히 무시되지 않음. 화면이 필드를 하나 더 보내려면 API가 먼저 바뀌어야 함 |
| 운영 요청은 한 접두사 아래 | 운영자만 쓰는 경로는 모두 `/api/admin` 아래에 둠. 같은 주문이라도 고객의 조회와 운영자의 조회는 경로가 다름 | 권한을 경로로 한 번에 판단하고, 응답에 담는 범위를 경로별로 다르게 함. 비슷한 조회가 두 벌임. 경로를 판단하는 기준은 [보안 설계](/ken-blog/post/doc-6a9c1e3b-5d7f-4c42-b0e8-3a5d7f9b1c86/) |
| 상태를 바꾸는 요청은 따로 둠 | 고객의 주문 취소, 상품과 공지의 공개·숨김, 글의 발행은 동작 이름을 가진 경로임. 운영자의 주문 상태 변경만 바꿀 상태를 값으로 받음 | 동작마다 따라오는 일이 다름. 취소는 재고를 되돌리고, 발행은 방문자에게 열리는 사진 목록을 바꿈. 경로가 늘어남 |
| 오류 형식은 하나 | 모든 오류는 `success`, `statusCode`, `message`, `fields`, `timestamp`를 가진 JSON임. `message`는 화면에 그대로 보여 주는 문장이고, 입력 오류는 `fields`에 입력 경로(`items.0.quantity`)별 문구를 담음 | 화면이 오류마다 문구를 만들지 않음. 업무 오류 코드가 따로 없어 화면은 상태 코드로만 종류를 구분하고, 문구가 한 언어로 API에 고정됨. 표준 형식(RFC 9457)을 따르지 않음 |
| 400과 409를 구분 | 입력 자체가 틀리면 400, 입력은 맞지만 지금 상태에서 할 수 없으면 409 | 화면이 입력을 고치게 할지, 최신 상태를 다시 보여 줄지를 상태 코드로 정할 수 있음. 재고 부족은 이 구분과 달리 400임 |
| 목록은 쪽 번호 방식 | 쪽 번호와 쪽 크기를 받고 응답에 전체 건수를 함께 줌. 숫자가 아니거나 범위를 벗어난 값은 오류 대신 기본값과 상한(100건)으로 고침 | 주소를 손으로 고쳐도 목록이 깨지지 않음. 앞쪽을 건너뛰는 방식이라 뒤로 갈수록 느려지고, 넘기는 사이 새 항목이 생기면 한 건이 겹치거나 빠질 수 있음 |
| 상태를 바꾸는 요청은 토큰을 실음 | 조회가 아닌 모든 요청은 `X-CSRF-Token` 헤더의 값이 세션에 저장된 토큰과 같아야 하고, 없거나 다르면 403임. 로그인과 가입도 포함함 | 다른 사이트가 만들어 보낸 요청을 걸러 냄. 화면은 요청하기 전에 토큰을 받아 와야 하고, 배포 전에 열어 둔 화면은 새로 고쳐야 저장이 됨 |
| 응답은 저장 금지가 기본 | 모든 응답에 `Cache-Control: no-store`를 붙이고, 누구에게나 같은 공개 사진만 하루 캐시를 허용 | P3. [사진 404를 쫓다가 찾은 CDN 캐시 구멍](/ken-blog/post/post-b4f19d3c-62a8-4e7d-95b1-0c8a7e3f5d26/) |

> 주문 요청에는 고객이 고른 것만 담기고, 금액과 입금 기한은 서버가 그 순간의 값으로 정함.

## 주문 생성 계약

```json
{
  "items": [
    { "variantId": "0b6f1d2a-7c3e-4a51-9d84-2e5f8a1c6b30", "quantity": 1 }
  ],
  "buyerName": "김담담",
  "buyerPhone": "010-0000-0000",
  "shipName": "김담담",
  "shipPhone": "010-0000-0000",
  "shipPostalCode": "00000",
  "shipAddress1": "예시시 예시구 예시로 1",
  "shipMemo": "문 앞에 놓아 주세요"
}
```

`POST /api/orders` 요청의 예임. 로그인한 회원만 보낼 수 있고, 서버는 한 트랜잭션에서 다음을 함.

1. 회원 행을 잠그고 그 회원의 결제 대기 주문이 5건 미만인지 확인함. 5건이면 409로 거절함. 회원 행을 먼저 잠그는 것은 같은 회원의 동시 주문이 같은 건수를 읽고 함께 통과하는 일을 막기 위함임. 그다음 요청에 든 옵션 행을 ID 순서로 잠금. 순서를 고정해, 같은 옵션들을 담은 두 주문이 서로를 기다리다 멈추는 일을 막음[* 옵션을 잠근 뒤 주문을 저장할 때 외래 키 검사가 회원 행에 `FOR KEY SHARE`를 요청함. 회원 행 잠금은 `FOR NO KEY UPDATE`라 이 요청과 충돌하지 않으므로, 회원 행을 잠그지 않고 옵션부터 잠그는 운영자 대리 주문·고객 취소와도 서로 기다리지 않음]
2. 잠근 뒤에 읽은 값으로 옵션이 판매 중인지와 재고를 확인하고, 그 시점의 가격으로 금액을 계산함
3. 주문, 주문 상품, 재고 변동 이력, 상태 이력을 저장하고 재고를 뺌. 주문 상품에는 당시의 상품 이름, 옵션 이름, 가격, 대표 사진을 복사해 둠. 나중에 상품을 고치거나 지워도 주문 내역은 바뀌지 않음

성공하면 201과 함께 주문번호, 금액, 입금 기한(`paymentDueAt`)을 돌려줌. 재고가 모자라면 아무것도 저장하지 않고 아래처럼 거절함.

```json
{
  "success": false,
  "statusCode": 400,
  "message": "재고 부족: 원목 도마 대",
  "timestamp": "2026-10-11T07:21:40.512Z"
}
```

한 주문에 옵션은 30개까지 담을 수 있고, 같은 옵션을 두 줄로 나눠 보내면 400임. 20건을 동시에 보낸 실험의 결과는 [입금 안 된 주문이 재고를 놓지 않던 쇼핑몰](/ken-blog/post/post-5d0f6c1e-7b3a-4c58-9e21-3f6a1d2b8c47/)에 있음.

- **중복 요청**: 요청에 중복을 가려낼 키가 없음. 응답을 받지 못한 화면이 같은 요청을 다시 보내면, 재고가 남아 있는 한 주문이 두 건 생김
- **기다리다 실패한 요청**: 잠금 대기를 포함해 5초를 넘긴 요청은 일반 오류(500)로 끝남. 화면은 이 실패를 재고 부족과 구분하지 못함

## 상태가 맞지 않는 요청

두 요청이 같은 주문이나 같은 글을 거의 동시에 바꾸려 할 때, 뒤의 요청은 앞의 요청이 만든 상태를 모르고 보낸 것임. 이런 요청은 덮어쓰지 않고 409로 거절함.

| 요청 | 요청이 담는 것 | 서버의 확인 | 맞지 않을 때 |
| --- | --- | --- | --- |
| 운영자의 주문 상태 변경 | 바꿀 상태, 사유 | 주문 행을 잠근 뒤, 현재 상태에서 그 상태로 가는 전이가 허용되는지 봄 | 409 |
| 고객의 주문 취소, 운영자의 입금 기한 변경 | 없음, 새 기한 | 주문 행을 잠근 뒤 결제 대기 상태인지 봄 | 409 |
| 글의 초안 저장, 비공개 | 편집을 시작한 `revision` | `revision`이 같은 행만 고치는 조건부 `UPDATE` | 409. 초안을 덮어쓰지 않음 |
| 글의 발행 | 편집을 시작한 `revision` | 글 행을 잠근 뒤 `revision`을 비교 | 409 |

주문에는 버전 번호가 없고 상태 전이표가 그 역할을 맡음. 입금 확인과 자동 취소가 같은 주문에서 겹치면 먼저 잠근 쪽이 상태를 바꾸고, 뒤의 처리는 바뀐 상태를 보고 물러남. 허용되는 전이는 [기능과 사용자 흐름](/ken-blog/post/doc-c5e7a1b9-3d2f-4a86-9c4e-1b8d6f0a3e75/)의 상태도에 있음.

글은 입력이 멈출 때마다 자동으로 저장되므로 화면 둘이 같은 글을 열어 두면 서로의 초안을 덮어쓸 수 있음. 그래서 저장할 때마다 `revision`을 올리고, 요청의 `revision`이 현재 값과 다르면 거절하는 낙관적 동시성 제어를 씀.

주문의 확인은 "현재 상태에서 요청한 상태로 갈 수 있는가"뿐임. 운영자가 오래된 화면을 보고 보낸 요청이라도 그 전이가 지금 상태에서 허용되면 그대로 반영됨. 예를 들어 다른 운영자가 이미 배송 준비로 넘긴 주문에, 결제 완료 화면을 보던 운영자가 보낸 전액 환불은 통과함.

## 사진 업로드와 제공 계약

사진은 운영자만 올리고, 두 번의 요청으로 나눔.

| 단계 | 요청이 담는 것 | 서버의 확인 | 거절 |
| --- | --- | --- | --- |
| 티켓 발급 | 쓸 곳, 형식, 크기 | JPG, PNG, WebP 가운데 하나이고 5MB 이하인지 | 400 |
| 파일 올리기 | 티켓 ID와 파일 | 티켓을 발급받은 본인인지, 30분이 지나지 않았고 아직 쓰지 않은 티켓인지, 실제 파일의 형식과 크기가 신고한 것과 같은지 | 티켓이 없으면 404, 남의 티켓이면 403, 나머지는 400 |

- 저장 키는 서버가 만들고 화면이 정하지 못함. 쓸 곳의 이름, 임의의 UUID, 확장자로 이루어짐
- 세 크기의 변환은 트랜잭션 밖에서 하고, 저장하는 순간에만 티켓 행을 잠금. 같은 티켓으로 두 번 올리면 한 번만 통과함
- 상품과 글에는 확인이 끝난 사진의 키만 연결할 수 있음. 올리다 만 키를 보내면 400임
- 파일을 저장한 뒤 트랜잭션이 실패하면 티켓은 되돌아가지만 저장된 파일은 남음. 이런 파일과, 올린 뒤 어디에도 연결하지 않은 사진은 하루가 지나면 주기 작업이 지움

사진을 내려받는 주소는 하나이고, 누가 어떤 사진을 요청했는지에 따라 응답이 달라짐.

| 사진 | 응답 |
| --- | --- |
| 공개된 상품, 글, 공지에 쓰인 사진 | 200, `Cache-Control: public, max-age=86400` |
| 운영자가 보는 비공개 사진, 회원 본인 주문의 대표 사진 | 200, `no-store` |
| 그 밖의 사진 | 404 |

볼 수 없는 사진은 없는 사진과 같은 404로 답해, 공개하지 않은 사진이 있다는 사실이 드러나지 않음. 주소의 `size` 값(`s`, `m`, `l`)으로 변환본을 고르고, 생략하면 가장 큰 것을 줌. 변환본이 있는 사진은 원본을 내보내지 않음. 원본에는 촬영 위치 같은 정보가 남아 있기 때문임. 변환 방식과 전송량은 [목록이 원본 사진을 통째로 받고 있던 쇼핑몰](/ken-blog/post/post-8c2e4a97-1d5b-4f36-a0c9-6b7e2f4d1a83/)에서 다룸.
