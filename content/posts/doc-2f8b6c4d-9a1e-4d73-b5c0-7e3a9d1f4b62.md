웹, API, PostgreSQL이 서버 한 대의 Docker Compose에서 함께 돌고, 방문자가 들어오는 길은 Cloudflare 터널 하나임.

## 품질 요구사항

| 요구 | 뜻 | 핵심 문제 | 수단 |
| --- | --- | --- | --- |
| 재고 정합성 | 동시에 주문해도 재고보다 많이 팔리지 않고, 입금하지 않은 주문이 재고를 계속 잡지 않음 | P1 | 옵션 행 잠금, 입금 기한, 주기 작업의 자동 취소 |
| 가벼운 전송 | 목록과 썸네일이 화면에 필요한 크기의 사진만 받음 | P2 | 올릴 때 만드는 세 크기의 변환본, 공개 사진의 캐시 |
| 캐시 안전 | 사람에 따라 달라지는 응답이 CDN에 저장되지 않음 | P3 | 모든 응답의 기본값 `no-store` |
| 한 사람이 운영 | 구성 요소가 적고, 장애가 났을 때 볼 곳이 한 대임 | 전체 | 서버 한 대, PostgreSQL 하나, Redis와 메시지 큐 없음 |

## 인프라 구성

배포 경계는 Cloudflare, 운영 서버, GitHub Actions의 세 영역.

```mermaid caption="방문자의 요청은 Cloudflare를 거쳐 서버의 터널 프로세스로 들어오고, 웹이 /api 요청을 API로 넘김. API 컨테이너는 서버 밖으로 포트를 열지 않음. 배포는 워크플로를 수동으로 실행해 코드를 서버에 전달하고 서버에서 이미지를 빌드함"
architecture-beta
  %% layout: damdam-infrastructure
  group users[Users]
  group cf[Cloudflare]
  group deploy[Deployment]
  group server[Server]
  group compose(ken:docker)[Docker Compose] in server

  service customer(ken:user)[Customer] in users
  service operator(ken:user)[Operator] in users
  service cdn(ken:cloudflare)[Cloudflare] in cf
  service actions(ken:github-actions)[GitHub Actions] in deploy
  service tunnel(ken:vpn)[cloudflared] in server
  service web(ken:nextjs)[Next.js web] in compose
  service api(ken:spring)[Spring Boot API] in compose
  service uploads(ken:disk)[Uploads volume] in compose
  service pg(ken:postgresql)[PostgreSQL] in compose

  customer:R -[HTTPS]-> L:cdn
  operator:R -[HTTPS]-> L:cdn
  cdn:R -[Tunnel]-> L:tunnel
  tunnel:B -[HTTP]-> T:web
  web:B -[API]-> T:api
  api:R -[Files]-> L:uploads
  api:R -[SQL]-> L:pg
  actions:R -[Deploy]-> L:api{group}
```

| 배포 경계 | 구성 요소 | 책임 |
| --- | --- | --- |
| Cloudflare | CDN | HTTPS를 받고 공개 사진을 캐시함. 서버로는 터널로만 연결됨 |
| 운영 서버 | 가상 머신 | VMware ESXi 위의 가상 머신 한 대(4 vCPU, 메모리 8GB, Ubuntu 24.04) |
| 운영 서버 | cloudflared | 서버에서 Cloudflare로 나가는 연결을 열어 두고, 들어온 요청을 웹으로 넘김. 웹과 API는 밖에서 직접 닿는 포트를 열지 않음 |
| 운영 서버 | 웹(Next.js) | 화면을 그리고 `/api` 요청을 API로 넘김. 서버 안의 주소에만 열려 있음 |
| 운영 서버 | API(Spring Boot) | 업무 규칙, 권한 확인, 주기 작업. 컨테이너 밖으로 포트를 열지 않음 |
| 운영 서버 | PostgreSQL | 업무 데이터와 로그인 세션 |
| 운영 서버 | 업로드 볼륨 | 사진의 원본과 변환본 |
| GitHub Actions | CI, 배포 워크플로 | push마다 검사하고, 수동으로 실행하면 CI가 성공한 커밋만 서버로 전달함 |

## 주요 흐름

| 흐름 | 처리 경로 | 실패하면 | 관련 문제 |
| --- | --- | --- | --- |
| 상품·글 보기 | 브라우저 → Cloudflare → 터널 → 웹 → API → PostgreSQL. API 응답은 `no-store`라 CDN이 저장하지 않음 | 서버와 API가 한 대뿐이라 둘 중 하나가 멈추면 사이트 전체가 응답하지 못함 | P3 |
| 주문 | API가 한 트랜잭션에서 회원 행을 잠가 결제 대기 건수를 보고, 옵션 행을 ID 순서로 잠근 뒤 재고를 빼고 주문과 이력을 저장함 | 재고 부족은 400, 결제 대기 5건이면 409, 잠금 대기를 포함해 5초를 넘기면 500. 어느 경우든 아무것도 저장하지 않음 | P1 |
| 입금 확인과 자동 취소 | 운영자의 입금 확인과 5분마다 도는 주기 작업이 모두 주문 행을 잠그고 상태를 다시 확인함 | 먼저 잠근 쪽만 반영됨. 뒤에 온 입금 확인은 409, 뒤에 온 주기 작업은 그 주문을 건너뜀 | P1 |
| 사진 올리기 | 티켓 발급 → 파일 업로드 → 트랜잭션 밖에서 세 크기로 변환 → 티켓 행을 잠가 다시 확인하고 저장 | 형식·크기가 신고와 다르거나 변환에 실패하면 400이고 저장하지 않음. 저장 뒤 트랜잭션이 실패해 남은 파일은 하루 뒤 주기 작업이 지움 | P2 |
| 사진 보기 | API가 공개 여부를 판정해 공개 사진만 하루 캐시를 허용하고, 운영자·주문자에게만 보이는 사진은 `no-store`로 줌 | 볼 수 없는 사진은 없는 사진과 같은 404 | P2, P3 |
| 배포 | 수동 실행 → 그 커밋의 CI 성공 확인 → 코드 전달 → 서버에서 이미지 빌드와 기동. 상세는 [배포와 운영](/ken-blog/post/doc-e1b3f5a7-6c8d-4b20-8f9a-4d2e6c0b7a39/) | CI가 성공하지 않았거나 서버에 환경 파일이 없으면 서버를 바꾸지 않고 멈춤. 스키마 변경이 실패하면 API가 시작하지 못해 사이트가 멈춤 | — |

```mermaid caption="브라우저의 요청은 Cloudflare와 터널을 거쳐 웹에 닿고, 웹이 /api 요청을 API로 넘김. API는 요청마다 세션의 사용자를 DB에서 다시 읽어 권한을 확인함"

    W->>A: /api 요청 전달
    A->>D: 세션과 사용자 조회
    A->>D: 업무 데이터 조회·변경
```

## 상태를 두는 곳

| 상태 | 저장 위치 | 재시작하면 |
| --- | --- | --- |
| 상품, 주문, 재고 이력, 글, 운영 기록 | PostgreSQL | 유지됨 |
| 로그인 세션 | PostgreSQL(Spring Session JDBC) | 유지됨 |
| 사진의 원본과 변환본 | 업로드 볼륨 | 유지됨 |
| 로그인·가입 시도 횟수 | API 프로세스의 메모리 | 사라짐 |
| 장바구니 | 방문자 브라우저의 저장소(`localStorage`) | 서버와 무관함. 로그인하면 그 계정의 장바구니로 옮기고 로그아웃하면 비움. 다른 기기에서는 보이지 않음 |

주기 작업은 API 프로세스 안에서 실행함. 기한이 지난 결제 대기 주문의 취소는 5분마다 돎. 나머지는 한 시간에 한 번씩 돎. 기한이 지난 업로드 티켓의 정리는 정각에, 어디에도 쓰이지 않는 사진의 삭제는 15분에, 재고와 재고 이력의 대조는 30분에 실행함.

## 일관성 보장 범위

| 대상 | 보장하는 것 | 수단 | 보장하지 않는 것 |
| --- | --- | --- | --- |
| 재고와 주문 | 재고보다 많이 팔리지 않음. 한 주문의 재고는 한 번만 돌아옴 | 옵션 행 잠금, 주문 행 잠금과 잠근 뒤의 재확인, `CHECK (stock >= 0)` | 잠금 순서와 재확인은 코드 규칙으로 지킴. 어긴 경로를 자동으로 잡지 못함 |
| 재고 수량과 이력 | 옵션마다 이력의 합이 현재 수량과 같음 | 수량을 바꾸는 경로가 같은 트랜잭션에서 이력을 남김 | 매시간 대조해 어긋난 옵션을 운영자의 첫 화면과 오류 로그에 알림. 고치지는 않음 |
| 입금 기한 | 주문할 때 안내한 기한이 설정을 바꿔도 유지됨 | 기한을 주문에 저장 | 기한이 지난 뒤 취소까지 최대 5분이 걸림 |
| 사진 파일과 DB | 검증을 통과한 파일만 저장됨 | 업로드 티켓과 실제 파일의 형식·크기 대조 | 올린 뒤 어디에도 붙이지 않은 파일은 하루 동안 볼륨에 남고, 그 뒤 주기 작업이 지움 |
| 공개 여부와 캐시 | 비공개 사진은 캐시되지 않음 | 공개로 판정된 응답에만 캐시 허용 | 공개 사진을 숨겨도 받아 간 쪽에는 최대 하루 남음 |

서버와 API가 한 대뿐이라 둘 중 하나가 멈추면 사이트 전체가 멈춤. 배포할 때도 컨테이너를 바꾸는 동안 요청이 끊김. DB와 사진의 백업은 하지 않음.

결정의 대안과 대가는 [주요 기술적 의사결정](/ken-blog/post/doc-7a3c9e51-4b6d-4f82-a1e7-2d5c8b0f6e94/)에서, 배포 절차는 [배포와 운영](/ken-blog/post/doc-e1b3f5a7-6c8d-4b20-8f9a-4d2e6c0b7a39/)에서 다룸.
