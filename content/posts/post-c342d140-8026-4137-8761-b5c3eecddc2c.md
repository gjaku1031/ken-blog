ken-blog의 공개 화면은 원래 브라우저가 API를 불러 글을 그리는 방식이었는데, 빌드할 때 HTML을 미리 만들어 두는 정적 생성으로 바꿨음. 서버가 일본에 있는 1코어짜리 VM이고 독자는 한국에 있어서, 바꾼 효과가 실제로 있었는지 2026년 10월에 세 가지 구조를 같은 데이터로 다시 세워 쟀음.

> 정적 생성이 20개 조건 모두에서 본문을 가장 빨리 보여 줬고(p95로는 20개 중 19개), 본문을 보여 주는 데 API가 필요 없어졌음. 받는 양은 오히려 가장 많았으므로, 서버와 차례로 주고받던 왕복이 없어진 것이 가장 큰 요인으로 보임.

## 무엇을 알고 싶었나

대문의 핵심 문제 P2(제한된 자원에서의 열람 성능)에 대해 두 가지를 물었음. 첫째는 첫 방문, 다시 방문, 사이트 안 이동에서 본문이 보이기까지의 시간이 줄었는지이고, 둘째는 독자가 글을 읽는 것이 API 서버의 부담으로 이어지는지임. 조건과 반복 횟수는 미리 정했지만 결과에 대한 가설은 적어 두지 않은 탐색적 실험임.

측정 당시 서버는 OCI 일본 리전의 ARM 1코어, 약 4GB VM이었고, 한국에서 이 서버까지 한 번 왕복하는 데 약 38.6ms가 걸렸음.[* 한국의 맥에서 측정 VM까지 ping 30회 평균. 측정 VM은 운영 서버와 같은 도쿄 리전]

## 어떻게 비교했나

세 구조를 같은 데이터로 다시 세웠음.

| 구조 | 본문이 어디서 오나 | 글을 읽는 동안 부르는 API |
| --- | --- | --- |
| 순수 CSR | HTML에는 없고, 스크립트가 API로 받아 그림 | 로그인 확인 뒤 프로젝트와 문서 조회, 역링크, 조회수 기록 |
| 하이브리드 | 빌드할 때 HTML에 넣음 | 순수 CSR과 같은 호출이 그대로 남음 |
| 정적 생성 | 빌드할 때 HTML에 넣음. 목록과 역링크도 포함 | 로그인 확인 1회 |

하이브리드는 정적 생성으로 바꾸기 직전의 운영 구조임. 검색엔진에 보이려고 본문을 미리 넣었지만, 화면이 뜬 뒤 부르는 API는 그대로였음.[* 세 구조의 코드는 각각 커밋 `f29ef35`, `135169f`, `811c95f`]

![세 구조가 본문을 화면에 띄우기까지 기다리는 단계. 순수 CSR은 로그인 확인, 프로젝트 조회, 본문 조회를 차례로 기다리고, 하이브리드와 정적 생성은 HTML만으로 본문이 보임|dark=88|w=100|a=center](attachment:87)

데이터는 운영 공개 스냅샷과 Git 원고로 글 16개와 프로젝트 6개를 맞췄고, 정적 파일은 세 구조 모두 같은 Caddy 서버에서, 운영 GitHub Pages와 같은 캐시 규칙으로 내보냈음. 옛 API는 운영과 같은 자원 한도(1 CPU, 1.5GiB)로 띄웠음. 네트워크는 두 가지로 쟀음. 하나는 한국에서 실제로 잰 왕복 38.6ms 조건(R)이고, 다른 하나는 왕복 150ms의 느린 모바일 조건(M)임.[* R은 다운로드 처리량 16.3MB/s(5회 중앙값)를 함께 적용. M은 다운로드 1.6Mbps, 업로드 750kbps로 Lighthouse 등에서 흔히 쓰는 조건이며 특정 망의 실측값이 아님. 둘 다 Chromium의 네트워크 조건 흉내 기능으로 적용]

문서 다섯 가지 상황(프로젝트 대문, ERD 문서, 일반 글, 홈 목록, 대문에서 ERD로 이동)을 첫 방문과 다시 방문, 두 네트워크에서 각각 15번씩, 모두 900번 쟀음. 조합마다 워밍업을 두 번 하고 세 구조의 순서를 바꿔 가며 돌렸음. "본문이 보인 시각"은 본문에 넣어 둔 표식 문장이 화면에 나타난 때로 정했음. 서버 부담은 ERD 문서를 한 번 열 때 실제로 나가는 요청을 그대로 1초에 5번씩 60초 동안 다시 보내며 API 컨테이너의 CPU를 봤음.

## 결과가 말해 주는 것

순수 CSR이 느린 이유는 기다림이 줄줄이 이어지기 때문이었음. 스크립트를 받고, 로그인 상태를 묻고, 프로젝트 정보를 받은 뒤에야 본문을 요청해서, 본문 전에 API 응답을 세 번 차례로 기다림.[* 세 단계는 옛 화면 코드에서 확인한 본문 전 의존 순서임. 요약 자료의 단계 수(순수 CSR 5, 하이브리드 4)는 페이지 로드가 끝날 때까지의 요청을 모두 센 값이라 더 큼] 왕복 한 번이 길수록 이 차이가 커져서, ERD 문서 첫 방문은 네트워크 R에서 1.6배였던 차이가 왕복 150ms인 M에서는 4.1배로 벌어졌음.

하이브리드는 절반만 나아졌음. 본문을 HTML에 넣어 첫 방문은 순수 CSR보다 빨랐지만, 화면이 뜬 뒤 부르는 API와 큰 스크립트가 남아 정적 생성보다는 느렸음. 사이트 안에서 문서를 옮길 때는 네트워크 R에서 API를 7번 다시 불러 오히려 순수 CSR보다 느렸고(701ms 대 414ms), M에서는 반대로 빨라 조건에 따라 순위가 바뀌었음.

정적 생성은 받는 양이 가장 많았는데도 가장 빨랐음. ERD 문서 첫 방문에서 도식 렌더러까지 1,061KB를 받았지만, HTML 하나만 받으면 본문이 확정되고 API 응답을 기다릴 일이 없었음. 다시 방문할 때는 캐시 덕분에 11KB만 받았음.

서버 부담도 갈렸음. 옛 두 구조는 글을 한 번 열 때마다 API 요청 6~9개가 1코어 서버로 갔고, 1초에 5번 열면 CPU가 최대 42~66%까지 올랐음. 정적 생성에서는 본문과 목록을 위한 요청이 서버로 가지 않고, 관리자 메뉴를 보일지 정하는 로그인 확인 한 번만 남음. 이번 측정에서는 이 확인을 브라우저가 대신 응답하게 해서 서버 요청을 0으로 셌으므로, 실제 운영에서는 글을 열 때마다 가벼운 요청 1건이 서버에 감. 그래도 본문을 그리는 데는 이 응답을 기다리지 않음.

이 결과에서 생긴 다음 질문은 "왕복이 길수록 정적 생성의 이득이 커지는가"임. 네트워크 조건이 두 개뿐이라 이번 실험으로는 답하지 못함. 답하려면 왕복 시간을 여러 단계로 바꾸고, 같은 코드에서 정적 생성만 켜고 끈 두 구조를 비교하며, 가설과 기각 기준을 미리 적어 두는 확증 실험이 필요함.

## 결과를 믿기 어려운 부분

Shadish·Cook·Campbell(2002)의 네 가지 관점으로 점검했음.

- **다른 원인이 섞였을 가능성**: 세 구조는 정적 생성 여부 말고도 화면 스크립트, 도식 렌더러, 부가 기능이 서로 달랐음. 그래서 결과 전체를 정적 생성 하나의 효과라고 나눠 말할 수는 없음. 같은 날 먼저 한 1차 측정(640회)은 아래 문제가 있어 결론에 쓰지 않았음

<details><summary>1차 측정에서 발견한 문제와 고친 방법</summary>

| 문제 | 영향 | 고친 방법 |
| --- | --- | --- |
| 옛 구조로 하이브리드 하나만 비교함 | 본문이 이미 HTML에 있어 API 왕복이 본문 표시에 주는 영향을 볼 수 없었음 | 순수 CSR과 사이트 안 문서 이동 상황을 추가함 |
| 측정용 서버가 정적 파일에 캐시 규칙 없이 응답함 | 구조마다 다시 방문할 때의 캐시 동작이 달라, "다시 방문은 옛 구조가 빠르다"는 잘못된 결과가 나옴 | 운영 GitHub Pages의 응답 헤더를 확인해 세 구조에 같은 캐시 규칙을 적용하고, 캐시가 실제로 쓰이는지 확인함 |
| 옛 구조의 로그인 확인 요청에서 브라우저의 완료 신호가 빠짐 | API를 몇 번 차례로 기다리는지 잘못 셈 | 응답을 받은 시점 기준으로 다시 셈 |

</details>

- **일반화**: 측정용으로 다시 세운 환경이라 운영 DB와 CDN을 거치지 않았음. 참고로 맥에서 운영 GitHub Pages의 HTML 첫 바이트까지는 중앙값 33~36ms였음
- **재는 것이 맞나**: 네트워크 지연은 브라우저가 요청마다 지연을 넣는 방식으로 흉내 낸 것이라, 연결을 맺을 때의 왕복까지 정확히 재현하지는 않음. 정적 생성의 로그인 확인은 브라우저가 대신 응답하게 해 서버 부담에서 빠졌음
- **표본 크기**: 조합마다 15번이라 p95는 사실상 15번 중 가장 느린 값임. 그래서 중앙값 위주로 읽었고, p95로 보면 20개 중 1개 조합에서 순위가 바뀜. 같은 회차끼리 짝지은 비교는 아직 하지 않았음
