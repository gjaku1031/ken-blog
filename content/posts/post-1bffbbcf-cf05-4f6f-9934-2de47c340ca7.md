Vowser가 작업 경로 저장소로 고른 Neo4j를, 같은 경로 연산을 MySQL로도 구현해 다시 측정한 기록. 분류: 탐색적 실험(2026-09-28~29 사후 재현).

> 현재 경로 모델의 모든 연산에서 인덱스를 둔 MySQL이 Neo4j보다 빨랐음. 차이를 가장 크게 만든 것은 DB 종류가 아니라 트랜잭션 경계와 조회 순서 같은 구현이었음.

## 연구 질문

개발 당시에는 "데이터가 많을수록 그래프 탐색이 빠르다"는 간단한 실험과 벡터 검색을 같은 DB에서 쓸 수 있다는 점으로 Neo4j를 골랐음. 그 실험의 조건과 수치는 남아 있지 않아, 같은 연산을 두 DB로 구현해 다시 측정함.

- **Q1 운영 연산**: 경로 등록·인기 경로 조회·시각화·가중치 갱신에서 Neo4j가 MySQL보다 빠른가
- **Q2 의도 검색**: 의도 벡터로 경로를 찾아 전체 단계를 돌려주는 검색에서 어느 쪽이 빠르고, 결과가 정확한가
- **Q3 그래프가 유리할 기능**: 지금은 없는 기능인 여러 경로가 단계를 공유하는 분기·대체 경로에서는 Neo4j가 유리한가

대문의 핵심 문제 P1(사용자 기록을 단계 연결 경로로 저장)의 저장소 선택을 다시 보는 질문임. 데이터·자원·실행 순서·정답 확인 절차는 실행 전에 프로토콜로 정했지만, 어느 DB가 빠를지에 대한 가설과 판정 기준은 미리 정하지 않았음.

### Q2 의도 검색

경로 1천·1만 개의 균등·편중 분포 네 조건에서, 도메인 힌트 없이 상위 3개를 찾는 검색의 지연 중앙값은 다음과 같았음. 공식 요청 33,600건에 오류는 없었음.

| 구현 | p50 |
| --- | ---: |
| MySQL + FAISS 벡터 인덱스 | 2.04~2.15ms |
| Neo4j 개선형(필터·정렬 순서 수정) | 10.52~12.01ms |
| Neo4j 원본형(현재 코드의 조회 순서) | 28.58~29.91ms |

- 원본형은 경로 1만 개에서도 1위 결과가 모든 조건에서 정답(190/190)이었지만, 상위 결과 전체의 순서 일치는 150~164/190으로 떨어졌음. 도메인 필터와 결과 수 제한이 재정렬보다 먼저 적용되는 순서 때문임
- 경로 3만 개에서는 Neo4j가 벡터 속성을 포함한 데이터를 적재하다 메모리 부족으로 멈춰 검색을 측정하지 못함. 이 자원 조건에서의 적재 실패이며 일반적인 용량 한계는 아님

### Q3 공유 단계·분기 경로

여러 경로가 같은 단계를 공유하고 막힌 단계를 돌아가는 대체 경로를 찾는 기능은 현재 Vowser에 없음. 그래프 DB가 유리할 만한 이 기능을 프로토타입으로 만들어, 경로 1천·1만 개, 공유율 0·25·50%, 분기 상한 1·2·4의 16개 조건에서 측정함. 본측정 38,400건은 모두 정답이었음.

| 구현 | p50 / p95(16개 조건 합산) |
| --- | ---: |
| Neo4j 경로 탐색 | 8.25 / 55.88ms |
| Neo4j 소속 테이블 방식 | 6.21 / 15.72ms |
| MySQL 재귀 CTE | 3.76 / 16.55ms |
| MySQL 소속 테이블 방식 | 3.18 / 8.13ms |

같은 방식끼리 조건별로 비교하면 16개 조건 가운데 MySQL이 p50에서 14~15개, p95에서 15~16개 조건에서 빨랐음. Neo4j가 빠른 조건(경로 1천 개, 공유 50%, 분기 2·4)도 p95까지 일관되지는 않았음.

## 해석

- 현재 경로 모델은 기록마다 단계를 따로 만들어 서로 겹치지 않는 사슬의 모음임. 그래프 DB의 장점인 공유 노드와 가변 길이 탐색이 거의 쓰이지 않아, 인덱스를 둔 관계형 DB의 단순 조회를 앞서지 못함
- 지연 차이를 가장 크게 만든 것은 DB 종류보다 구현이었음. 같은 Neo4j에서도 저장을 배치로 묶으면 등록이 약 16배, 검색 순서를 고치면 약 2.5배 빨라짐
- 그래프가 유리할 분기 기능에서도 이 규모에서는 우위를 확인하지 못함

그래서 지금 다시 고른다면, 관계형 DB 하나에 경로를 두고 벡터 검색만 별도 인덱스로 붙이는 쪽이 운영할 DB도 하나 줄어 합리적이라고 판단함. 이 실험에서 나온 다음 가설은 "단계 공유가 많고 탐색 깊이가 깊어지면 Neo4j가 앞선다"이며, 분기 경로가 수만 단위로 커지고 탐색이 깊어지는 조건은 측정하지 않아 확인하지 못함.

## 타당성과 한계

Shadish·Cook·Campbell(2002)의 네 분류로 정리함.

- **내적 타당성**
  - 두 DB를 번갈아 하나씩만 띄우고 실행 순서를 라운드마다 교차해, 순서·캐시 효과를 줄임
  - 다른 서비스가 함께 돌던 공유 VM에서 측정해 호스트가 유휴 상태였다고 보장하지 않음
  - 분기 실험의 MySQL 소속 테이블 방식은 첫 측정에서 불리한 조인 순서가 드러나 순서만 고친 별도 코호트로 다시 측정함. 첫 결과와 방법 변경 기록은 따로 보존함
- **외적 타당성**: 합성 데이터와 단일 클라이언트의 순차 요청임. 동시 요청 처리량과 실제 사용자 경로의 분포는 측정하지 않음. 의도 검색의 정확도는 이 실험이 아니라 [Vowser 의도 검색 정확도와 재검색 임계값](/ken-blog/post/post-ccb0e7cb-986a-4f7d-832e-ba4fd69e49e1/)에서 다룸
- **구성 타당성**
  - DB 저장 경로가 메모리 기반 파일 시스템(tmpfs)이라 실제 SSD의 입출력 지연을 대표하지 않음
  - 지연은 클라이언트 쪽 왕복 시간이라 DB 엔진만의 성능 차이와 같지 않음
- **통계적 타당성**: 조건마다 3라운드 반복이고, 모든 응답을 정답과 대조함. 경로 3만 개의 Neo4j 의도 검색은 적재 중 메모리 부족으로 측정하지 못해 그 조건의 비교가 없음
