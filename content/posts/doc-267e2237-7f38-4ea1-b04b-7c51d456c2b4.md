P3는 P1과 P2를 택한 결과로 생긴 문제를 푸는 결정임. 본문은 Git에, 글 정보는 DB에 있어 빌드 때 둘을 합치는데, 그 사이에 관리자가 글 정보를 바꾸면 한 사이트에 서로 다른 시점의 자료가 섞일 수 있음.

## P1. Git Markdown을 원고의 정본으로

### 문제

처음에는 Next.js 화면의 웹 블록 편집기로 본문을 써서 DB에 저장했음. 그랬더니 원고가 어떻게 바뀌었는지 diff로 보거나 수정 이력을 따라가기 어려웠고, 사람과 에이전트가 같은 원고를 같은 방법으로 다루기도 어려웠음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 웹 편집기와 DB 저장 유지 | 변경 검토와 이력 추적 문제가 그대로 남음 |
| DB에 버전 이력 테이블 추가 | 이력 저장은 가능하지만 diff 검토 화면과 되돌리기 기능을 따로 만들어야 함. 에이전트는 파일과 Git으로 일하므로, 본문이 DB에 있으면 에이전트의 수정만 별도 도구를 거치게 됨 |
| **Git 저장소의 Markdown을 정본으로 사용 (채택)** | diff·검토·되돌리기를 Git이 제공하고, 사람과 에이전트가 같은 파일을 같은 도구로 수정함 |

### 대가

본문(Git)과 글 정보(DB)가 서로 다른 저장소에 있게 되었고, 둘을 일관되게 발행하는 문제가 P3로 이어짐.

### 검증

지금 API에는 본문을 저장하거나 읽는 경로가 없음. 글 편집 요청은 정해진 글 정보 키 8개가 모두 있고 다른 키가 없을 때만 받으므로, 본문을 바꾸려면 Git 커밋을 거쳐야 함. 그래서 본문의 모든 변경이 커밋으로 남고 diff로 검토하거나 되돌릴 수 있음. 다만 이것은 검토할 수 있는 상태를 보장할 뿐이고, 1인 프로젝트라 커밋마다 다른 사람의 검토를 거치지는 않음.[* [글 편집 요청 검증](https://github.com/gjaku1031/ken-blog/blob/1072a36/src/main/java/io/github/gjaku1031/kenblog/post/dto/PostEditRequest.java)] 아키텍처·ERD 도식도 Mermaid 원문으로 원고에 들어 있어 설명과 같은 커밋에서 바뀜. 본문이 담긴 키를 보낸 요청은 400으로 거부됨([API 설계](/ken-blog/post/doc-6bf82223-5b13-49ae-894b-5da5a0de6ddf/) 참조).

## P2. 빌드 시 정적 생성으로 본문 열람에서 API 제거

### 문제

예전 구조에서는 브라우저가 화면 스크립트를 받은 뒤 API를 불러 본문을 받아 그렸음. 프로젝트 문서 하나를 열면 로그인 상태 확인, 프로젝트 조회, 문서 조회가 앞 응답을 기다려 차례로 이어졌고, 이미지를 빼고도 화면 하나에 API 요청이 5~10번 나갔음.[* 로그인 상태, 프로젝트, 문서, 역링크, CSRF 토큰, 조회수 기록 등. 측정한 다섯 상황의 서버 API 요청 수이고, ERD 문서는 순수 CSR 6번, 하이브리드 9번] 응답은 모두 캐시하지 않게(`no-store`) 되어 있어서 다시 방문해도 같은 요청이 반복됐음. 차례로 기다리는 단계마다 왕복 시간(약 38ms)과 1코어 서버의 처리 시간이 쌓였음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 브라우저의 API 호출(CSR) 유지 | 본문 전의 순차 왕복과 화면당 API 요청 5~10회가 열람마다 반복됨 |
| Redis 캐시로 본문 조회 가속 | 당시 격리 환경에서 관리형 Redis를 거친 조회가 DB 직접 조회보다 1.4~1.7배 느렸음[* 2026-09-26, API 응답 시간 각 10회의 중앙값으로 본문 약 1KB와 128KiB 두 크기에서 비교. 원자료는 저장소에 남기지 않았음. 이 환경의 결과이며 일반적인 Redis 성능으로 확대하지 않음. 같은 VM에 둔 Redis는 측정하지 않았고, 측정했더라도 순차 왕복은 남아 결정은 바뀌지 않는다고 판단함]. 서버 처리 시간을 줄여도 순차 왕복은 남음 |
| 요청마다 서버에서 렌더링(SSR) | 순차 왕복은 서버 안으로 옮겨지지만 모든 열람 요청이 1코어 서버의 렌더링 부하가 됨. 측정하지 않고 구조로 판단함 |
| **빌드 시 정적 생성 (채택)** | 본문을 포함한 HTML 한 번의 응답으로 본문 표시가 끝나고, 본문 표시에 API 요청이 필요 없음 |

### 대가

글과 공개 상태를 바꾸면 Pages를 다시 배포해야 반영되고, 발행을 취소해도 다시 배포하기 전까지는 이전 페이지가 남음. 재배포는 대기 시간을 포함해 보통 1분 남짓 걸리고, 배포 뒤에도 Pages 캐시 때문에 최대 10분 동안 이전 페이지가 보일 수 있음.[* 2026-10-08 06:21(UTC) 이전에 성공한 Pages 워크플로 실행 20번의 중앙값 67초, 최장 345초. 2026-10-09 기준 최근 20번은 중앙값 67.5초, 최장 130초. 실행 시간은 대기열을 포함한 값. 캐시는 GitHub Pages의 `max-age=600`]

### 검증

세 구조를 같은 데이터로 다시 세워 비교했음. 본문을 API로만 받는 순수 CSR, 본문을 HTML에 미리 넣었지만 API도 부르는 전환 직전의 하이브리드, 그리고 지금의 정적 생성임. 맥에서 잰 왕복 시간 38.6ms와 처리량을 브라우저의 네트워크 조건으로 넣고, 세 구조 모두 GitHub Pages와 같은 캐시 규칙으로 내보냈음. 20개 조건에서 15번씩 쟀더니 정적 생성이 모든 조건에서 본문을 가장 빨리 보여 줬음.

| 측정 항목(중앙값, 괄호 안 p95) | 순수 CSR | 하이브리드 | 정적 생성 |
| --- | ---: | ---: | ---: |
| ERD 문서 첫 방문, 본문 표시 | 747 (810)ms | 625 (1,148)ms | 463 (494)ms |
| 같은 조건, 모바일 네트워크(150ms·1.6Mbps) | 3,536 (4,063)ms | 1,582 (2,144)ms | 869 (1,607)ms |
| 대문에서 ERD 문서로 이동, 클릭 후 본문 표시 | 414ms | 701ms | 216ms |
| ERD 문서 한 번 열 때 본문 표시까지의 API 요청 | 6회 | 9회 | 0회 |
| 초당 5회 ERD 열람 60초, API 서버 CPU 평균/최대 | 17.1% / 42.2% | 25.6% / 66.0% | 요청 없음 |

> 정적 생성은 첫 방문 전송량이 가장 컸지만 중앙값 기준 모든 조합에서 본문이 가장 빨리 보였음(p95 기준 20개 중 19개). API 응답을 차례로 기다리는 단계가 없어진 것이 가장 큰 요인으로 보임.

측정용으로 다시 세운 환경에서 브라우저로 잰 결과이고, 네트워크 지연은 브라우저가 요청마다 지연을 넣는 방식[* Chromium DevTools Protocol의 네트워크 조건 에뮬레이션. TCP·TLS 핸드셰이크 왕복은 정확히 재현하지 않음]으로 근사함. 측정 방법과 전체 결과는 [정적 생성 전환 전후의 글 열람 지연 측정](/ken-blog/post/post-c342d140-8026-4137-8761-b5c3eecddc2c/) 참조.

## P3. revision 재검증으로 서로 다른 시점의 자료 혼합 방지

### 문제

공개 페이지는 Git의 원고, DB의 글 정보, 디스크의 이미지를 빌드할 때 합쳐 만듦. 빌드가 자료를 모으는 동안 관리자가 글 정보를 바꾸면 서로 다른 시점의 자료가 섞인 사이트가 나갈 수 있고, 원고가 빠지거나 이미지가 깨져 있으면 일부만 망가진 사이트가 배포될 수 있음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 검증 없이 수집한 그대로 빌드 | 서로 다른 시점의 자료가 섞이거나 일부가 깨진 사이트가 배포될 수 있음 |
| 빌드하는 동안 DB 쓰기 잠금 | 빌드 시간 동안 관리 기능이 멈추고, 빌드 실패 시 잠금 해제를 따로 보장해야 함 |
| DB에 단조 증가 버전 번호를 두고 비교 | 모든 쓰기 경로에서 번호를 올려야 하고 하나라도 빠지면 감지하지 못함. 운영자가 SQL로 직접 고친 변경은 DB 트리거 없이는 놓치는데, 이 블로그는 글 정보를 SQL로 직접 고치는 일이 실제로 있음. 또 초안 편집처럼 공개 결과와 무관한 변경에도 번호가 올라 불필요한 재빌드가 생김 |
| **공개 자료 해시(revision) 기반 낙관적 검증 (채택)** | 관리 기능을 멈추지 않고, 수집 도중의 변경을 빌드 결과 확정 전에 감지함. 공개 결과 자체로 계산하므로 어떤 경로로 바뀌어도 감지하고, 공개와 무관한 변경에는 값이 그대로임 |

revision은 공개 사이트에 들어갈 DB 자료 전체의 SHA-256 지문임.[* 공개 스냅샷 JSON과 공개 글의 첨부 연결 행(글 ID·첨부 ID·object_key·형식·크기·수정 시각)을 합쳐 계산함. Git 원고는 포함하지 않으며, 원고 쪽 변경은 배포 직전 `main` 재확인으로 검사] API가 이 값을 공개 스냅샷과 함께 제공하고, 빌더가 수집 시작 때와 페이지 생성 후의 revision을 비교해 다르면 결과를 폐기함. Git 쪽은 배포 직전 `main`의 사이트 입력 변경 여부를 다시 확인함. 페이지는 임시 디렉터리에서 만들어 검사하고, 수집이나 생성이나 검증 어느 하나라도 실패하면 결과를 버리고 배포하지 않으므로 공개 중인 사이트가 그대로 남음.

### 대가

- 빌드 중 관리자 변경이 있으면 빌드를 다시 실행해야 함.
- 확인할 때마다 공개 자료 전체를 읽어 해시를 계산하므로, 글 수에 비례해 비용이 늚. 스냅샷 응답의 상한은 글 10,000건·약 8MB.
- 이미지 파일 바이트는 해시에 들어가지 않아, 같은 키로 파일을 덮어쓰면 감지하지 못함. 파일 교체는 항상 새 키로 함.[* [인프라 ADR](https://github.com/gjaku1031/ken-blog/blob/b768152/docs/ADR/ADR_infra.md)의 기술 아이콘 직접 관리 절차]
- 마지막 검증부터 배포 완료까지의 구간은 원자적으로 묶이지 않음. 배포 작업은 Git `main`만 다시 확인하고 DB revision은 다시 확인하지 않아, 그 사이에 바뀐 글 정보는 배포 대기 표시로 드러나고 다음 배포에서 반영됨.

### 검증

아래 실패 상황마다 새 결과를 내보내지 않고 기존 사이트를 그대로 두는지 빌드 파이프라인 회귀 검사로 확인함. 수집·검증 순서와 보장하지 않는 구간은 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)의 일관성 모델 절에서 다룸.[* [파이프라인 검사](https://github.com/gjaku1031/ken-blog/blob/b768152/.github/pages/pipeline.test.mjs)]
