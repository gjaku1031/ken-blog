# 1차 측정 (결론에 쓰지 않음)

2026-10-07에 먼저 한 측정의 요약. 시나리오 4개(프로젝트 대문·ERD 문서·일반 글·홈 목록) × 구조 2개 × 네트워크 2조건 × 캐시 2조건 × 20회, 모두 640회(워밍업 64회 제외)를 쟀음. 아래 두 결함 때문에 결론에 쓰지 않고, 조건을 고친 2차 측정(`../summary.md`)으로 다시 쟀음.

## 결론에 쓰지 않은 이유

1. **옛 구조의 기준이 하이브리드였음**: 옛 구조로 쓴 커밋 `135169f`는 본문을 빌드 때 HTML에 미리 넣고 런타임에 API도 부르는 구조라, 본문을 API로만 받는 구조의 순차 왕복 효과를 재지 못함. 2차에서는 순수 CSR(`f29ef35`)을 더해 세 구조를 비교함.
2. **측정 서버의 캐시 규칙이 운영과 달랐음**: 1차 측정 서버는 HTML·JS·CSS에 `cache-control`을 보내지 않았음(`../caddy-v1-headers.txt`). 그래서 정적 생성 쪽 재방문(warm) 전송량이 첫 방문과 거의 같았음(ERD 문서, 네트워크 M 기준 중앙값 1,054,392바이트 → 1,054,335바이트, `summary.md`). 운영 GitHub Pages는 `cache-control: max-age=600`과 `ETag`를 보냄(`../github-pages-headers.txt`). 2차에서는 세 구조 모두 Pages와 같은 캐시 헤더로 제공함(`../caddy-v2-headers.txt`).

2차에서는 앱 안에서 대문 → ERD 문서로 이동하는 시나리오와, 초당 5회 ERD 열람을 60초 동안 재생하며 API 서버 CPU를 비교하는 측정도 더함.
