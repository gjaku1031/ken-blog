사용자가 같은 일을 다르게 말해도 Vowser가 맞는 작업을 찾는지 궁금했음. 먼저 질문 96개로 정확도를 재 보니, 유사도가 낮을 때 LLM으로 다시 찾는 단계가 오히려 정답률을 떨어뜨리는 것처럼 보였음. 그런데 질문을 새로 써서 같은 질문에 두 방식을 나란히 돌려 보자 차이 대부분이 사라졌음.

> 처음 본 큰 차이(65% 대 29%)는 같은 질문으로 비교하자 65% 대 56%(80개 중 52 대 45)로 줄었고, 우연으로도 나올 수 있는 차이였음. 차이의 대부분은 다시 찾는 단계로 간 질문이 원래 어려웠기 때문으로 보임.

## 무엇을 알고 싶었나

Vowser는 사용자의 요청 문장을 임베딩해 등록된 작업 의도 중 가장 비슷한 것을 찾음. 가장 높은 유사도가 0.43 이상이면 그 검색 결과를 그대로 순위로 쓰고(이하 **바로 순위화**), 0.43보다 낮으면 LLM이 뽑은 키워드로 한 번 더 찾음(이하 **다시 찾기**). 앱은 1위 작업만 실행하므로, 1위가 맞는지가 곧 사용자가 원하는 일이 실행되는지임.

궁금한 건 두 가지였음. 다르게 말한 요청에서 1위로 맞는 작업을 고르는 비율은 얼마인지(1부), 그리고 다시 찾기가 실제로 정확도를 높이는지와 기준값 0.43이 적절한지(2부). 대문의 핵심 문제 P2(같은 작업을 사람마다 다르게 말함)에 대한 질문임.

## 1부. 지금 검색은 얼마나 맞히나

1부는 미리 가설을 세우지 않고 현재 상태를 재 본 탐색적 평가임. 질문과 정답만 실행 전에 정해 두었음.

당시 서버 코드와 모델을 그대로 띄우고, 7개 사이트의 작업 16개를 등록했음(날씨, 뉴스, 코레일, 정부24, 유튜브, 쿠팡, 지도). 질문 96개를 한 번씩 보냈는데, 대부분은 작업마다 다르게 말한 문장이고 뜻이 애매한 질문과 등록하지 않은 작업을 묻는 질문을 조금 섞었음.[* 정답이 있는 질문 80개(작업 16개마다 5개), 뜻이 애매한 질문 8개, 등록하지 않은 작업 8개] 같은 사이트의 비슷한 작업을 고르면(예: 기차 예매를 원했는데 예약 조회) 틀린 것으로 셌음.[* 질문과 등록 작업은 실험용으로 만든 합성 자료이며 실제 사용자 발화가 아님. 서버 버전과 모델, 질문 목록은 재현 자료에 있음]

| 질문 유형 | 1위 정답 | 3위 안 정답 |
| --- | ---: | ---: |
| 작업 이름에 가까운 직접 표현 | 15/16 | 16/16 |
| 바꿔 말하기 | 20/32 | 26/32 |
| 목적만 말하는 간접 표현 | 7/16 | 8/16 |
| "A 말고 B" 같은 배제 표현 | 4/16 | 16/16 |
| 합계(정답이 있는 질문) | 46/80 (57.5%)[* Wilson 95% 신뢰구간 46.6~67.7%] | 66/80 (82.5%) |

틀린 질문의 절반 넘게(34건 중 19건)는 같은 사이트의 비슷한 작업을 고른 경우였음. 코레일의 예매, 조회, 취소, 시간표 네 작업은 서로 헷갈려 1위 정답이 셋 중 하나꼴이었음.[* 20개 중 7개] "초본 말고 등본"처럼 배제하는 말은 정답이 늘 3위 안에 있었지만 1위는 거의 놓쳤음. 등록하지 않은 작업을 물으면 8개 모두 엉뚱한 작업을 돌려줬음. 예를 들어 "주민등록증 재발급"은 "주민등록등본 발급"과 유사도 0.78로 잡혔음. 응답에는 질문당 중앙값 1.3초가 걸렸음.

### 여기서 세운 가설

결과를 나눠 보니 바로 순위화로 처리된 질문은 65%가 맞았는데, 다시 찾기로 넘어간 질문은 29%만 맞았음. 다시 찾는 단계가 문제라고 결론 내리기 쉬운 숫자였음. 하지만 다시 찾기로 간 질문은 애초에 유사도가 낮은, 어려운 질문들이었음. 어느 쪽이 원인인지 이 결과만으로는 알 수 없어서, 질문을 새로 쓰고 같은 질문에 두 방식을 모두 돌려 보기로 했음.

## 2부. 같은 질문으로 두 방식을 비교하기

이번에는 결과를 보기 전에 무엇을 확인할지부터 정했음. 가설 세 개와, 어떤 결과가 나오면 가설이 틀렸다고 볼지를 적어 실행 전에 저장소에 올려 두고 한 번만 실행했음. 계획을 올린 커밋이 18시 2분, 질문을 보낸 것이 18시 4분부터 7분까지, 결과를 올린 커밋이 18시 11분이고(UTC), 그 사이 계획서는 바뀌지 않았음.[* 실행 전에 올린 [계획서](https://github.com/gjaku1031/ken-blog/tree/7a249b1/docs/experiments/2026-10-09-vowser-intent-threshold). 가설을 만든 1부 질문과 겹치지 않게 질문 104개를 새로 썼음]

| 가설 | 틀렸다고 볼 기준 |
| --- | --- |
| H1. 같은 질문에서 바로 순위화가 다시 찾기보다 1위를 더 많이 맞힘 | 바로 순위화만 맞은 질문이 더 많지 않거나, 그 차이가 우연으로 설명될 정도(McNemar 검정 p ≥ 0.05) |
| H2. 다시 찾기를 끄면(기준값 0) 정답이 0.43보다 줄지 않고, 기준값을 0.60으로 올리면 늘지 않음 | 둘 중 하나라도 어긋남 |
| H3. 가장 높은 유사도만으로는 등록하지 않은 작업을 잘 가려내지 못함 | 가려내는 정도(ROC AUC)가 0.80 이상 |

질문마다 유사도 검색과 LLM 의도 분석을 한 번만 하고, 그 결과를 복사해 두 방식에 똑같이 넣었음. 그러면 같은 질문, 같은 LLM 응답에서 두 방식의 결과만 달라짐. 기준값은 어느 방식을 쓸지 고르는 데에만 쓰이므로, 0부터 0.60까지 여러 값의 결과를 이 기록에서 계산했음.

실험 코드가 당시 서버와 같게 동작하는지는 1부 질문 96개로 확인했음. 기준값 0.43으로 계산한 1위가 1부에서 서버가 낸 1위와 96개 중 95개 같았음. 다른 하나는 유사도가 0이라 LLM 키워드로 다시 찾은 질문이었는데, LLM이 뽑은 키워드가 실행마다 달라 1부에서는 빈 결과가, 이번에는 정답이 나왔음.

### 결과가 말해 주는 것

H1은 지지하지 못했음. 같은 질문에서 바로 순위화가 52 대 45로 앞섰지만, 두 방식의 결과가 갈린 29개 질문에서 18 대 11은 우연으로도 충분히 나올 수 있는 차이임. 1부의 65% 대 29%라는 큰 차이는 같은 질문으로 비교하자 대부분 사라졌음. 1부 숫자만으로는 "다시 찾기가 정확도를 떨어뜨린다"고 쓸 수 없었던 것임. 그렇다고 두 방식이 같다는 뜻은 아니고, 이 정도 질문 수로는 차이를 가릴 수 없다는 뜻임.

H2는 지지했지만, H1의 방향이 맞으면 거의 저절로 성립하는 예측이어서 근거로서의 무게는 작음. 실제로 다시 찾기를 꺼도 1위 정답은 52개로 같았고 응답은 0.1초쯤 빨라졌음. 이 자료에서는 다시 찾기의 정확도 이득이 보이지 않았고, LLM 키워드 검색 비용만 더해졌음.

H3은 경계에 걸렸음. 가려내는 정도는 0.77로 기준보다 낮았지만, 신뢰구간 위쪽이 0.87이라 단정하기는 어려움. 오류는 양쪽에서 났음. 등록하지 않은 작업을 물은 16개 중 6개가 유사도 0.43을 넘었고, 반대로 정답이 있는 80개 중 29개(36%)는 0.43 아래였음. 지금 기준값을 "모르는 작업" 판단에 쓰면, 모르는 요청 일부는 엉뚱한 작업으로 실행되고 아는 요청 셋 중 하나는 거절됨.

계획에 없던 것도 하나 보였음. 1위 정답은 기준값 0.35에서 56개로 가장 많았음. 하지만 열 개 값 중에서 결과를 보고 고른 값이라, 이 자료로 0.35가 낫다고 말하지는 않음. 확인하려면 질문을 새로 써서 다시 실험해야 함.

정확도를 올리려면 기준값보다 다른 쪽이 더 급해 보였음. 틀린 질문은 같은 사이트의 비슷한 작업을 헷갈리거나 "A 말고 B"를 알아듣지 못한 경우에 몰려 있었음.

## 결과를 믿기 어려운 부분

Shadish·Cook·Campbell(2002)의 네 가지 관점으로 점검했음.

- **다른 원인이 섞였을 가능성**: 1부에서 섞였던 질문 난이도는 2부에서 같은 질문에 두 방식을 모두 돌려 없앴음. 실험 코드가 서버와 다르게 동작할 가능성은 위의 95/96 일치로 확인했음. 검색 후 인기도를 올리는 원래 동작은 질문 순서가 결과에 영향을 주지 않도록 일부러 뺐음. 1부 첫 실행은 실험용 Neo4j에 APOC 플러그인이 없어 서버가 DB에 붙지 못하고 실패했고, 그 기록을 남긴 채 플러그인을 넣고 다시 실행했음
- **일반화**: 작업 16개와 질문은 모두 합성 자료임. 실제 사용자의 말투나 음성 인식 오류, 작업이 수백 개인 상황으로 넓혀 말할 수 없음
- **재는 것이 맞나**: 앱이 1위만 실행하므로 1위 정답을 기준으로 삼았음. 질문은 실험용으로 지은 문장이고, 2부 질문은 1부 결과를 본 뒤 썼음. 같은 유형과 작성 규칙을 따랐지만 쓴 사람의 치우침은 남음
- **표본 크기**: 정답이 있는 질문 80개, 등록하지 않은 작업 16개라 작은 차이는 가리지 못함. 필요한 표본 수를 미리 계산하지는 않았음. 결과가 갈린 29쌍에서 차이를 주장하려면 21 대 8 정도는 되어야 했음
- **같은 요청의 재실행**: LLM은 temperature 0이지만 같은 요청을 다시 보내면 결과가 다를 수 있음(위 확인 과정의 1건). 각 질문은 한 번씩만 보냈음
- **다음 단계**: 실제 사용자 발화나 음성 인식 결과를 모아 다시 재야 일반화할 수 있음. 동시에 여러 요청이 올 때의 동작은 이 실험에서 보지 않았고, 서버 간 응답이 섞이는 결함은 따로 재현했음([API 설계](/ken-blog/post/doc-6da63c60-c6ed-47d5-bf69-ecd87641cda5/))
