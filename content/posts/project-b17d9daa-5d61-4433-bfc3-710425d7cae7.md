| 항목 | 내용 |
| --- | --- |
| 소개 | 학원 직원의 업무 지시, 일일보고, 자료 공유를 한곳에서 처리하고, 누가 무엇을 할 수 있는지를 학원이 직접 구성하는 사내 ERP |
| 목적 | 날마다 다시 적던 업무 지시와 보고를 한 번 정해 두고 쓰게 하고, 기능이 늘어도 권한 판단과 외부 기록이 어긋나지 않게 함 |
| 개발 형태 | 개인 프로젝트(1인). 요구사항은 학원의 기획 담당자와 운영진, 각 팀의 팀장에게서 받음 |
| 담당 범위 | 권한 모델, 모듈 경계와 포트 설계, 업무일지의 요구사항 정리와 운영 |
| 주요 기능 | 업무일지(업무 배정, 일일보고, 상담 전송), 자료실(폴더별 접근 허용), 권한 관리(역할 구성, 감사 기록) |
| 링크 | [![GitHub\|dark=61\|w=20\|a=center](attachment:60) GitHub](https://github.com/gjaku1031/npr-erp) |

로그인, 권한 엔진, 자료실, 업무일지를 하나의 Spring Modulith 애플리케이션으로 묶은 시스템임. 상태를 바꾸는 요청과 화면을 여는 요청은 권한 엔진을 거친 뒤에 업무 모듈로 들어가고, 업무 모듈은 서로를 모르며 권한 엔진도 모름. 파일 저장소와 외부 ERP처럼 바뀔 수 있는 바깥 경계에만 포트를 둠.

## 담당 범위

- **요구사항 조율**: 시제품을 먼저 만들어 기획 담당자와 1차로 다듬고, 팀장이나 원장의 확인을 거쳐 요구사항을 정함. 권한 목록처럼 학원 안의 사정에 달린 세부는 기획 담당자에게서 들어 반영함
- **직접 정한 설계**: 권한 판단을 RBAC·ABAC·ACL로 나눠 하나의 엔진에 모은 방식, 모듈 경계와 포트를 둘 곳
- **업무일지**: 요구사항을 정리하고 시범 운영을 맡았음. 강사로 일하며 직접 사용함

## 개발 배경과 핵심 문제

학원은 기존 ERP에 딸린 업무일지를 쓰고 있었음. 표 하나로 된 화면이라 상담일지 쓰기처럼 날마다 반복되는 업무도 매번 다시 적어야 했고, 상담일지를 쓴 뒤에 상담한 학생의 이름을 업무일지에 한 번 더 적어야 했음. 팀장은 그날 확인할 사항을 퇴근 전후로 손으로 적었는데, 월요일부터 목요일까지 이어지는 업무는 나흘 모두 적어야 했음. 팀장이 항목을 빠뜨리면 그 업무를 하지 않는 사람이 생겼고, 작성이 늦어지면 팀의 퇴근이 늦어졌음.

업무일지를 새로 만들면서 세 가지를 바꿈.

| 불편 | 바꾼 것 |
| --- | --- |
| 날마다 반복되는 업무를 매번 다시 적음 | 일일보고의 체크리스트로 옮김. 날짜별 체크리스트는 앞 날짜의 항목을 복사해 만듦 |
| 상담일지를 쓴 뒤 업무일지에 학생 이름을 다시 적음 | 일일보고가 그날의 상담 기록을 외부 ERP에서 불러와 보여 주고, 강사는 확인만 함 |
| 여러 날 이어지는 업무를 팀장이 날마다 적음 | 업무에 시작일과 마감일을 두면 그 기간의 일일보고에 자동으로 나타남 |

업무일지는 ERP의 기능 가운데 먼저 시범 운영한 부분이고, 시범 운영의 결과를 보고 다음 단계로 넘어가기로 돼 있었음. 시범 운영에서 기존 업무일지를 완전히 대체했고, 13명이 참여해(일일보고 대상 10명, 다른 팀 3명) 일일보고를 연 55일 동안 493건을 제출했음. 퇴근 전에 업무일지를 마치는 데 필요한 클릭은 평균 50번쯤에서 10번 안으로 줄었음. 권한 엔진과 자료실은 시범 운영에 포함되지 않았고, 이 문서에서 두 기능의 검증은 테스트와 시연 구성으로 한 것임.

업무일지를 자료실·권한 관리와 한 시스템으로 넓히려면, 팀장·강사·다른 팀처럼 팀마다 맡는 일이 다른 역할을 코드에 고정하지 않고 모든 기능이 같은 방식으로 권한을 묻게 해야 했음.

설계 제약은 3가지.

- **역할 구성이 고정돼 있지 않음**: 같은 "강사"라도 학원과 시기에 따라 맡는 일이 달라짐. 역할 이름과 권한 조합을 배포 없이 바꿀 수 있어야 함
- **반·학생·출결의 원장은 외부 ERP임**: 학원이 이미 쓰는 시스템이라 바꿀 수 없고, 응답이 늦거나 끊길 수 있음. 상담과 알림장은 그쪽에 써야 함. 계약이 비공개라 공개 저장소에는 실제 연동 대신 가상 구현을 둠
- **한 사람이 운영함**: 프로세스 하나와 PostgreSQL 하나로 돌아가야 하고, 메시지 브로커나 분산 트랜잭션을 둘 수 없음

이 제약에서 다음 3개 문제를 핵심 문제로 정의함.

- **P1 인가의 일관성**: 모든 요청이 한 곳의 규칙으로 판단되고, 권한 정책을 동시에 고쳐도 서로 덮어쓰거나 관리자가 사라지지 않아야 함
- **P2 변경의 격리**: 한 모듈이나 외부 시스템의 구현을 바꿔도 다른 모듈의 코드가 바뀌지 않아야 함
- **P3 외부 상태와의 정합성**: DB와 파일 저장소, DB와 외부 ERP가 중간 실패 뒤에도 어긋난 채로 남거나 같은 기록이 두 번 들어가지 않아야 함

### 주요 흐름

화면 요청은 인터셉터에서 계정이 활성인지와 그 학원에 소속돼 있는지를 확인받고, 컨트롤러가 필요한 권한과 대상을 권한 엔진에 물은 뒤에 업무 모듈을 부름. 자료실의 변경은 작업 원장에 먼저 기록되고, DB 트랜잭션 밖에서 저장소를 호출한 다음 결과로 트리를 확정함. 상담 전송도 같은 순서로, 전송 중이라는 표시를 먼저 커밋한 뒤에 외부 ERP에 씀. 흐름별 경로와 실패 시 동작은 [아키텍처](/ken-blog/post/doc-c2513d8a-31f4-49df-a99a-675fca3305a3/)에서 다룸.

## 핵심 문제별 설계와 검증

문제마다 결정과 대표 근거만 요약함. 검토한 대안과 대가, 검증 상세는 [주요 기술적 의사결정](/ken-blog/post/doc-f47c5aab-4b47-412a-a28c-db6f0c36a314/)에서 다룸.

### P1. 역할 권한과 리소스 허용을 함께 보는 엔진 하나로 인가를 모음

- **문제**: 역할 이름을 보는 조건문이 기능마다 흩어져 있으면 역할을 바꿀 때마다 코드를 고쳐야 하고, 검사가 빠진 기능을 찾기 어려움
- **결정**: 역할이 기능을 쓸 자격을 주고(RBAC), 폴더의 허용 목록이 그 자격을 쓸 범위를 정하며(ACL), 소속·학원 일치 같은 조건을 그 앞에서 확인하는(ABAC) 엔진을 하나 둠. 허용이 없으면 거부함
- **대가**: 요청마다 권한 원장을 읽음. 명시적 거부, 상속 차단, 파일별 허용은 지원하지 않음
- **검증**: 판단 규칙은 DB 없이 도는 단위 테스트로, 정책 변경의 경쟁과 마지막 관리자 보호는 실제 PostgreSQL에서 스레드를 겹쳐 실행하는 통합 테스트로 확인함[* 판단 규칙 테스트(`AuthorizationPolicyEngineTest.java`), 정책 변경 경쟁 테스트(`AccessControlLockoutIntegrationTest.java`). 전체는 단위 56개, 통합 76개이고 통합 테스트는 임베디드 PostgreSQL 18에서 실행함. 2026-10-11 기준]

| 구성 | 파일 읽기 요청의 결과 |
| --- | --- |
| 읽기 권한이 있는 역할 + 상위 폴더의 상속되는 읽기 허용 | 허용 |
| 읽기 권한만 있고 적용되는 허용이 없음 | 거부 (`ACL_NOT_GRANTED`) |
| 개인에게 읽기 허용이 있지만 역할에 읽기 권한이 없음 | 거부 (`MISSING_PERMISSION`) |
| 구성은 같지만 소속이 종료됨 | 거부 (`MEMBERSHIP_INACTIVE`) |

> 리소스에 대한 요청은 역할의 권한과 폴더의 허용이 둘 다 맞아야 통과하고, 일치하는 허용이 없으면 거부됨.

### P2. 모듈은 공개 계약으로만 만나고, 포트는 바깥 경계에만 둠

- **문제**: 업무일지가 권한 엔진을 직접 부르면 두 모듈이 함께 바뀌고, 모든 계층에 인터페이스를 두면 구현이 하나뿐인 곳까지 읽을 코드가 늘어남
- **결정**: 모듈마다 공개 계약과 내부 구현을 나누고 의존 방향을 빌드에서 검사함. 업무일지는 "업무를 받는 사람" 같은 집합을 스스로 구하지 않고 호출자에게 받음. 포트는 파일 저장소와 외부 ERP 두 곳에만 둠
  - 비교한 대안: DB 접근까지 모든 경계를 포트 뒤에 두는 헥사고날 아키텍처. DB 접근은 구현이 하나뿐이어서 포트를 두면 간접 호출만 늘어나므로, 구현이 바뀔 수 있는 두 경계로 줄임
- **대가**: 기능을 쓸 자격은 컨트롤러가, 대상이 본인의 것인지는 업무일지가 확인하므로 검사가 두 층으로 나뉨
- **검증**: 모듈 의존 방향과 내부 패키지 침범을 구조 테스트가 검사함. 외부 ERP 포트의 구현을 가상 데이터를 돌려주는 대역으로 두고도 전체 기능이 실행됨[* 구조 테스트(`ModularityTest.java`), 외부 ERP 포트(`TngGateway.java`), 가상 구현(`MockTngGateway.java`)]

### P3. 외부 호출을 기록·호출·확정으로 나누고 끊긴 작업을 따로 마무리함

- **문제**: 폴더를 옮기거나 상담을 보내는 도중에 프로세스가 끊기면 DB와 바깥 상태가 달라짐. 결과를 모르는 채로 다시 보내면 같은 상담이 두 번 기록됨. 시범 운영에서는 수정 23건 가운데 18건이 외부 ERP와 주고받는 자료(상담, 반 명단, 출결)에 관한 것이었고, 외부 ERP가 저장을 거부한 상담이 전송 중 상태에 갇혀 다시 보내지도 고치지도 못한 일이 있었음[* 2026-07-17부터 2026-09-05까지의 수정 기록을 제목으로 분류한 값]
- **결정**: 하려는 일을 먼저 DB에 커밋하고, 트랜잭션 밖에서 바깥을 호출한 뒤, 결과를 다시 커밋함. 끊긴 작업은 바깥이 멱등하면(파일 저장소) 같은 작업 ID로 다시 실행하고, 멱등하지 않으면(상담 기록) 다시 보내지 않고 외부의 기록과 대조함
- **대가**: 마무리되기 전에는 그 폴더나 상담을 다시 다룰 수 없음. 재실행과 대조는 사람이 화면에서 실행함
- **검증**: 호출 전후에 중단된 상황을 테스트에서 직접 만들어 확인함. 외부 ERP는 가상 구현이어서 실제 지연과 장애로는 확인하지 못했음[* 자료실 중단 테스트(`StorageIntegrationTest.java`), 상담 전송 테스트(`WorklogTaskIntegrationTest.java`), 거부와 결과 모름을 나누는 테스트(`DefaultCounselDeskTest.java`)]
