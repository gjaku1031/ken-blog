브라우저 조작을 사용자 PC에 둔 결정(P3) 때문에 서버에는 경로 검색·저장과 인증만 남았고, 그래서 Spring Boot·FastAPI 두 컨테이너를 Proxmox와 Fargate 어느 쪽에서도 같은 이미지로 띄울 수 있음(P4). 검색·저장의 대상인 경로는 사용자 기록에서 나옴(P1·P2).

## P1. 사용자 기록을 단계 연결 경로로 저장

### 문제

초기에는 개발자가 준비한 작업만 실행할 수 있었음. 지원 작업을 늘리려면 개발자가 사이트마다 경로를 조사해 등록해야 했고, 4인 팀이 사용자가 원하는 작업을 모두 등록할 수 없었음.

### 검토한 대안

사용자의 실제 조작을 녹화해 경로로 저장하면 작업 지식을 사용자 조작에서 바로 얻고, 기록한 경로가 다른 사용자의 검색 대상이 됨. 저장소는 다음 두 가지를 놓고 정함.

| 저장소 | 판단 |
| --- | --- |
| 관계형 DB(회원 정보와 같은 MySQL) | 경로를 단계 테이블의 자기 참조와 재귀 조회로 이어야 함. 당시 실험에서 데이터가 많을수록 Neo4j보다 느렸음(조건·수치 기록 없음) |
| **그래프 DB Neo4j (채택)** | 첫 모델은 여러 경로가 같은 페이지 노드를 공유하고 가변 길이 관계로 이동을 표현해 그래프 탐색이 맞았음. 경로 구조를 그래프로 시각화해 볼 수 있고, 벡터 검색도 같은 DB에서 쓸 수 있음 |

설계 단계부터 Neo4j를 저장소로 정함.[* 본인이 2025-07에 작성한 [에이전트 서버 PRD](https://github.com/Vovvser/vowser-agent-server/blob/4ea78bf/docs/PRD.md)에 Neo4j가 저장소로 정해져 있음] 첫 모델은 웹 페이지 요소를 `PAGE` 노드로, 화면 이동을 `NAVIGATES_TO` 관계로 두고 페이지 ID를 URL과 요소로 만들어, 여러 경로가 같은 페이지 노드를 공유하는 그래프였음.[* [이전 저장 코드](https://github.com/Vovvser/vowser-agent-server/blob/d94eaf5/app/services/neo4j_service_old.py)] 이후 의도를 표현할 노드가 없고 경로가 `PAGE` 관계와 `PATH` 노드에 이중으로 저장되는 문제 때문에, 작업 의도를 `HAS_STEP` 관계에 두고 기록 세션마다 단계를 따로 만드는 현재 구조로 재설계함.[* [재설계 문서](https://github.com/Vovvser/vowser-agent-server/blob/d94eaf5/docs/DB_refactor.md)] 재설계 뒤에는 경로끼리 공유하는 노드가 없어, 그래프 DB의 장점인 가변 길이 탐색과 공유 노드가 거의 쓰이지 않게 됨. 이 선택은 아래 검증의 2026년 실험에서 다시 측정함.

### 대가

- 회원 정보(MySQL)와 별도로 그래프 DB를 운영함.
- 같은 작업을 여러 사람이 기록하면 같은 화면의 단계도 따로 저장되어, 한 사이트의 변경이 여러 경로에 반복해서 영향을 줌.
- 경로 하나를 저장할 때 단계 n개에 대해 2n+1개의 쿼리가 각각 커밋되어, 중간에 실패하면 일부만 저장된 경로가 남음.

### 검증

기록한 경로가 검색 대상이 되는 연결은 코드로 확인함. 저장할 때 작업 의도의 임베딩을 `HAS_STEP`에 넣고, 검색이 이 관계의 벡터 인덱스를 조회함. 시연 경로는 팀이 준비했고(KTX 예매, 주민등록등본 발급, 날씨, 뉴스, 네이버 웹툰), 팀 밖 사용자가 기록한 경로나 재사용 횟수는 없음.

저장소 선택은 2026년에 같은 경로 연산을 MySQL과 다시 비교함. 등록·인기 조회·시각화·가중치 갱신을 경로 1천~3만 개, 읽기:쓰기 90:10·50:50의 8개 조건에서 측정했고, 짝지은 연산 32개 군 모두에서 인덱스를 둔 MySQL의 지연 중앙값과 p95가 낮았음.[* 2026-09-29 사후 재현 실험. 합성 경로, DB 컨테이너 1 CPU·3GiB와 Python 워커 1 CPU·1GiB, 한 번에 DB 하나만 기동, 저장 경로는 tmpfs, 다른 서비스가 함께 실행된 공유 VM. 지연은 드라이버·localhost 왕복·결과 구성 포함이며 원본 API·임베딩 생성은 제외. 블록마다 200연산, 3회 반복, 공식 9,600요청 정답·오류 0]

| 측정 항목(경로 3만 개, 읽기:쓰기 90:10, 중앙값) | MySQL | Neo4j |
| --- | ---: | ---: |
| 인기 경로 조회 | 0.73ms | 5.03ms |
| 경로 시각화 | 1.65ms | 5.47ms |
| 신규 경로 등록 | 7.14ms | 26.50ms |
| 가중치 갱신 | 1.23ms | 6.23ms |

> 경로끼리 단계를 공유하지 않는 지금의 모델에서는, 경로를 그래프로 저장해서 얻는 속도 이점이 측정되지 않았음.

같은 실험에서 원본처럼 단계마다 쿼리를 나눠 커밋하던 Neo4j 등록을 한 번의 배치 쿼리로 묶으면 등록 중앙값이 164.34ms에서 10.35ms로 줄었음.[* 경로 1천 개, 깊이 5·10·20의 등록 3건을 3회 측정한 보조 진단. 임베딩 생성 제외] 이 차이는 DB 종류보다 트랜잭션 경계의 영향이 크다는 뜻이고, 앞의 '일부만 저장된 경로' 문제도 같은 수정으로 사라짐. 단계를 공유하는 분기 경로(현재 미구현)는 별도로 시험했으며, 측정 조건과 전체 결과는 [Vowser 경로 저장소 재평가: Neo4j와 MySQL](/ken-blog/post/post-1bffbbcf-cf05-4f6f-9934-2de47c340ca7/)에서 다룸.

## P2. 의도 임베딩 검색과 낮은 유사도의 재검색

### 문제

같은 작업을 사람마다 다르게 말함. "오늘 날씨 어때?"와 "날씨 보기"는 글자가 거의 겹치지 않고, 음성 인식 결과에는 띄어쓰기·숫자 표기 차이도 섞임.

### 결정

요청 문장과 등록 문장이 글자로 겹치지 않아도 뜻이 같으면 같은 작업을 찾아야 하므로, 의도 문장의 임베딩 유사도를 1차 검색으로 두고 애매한 요청만 LLM 재검색으로 보냄. 대부분의 요청은 임베딩 한 번과 벡터 검색으로 끝남.

임계값은 0.43으로, 최고 유사도가 이보다 낮으면 GPT-4o-mini로 요청의 의도와 키워드를 뽑아 키워드 2개까지 병렬로 다시 검색하고 결과를 합침. 유사도 검색과 의도 분석은 병렬로 실행하고, 같은 요청의 임베딩은 메모리 캐시에서 재사용함.[* [LangGraph 검색 흐름](https://github.com/Vovvser/vowser-agent-server/blob/d94eaf5/app/services/langgraph_service.py) · [임베딩 캐시](https://github.com/Vovvser/vowser-agent-server/blob/d94eaf5/app/services/embedding_service.py)] 0.43은 예시 요청으로 실험해 정했으나 실험 기록은 남아 있지 않음.

초기 구현에서는 사용 중인 Neo4j 환경에서 GDS 함수를 쓸 수 없어, 경로 모델은 유지하고 코사인 유사도 계산을 Python으로 옮김.[* [GDS 대체 커밋](https://github.com/Vovvser/vowser-agent-server/commit/b4dcf835cadac6da12bf11619965c9e7aeaea72a)] 이후 관계 벡터 인덱스로 후보를 찾게 바뀌었지만, 후보의 유사도를 Python에서 다시 계산해 0.3 미만을 버리는 단계가 남아 있음.

### 대가

- 요청마다 OpenAI 임베딩 호출이 필요하고, 재검색 경로에서는 LLM 호출이 더해짐. LLM 호출에는 10초 제한을 둠.
- 등록되지 않은 작업은 찾지 못하며 새 경로를 만들지 않음.
- 도메인 힌트가 있으면 벡터 인덱스에서 후보를 먼저 뽑은 뒤 도메인으로 거르므로, 다른 도메인의 후보가 많으면 해당 도메인의 경로가 후보에서 빠질 수 있음.

### 검증

개발 당시 시연에서 날씨를 묻는 표현으로 네이버 날씨, 추상적인 시사 질문으로 뉴스 작업이 선택됨. 이 정도로는 정확도를 말할 수 없어 2026-10-09에 원본 서버와 원본 모델로 두 단계 측정을 함. 설계·원자료·타당성은 [Vowser 의도 검색 정확도와 재검색 임계값](/ken-blog/post/post-ccb0e7cb-986a-4f7d-832e-ba4fd69e49e1/)에 있음.

| 측정 | 분류 | 결과 |
| --- | --- | --- |
| 합성 질의 96개로 잰 검색 정확도 | 탐색적 평가 | 정답형 80개 중 1위 정답 46(57.5%), 3위 안 66(82.5%). 오답은 같은 사이트의 비슷한 작업과 "A 말고 B" 배제 표현에 몰림. 미등록 작업 8개는 모두 다른 작업을 반환 |
| 새 질의 104개로 재검색 분기와 임계값을 비교 | 확증 실험(사전 등록) | 같은 요청에서 순위화 분기 52, 재검색 분기 45(80개 중), McNemar p = 0.265로 재검색이 정확도를 높인다는 근거 없음. 임계값 0과 0.43의 1위 정답이 같음(52) |

탐색적 평가에서 순위화 63건 중 41건, 재검색 17건 중 5건이 맞아 큰 차이로 보였지만, 같은 요청에서 두 분기를 비교하자 차이 대부분이 사라졌음. 유사도가 낮은 어려운 요청이 재검색으로 몰린 결과였음.

2026-09 사후 실험은 합성 벡터로 검색 지연만 비교했고, 원본 검색 순서를 재현한 경우 경로 1만 개에서도 1위 결과는 모든 조건에서 정답(190/190)이었지만, 상위 결과 전체의 순서 일치는 150~164/190으로 떨어졌음. 앱은 1위 경로만 실행하므로 이 차이는 결과 목록에만 영향을 줌. 순서가 어긋나는 원인은 도메인 필터와 결과 수 제한이 재정렬보다 먼저 적용되는 순서임. 검색 실험의 전체 결과도 [같은 글](/ken-blog/post/post-1bffbbcf-cf05-4f6f-9934-2de47c340ca7/)에 있음.[* 2026-09-29, 1536차원 합성 벡터, 질의 200개 × 3회. OpenAI 임베딩·LLM은 쓰지 않은 검색 전용 투영]

## P3. 실행기를 사용자 PC에 두고 인증 단계는 사용자 입력 대기

### 문제

예매·민원 작업에는 로그인·본인 인증·결제가 들어 있음. 서버에서 브라우저를 대신 실행하면 사용자 계정의 비밀번호나 인증 수단을 서버가 다뤄야 함.

### 결정

로그인·본인 인증·결제는 사용자 계정의 비밀을 다루므로 서버가 대신할 수 없다고 보고, 실행기를 사용자 PC에 두는 구조로 정함. 인증은 사용자 PC의 브라우저에서 사용자가 직접 하고, 서버는 경로만 다룸.

입력 단계의 값은 회원 정보 자동 입력, 경로에 저장된 입력값, 사용자 입력 순으로 정하고, 대기 단계는 사용자가 완료를 확인할 때까지 멈춤. 기록할 때 비밀번호·이메일·아이디로 분류된 칸의 값은 저장하지 않음.[* [경로 실행기](https://github.com/Vovvser/vowser-client/blob/8065803/shared/src/commonMain/kotlin/com/vowser/client/api/PathExecutor.kt) · [경로 저장 변환](https://github.com/Vovvser/vowser-client/blob/8065803/shared/src/commonMain/kotlin/com/vowser/client/api/PathApiClient.kt)]

### 클라이언트 구현 기술

실행기를 사용자 기기에 두면 클라이언트 기술이 곧 앱을 둘 수 있는 기기의 범위가 됨. PC 데스크톱 앱만으로는 쓰임에 한계가 있다고 보고, 이후 장애인용 키오스크나 관공서 태블릿으로 넓힐 것을 고려함.

| 대안 | 판단 |
| --- | --- |
| React Native | 모바일·태블릿에는 맞음 |
| **Kotlin Compose Multiplatform (채택)** | 데스크톱·Android·iOS가 공통 모듈을 공유함[* [공통 모듈 대상 설정](https://github.com/Vovvser/vowser-client/blob/8065803/shared/build.gradle.kts)]. 팀원이 모두 Java 개발자라 개발 속도를 유지할 수 있음 |

### 대가

- 사이트 구조가 바뀌면 저장된 선택자가 맞지 않음. 선택자 여러 개, 링크 주소 대체 클릭, 직접 이동 순으로 시도해 피해를 줄임.
- 입력 칸 분류가 `type`·`name`·`placeholder` 속성에만 의존해, `type="text"`인 이름·전화번호 칸의 20자 이하 입력은 경로에 저장되고 다른 사용자의 실행에서 회원 정보 자동 입력보다 먼저 쓰임.
- 기록 모드는 대기 단계를 만들지 않아, 본인 인증 대기는 수집 스크립트로 준비한 경로에만 있음.

### 검증

개발 당시 실제 사이트 시연에서 아래 단계까지 도달함. 결제·발급 완료나 전체 작업 완주율은 측정하지 않았음.

| 시연 작업 | 도달한 단계 |
| --- | --- |
| 날씨·뉴스 조회 | 날씨를 묻는 표현에서 네이버 날씨, 추상적인 시사 질문에서 뉴스 표시 |
| 네이버 웹툰 | 요청한 웹툰 화면 표시 |
| 열차(KTX) 예매 | 중간 로그인 단계에서 사용자 입력을 기다린 뒤 결제 직전 단계까지 진행 |
| 주민등록등본 조회 | 사용자 인증 후 문서가 표시되는 단계 |

## P4. Proxmox 기본 실행과 AWS Fargate 확장

### 문제

관공서·소규모 사업장에 두는 접근성 오픈소스 앱이라 평소 요청은 적고, 서버(Spring Boot·FastAPI)를 AWS에 상시 띄우는 비용은 학생 팀이 감당하기 어려움. 반면 명절 열차 예매처럼 고령층·장애인 우선 예매 기간에 접속이 몰리는 상황을 가정해 대비해야 했음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| AWS 상시 운영 | 평소 요청이 적어도 비용이 계속 듦. 비용은 수치로 계산하지 않음 |
| Proxmox 단독 운영 | 비용은 낮지만 부하가 몰리면 처리 용량을 늘릴 수 없어 서비스가 멈출 수 있음 |
| **Proxmox 기본 + AWS Fargate 확장 (채택)** | 평소에는 이미 다루던 Proxmox로 처리하고, 부하 경보가 울리면 같은 이미지를 Fargate로 기동 |

브라우저 실행이 사용자 PC에 있어(P3) 서버는 경로 검색·저장과 인증만 처리함. 그래서 확장 대상이 Spring Boot와 FastAPI 두 컨테이너로 좁혀짐. 두 환경이 같은 데이터를 보도록 회원 DB는 RDS MySQL에 두고 Proxmox에서는 Site-to-Site VPN으로 접근하며, 토큰과 경로는 Redis Cloud·Neo4j Cloud에 둠.

### 대가

- 두 실행 환경의 이미지·설정을 함께 관리하고 VPN을 유지해야 함.
- 전환은 Route 53 레코드 변경이라 DNS 캐시가 남은 동안 요청이 두 환경으로 나뉘고, Spring Boot와 에이전트 서버 사이의 WebSocket처럼 이미 열린 연결은 옮겨지지 않음.
- Fargate 기동에는 시간이 걸려, 경보부터 실제 처리 시작까지 부하를 기존 서버가 감당함.

### 검증

CloudWatch CPU·메모리 경보 → EventBridge → Lambda → Fargate 기동·Route 53 변경 흐름을 구현·실습함. 경보 임계값, 전환 시간, 비용 절감률, 무중단 여부는 측정하지 않았음. 부하 시험 기록은 [배포와 운영](/ken-blog/post/doc-388fbde8-12bf-4281-9e74-bf90c396e8d6/)에 있음.

## 한계

결정의 대가와 별개로, 동시 사용자가 늘 때 먼저 드러날 구조적 한계가 코드에 남아 있음. 시연은 한 사람이 순차로 쓰는 조건이었고, 여러 사용자의 동시 사용은 시험하지 않았음.

- **서버 간 요청 연결**: 요청 번호가 메시지에 실리지 않아 동시 요청의 응답이 뒤바뀔 수 있음. 요청 번호를 메시지에 싣고 응답에서 돌려받아야 함.
- **브라우저 제어 채널**: 에이전트의 비동기 메시지와 서버 측 브라우저 명령을 마지막에 연결된 앱 하나로 보냄. 사용자별 세션 대응이 필요함.
- **경로 저장의 원자성**: 단계별 커밋을 한 트랜잭션(배치 쿼리)으로 묶어야 함.
- **경로 정리**: 30일 지난 `NEXT_STEP`만 지워 경로가 중간에서 잘림. 경로 단위로 지워야 함.

상세 위치는 [아키텍처](/ken-blog/post/doc-fd568125-2806-4210-a0b2-e4bf2d1b509e/)의 일관성 절에 있음.

## 참고한 기법

| 결정 | 기법 | 이 프로젝트에서의 적용 |
| --- | --- | --- |
| P1 | 기록-재생(record and replay) 웹 자동화 | 사용자의 클릭·입력·이동을 단계로 기록하고 실행기가 같은 순서로 재생함 |
| P2 | 밀집 벡터 검색(dense retrieval)과 질의 재작성 | 의도 임베딩 유사도로 찾고, 유사도가 낮으면 LLM이 뽑은 의도·키워드로 다시 찾음 |
| P3 | 사람 개입 자동화(human in the loop) | 로그인·본인 인증 단계에서 실행을 멈추고 사용자의 완료 확인을 기다림 |
| P4 | 클라우드 버스팅(cloud bursting) | 평소에는 자체 서버에서 돌리고 부하가 몰릴 때만 클라우드에 같은 이미지를 띄움 |

## 다시 한다면

- 경로 저장을 처음부터 한 트랜잭션으로 묶고, 저장소는 관계형 DB 하나에 벡터 인덱스를 붙이는 쪽을 먼저 측정해 비교함. 2026년 재평가에서 지연 차이는 DB 종류보다 트랜잭션 경계에서 더 크게 났음([Vowser 경로 저장소 재평가: Neo4j와 MySQL](/ken-blog/post/post-1bffbbcf-cf05-4f6f-9934-2de47c340ca7/))
- 서버 간 메시지에 요청 번호를 싣고, 동시 요청 시험을 시연 전에 함. 한 사람이 순차로 쓰는 시연에서는 드러나지 않았지만, 사후 재현에서 동시 요청 두 건의 응답이 서로 바뀌는 것을 확인함
