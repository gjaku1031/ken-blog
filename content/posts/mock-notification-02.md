관련 프로젝트 연결을 확인하기 위한 가상 개발 기록이다. 같은 주문 알림이 여러 번 접수되는 상황을 가정한다.

## 중복을 무엇으로 판단할까

요청 시각으로만 구분하면 재시도가 새로운 요청이 된다. 반대로 주문 번호만 사용하면 같은 주문의 접수 알림과 배송 알림을 구별하지 못한다.

이 예시에서는 **이벤트 ID·수신자 ID·채널** 조합을 하나의 발송 요청으로 정했다. 같은 조합을 다시 받으면 기존 작업을 반환한다. 내용이 바뀐 새 이벤트는 다른 ID를 사용한다.

## 조회 다음 저장 사이의 틈

애플리케이션에서 먼저 조회하고 없을 때 저장하는 것만으로는 동시 요청을 막지 못한다. 두 요청이 모두 없다는 결과를 본 뒤 각각 저장할 수 있다.

중복 여부는 데이터베이스의 유일 제약으로 최종 결정한다. 유일 제약 충돌이 발생했을 때만 기존 작업을 조회하고, 연결 장애 같은 다른 오류를 중복으로 처리하지 않는다.

| 요청 | 기대 결과 |
| --- | --- |
| 같은 이벤트·수신자·채널 | 기존 작업 반환 |
| 같은 이벤트·다른 수신자 | 새 작업 생성 |
| 다른 이벤트·같은 수신자 | 새 작업 생성 |
| 같은 조합·다른 본문 | 입력 충돌로 처리 |

## 외부 발송의 중복은 별도 문제

작업 저장을 한 번으로 제한해도 외부 발송까지 한 번만 일어난다는 보장은 없다. 발송은 성공했지만 결과 기록에 실패하면 작업자가 다시 보낼 수 있다.

제공자가 멱등 키를 지원한다면 같은 작업에 같은 키를 보낸다. 지원하지 않는다면 응답 유실을 별도 상태로 기록하고 처리 결과를 조회하거나 확인 절차를 거친다. 불확실한 결과를 무조건 재발송하는 규칙은 피한다.

## 확인할 사례

동일 요청의 동시 접수, 발송 직후 작업자 종료, 응답 유실을 각각 재현한다. 작업 행의 개수와 실제 발송 횟수를 따로 확인해야 어느 경계에서 중복이 발생했는지 알 수 있다.
