주소창에 `https://example.com/`을 넣고 엔터를 누르면 브라우저는 서버의 IP 주소를 찾고, 그 주소와 연결을 열고, HTTP 요청 메시지를 보냄. 메시지는 CDN이나 프록시 같은 중간 서버를 거쳐 서버 안의 코드에 닿고, 응답은 같은 길을 거꾸로 돌아옴.

## 학습 목표

- 요청 하나가 브라우저에서 서버 코드까지 거치는 단계를 순서대로 말할 수 있음
- 각 단계에서 무엇이 정해지고 무엇이 오가는지 한 문장으로 설명할 수 있음
- `curl` 출력에서 각 단계의 흔적을 찾을 수 있음

## 단계별로 따라가기

1. **URL 해석**(3편): 브라우저는 주소를 스킴(`https`), 호스트(`example.com`), 경로(`/`), 쿼리로 나눔. 어느 서버에, 어떤 방식으로, 무엇을 달라고 할지가 여기서 정해짐.
2. **저장된 응답 확인**(5편): 같은 주소로 받아 둔 응답이 있고 아직 유효하면 네트워크에 나가지 않고 그 응답을 씀. 얼마 동안 유효한지는 그 응답에 붙어 온 `Cache-Control` 헤더가 정함.
3. **DNS로 IP 찾기**(1편): `example.com`이라는 이름을 `104.20.23.154` 같은 IP 주소로 바꿈.[* DNS(Domain Name System): 도메인 이름과 IP 주소의 대응을 알려 주는 분산 데이터베이스. 브라우저와 운영체제가 최근 결과를 저장해 두므로 매번 처음부터 묻지는 않음]
4. **TCP 연결**(1편): 그 IP의 443번 포트와 연결을 엶. 이 연결이 바이트를 순서대로, 빠짐없이 전달하는 통로가 됨.[* 같은 서버와 이미 열어 둔 연결이 있으면 3\~5단계를 건너뛰고 그 연결을 다시 씀]
5. **TLS 암호화**(8편): `https`이면 TCP 연결 위에서 서버 인증서를 확인하고 암호화 키를 정함. 이후 오가는 내용은 중간에서 읽거나 바꿀 수 없음.[* TLS(Transport Layer Security): HTTPS의 S를 담당하는 암호화 규약. 인증서로 상대가 진짜 `example.com`인지 확인함]
6. **요청 메시지 전송**(2편, 4편): 메서드, 경로, 헤더, 본문으로 된 요청을 보냄. 브라우저에 저장된 쿠키 중 이 주소에 해당하는 것은 `Cookie` 헤더로 자동으로 실림.
7. **CDN**(6편): 많은 사이트는 사용자와 가까운 곳에 사본을 두는 CDN이 요청을 먼저 받음. 사본이 있으면 여기서 바로 응답하고, 없으면 원 서버(origin)로 넘김. 이런 사이트에서는 3단계의 DNS가 원 서버가 아닌 CDN 서버의 IP를 알려 주므로, 4\~5단계의 연결도 CDN 서버와 맺음.[* CDN(Content Delivery Network): 여러 지역에 서버를 두고 원 서버의 응답 사본을 나눠 들고 있는 전달망]
8. **리버스 프록시**(7편): 원 서버 앞에 선 프록시가 요청을 받아 실제 애플리케이션 서버로 전달함. 뒤쪽 서버가 보는 연결 상대는 프록시이므로, 원래 요청한 사람의 IP는 `X-Forwarded-For` 같은 헤더로 따로 넘겨받아야 알 수 있음.[* 리버스 프록시: 서버 쪽에 놓여 여러 서버를 대신해 요청을 받는 중간 서버. 사용자 쪽에 놓여 사용자를 대신하는 포워드 프록시와 구분함]
9. **서버 안쪽**(9편): 웹 서버(예: Tomcat)가 받은 바이트를 요청 객체로 바꾸고, 필터를 거쳐 URL에 맞는 컨트롤러 코드를 실행함.
10. **응답**(2편, 4편, 5편): 상태 코드, 헤더, 본문으로 된 응답이 같은 길을 거꾸로 돌아옴. `Set-Cookie`가 있으면 브라우저가 쿠키를 저장하고, `Cache-Control`에 따라 CDN과 브라우저가 응답을 저장해 다음 요청에 씀.

여기까지는 요청 하나에 응답 하나가 짝을 이룸. 채팅이나 알림처럼 서버가 먼저 알려야 하는 기능은 이 짝으로는 만들기 어려워서, 요청을 반복하거나(폴링) 연결을 계속 열어 두는 방법(SSE, WebSocket)을 씀. 10편에서 다룸.

## 직접 확인해 보기

`curl -v`는 요청을 보내면서 각 단계에서 한 일을 출력함. `*`로 시작하는 줄은 curl의 진행 기록, `>`는 보낸 요청, `<`는 받은 응답임.[* 2026-10-23, Linux VM에서 curl 8.18.0(OpenSSL 3.5.5)으로 실행. 인증서 세부, TLS 내부 메시지, IPv6 시도 줄은 생략하고 로컬 내부 주소는 지움]

```text
$ curl -v -o /dev/null https://example.com/
* Host example.com:443 was resolved.
* IPv4: 104.20.23.154, 172.66.147.243
*   Trying 104.20.23.154:443...
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / X25519MLKEM768 / id-ecPublicKey
* Server certificate:
*   subject: CN=example.com
*   issuer: C=US; O=SSL Corporation; CN=Cloudflare TLS Issuing ECC CA 3
* Established connection to example.com (104.20.23.154 port 443)
* using HTTP/2
> GET / HTTP/2
> Host: example.com
> User-Agent: curl/8.18.0
> Accept: */*
>
< HTTP/2 200
< content-type: text/html; charset=utf-8
< server: cloudflare
< age: 6
< cf-cache-status: HIT
```

| 출력 | 단계 |
| --- | --- |
| `was resolved`, `IPv4: …` | 3 DNS로 IP 찾기 |
| `Trying 104.20.23.154:443` | 4 TCP 연결 |
| `SSL connection using TLSv1.3`, `Server certificate` | 5 TLS 암호화 |
| `> GET / HTTP/2`부터 빈 `>` 줄까지 | 6 요청 메시지 |
| `server: cloudflare`, `cf-cache-status: HIT`, `age: 6` | 7 CDN이 저장해 둔 사본으로 응답함 |
| `< HTTP/2 200`과 그 아래 헤더 | 10 응답 |

인증서 발급자와 `server` 헤더가 모두 Cloudflare임. 브라우저 쪽에서 연결을 맺은 상대가 원 서버가 아니라 CDN 서버라는 뜻이고, `cf-cache-status: HIT`와 `age: 6`은 CDN이 6초 전에 저장한 사본을 돌려줬다는 뜻임.[* `age`는 응답이 중간 저장소에 머문 초. `cf-cache-status`는 이 CDN이 붙이는 자체 헤더로, 표준 헤더는 아님]

각 단계에 걸린 시간도 curl로 나눠 볼 수 있음. `-w`에 적은 변수는 요청을 시작한 때부터 그 단계가 끝날 때까지의 누적 시간(초)임.

```text
$ curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com/
dns=0.000845 tcp=0.002546 tls=0.016051 ttfb=0.021655 total=0.021767
```

| 단계 | 계산 | 걸린 시간 |
| --- | --- | --- |
| DNS 조회 | `time_namelookup` | 0.8ms |
| TCP 연결 | `time_connect` − `time_namelookup` | 1.7ms |
| TLS 핸드셰이크 | `time_appconnect` − `time_connect` | 13.5ms |
| 요청 전송부터 응답 첫 바이트까지 | `time_starttransfer` − `time_appconnect` | 5.6ms |

같은 명령을 세 번 실행해 그중 첫 번째를 적었고, 세 번 모두 합계가 21\~25ms였음. DNS가 1ms도 걸리지 않은 것은 직전 실행의 조회 결과가 저장돼 있었기 때문임.[* 이보다 앞서 처음 실행했을 때는 DNS 조회에 4.7ms가 걸렸음] TCP 연결 한 번이 왕복 한 번에 해당하므로 CDN 서버까지 왕복은 2ms 남짓임. 그보다 TLS 핸드셰이크가 몇 배 길었으므로, 이 경우 TLS 시간의 대부분은 네트워크 대기보다 키 교환과 인증서 검증 계산에 쓰인 것으로 보임.

> 요청 하나는 이름을 주소로 바꾸고, 연결을 열고, 암호화하고, 메시지를 보내는 단계를 차례로 거침. 그 메시지가 서버 코드에 닿기 전에 CDN이나 프록시가 먼저 받아 응답하거나 넘기는 경우가 많음.

## 확인 질문

**1. 주소창에 주소를 넣고 엔터를 눌렀는데 네트워크로 요청이 하나도 나가지 않을 수 있는가?**

<details><summary>답</summary>

있음. 같은 주소의 응답을 브라우저가 저장해 두었고, 그 응답의 `Cache-Control`이 정한 유효 기간이 남아 있으면 브라우저는 서버에 묻지 않고 저장된 응답을 씀(2단계, 5편).

</details>

**2. CDN을 쓰는 사이트에 접속할 때 브라우저가 TCP 연결을 맺는 상대는 누구인가?**

<details><summary>답</summary>

CDN 서버. DNS가 원 서버가 아닌 CDN 서버의 IP를 알려 주기 때문임. 위 `curl -v` 출력에서 인증서 발급자와 `server` 헤더가 CDN 회사인 것으로 확인할 수 있음. CDN은 사본이 없을 때만 원 서버에 따로 요청함(6편).

</details>

**3. 요청의 `Cookie` 헤더는 누가 넣는가?**

<details><summary>답</summary>

브라우저. 서버는 응답의 `Set-Cookie` 헤더로 쿠키 저장을 요청할 뿐이고, 이후 요청마다 저장된 쿠키 중 도메인과 경로 조건이 맞는 것을 브라우저가 자동으로 실어 보냄(4편).

</details>

**4. 리버스 프록시 뒤에 있는 애플리케이션 서버가 TCP 연결 상대의 IP를 읽으면 누구의 IP가 나오는가?**

<details><summary>답</summary>

프록시의 IP. 서버와 직접 연결을 맺은 상대가 프록시이기 때문임. 실제 사용자의 IP는 프록시가 `X-Forwarded-For` 같은 헤더에 적어 넘겨야 알 수 있고, 그 헤더를 어디까지 믿을지도 따로 정해야 함(7편).

</details>

**5. `curl -w`의 `time_appconnect`에서 `time_connect`를 빼면 무엇을 잰 값이 되는가?**

<details><summary>답</summary>

TLS 핸드셰이크에 걸린 시간. `time_connect`는 TCP 연결이 끝난 시점, `time_appconnect`는 TLS 핸드셰이크가 끝난 시점까지의 누적 시간이기 때문임(8편).

</details>
