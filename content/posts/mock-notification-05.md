관련 프로젝트 연결을 확인하기 위한 가상 회고다. 구현·운영 성과를 주장하는 글이 아니라 앞선 예시에서 선택한 범위와 남은 문제를 정리한다.

## 처음부터 범위를 줄였다

알림 채널은 이메일 하나, 저장소는 기존 관계형 데이터베이스 하나로 잡았다. 먼저 작업이 접수되고, 실패하고, 다시 처리되는 경계를 설명할 수 있게 만드는 데 집중했다.

메시지 브로커를 추가하면 전달 방식이 달라질 수 있지만 중복 처리와 외부 응답 유실 문제까지 없어지는 것은 아니다. 현재 선택으로 해결되는 문제와 남는 문제를 구분해 두었다.

## 유지할 선택

| 선택 | 이유 | 남은 조건 |
| --- | --- | --- |
| 주문과 작업의 동시 저장 | 작업 누락 방지 | 같은 DB 트랜잭션 사용 |
| 요청 식별 조합의 유일 제약 | 동시 접수의 중복 판정 | 외부 발송 중복은 별도 제어 |
| 다음 실행 시각 저장 | 재시작 후 예약 복구 | 작업 점유 만료 정책 필요 |
| 실패 보관함 | 무한 재시도 방지 | 재실행 기준과 이력 필요 |

## 다음 실험

가장 먼저 확인할 것은 처리량의 최대치보다 복구 동작이다. 발송 직전에 작업자를 종료하고, 발송 직후 결과 저장을 실패시키고, 같은 요청을 동시에 넣어 본다.

그다음 작업 수가 늘었을 때 조회 비용과 잠금 대기를 측정한다. 작업자를 늘리는 것만으로 대기 시간이 줄어드는지, 외부 제공자의 제한이 병목인지 구분한다. 측정 결과가 없으므로 이번 예시에는 처리량 개선 수치를 적지 않았다.

## 글과 프로젝트의 관계

다섯 글은 각각 독립적인 개발 기록으로 Posts에 남고, 같은 프로젝트를 참조한다. 프로젝트 소개에는 전체 맥락을 두고 글에는 개별 판단을 남기면 나중에 다른 프로젝트에서도 주제별로 찾아 읽기 쉽다.

상단의 **연관 프로젝트** 링크에서 예시 프로젝트와 전체 글 목록을 다시 확인할 수 있다.
