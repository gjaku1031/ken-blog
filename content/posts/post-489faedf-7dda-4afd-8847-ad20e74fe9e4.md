ken-blog API는 메모리를 적게 쓰는 Native Image 대신 일반 JVM으로 돌리기로 했음. Spring과 JPA, jOOQ, ImageIO는 리플렉션 같은 동적 기능을 많이 써서, Native Image로는 빌드 설정과 런타임 힌트를 계속 맞춰야 했기 때문임. 대가는 메모리임. 예전 구현을 같은 조건에서 재 봤을 때 JVM이 Native Image보다 메모리를 약 5배(684MiB 대 136MiB) 썼으므로, 당시 1코어, 약 4GB 서버에서 정말 버틸 수 있는지 2026년 10월 2일에 직접 부하를 걸어 봤음.[* 예전 구현에서 같은 코드, 1 CPU·1GiB 조건으로 읽기 요청 120번 뒤의 메모리 중앙값. [인프라 ADR](https://github.com/gjaku1031/ken-blog/blob/1072a36/docs/ADR/ADR_infra.md)의 Native Image 검증 기록]

> 잰 범위에서는 API가 1.5GiB 한도 안에서 멈추거나 다시 시작되지 않고 버텼음. 메모리는 많아야 474.5MiB였지만, 초당 200건에서 서버 CPU가 88%까지 올라 여유는 크지 않았음.

## 무엇을 알고 싶었나

1코어, 약 4GB 서버에서 일반 JVM API가 메모리 한도를 넘지 않고 요청을 처리할 수 있는지가 궁금했음. 대문의 핵심 문제 P2(제한된 자원에서의 열람 성능)와 이어지는 질문임. 어떤 요청을 얼마나 보낼지는 미리 정했지만, 몇 ms, 몇 MiB면 통과로 볼지는 기록에 남아 있지 않아 탐색적 실험으로 봄.

## 어떻게 쟀나

같은 리전의 다른 VM에서 HTTPS로 요청을 일정한 속도로 보냈음. 주된 요청은 당시 공개 API 조합(공개 상태 30%, 기술 배지 70%)이고, 초당 10, 50, 100, 200건으로 30초씩 올렸음. 여기에 이미지 첨부, 글 100개짜리 스냅샷, 로그인한 관리자 조회를 따로 더했음. JVM은 기동과 기능 검사를 마친 상태에서 쟀고, 메모리는 1초마다 컨테이너 사용량을 기록했음. Native Image와 같은 조건으로 나란히 잰 것은 아니라서, 이번 결과에는 비교 대상이 없음.

## 결과가 말해 주는 것

잰 범위에서 API는 메모리 한도 안에서 멈추거나 다시 시작되지 않았고, 가장 많이 쓴 메모리(474.5MiB)도 한도의 약 31%였음. 메모리는 걱정한 만큼 문제가 아니었음.

오히려 CPU가 먼저 빠듯해졌음. 초당 200건에서 서버 전체 CPU가 88.4%까지 올라, 이 서버로 이 요청 조합을 더 받을 여유는 크지 않았음.

초당 요청이 늘어도 p95가 계속 늘지는 않았음(초당 10건에서 23.55ms, 100건에서 10.17ms). 부하 단계를 어떤 순서로 돌렸는지 기록이 없어, 앞 단계에서 JIT 컴파일이 진행돼 뒤 단계가 빨라졌을 가능성을 가리지 못함. 순서를 바꿔 반복해야 가릴 수 있음.

## 결과를 믿기 어려운 부분

- **다른 원인이 섞였을 가능성**: 테스트용 MySQL이 같은 서버에서 함께 돌았고, CPU 수치는 API만이 아니라 MySQL과 운영체제까지 포함한 값임. 다시 잰다면 컨테이너의 cgroup CPU 통계를 따로 받아야 API만의 부하를 볼 수 있음
- **일반화**: 당시 이미지와 당시 스냅샷 계약(v2, 지금은 v3)으로 잰 결과라, 지금의 운영 서버 성능이나 최대 처리량, 오래 돌렸을 때의 메모리로 넓혀 말하지 않음
- **재는 것이 맞나**: 공개 상태와 배지는 당시 API 요청 조합이며, Pages에서 HTML을 받거나 브라우저가 그리는 시간은 아님
- **표본 크기**: 조건마다 30초씩 한 번 쟀고, 스냅샷 p95는 15번 관측에 그침
