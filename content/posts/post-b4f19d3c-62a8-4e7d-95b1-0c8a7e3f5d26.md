[담담공방 쇼핑몰](/ken-blog/post/project-a3d53a55-de01-4888-9e9a-02e34f2579bb/)의 API는 모든 응답에 `Cache-Control: no-store`를 먼저 적고, 캐시해도 되는 응답만 처리하는 코드가 직접 풀어 줌. 사진의 404가 CDN에 저장되는 문제를 고치다가 같은 원인의 더 큰 문제를 찾았음.

## 발견한 문제

운영 사이트는 Cloudflare 뒤에 있음. 이미지 최적화를 배포하면서 공개 사진에 `Cache-Control: public, max-age=86400`을 붙였고, 그 확인을 하다가 두 가지를 봄.

**1. 사진 주소의 404가 캐시됨.** 없는 사진 주소를 두 번 요청하면 두 번째는 CDN이 대신 응답함. 브라우저에는 4시간 동안 다시 묻지 말라는 헤더까지 붙음.

```
GET /api/storage/files/product/00000000-….jpg   → 404  cf-cache-status: MISS
GET /api/storage/files/product/00000000-….jpg   → 404  cf-cache-status: HIT   cache-control: max-age=14400
```

API가 보낸 404에는 `Cache-Control`이 없었음. `max-age=14400`은 CDN이 붙인 값임. 공개 전이거나 숨긴 사진을 한 번 요청한 브라우저는 사진이 공개된 뒤에도 최대 4시간 동안 빈칸을 봄.

**2. 주소 끝에 `;x.jpg`를 붙이면 JSON 응답도 캐시됨.** 이쪽이 더 큼.

```
GET /api/products;probe1.jpg   → 200 application/json  cf-cache-status: MISS
GET /api/products;probe1.jpg   → 200 application/json  cf-cache-status: HIT   cache-control: max-age=14400
```

세 가지가 겹쳐서 생김.

- **CDN은 주소의 확장자를 봄.** `.jpg`·`.css`처럼 끝나는 주소는 정적 파일로 보고 저장함. 응답의 `Content-Type`이 JSON이어도 저장함.
- **Spring MVC는 `;` 뒤를 버리고 경로를 찾음.** `/api/products;x.jpg`는 `/api/products` 핸들러가 받음. 경로 매개변수라는 오래된 URL 문법임.
- **API가 캐시 지시를 보내지 않았음.** 지시가 없으면 CDN은 자기 기본값으로 저장하고, 200이 404보다 오래 남음.

이 조합을 Web Cache Deception이라고 부름. 공격 순서는 이럼.

1. 공격자가 로그인한 사용자에게 `https://damdamwood.co.kr/api/orders/me;a.jpg` 같은 링크를 누르게 함.
2. 브라우저가 쿠키와 함께 요청하고, API는 그 사용자의 주문 목록을 200으로 응답함.
3. CDN은 주소가 `.jpg`로 끝나므로 그 응답을 저장함.
4. 공격자가 같은 주소를 쿠키 없이 요청하면 CDN이 저장해 둔 남의 주문 목록을 돌려줌.

이름·전화번호·주소가 든 응답이 대상이 됨.

## 1. 막는 곳

| 기준 | A. 원 서버가 `Cache-Control`을 보냄 | B. CDN 규칙으로 `/api/*`를 캐시에서 제외 |
|---|---|---|
| 설정이 있는 곳 | 코드. 리뷰와 배포 기록에 남음 | CDN 대시보드. 저장소에 없음 |
| CDN을 바꾸거나 규칙을 지웠을 때 | 그대로 동작 | 구멍이 다시 열림 |
| 브라우저·중간 프록시의 캐시 | 함께 막음 | CDN만 막음 |
| 사진 캐시와의 관계 | 응답마다 다르게 보낼 수 있음 | `/api/storage/files/*`는 예외로 빼야 함. 규칙이 둘로 늘어남 |
| 응답 내용에 따른 판단 | 가능(공개 사진만 캐시) | 불가능. 주소만 보고 정함 |
| 원 서버의 실수 | 헤더를 빠뜨리면 그대로 샘 | 원 서버가 빠뜨려도 막아 줌 |

**선택: A.** 이 사진이 공개인지 아닌지는 원 서버만 앎. 같은 주소가 어제는 비공개였다가 오늘은 공개가 되므로 주소만 보는 규칙으로는 가를 수 없음. 그리고 저장소에 없는 설정은 누가 언제 바꿨는지 추적이 안 됨.

**A가 치르는 비용.** 원 서버가 헤더를 한 번 빠뜨리면 그대로 샘. 그래서 2번과 3번에서 빠뜨릴 수 없는 구조로 만듦. B는 버린 게 아니라 두 번째 방어선으로 남겨 둠. CDN의 Cache Deception Armor(확장자와 `Content-Type`이 맞을 때만 저장)를 켜면 원 서버가 실수해도 JSON이 `.jpg` 주소로 저장되지 않음. 대시보드 권한이 필요한 작업이라 이번 변경에는 넣지 못함.

## 2. 지시를 붙일 응답

처음 본 증상은 404였음. 404만 고치면 되는지가 갈림길임.

| 기준 | A. 모든 응답에 기본으로 `no-store` | B. 오류 응답에만 `no-store` |
|---|---|---|
| 사진 404 캐시 | 막음 | 막음 |
| `;x.jpg`를 붙인 JSON 200 | 막음 | 못 막음. 200은 오류가 아님 |
| 새 API를 추가할 때 | 아무것도 안 해도 안전 | 개인 정보가 든 응답마다 헤더를 기억해야 함 |
| 캐시하고 싶은 응답 | 핸들러가 명시해야 함 | 지금처럼 명시 |
| 실수했을 때의 결과 | 캐시가 안 됨(느려짐) | 캐시가 됨(샘) |

**선택: A.** B는 본 증상만 고치고 원인은 남김. 원인은 "지시가 없는 응답을 CDN이 알아서 저장한다"는 것이고, 지시가 없는 응답은 오류보다 성공 응답이 훨씬 많음.

결정적인 차이는 마지막 줄임. A에서 헤더를 빠뜨리면 사진이 캐시되지 않아 느려지고, 누군가 알아채서 고침. B에서 빠뜨리면 남의 주문이 캐시되고, 아무도 알아채지 못함. 틀렸을 때 조용히 새는 쪽보다 시끄럽게 느려지는 쪽을 고름.

**A가 치르는 비용.** 공개 JSON(상품 목록 등)을 나중에 CDN에 올리고 싶어지면 그 핸들러에 캐시 허용을 따로 적어야 함. 지금은 그런 응답이 없고, 웹도 모든 API 호출을 `cache: 'no-store'`로 하고 있어 달라지는 동작이 없음.

## 3. 코드에서 붙이는 자리

| 기준 | A. 맨 앞 필터에서 미리 적어 둠 | B. 응답을 만드는 곳마다(오류 처리기, 컨트롤러) |
|---|---|---|
| 고칠 곳 | 한 곳 | `GlobalExceptionHandler`, 본문 크기 필터, 컨트롤러 전부 |
| 필터가 직접 쓰는 응답(413) | 포함 | 필터마다 따로 넣어야 함 |
| 인터셉터가 막은 응답(401·403) | 포함 | 오류 처리기를 거치므로 포함 |
| 나중에 추가되는 필터·핸들러 | 자동으로 포함 | 넣는 걸 기억해야 함 |
| 캐시를 허용하는 방법 | 핸들러가 `ResponseEntity.cacheControl`로 덮어씀 | 같음 |
| 헤더가 두 줄이 될 위험 | 확인 필요(아래) | 없음 |

**선택: A.** `NoStoreByDefaultFilter`가 가장 먼저 실행돼 `Cache-Control: no-store`를 적고 넘김. 뒤에서 무엇이 응답을 만들든 헤더는 이미 있음. 본문 크기 제한 필터는 이 필터 바로 다음으로 순서를 옮김.

걱정한 점은 필터가 적어 둔 `no-store`와 사진 컨트롤러가 적는 `max-age=86400, public`이 두 줄로 나가는 경우였음. 두 줄이면 브라우저는 엄격한 쪽을 따르므로 사진 캐시가 조용히 꺼짐. 실제로 띄워서 보니 `max-age=86400, public` 한 줄만 나감. `ResponseEntity`에 적은 헤더가 필터의 값을 대체함(Spring Boot 4.1 기준). 사진 컨트롤러는 고치지 않았음.

**A가 치르는 비용.** 톰캣이 필터에 닿기 전에 거절하는 요청(깨진 퍼센트 인코딩의 400)에는 헤더가 붙지 않음. 운영 사이트에서는 이런 요청이 원 서버에 닿지 않았음. 퍼센트 인코딩이 깨진 주소 세 가지를 두 번씩 요청하니 CDN이 직접 400으로 거절했고, 응답에 캐시 상태 헤더가 없었음.[* 2026-10-13 운영 사이트. `/api/%zz.jpg`, `/api/products/%.jpg`, `/api/%E0%A4%A.jpg`. 인코딩하지 않은 `{`와 `|`가 든 주소는 정상 처리되어 `no-store`가 붙었음] 원 서버가 헤더 없이 낸 400이 CDN을 지나는 경우는 만들지 못했음.

## 4. 404의 캐시

404를 CDN이 대신 응답해 주면 원 서버가 편함. 완전히 끌지, 짧게 남길지의 문제임.

| 기준 | A. 캐시하지 않음(`no-store`) | B. 404를 짧게 캐시(예: 60초) |
|---|---|---|
| 없는 사진을 반복 요청할 때 | 매번 원 서버까지 옴 | 같은 주소는 CDN이 막아 줌 |
| 주소를 바꿔 가며 요청할 때 | 매번 원 서버까지 옴 | 똑같이 매번 옴. 캐시가 도움이 안 됨 |
| 공개 직후 | 바로 보임 | 캐시 기간만큼 빈칸 |
| 비공개 사진을 운영자가 볼 때 | 정상 | 비로그인 요청의 404가 운영자에게도 감 |

**선택: A.** B의 마지막 줄이 문제임. 같은 사진 주소가 비로그인에게는 404, 운영자에게는 200임. CDN은 쿠키를 구분하지 않으므로(쿠키를 붙여 요청해도 저장된 404가 돌아오는 것을 확인함) 404를 60초만 캐시해도 그 60초 동안 운영자는 방금 올린 사진을 못 봄. 사람에 따라 달라지는 응답은 공용 캐시에 넣을 수 없음.

**A가 치르는 비용.** 없는 사진 주소 요청이 전부 원 서버까지 옴. 한 건에 DB 조회 한두 번이고, 로컬에서 200건을 재니 중앙값 6.9ms였음(데이터가 거의 없는 DB 기준). 주소를 바꿔 가며 보내는 요청은 B로도 못 막으므로, 이 부하를 줄이려면 캐시가 아니라 요청 수 제한이 맞는 도구임.

## 5. `;`가 든 주소

구멍의 재료 가운데 하나가 `;` 경로 매개변수임. 이것까지 없앨지의 문제임.

| 기준 | A. 거부하지 않음 | B. `;`가 든 요청을 400으로 거부 |
|---|---|---|
| 캐시 속이기 | 2번으로 이미 막힘 | 한 겹 더 막음 |
| 다른 방법으로 확장자를 붙이는 경우 | 2번이 함께 막음 | `;`만 막음 |
| 정상 요청에 미치는 영향 | 없음 | 이 서비스는 `;`를 쓰지 않으나, 중간 프록시가 주소를 다듬는 방식에 따라 달라질 수 있음 |
| 추가 코드 | 없음 | 필터 하나와 그 검증 |

**선택: A.** 응답이 `no-store`면 주소를 어떻게 꾸미든 저장될 것이 없음. B는 원인이 아니라 재료 하나를 막는 것이라, 같은 효과를 내는 다른 주소 형태가 나오면 다시 뚫림. 권한 판단에서 `;`를 조심해야 하는 문제는 이미 `RequestPaths.segments` 규칙으로 따로 다루고 있음.

**A가 치르는 비용.** 방어선이 한 겹임. 누군가 필터를 지우거나 민감한 응답에 캐시 허용을 잘못 붙이면 `;x.jpg`가 다시 통함. 그래서 컨벤션 문서에 "기본은 `no-store`, 사용자에 따라 달라지는 응답에는 캐시 허용 금지"를 규칙으로 적음.

## 남는 위험

- 이미 CDN에 저장된 응답은 기간이 끝날 때까지 남음. 확인하면서 만든 `/api/products;probe1.jpg`, `;probe2.jpg`가 그렇고(배포 뒤에도 `HIT`), 내용은 공개 상품 목록임. 바로 지우려면 CDN에서 캐시 삭제를 실행해야 함.
- 방어선이 원 서버 한 겹임. CDN의 Cache Deception Armor를 켜고 `/api/*` 가운데 사진 주소만 캐시 대상으로 두는 규칙을 더하면 두 겹이 됨.
- 공개 사진은 여전히 하루 동안 캐시됨. 숨긴 사진이 그동안 남는 것은 이미지 최적화에서 받아들인 비용이며 이번 변경과 무관함.
- 캐시를 허용하는 핸들러가 늘어나면 그때마다 "이 응답이 사람에 따라 달라지는가"를 확인해야 함. 지금은 사진 응답 하나뿐임.
