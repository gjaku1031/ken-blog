[1편](/ken-blog/post/post-adf39eb5-c2bf-4064-b443-e89613393020/)에서 TCP 연결이 열리는 것까지 봤다. 이제 그 연결 위로 HTTP 요청이 간다. 컨트롤러에서는 `@GetMapping`을 달고, `@RequestBody`로 JSON을 받고, `ResponseEntity.status(201)`로 응답을 만들어 봤지만, 그게 실제로 선을 타고 갈 때 어떤 모양인지는 본 적이 없었다. 그래서 요청을 손으로 직접 써서 보내 봤다.

## 학습 목표

- 요청과 응답 메시지가 시작 줄, 헤더, 빈 줄, 본문으로 이뤄진다는 것을 알고 직접 써 볼 수 있다

- 상태 코드 다섯 계열을 구분하고 대표 코드를 말할 수 있다

## HTTP 메시지의 모양

HTTP/1.1 메시지는 사람이 읽을 수 있는 글자다. 시작 줄, 헤더, 빈 줄, 본문 순서로 이뤄진다.

```text
POST /notes HTTP/1.1                  ← 시작 줄: 메서드, 경로, 버전
Host: example.com                     ← 헤더: "이름: 값"을 한 줄에 하나씩
Content-Type: application/json
Content-Length: 18
                                      ← 빈 줄: 여기서 헤더가 끝남
{"title":"공부"}                      ← 본문
```

응답도 같은 모양이고, 시작 줄만 `HTTP/1.1 201 Created`처럼 버전, 상태 코드, 설명 문구로 바뀐다. 줄 끝은 `\r\n`(CRLF)이고, 헤더가 끝났다는 표시는 아무것도 없는 줄 하나다.[* HTTP의 의미(메서드, 상태 코드, 헤더)는 RFC 9110, HTTP/1.1의 글자 형식은 RFC 9112에 있다]

0편에서 curl은 `HTTP/2`로 통신했다. HTTP/2는 같은 내용을 글자 대신 이진 프레임으로 포장해 보내고, 연결 하나로 여러 요청을 동시에 보낼 수 있다. 메서드, 헤더, 상태 코드의 뜻은 그대로라서, 공부할 때는 눈으로 읽을 수 있는 HTTP/1.1 모양으로 이해해도 된다.[* HTTP/2는 RFC 9113. 헤더 이름을 모두 소문자로 쓰고, 시작 줄 대신 `:method`, `:path` 같은 가짜 헤더를 쓴다. 0편의 curl 출력에서 `[:method: GET]` 같은 줄이 그것이다]

### 헷갈렸던 것: Host 헤더는 왜 꼭 있어야 하나

1편에서 연결은 IP 주소로 맺는다고 했다. 그런데 IP 하나에 사이트가 여러 개 있을 수 있다. example.com이 쓰는 CDN 서버도 수많은 도메인을 같은 IP로 받는다. 그래서 서버가 어느 사이트로 온 요청인지 알 수 있게 HTTP/1.1은 `Host` 헤더를 반드시 넣게 했고, 아래 실습에서 빼고 보냈더니 400이 돌아왔다.

### 헷갈렸던 것: 본문은 어디서 끝나나

헤더 끝은 빈 줄로 알 수 있지만, 본문 끝에는 표시가 없다. 그래서 받는 쪽에 길이를 알려 줘야 한다. 방법은 두 가지다.

- `Content-Length`: 본문이 몇 **바이트**인지 미리 적는다. 글자 수가 아니라 바이트 수라서, 한글은 UTF-8에서 한 글자가 3바이트다.
- `Transfer-Encoding: chunked`: 길이를 미리 모를 때 조각마다 크기를 적어 보내고, 크기 0인 조각으로 끝을 알린다.

## 메서드: 무엇을 해 달라는 요청인가

| 메서드 | 뜻 | 안전 | 멱등 |
| --- | --- | --- | --- |
| GET | 자원을 달라 | O | O |
| HEAD | GET과 같지만 헤더만 달라 | O | O |
| POST | 본문을 처리해 달라(새로 만들기 등) | X | X |
| PUT | 이 경로의 자원을 본문으로 통째로 바꿔라 | X | O |
| PATCH | 일부만 고쳐라 | X | X[* PATCH는 멱등이 보장되지 않는다. "값을 5로 바꿔라"처럼 멱등하게 만들 수도 있지만 "1 늘려라"처럼 아닐 수도 있다] |
| DELETE | 이 경로의 자원을 지워라 | X | O |

**안전**은 서버의 상태를 바꾸지 않는다는 약속이다. 읽기만 한다. **멱등**은 같은 요청을 한 번 보내든 열 번 보내든 서버에 남는 결과가 같다는 약속이다. 멱등은 엘리베이터 버튼과 자판기 버튼에 비유할 수 있다. 엘리베이터 버튼은 여러 번 눌러도 엘리베이터가 한 대 오니 멱등이고, 자판기 버튼은 누를 때마다 음료가 하나씩 나오니 멱등이 아니다.

처음엔 이 구분이 왜 필요한지 몰랐다. 응답을 받기 전에 연결이 끊기면, 클라이언트는 요청이 처리됐는지 모른다. 멱등한 요청은 그냥 다시 보내도 되지만, POST를 다시 보내면 주문이 두 번 들어갈 수 있다. 브라우저가 POST로 받은 페이지를 새로고침할 때 "양식을 다시 제출할까요?"라고 묻는 것도 같은 이유다.

다만 엘리베이터 버튼은 기계가 멱등을 보장하지만, HTTP 메서드의 안전과 멱등은 서버가 지키기로 한 약속일 뿐이다. 내가 `@GetMapping` 안에서 DB를 고치는 코드를 쓰면 HTTP는 막지 않는다. 약속을 깬 서버가 될 뿐이다.

## 상태 코드: 결과를 세 자리 숫자로

응답 첫 줄의 세 자리 숫자가 결과를 알려 준다. 첫 자리가 계열이다.

| 계열 | 뜻 | 대표 코드 |
| --- | --- | --- |
| 1xx | 아직 처리 중, 계속하라 | 101 프로토콜 전환([10편](/ken-blog/post/post-faadfcd9-8851-488b-b485-253aee1b297c/)) |
| 2xx | 성공 | 200 OK, 201 Created(새로 만듦, `Location`에 주소), 204 No Content(본문 없음) |
| 3xx | 다른 곳으로 가라, 또는 가진 걸 써라 | 301 영구 이동, 302 임시 이동, 304 바뀐 것 없음([5편](/ken-blog/post/post-69de2eba-53bf-4cf2-9c86-fdd0aa3dadc5/)) |
| 4xx | 요청한 쪽의 문제 | 400 잘못된 요청, 401 누군지 모름, 403 권한 없음, 404 없음, 405 이 메서드는 안 됨 |
| 5xx | 서버 쪽의 문제 | 500 서버 내부 오류, 502 앞단이 뒤쪽 서버에서 이상한 응답을 받음, 503 지금 처리 불가 |

4xx와 5xx를 가르는 기준은 "누구 탓인가"다. 같은 요청을 다시 보내도 결과가 같으면 4xx, 서버 사정이 나아지면 성공할 수 있으면 5xx라고 생각하니 기억하기 쉬웠다. 401과 403은 이름 때문에 헷갈렸는데, 401은 "당신이 누구인지 모르겠다"(로그인 필요), 403은 "누군지는 아는데 이건 안 된다"이다.[* 401의 이름은 Unauthorized지만 실제 뜻은 인증(authentication)이 없다는 것이다. 이름이 역사적으로 잘못 붙은 경우로 자주 언급된다]

## 직접 확인해 보기

먼저 `nc`로 example.com의 80번 포트에 연결해 요청을 손으로 써 보냈다. `printf`로 줄 끝의 `\r\n`과 마지막 빈 줄까지 그대로 넣었다.[* 위치를 드러내는 `CF-RAY`와 `alt-svc` 줄을 지우고, 본문 HTML은 줄였다][* 2026-10-23, Linux VM에서 OpenBSD netcat 1.234, curl 8.18.0, Python 3.14.4로 실행했다. HTTPS 포트에 손으로 쓰려면 `nc` 대신 `openssl s_client -connect example.com:443`을 쓴다]

```bash
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80
```

```text
HTTP/1.1 200 OK
Date: Fri, 23 Oct 2026 20:53:53 GMT
Content-Type: text/html; charset=utf-8
Transfer-Encoding: chunked
Connection: close
Server: cloudflare
Last-Modified: Wed, 21 Oct 2026 20:09:25 GMT
Allow: GET, HEAD
Accept-Ranges: bytes
Age: 6646
cf-cache-status: HIT

241
<!doctype html><html lang=en><head><meta charset=utf-8>…(생략)…</html>

0
```

| 출력 | 뜻 |
| --- | --- |
| `HTTP/1.1 200 OK` | 시작 줄. 버전, 상태 코드, 설명 문구 |
| `Content-Type: text/html; charset=utf-8` | 본문이 UTF-8로 쓴 HTML이다 |
| `Transfer-Encoding: chunked` | `Content-Length` 대신 조각 단위로 길이를 알린다 |
| `Allow: GET, HEAD` | 이 자원에 쓸 수 있는 메서드 |
| 빈 줄 | 헤더 끝 |
| `241` | 첫 조각의 크기. 16진수라서 577바이트다 |
| 마지막 `0` | 크기 0인 조각. 본문이 여기서 끝난다 |

`Allow`가 GET과 HEAD만 허락한다고 해서, 다른 경우도 보내 봤다.[* 응답마다 시작 줄과 설명에 필요한 헤더만 남겼다]

```bash
printf 'GET / HTTP/1.1\r\nConnection: close\r\n\r\n' | nc example.com 80
```

```text
HTTP/1.1 400 Bad Request
```

```bash
curl -si -X POST -d 'a=1' https://example.com/
```

```text
HTTP/2 405
```

```bash
curl -sI https://example.com/
```

```text
HTTP/2 200
content-type: text/html; charset=utf-8
```

```bash
curl -si https://example.com/nope
```

```text
HTTP/2 404
```

```bash
curl -sI http://github.com/
```

```text
HTTP/1.1 301 Moved Permanently
Content-Length: 0
Location: https://github.com/
```

| 보낸 요청 | 받은 코드 | 이유 |
| --- | --- | --- |
| `Host` 없이 GET | 400 | HTTP/1.1에서 `Host`는 필수다 |
| POST | 405 | 이 자원은 GET, HEAD만 받는다 |
| HEAD | 200 | GET과 같은 헤더를 주고 본문은 보내지 않는다 |
| 없는 경로 `/nope` | 404 | 그런 자원이 없다 |
| `http://`로 GitHub | 301 | `Location`의 `https://` 주소로 영구히 옮겼다 |

하나 의외였던 건 405 응답에 `Allow` 헤더가 없었다는 점이다. RFC 9110은 405를 보낼 때 허용하는 메서드를 `Allow`에 적어야 한다고 하는데, 이 응답에는 없었다. 규약과 실제 서버가 다를 수 있다는 걸 처음 직접 봤다.

마지막으로 서버가 받는 쪽에서 요청을 보고 싶었다. 받은 바이트를 그대로 출력하고 `201 Created`를 돌려주는 작은 Python 서버를 띄우고, curl로 JSON을 보냈다.[* 서버는 표준 라이브러리 `socket`으로 연결 하나를 받아, 헤더 끝(`\r\n\r\n`)까지 읽고 `Content-Length`만큼 본문을 더 읽은 뒤 응답하는 30줄짜리 코드다]

```bash
curl -si -X POST http://127.0.0.1:18101/notes -H 'Content-Type: application/json' -d '{"title":"공부"}'
```

```text
HTTP/1.1 201 Created
Content-Type: application/json
Content-Length: 8
Location: /notes/1

{"id":1}
```

서버가 받은 바이트(Python `repr`로 출력):

```text
b'POST /notes HTTP/1.1\r\nHost: 127.0.0.1:18101\r\nUser-Agent: curl/8.18.0\r\nAccept: */*\r\nContent-Type: application/json\r\nContent-Length: 18\r\n\r\n{"title":"\xea\xb3\xb5\xeb\xb6\x80"}'
```

내가 컨트롤러에서 `@RequestBody`로 받던 게 결국 이 한 줄이었다. 시작 줄, 헤더, `\r\n\r\n`, 본문이 그대로 보인다. `{"title":"공부"}`는 14글자인데 `Content-Length`는 18이었다. `공부` 두 글자가 UTF-8에서 각각 3바이트(`\xea\xb3\xb5`, `\xeb\xb6\x80`)라서 4바이트가 더 붙었다.

> HTTP 메시지는 시작 줄, 헤더, 빈 줄, 본문으로 된 글자다. 메서드는 무엇을 해 달라는지, 상태 코드는 어떻게 됐는지를 알려 주고, 안전과 멱등은 서버가 지키기로 한 약속이다.

## 확인 질문

**1. 서버는 요청의 헤더가 어디서 끝나고 본문이 어디서 시작하는지 어떻게 알까?**

<details><summary>답</summary>

빈 줄로 안다. 마지막 헤더 줄 뒤에 아무것도 없는 줄(`\r\n\r\n`)이 오면 그다음부터가 본문이다. 본문의 끝은 `Content-Length`나 chunked 조각 크기로 안다.

</details>

**2. `{"title":"공부"}`를 보냈는데 `Content-Length`가 14가 아니라 18이었다. 왜일까?**

<details><summary>답</summary>

`Content-Length`는 글자 수가 아니라 바이트 수이기 때문이다. 한글은 UTF-8에서 한 글자가 3바이트라서, 두 글자가 6바이트를 차지해 4바이트가 더 붙는다.

</details>

**3. 결제 요청을 보냈는데 응답을 받기 전에 연결이 끊겼다. PUT과 POST 중 그냥 다시 보내도 안전한 쪽은 어느 것이고, 왜 그럴까?**

<details><summary>답</summary>

PUT이다. PUT은 멱등이라 같은 요청이 두 번 처리돼도 결과가 같다. POST는 멱등이 아니라서 다시 보내면 결제가 두 번 될 수 있다. 그래서 POST를 다시 보내야 하는 API는 요청마다 고유한 키를 붙여 서버가 중복을 걸러 내게 하기도 한다.

</details>

**4. 로그인하지 않고 내 정보 API를 불렀을 때와, 로그인했지만 관리자 API를 불렀을 때 각각 어떤 상태 코드가 알맞을까?**

<details><summary>답</summary>

앞의 경우는 401, 뒤의 경우는 403이다. 401은 누구인지 모른다(인증 필요), 403은 누군지 알지만 권한이 없다는 뜻이다.

</details>

**5. 502 Bad Gateway를 받았다. 내 요청이 잘못됐을 가능성이 높을까, 서버 쪽 문제일 가능성이 높을까?**

<details><summary>답</summary>

서버 쪽이다. 5xx는 서버 쪽 문제이고, 502는 특히 프록시 같은 앞단 서버가 뒤쪽 서버에서 제대로 된 응답을 받지 못했다는 뜻이다. 프록시는 [7편](/ken-blog/post/post-ca04bdf2-91f9-4bf6-abff-b422dc854eb4/)에서 다룬다.

</details>
