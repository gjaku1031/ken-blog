원고 작성·공개 열람·메타데이터 관리의 책임 분리와, 저장·조회 모델 및 편집 충돌 처리의 주요 결정.

## 결정 요약

| 결정 | 해결 대상 | 수용한 비용 |
| --- | --- | --- |
| Git Markdown을 본문 정본으로 사용 | 프로젝트 경험·학습 문서의 분산, 에이전트와의 원고 활용 | 원고와 DB 메타데이터의 상태를 함께 관리 |
| 공개 화면을 정적 생성 | 일본 리전 API의 글 열람 처리와 왕복 의존 | 변경 반영에 Pages 재배포 필요 |
| JPA 모델에서 jOOQ 타입 생성 | 엔티티·수동 SQL의 스키마 중복 관리 | 도메인 선행 컴파일·생성 태스크 유지 |
| 편집 버전 비교 | 오래된 화면이 최신 변경을 덮어쓰는 문제 | 충돌 후 최신 상태 비교·재저장 필요 |

## Git 원고와 정적 공개 화면

### 문제와 조건

포트폴리오에 필요한 개발 경험과 학습 기록이 여러 곳에 분산. 프로젝트에서 작성한 학습 문서를 다시 활용하고 팀원과 공유할 공간 필요. 본인이 다시 읽는 용도를 우선.

공개 글을 읽을 때마다 일본 리전 API에 본문을 요청하면 서버 처리와 네트워크 왕복에 의존. 원고 편집·웹 관리·독자 열람이 같은 실행 경로를 사용할 필요는 없음.

### 선택과 변화

본문은 Git Markdown, 제목·소속·발행 상태는 MySQL, 공개 결과물은 Pages로 분리. Node 빌더가 원고와 API 자료를 결합해 HTML·검색 자료·이미지 생성.

기존 웹 본문 편집·API 원고 접근·블로그 전용 MCP는 제거된 상태.

아키텍처·ERD도 텍스트 원문으로 관리. 문서 설명과 도식의 변경을 같은 Git 이력에서 검토.

### 검증과 한계

빌드 검사는 원고 누락, 수집 중 revision 변경, 첨부 접근 거부, 잘못된 MIME·이미지 시그니처와 리다이렉트 처리 포함. 실패 시 새 결과를 확정하지 않는 계약 확인용.

공개 본문·이미지는 API와 분리되지만 새 빌드와 관리자 작업은 API에 의존. 최종 검증부터 배포 완료까지 모든 변경을 단일 트랜잭션으로 묶지 않음. 요청 수·CPU·응답 시간의 전환 전후 개선율은 미측정.

## JPA와 jOOQ의 역할 분담

### 문제와 선택

JPA 저장·도메인 변경과 jOOQ 목록·집계 조회를 함께 사용. 수동 jOOQ DDL을 별도로 유지하면 엔티티와 두 곳의 스키마를 수정해야 하는 문제.

원본 도메인 선행 컴파일 → 앱과 같은 Hibernate의 DDL 출력 → jOOQ 타입 생성 → 앱 컴파일로 연결. 개발·CI 코드 생성에서 실제 DB 접속 의존 제거.

### 비용과 검증

도메인이 서비스·생성된 jOOQ 타입에 의존하지 않도록 경계 유지 필요. 엔티티 위치·이름 정책·dialect 변경 시 생성 태스크도 점검.

과거 검증은 DDL 해시 일치, clean 생성 순서, 재실행의 up-to-date 동작, API JAR의 빌드 전용 산출물 제외. 운영 DB 이관은 별도 책임. 상세 대안과 검증 시점은 [독립 ADR](/ken-blog/post/post-f69cf0bb-68a1-4b72-b6c9-6aea1ed04db9/)에서 관리.

jOOQ와 JPA의 속도 차이를 입증한 결정은 아님. 조회 수·응답 크기의 회귀 기준은 [실험과 성능 검증](/ken-blog/post/post-b46d1115-97ad-4d25-a9d9-1801b56857db/) 참조.

## 편집 버전으로 오래된 저장 거부

### 문제와 선택

같은 글을 두 화면에서 조회한 뒤 순서대로 저장하면, 늦은 저장이 먼저 저장한 변경을 덮어쓸 수 있음. 상세 응답의 `editVersion`을 편집 요청의 `baseVersion`으로 보내고 글 잠금 안에서 비교.

다르면 409. 같으면 제목·요약·분류·태그·소속·순서·관련 프로젝트를 한 트랜잭션에서 변경하고 버전 증가. 버전은 서비스에서 관리하며 JPA `@Version`과 혼용하지 않음.

### 적용 범위와 검증

글 메타데이터·소속·순서 요청에 버전 비교 적용. 출간 변경은 기준 버전 입력 없이 버전 증가. 첨부·위키 선언 교체는 별도 계약으로 마지막 저장 적용. 시리즈 메타데이터는 `baseUpdatedAt` 사용.

영속성 검사는 같은 버전의 동시 저장 중 하나만 성공하는지, 실패 시 제목·태그 등 일부 변경이 남지 않는지, 분류 삭제 뒤 이전 버전 요청을 거부하는지 확인. 화면은 충돌 시 사용자 입력 보존.

자동 병합은 제공하지 않음. 최신 내용을 다시 읽고 사용자가 유지할 변경을 선택해야 함.
