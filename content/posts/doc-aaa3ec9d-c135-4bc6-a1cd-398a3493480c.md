공개 사이트와 API의 배포 경로 분리. Pages에는 Node가 생성한 정적 산출물, OCI VM에는 Spring Boot JVM 이미지 반영. 외부 MySQL과 이미지 원본은 애플리케이션 교체와 별도로 유지.

## 변경별 반영 경로

| 변경 | 반영 경로 | 완료 조건 |
| --- | --- | --- |
| Markdown 원고 | main의 대상 경로 변경 → Pages | 공개 대상 원고가 새 HTML에 반영 |
| 제목·분류·소속·문서 순서·발행 상태 | 관리자 API → MySQL → 수동 Pages 실행 | DB 저장과 새 공개 화면 모두 확인 |
| 템플릿·CSS·TypeScript | 프런트 검사 → Pages | 새 정적 자산 배포 |
| API 소스·런타임 설정 | CI 검사 → JVM 이미지 아카이브 → 운영 수동 반영 | 실제 컨테이너 이미지와 HTTPS 계약 확인 |
| 이미지·기술 아이콘 | 원본 파일·DB 정보 준비 → API 조회 → Pages 수집 | 원본 접근과 정적 복사본 확인 |
| DB 스키마 | 복사 DB 이관 검증 → 운영 SQL → API 검증 | 자료 보존·새 계약 확인 |

DB 변경 자체는 GitHub Actions를 실행하지 않음. API 코드만 바뀌면 Pages 자동 실행 대상에 포함되지 않을 수 있으므로 공개 계약 변경 시 사이트 반영도 확인.

## Pages 빌드·배포

1. 원고·웹 소스·npm 설정·사이트 빌드 코드 등 지정 경로의 main 변경 또는 수동 실행.
2. 의존성 설치, Node 검사와 사이트 빌드 준비.
3. 공개 스냅샷과 Git 원고 수집, 이미지 출처·경로·크기·MIME·시그니처 검증.
4. 임시 디렉터리에 전체 페이지 생성.
5. 공개 revision 재확인 후 검증된 산출물 확정.
6. Pages artifact 전달, 배포 직전 main의 사이트 입력 변경 확인.
7. 실제 공개 주소의 글·이미지·탐색 확인.

원고 누락·잘못된 이미지·revision 변경 시 실패. 기존 최종 산출물은 검증된 새 결과로 교체하기 전까지 유지. 성공한 전체 빌드에는 공개 취소된 글과 불필요한 옛 파일을 이전 출력에서 복사하지 않음.

브라우저 JS·CSS 번들은 입력 해시와 산출물 검사를 통과하면 재사용. 페이지 전체 재생성과 웹 번들 재생성은 별도 단계.

## API 배포

API CI의 검증 job은 Gradle·MySQL 통합 검사와 배포 관련 검사를 수행. ARM64 이미지 job은 PR에서 생략하며 검증 job 성공 후 실행. Buildpacks로 일반 JVM 이미지를 생성하고 실제 HTTP 계약 검사 후 아카이브·SHA-256·출처 정보 보관.

운영자는 배포할 커밋·이미지를 선택하고 아카이브 해시·이미지 ID 대조 후 Compose에 반영. 현재 CI에 운영 서버 자동 교체 단계는 없음.

| 운영 구성 | 계약 |
| --- | --- |
| API | 1 CPU, 기본 1,536MiB 한도. 일반 JVM·비루트 사용자 |
| 호스트 포트 | loopback에 바인딩, 기본 18081 → 컨테이너 8080 |
| Caddy | 공개 HTTPS 진입, 허용 API 경로 전달 |
| MySQL | Compose 밖의 외부 DB |
| 이미지 원본 | 전용 영속 디렉터리를 API에 읽기 전용 마운트 |
| 스키마 | `APP_JPA_DDL_AUTO=validate`, `APP_SQL_INIT_MODE=never` |
| 환경 값 | 저장소 밖 운영 설정 파일 사용 |

이미지 태그만으로 재현 범위를 정하지 않고 실제 이미지 ID·빌드 자료·환경 구성을 함께 보관.

## CI 결과의 의미

| 검사 | 확인 범위 | 추가 확인 |
| --- | --- | --- |
| 백엔드 verify | 빌드·격리 DB·인증·배포 계약 | 실제 운영 DB·TLS·네트워크 |
| JVM 이미지 | ARM64 컨테이너와 HTTP 동작 | 운영 반영 후 공개 진입점 |
| Frontend | 타입·Node·모의 API 브라우저 검사 | 운영 계정과 실제 API 연동 |
| Pages build | 공개 자료 수집·정적 생성 | 실제 호스팅 반영 |
| Pages deploy | 해당 artifact 발행 | 공개 화면의 본문·이미지·탐색 |

Frontend 검사는 Pages deploy의 직접 선행 job이 아님. Pages 성공만으로 브라우저 검사 결과를 대신하지 않음.

## API·DB·관리 화면의 동시 전환

편집 버전·스냅샷 계약처럼 API와 화면이 함께 바뀌는 경우의 순서.

1. 구·신 응답을 처리할 빌더와 새 화면 준비.
2. 복사 DB에서 SQL 이관과 새 API 기동·자료 보존 확인.
3. 관리자 쓰기 중지, 백업과 복원 가능성 확인.
4. 명시 SQL 적용, 검증된 API 이미지 반영.
5. Pages 배포 후 관리자 화면 새로고침.
6. 인증·글 조회·편집 충돌·발행·이미지·공개 스냅샷 확인 후 작업 재개.

롤백 시 API 이미지뿐 아니라 관리자 화면·환경·Caddy의 계약도 함께 확인. 추가한 열·테이블은 즉시 삭제하지 않고 구버전과의 호환 범위 검토.

## 상태 점검과 장애 영향

`/actuator/health`로 기동 상태 확인. 글 조회·인증·이미지와 사이트 전체 발행 성공은 별도 점검.

| 상황 | 영향·확인할 항목 |
| --- | --- |
| API·DB 장애 | 로그인·관리·새 빌드 실패 가능. 기존 Pages 본문은 별도 제공 |
| 이미지 디스크 장애 | 원본 제공·새 이미지 수집 실패. 기존 정적 이미지와 구분 |
| Pages 빌드 실패 | 현재 공개본과 실패한 변경 분리, 원인 수정 후 재실행 |
| 발행 취소 후 옛 글 노출 | DB 상태·Pages 실행·배포 결과·캐시 순서로 확인 |
| DB 이관 불일치 | 운영의 스키마 검증 실패 또는 새 계약 오류. 복사 DB 검증과 이관 기록 대조 |

## 백업·복구 범위

| 자료 | 함께 보존할 내용 |
| --- | --- |
| Git 원고·웹 소스 | 커밋·slug별 파일·배포 입력 |
| MySQL | 메타데이터·연결·계정·세션·인증 상태·이관 전 스키마 |
| 이미지 디스크 | 객체 키·실제 파일·참조 정보·내용 해시 |
| 운영 구성 | 이미지 ID·아카이브·Compose·Caddy·접근 제한된 환경 파일 |
| 공개 사이트 | 대응하는 원고·DB·이미지 상태와 재생성 가능성 |

복구 후 FK·글 주소·첨부 해시·공개 대상 대조 필요. 인증 상태 누락은 일반 재시작에서 자동 복구하지 않으며 별도 복구 절차 사용.

자동 백업의 주기·보존 기간, 실제 복구 소요 시간과 허용 데이터 손실 범위는 미확정.
