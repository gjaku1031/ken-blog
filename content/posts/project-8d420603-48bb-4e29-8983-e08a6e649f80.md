## 개발 배경과 핵심 문제

손을 쓰기 어려운 가족이 컴퓨터를 쓸 수 있도록, 자주 쓰는 Bash 명령을 음성으로 실행하는 스크립트 도구를 먼저 만들었음. 실제 사용에는 도움이 되었지만 새 기능이 필요할 때마다 직접 스크립트를 추가해야 했음. 이 경험을 팀원들과 논의해 명령 몇 개를 대신 입력하는 도구에서, 여러 단계의 웹 작업을 기록하고 찾아 재사용하는 앱으로 범위를 넓혔음.

다음 제약 안에서 설계함.

- **사용자**: 마우스·키보드 조작을 여러 번 반복하기 어려움. 입력은 음성과 최소한의 선택으로 끝나야 함.
- **대상 사이트**: 예매·민원 사이트는 외부 서비스라 구조를 바꿀 수 없고, 로그인·본인 인증·결제 단계가 있음.
- **인력·기간**: 4인 팀이 대회 일정(2025.04~11) 안에 클라이언트·백엔드·AI 서버를 함께 개발함.
- **운영 비용**: 클라우드 서버를 상시 운영할 비용을 줄여야 하지만, 명절 열차 예매처럼 접속이 특정 시점에 몰리는 상황도 가정함.

이 제약에서 다음 네 문제를 핵심 문제로 정의함.

- **P1 작업 확장성**: 지원할 웹 작업을 늘릴 때 개발자의 코드 수정 없이, 사용자가 기록한 작업을 다른 사용자가 재사용할 수 있어야 함.
- **P2 의도 검색**: 등록할 때와 다른 표현으로 요청해도 같은 작업의 경로를 찾아야 함.
- **P3 실행 통제**: 로그인·본인 인증·결제는 사용자가 직접 하고, 비밀번호 같은 입력값이 경로에 저장·공유되지 않아야 함.
- **P4 비용 대비 확장**: 평소에는 클라우드 상시 비용 없이 운영하고, 접속이 몰리면 서버 처리 용량을 늘릴 수 있어야 함.

## 핵심 문제별 설계와 검증

검토한 대안 표와 검증 상세는 [주요 기술적 의사결정](/ken-blog/post/doc-d8735f2c-c9bf-45fa-bcac-a692eb4dc739/)에 있음.

### P1. 사용자 기록을 단계 연결 경로로 저장

- **문제**: 초기에는 개발자가 준비한 작업만 실행할 수 있어, 지원 작업을 늘릴 때마다 개발자가 경로를 등록해야 했음
- **결정**: 사용자가 브라우저에서 수행한 클릭·입력·이동을 단계로 기록해 `ROOT -HAS_STEP→ STEP -NEXT_STEP→ STEP` 구조의 경로로 저장함[* [경로 저장·검색 코드](https://github.com/Vovvser/vowser-agent-server/blob/d94eaf5/app/services/neo4j_service.py)]
  - 처음부터 사용자 조작을 녹화하는 방식으로 정했고, 다른 기록 방식과는 비교하지 않았음
  - 저장소: 관계형 DB로는 경로를 단계 테이블의 자기 참조와 재귀 조회로 이어야 했음. 당시 실험에서 데이터가 많을수록 Neo4j의 그래프 탐색이 빨랐고, 경로 구조를 그래프로 시각화해 볼 수 있고 벡터 검색도 같은 DB에서 쓸 수 있어 Neo4j를 택함. 당시 실험의 조건·수치는 남아 있지 않음
  - 선택 이유: 작업 지식을 사용자의 실제 조작에서 얻어 개발자 병목을 없앰. 작업 의도(`taskIntent`)와 임베딩을 첫 단계로 가는 관계에 두어 검색 단위와 실행 단위를 한 경로로 묶음
- **대가**: 기록마다 단계 ID가 달라 같은 화면의 단계도 공유되지 않고, 경로 하나를 저장할 때 단계 수에 비례한 개별 쿼리가 실행되어 중간에 실패하면 일부만 저장됨
- **검증**: 저장할 때 작업 의도의 임베딩을 `HAS_STEP` 관계에 넣고 검색이 이 관계의 벡터 인덱스를 조회하므로, 기록한 경로는 별도 등록 없이 다음 검색부터 후보가 됨. 시연 경로는 팀이 준비했고(KTX 예매, 주민등록등본 발급, 날씨, 뉴스, 네이버 웹툰), 팀 밖 사용자가 기록한 경로나 재사용 횟수는 없음
  - 저장소 선택은 2026년 사후 재현 실험에서 MySQL과 다시 비교함. 신규 경로 등록의 차이는 DB 종류보다 트랜잭션 경계에서 더 크게 났음[* 2026-09-29, 합성 경로 3만 개·읽기:쓰기 90:10(위 행)과 경로 1천 개(아래 행). DB 컨테이너 1 CPU·3GiB, Python 워커 1 CPU·1GiB, tmpfs 저장, 임베딩 생성 제외]

| 측정 항목(신규 경로 등록, 중앙값) | 비교 A | 비교 B |
| --- | ---: | ---: |
| DB 종류: MySQL / Neo4j | 7.14ms | 26.50ms |
| Neo4j 트랜잭션 경계: 단계별 커밋 / 배치 한 번 | 164.34ms | 10.35ms |

상세 조건과 나머지 연산은 [주요 기술적 의사결정](/ken-blog/post/doc-d8735f2c-c9bf-45fa-bcac-a692eb4dc739/)에 있음.

### P2. 의도 임베딩 검색과 낮은 유사도의 재검색

- **문제**: 같은 작업을 사람마다 다르게 말해, 등록 문장과 요청 문장이 글자로 일치하지 않음
- **결정**: 요청과 작업 의도를 OpenAI 임베딩으로 바꿔 유사도로 찾고, 최고 유사도가 0.43 미만이면 LLM의 의도·키워드 분석으로 등록 경로를 다시 찾음[* [LangGraph 검색 흐름](https://github.com/Vovvser/vowser-agent-server/blob/d94eaf5/app/services/langgraph_service.py)]
  - 키워드 검색이나 LLM 분류와 비교하지 않고 처음부터 임베딩 검색으로 시작함
  - 임계값 0.43은 예시 요청으로 실험해 정했으나 실험 기록은 남아 있지 않음
  - 초기 구현: 사용 중인 Neo4j 환경에서 GDS 함수를 쓸 수 없어 코사인 유사도 계산을 Python으로 옮기고 경로 모델은 유지함[* [GDS 대체 커밋](https://github.com/Vovvser/vowser-agent-server/commit/b4dcf835cadac6da12bf11619965c9e7aeaea72a)]
- **대가**: 요청마다 임베딩 생성과 경우에 따라 LLM 호출이 붙음. 등록되지 않은 작업의 경로를 새로 만들지는 않음
- **검증**: 시연에서 날씨를 묻는 표현으로 네이버 날씨, 추상적인 시사 질문으로 뉴스 작업이 선택됨. 검색 정확도를 정량으로 측정한 자료는 없음

### P3. 실행은 사용자 PC에서, 인증은 사용자 손에

- **문제**: 예매·민원 작업에는 로그인·본인 인증·결제가 들어 있어 서버가 사용자를 대신해 끝까지 수행할 수 없고, 비밀 입력값을 서버에 두면 위험함
- **결정**: 서버는 경로만 반환하고 Playwright 실행기를 사용자 PC에 둠. 입력 단계는 회원 정보 자동 입력 → 경로에 저장된 입력값 → 사용자 입력 순으로 값을 정하고, 대기 단계는 사용자가 완료를 확인할 때까지 멈춤[* [경로 실행기](https://github.com/Vovvser/vowser-client/blob/8065803/shared/src/commonMain/kotlin/com/vowser/client/api/PathExecutor.kt)]
  - 클라이언트: 이후 장애인용 키오스크나 관공서 태블릿으로 넓힐 것을 고려해 데스크톱·Android·iOS가 코드를 공유하는 Kotlin Compose Multiplatform으로 만듦[* [공통 모듈 대상 설정](https://github.com/Vovvser/vowser-client/blob/8065803/shared/build.gradle.kts)]. React Native와 비교했고, 팀원이 모두 Java 개발자여서 개발 속도를 위해 Kotlin을 택함
  - 기록할 때는 20자 이하의 검색어·일반 텍스트만 입력값으로 남기고 비밀번호 칸의 값은 저장하지 않음[* [경로 저장 변환](https://github.com/Vovvser/vowser-client/blob/8065803/shared/src/commonMain/kotlin/com/vowser/client/api/PathApiClient.kt)]
- **대가**
  - 사용자 PC에 브라우저 실행 환경이 필요함. 사이트 구조가 바뀌면 저장된 선택자가 맞지 않아, 여러 선택자와 URL 기반 대체 이동을 차례로 시도함
  - 입력 칸 분류가 `type`·`name`·`placeholder` 속성에 의존해, 일반 텍스트 칸으로 분류된 이름·전화번호 같은 20자 이하 입력은 경로에 저장되어 공유될 수 있음. 상세는 [보안 설계](/ken-blog/post/doc-005871e6-b37a-4873-bbab-0f93aaf467e2/)
- **검증**: 개발 당시 실제 사이트 시연에서 아래 단계까지 도달함

| 시연 작업 | 도달한 단계 |
| --- | --- |
| 날씨·뉴스 조회 | 날씨를 묻는 표현에서 네이버 날씨, 추상적인 시사 질문에서 뉴스 표시 |
| 네이버 웹툰 | 요청한 웹툰 화면 표시 |
| 열차(KTX) 예매 | 중간 로그인 단계에서 사용자 입력을 기다린 뒤 결제 직전 단계까지 진행 |
| 주민등록등본 조회 | 사용자 인증 후 문서가 표시되는 단계 |

> 서버는 경로를 찾아 돌려줄 뿐이고, 로그인·본인 인증·결제는 사용자 PC의 브라우저에서 사용자가 직접 끝냄.

### P4. Proxmox 기본 실행과 AWS 확장

- **문제**: 관공서·소규모 사업장에 두는 접근성 오픈소스 앱이라 평소 요청은 적고, 서버를 클라우드에 상시 실행하는 비용은 감당하기 어려웠음. 반면 명절 귀성 예매처럼 잠깐 접속이 몰리는 시점에도 서비스가 멈추면 안 됐음
- **결정**: 평소에는 다루기 익숙한 Proxmox 서버의 Docker Compose로 Spring Boot·FastAPI를 실행하고, 같은 서버를 AWS ECS Fargate 서비스로도 구성해 부하가 오르면 기동함
  - P3에서 브라우저 조작을 사용자 PC에 두어 서버 역할이 경로 검색·저장과 인증으로 좁혀졌고, 그래서 확장 대상이 Spring Boot·FastAPI 두 컨테이너로 줄었음
  - 비교한 대안: AWS 상시 운영(평소에도 비용이 계속 듦), Proxmox 단독 운영(몰리는 시점에 용량을 늘릴 수 없음). 비용은 수치로 계산하지 않음
  - 전환: CloudWatch의 CPU·메모리 경보가 EventBridge·Lambda를 거쳐 Fargate 서비스를 기동하고 Route 53 레코드를 바꿈. 앱은 다음 DNS 조회부터 ALB로 요청함
- **대가**: 두 환경의 이미지·설정을 함께 관리하고, Proxmox에서 RDS로 가는 Site-to-Site VPN을 유지함. DNS 캐시가 남는 동안 요청이 두 환경으로 나뉘고, 이미 열린 연결은 옮겨지지 않음
- **검증**: Fargate 기동과 DNS 변경을 구현·실습함. 전환 시간·비용 절감률·무중단 여부는 측정하지 않음. 팀은 k6로 앱 사용자 접속 증가를 흉내 내 지표를 보며 설정을 조정했음 [확인 필요]
