# 선택적 Redis Cloud 공개 본문 캐시

P1-04는 익명 방문자가 요청한 **출간·PUBLIC 글 상세의 본문**만 Redis Cloud에 잠시 보관하는 단계. MySQL은 글의 원본과 매 요청의 출간·공개 권한 판단을 계속 담당. 기본값은 캐시 비활성이고, Redis 없이 API·MySQL·Spring Session JDBC만으로 동일한 게시글 응답 제공. 활성 설정·실제 검증·main 반영 상태는 [P1-04 계획](../planning/issues/P1-04.md)에 기록. 이번 캐시는 새 HTTP 경로, 브라우저 글 화면 또는 공개 HTTPS API 배포를 뜻하지 않음.

## 캐시 대상과 동작

| 경로/데이터 | 캐시 처리 |
| --- | --- |
| 익명 `GET /api/v1/posts/{slug}`의 `PUBLISHED`·`PUBLIC` 본문 | 설정 활성 시 선택적 캐시. 매 요청 MySQL 메타데이터 확인 후 현재 본문 해시 키 조회 |
| 공개 목록과 건수 | 캐시 제외. 기존 본문 없는 SQL 조회 유지 |
| 로그인 `USER`/`ADMIN` 상세, 익명 `PRIVATE` 직접 잠금, `DRAFT`, 없는 slug | 캐시 조회·저장 제외. 기존 권한·404·잠금 응답 유지 |
| 계정·JDBC 세션·CSRF·관리자 응답·첨부 메타데이터/원본 | Redis 전송·캐시 제외. 세션은 MySQL, 이미지 원본은 OCI Object Storage |

활성된 익명 상세는 먼저 MySQL에서 `PUBLISHED`/`PUBLIC`, ID·제목·slug·최초 출간 시각·본문 SHA-256을 확인. 이 조회는 본문 열을 읽지 않는 설계. 공개가 아니면 캐시를 읽지 않고 기존 잠금/404 계약 적용. 공개면 `{prefix}:v1:post-body:{id}:{bodySha256}`에서 본문 조회. hit 값의 UTF-8 크기와 SHA-256을 현재 DB 해시와 비교하며, 일치할 때만 제목·KST 출간일은 **DB 메타데이터**, 본문만 캐시 값으로 응답. SHA-256은 값·원본의 일치 확인용이며 Redis 전송 암호화나 비밀번호 보호 수단이 아님.

miss·손상 값·Redis 연결/명령 오류는 MySQL 원문 조회로 돌아감. 정상 공개 본문의 UTF-8 크기가 **256 KiB 이하**일 때만 기본 **TTL 300초**로 저장하며 빈 문자열도 유효한 캐시 값. 기존 게시글 본문 입력 상한 **1 MiB**는 유지하므로 그 사이의 큰 본문은 정상 제공하되 캐시하지 않음. hit 판정에는 Redis의 `STRLEN`과 `GET` 두 명령을 사용하므로, 캐시가 항상 더 빠르다는 가정 없이 요청 구간을 측정해야 함. DB가 중단되면 캐시가 있어도 공개 판정을 생략하지 않고 기존 503 오류 경계 유지. 키의 본문 해시는 수정 후 새 값으로 바뀌고, 수정·공개 범위 변경·철회·삭제 뒤 예전 소유 키 제거는 트랜잭션 커밋 후 최선의 노력으로 수행. 삭제 실패의 잔여 키도 현재 DB 공개 판단·해시 비교로 재사용 방지, TTL로 자연 만료. 동시 변경 중 이미 시작된 읽기는 DB 읽기 트랜잭션의 일관성 경계 적용.

## 외부 설정

Compose에는 Redis 컨테이너·호스트 포트·볼륨을 추가하지 않음. 설정은 저장소 밖의 로컬 `.env` 또는 실행 환경에서 주입하며 실제 host·username·password는 Git·Pages·공유 로그에 기록하지 않음. 다음은 **계약값**이며 캐시 활성 전에는 연결을 만들거나 추가 조회하지 않음.

| 변수 | 기본값과 의미 |
| --- | --- |
| `CACHE_REDIS_ENABLED` | `false`; 활성 시에만 외부 Redis 사용 |
| `CACHE_REDIS_HOST` | 빈 값; 활성 시 실제 호스트 필수, URL에 비밀번호 포함 금지 |
| `CACHE_REDIS_PORT` | `6379`; 제공된 Redis Cloud 포트에 맞춤 |
| `CACHE_REDIS_USERNAME` | 빈 값; 공급자가 요구할 때 설정 |
| `CACHE_REDIS_PASSWORD` | 빈 값; 외부 비밀값 |
| `CACHE_REDIS_TLS` | `true`; **서버가 TLS를 지원할 때만** 사용. 인증서 검증 우회 없음 |
| `CACHE_REDIS_PREFIX` | `ken-blog:public-posts`; 다른 서비스와 겹치지 않는 전용 접두사 |
| `CACHE_REDIS_TTL_SECONDS` | `300`; 소유 캐시 키의 만료 시간 |
| `CACHE_REDIS_CONNECT_TIMEOUT_MS` | `300`; 연결 대기 상한 |
| `CACHE_REDIS_COMMAND_TIMEOUT_MS` | `300`; 명령 대기 상한 |

활성화 시 host는 URL이나 사용자 정보가 없는 호스트명이어야 하며 빈 값·잘못된 포트·접두사·TTL·timeout 설정은 기동 단계에서 거부. 허용 범위는 포트 1~65535, 접두사 1~80자의 영문·숫자·`.`·`_`·`:`·`-`(첫 글자는 영문·숫자), TTL 1~86400초, 각 timeout 50~5000ms. username을 사용하면 password도 필수. 비활성 기본값에서는 Redis 클라이언트를 만들지 않음.

캐시 활성 시 서버 준비 뒤 단일 백그라운드 작업으로 Redis 연결을 시작. 연결 준비 중 요청은 기다리지 않고 MySQL 본문으로 우회. 짧은 연결·명령 timeout과 실패 후 5초 재연결 유예로 Redis 장애가 MySQL 읽기를 장시간 막지 않도록 설계. 장기 명령 적재·무한 재시도 없음. 애플리케이션 종료 시 연결 자원 정리. 캐시는 선택 기능이므로 연결 실패를 사용자 503으로 바꾸지 않고 DB 조회로 복구; DB 자체 장애는 별도 503. 키는 전용 prefix 아래에만 기록·삭제하며 `FLUSHDB`·`FLUSHALL`·전체 `KEYS`나 다른 서비스 키 조작 금지.

기존 외부 설정의 사전 확인에서 Redis Cloud `PING`의 `PONG`, 전용 임시 prefix의 TTL `SET`·`GET`·`DEL`은 성공했으나 그 설정은 `CACHE_REDIS_TLS=false`인 **평문 연결**. 연결된 클라이언트의 `PING` 10회 중앙값은 2.45ms, 최댓값은 2.5ms; Docker 기동 시간은 제외한 명령 수치일 뿐 API 캐시 성능이나 사용자 지연 개선의 증거가 아님. TLS 지원 여부는 제공 환경에서 별도 확인이 필요하고, 해시 검사는 평문 전송을 암호화하지 않음.

2026-09-26 최종 소스의 기존 검사 28개 통과. 격리 Buildpacks·Compose 이미지에서는 V6 반영, JDBC 로그인과 세션 ID 교체, 실제 Redis Cloud 공개 본문 키와 TTL, 비공개 전환 뒤 키 제거·본문 차단, 게시글 삭제를 확인. 첫 냉간 연결이 실패하더라도 HTTP는 Redis 연결을 기다리지 않고 DB 본문을 반환했으며 5초 유예 후 재연결에서 실제 캐시 키가 생성됨. 최종 JAR에서는 캐시 miss·hit, 손상 값의 해시 불일치, Redis 중단 시 DB fallback(해당 요청 15.1ms)·복구, API 재시작 후 기존 JDBC 세션 유지, 비공개 전환 무효화와 삭제를 확인. 이 15.1ms는 단일 장애 요청의 관찰값이며 장기 지연 보장 아님. 검증 전용 JAR·MySQL·Redis·이미지 프로젝트·볼륨과 Cloud 소유 prefix는 정리했으며 기존 VM 앱·Redis의 ID·이미지·시작 시각은 유지. main·CI·Pages 반영은 아직 예정이며 공개 HTTPS API 배포도 수행하지 않음.

백그라운드 연결 변경 **이전** JAR에서 DB 직접 조회와 Redis Cloud 캐시를 각각 10회 측정한 요청 중앙값은 1,050바이트 본문 12.26ms/20.51ms, 128 KiB 본문 15.42ms/21.50ms. 이 환경과 표본에서는 Cloud 경로가 더 느렸음. 변경 후 성능을 나타내거나 다른 부하에서의 개선·회귀를 보장하지 않으며 캐시 기본값은 비활성으로 유지.

## 확인·복구 경계

1. 비활성 기본값에서 Redis 설정 없이 API 기동, 익명 공개/회원 비공개 조회와 JDBC 로그인 유지 확인.
2. 격리된 MySQL·API·검증 전용 Redis에서 공개 상세 miss→저장→hit, TTL·해시·빈 본문·256 KiB 경계 및 hit 시 본문 SQL 제외 확인. 메타데이터 권한 SQL은 항상 유지.
3. 비공개·초안·목록·로그인 상세와 잘못된 slug에서 캐시 키 생성/접근 없음, 잘못된 값 삽입 시 원본 DB fallback 확인.
4. 본문·slug·공개 범위·출간 상태·삭제를 바꾼 뒤 남은 오래된 키가 있어도 이전 본문·비공개 내용 반환 없음 확인. Redis 중단·접속 거부·복구 뒤 DB 조회와 JDBC 세션 유지 확인. DB 중단은 캐시 hit와 무관하게 503 확인.
5. 외부 Redis Cloud는 소유한 무작위 검증 prefix의 임시 키로만 연결·TTL·명령 지연을 확인하고 그 키만 정리. 기존 운영 자원이나 공급자 정책 변경 없음. 실측은 앱 시작/컨테이너 기동 시간을 제외한 요청/명령 구간으로 기록.

위 목록은 격리 검증의 확인 범위이며 실행 결과는 [P1-04 계획](../planning/issues/P1-04.md)에 기록. 게시글 공개 범위와 응답은 [게시글 API](posts.md), DB 해시·Flyway는 [게시글 저장 기반](persistence.md), 로컬 이미지·Compose 범위는 [런타임 안내](runtime.md) 참고.
