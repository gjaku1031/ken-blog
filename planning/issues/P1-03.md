## 구현 범위

### 1. 저장소 연결

- 기존 OCI Object Storage의 S3 호환 API와 Customer Secret Key 사용. Kotlin에서 AWS SDK for Java v2의 S3 클라이언트를 사용하되 서비스와 문서의 이름은 OCI Object Storage로 통일.
- HTTPS endpoint·도쿄 region·bucket·access key·secret key를 외부 주입. SigV4와 path-style 설정을 명시하고 현재 endpoint로 실제 호환성 확인.
- 새 버킷·키·유료 서비스 생성, 기존 버킷 공개 전환·권한 변경 없음. 기존 운영 설정 파일을 수정하지 않고 검증 전용 외부 설정 사용.
- 저장소가 설정되지 않은 기본 실행에서도 기존 로그인·게시글 기반은 기동 가능하게 구성. 미설정 상태의 첨부 API는 명시적 503, 가짜 저장 성공이나 로컬 파일 대체 없음. 부분적으로만 설정된 값은 잘못된 설정으로 기동 실패.
- 파일은 이번 기능 전용 object key 접두사 아래에 저장. 임의 UUID로 이름을 만들고 사용자 입력 파일명·경로·URL을 저장소 경로로 사용하지 않음. 검증은 실행별 추가 접두사로 분리.

### 2. 이미지 입력과 파일 정보

- 최초 지원은 **JPEG·PNG, 파일당 10 MiB 이하**, 요청당 파일 하나. WebP·GIF·SVG·문서·동영상은 이번 범위 밖.
- 확장자와 요청 Content-Type만 신뢰하지 않고 파일 시그니처·디코딩 가능한 이미지인지 확인. 반환 Content-Type은 서버가 판별한 값으로 결정.
- 디코딩 전 가로·세로·총 픽셀 수 상한을 확인해 큰 압축 이미지의 메모리 사용 제한. 기본 상한은 한 변 8,192픽셀, 총 2,000만 픽셀. 이미지 크기를 바꾸거나 메타데이터를 재가공하는 기능은 추가하지 않음.
- 원본 파일명은 화면 표시용 메타데이터로만 보관. 제어문자·길이·경로 문자 처리 규칙을 정하고 HTTP 헤더에는 안전한 인코딩 적용.
- Flyway `V4__create_attachments.sql`로 첨부 ID·object key·원본 파일명·판별 MIME·바이트 크기·업로드 계정·상태·생성/변경 시각 저장. 사용자 FK와 object key 고유 제약 포함.
- 게시글과의 연결은 글 편집·출간 흐름을 구현할 때 추가. 현재 없는 공개 범위나 임시 게시글을 만들어 넣지 않음.

### 3. 관리자 HTTP 계약

모든 경로는 `/api/v1/admin/attachments` 아래에 배치. 세션 인증과 ADMIN 역할 필요. POST·DELETE는 기존 CSRF 검증 유지.

| 요청 | 동작 |
| --- | --- |
| `POST /api/v1/admin/attachments` | multipart 이미지 검증→저장→READY 메타데이터 반환, 201 |
| `GET /api/v1/admin/attachments/{id}` | 첨부 메타데이터와 처리 상태 반환 |
| `GET /api/v1/admin/attachments/{id}/content` | READY 파일을 Spring을 통해 스트리밍 다운로드 |
| `DELETE /api/v1/admin/attachments/{id}` | 이번 기능의 첨부 객체와 메타데이터 삭제, 재시도 가능 |

비공개 버킷 유지. 공개 URL·공유 링크·presigned URL·브라우저 직접 업로드는 제공하지 않음. 파일 응답은 확인된 MIME과 `nosniff`, 안전한 파일명 및 다운로드용 Content-Disposition 사용. 관리 파일은 공유 캐시 대상에서 제외.

오류는 기존 ProblemDetail 사용. 입력 오류 400, 미인증 401, 권한·CSRF 403, 없는 첨부 404, 아직 다운로드할 수 없는 처리 상태 409, 크기 초과 413, 지원하지 않거나 손상된 이미지 415, 저장소 미설정·일시적 저장소/DB 연결 장애 503으로 구분. 비밀 설정·공급자 오류 원문·내부 object key를 오류 응답에 노출하지 않음.

### 4. DB와 파일 저장 실패 처리

DB와 OCI Object Storage를 하나의 트랜잭션으로 묶을 수 없으므로 `PENDING → READY`, 삭제 시 `DELETING`의 작은 상태 흐름으로 관리. 외부 네트워크 요청 동안 DB 트랜잭션을 길게 유지하지 않음.

- 업로드 전에 PENDING 메타데이터와 서버 생성 key를 기록. 이 저장이 실패하면 파일 업로드 시작 없음.
- 업로드와 READY 갱신이 모두 성공한 경우만 201 반환. 중간 실패 시 이번 객체만 삭제해 보상 처리.
- 파일 정리까지 실패하거나 응답 유실로 업로드 성공 여부가 불명확하면 미완료 행을 유지. 성공 상태로 숨기거나 무작위 새 key에 자동 재업로드하지 않음.
- 삭제는 DELETING 기록→객체 삭제→메타데이터 삭제 순서. 파일 삭제 실패 시 추적 행 유지. 파일이 이미 없는 경우는 정리 가능한 상태로 취급하고 DB 삭제 재시도 허용.
- 중간에 프로세스가 종료돼 남은 PENDING·DELETING 행은 관리자 메타데이터 조회와 삭제 재시도로 정리할 수 있도록 안내. 운영자가 대상을 찾을 수 있는 읽기 전용 조회 절차도 문서화.
- 이번 범위에는 자동 복구 배치·메시지 큐·분산 트랜잭션·관리 목록 화면 없음. 기존 객체를 탐색하여 일괄 삭제하는 기능 없음.

## 검증 방법

신규 테스트 클래스·시나리오 작성 없음. 기존 검사에서 V4 적용 등 변경된 계약에 필요한 부분만 수정. 로컬 빌드와 격리된 환경의 실제 HTTP·CLI 결과를 구분하여 기록.

1. `-DskipTests clean package`로 운영 코드·기존 테스트 컴파일 확인. 저장소 미설정 기본 기동과 기존 인증 기능 유지 확인.
2. 기존 배포본과 다른 MySQL·API·계정·포트 및 실행별 object key 접두사 사용. 승인한 검증 파일만 업로드하며 실제 OCI 쓰기 권한 확인.
3. 실제 HTTP 관리자 로그인·CSRF 준비→JPEG/PNG 업로드 201→메타데이터 조회→다운로드 바이트 일치→삭제→404 확인.
4. 익명·일반 사용자·CSRF 누락 요청 거부, 용량 초과·확장자 위장·손상 이미지 거부 확인.
5. 검증 전용 endpoint·권한 조건으로 저장소 실패를 재현하고 DB 연결 장애도 분리 확인. 상태 행·객체가 처리 규칙대로 남거나 제거되는지 확인. 기존 버킷 IAM이나 정책을 변경하여 장애를 만들지 않음.
6. 중단된 업로드·삭제를 재시도해 이번 기능의 미완료 객체만 정리 가능한지 확인. 실제 OCI 접근 검증과 인위적인 실패 재현을 별도 기록.
7. Buildpacks 실행 이미지와 격리 Compose 최소 기동, 원격 CI·Pages와 공개 도면 확인. 기능 검증과 VM 상시 배포를 구분.
8. 이번에 만든 객체·검증 DB·컨테이너·볼륨·임시 비밀 파일만 정리. 기존 버킷 객체와 기존 앱·Redis 유지 확인.

## 실제 구현·검증 — 2026-09-25 UTC

- AWS SDK v2에 SigV4·path-style·chunked encoding 비활성화·요청/응답 checksum `WHEN_REQUIRED` 적용. OCI의 기본 chunked encoding 거부를 별도 Python 클라이언트로 확인한 뒤 Spring HTTP에서도 실제 저장·조회 검증.
- V4에 `pending_cleanup` 포함. 불확실한 PUT은 추적 행 유지. 활성 PENDING은 2분간 삭제 거부, 오래된 PENDING은 DELETING 전환 뒤 다시 2분 유예. 유예 중 DELETE는 409, 객체와 행 정리가 끝나야 204. 자동 복구 작업 없음.
- `./mvnw -B -DskipTests clean package` 성공. 운영 코드·기존 테스트 컴파일 수행. 신규 테스트 코드 없음, 기존 마이그레이션 검사의 기대 버전만 V1~V4로 변경.
- 저장소 미설정 기본 실행에서 로그인 성공·첨부 503, 부분 설정은 기동 실패 확인.
- 실제 Spring HTTP로 PNG·JPEG 업로드 201/READY, 메타데이터 200, HTTP 다운로드·OCI 직접 GET 모두 원본과 바이트 일치. 다운로드 MIME·Content-Disposition·nosniff·no-store 확인.
- 익명 401, 일반 USER·CSRF 누락 403, 위장 확장자·MIME·손상 이미지·허용하지 않는 형식 415, 경로/과도한 파일명 400, 10 MiB 초과 413, 중복 multipart 파일 400 확인. 픽셀 상한 검증 포함.
- API 재시작 후 기존 쿠키로 관리자 인증·첨부 다운로드 유지. DELETE 204 후 메타데이터·실제 OCI 객체 조회 404 확인.
- 검증 전용 실패 endpoint와 가짜 키로 저장소 읽기·쓰기·삭제 503 재현. DELETING 추적 행 유지와 정상 endpoint 복구 후 삭제 재시도 확인.
- 중단 업로드는 검증 DB의 READY→PENDING 변경으로 상태를 구성. 생성/변경 시각을 검증 DB에서 앞당겨 활성 상태 거부·두 단계 유예·재시도 204 확인. 실제 프로세스 강제 종료나 4분 실시간 대기 검증은 아님.
- 검증 DB에만 UPDATE 거부 트리거를 넣어 실제 OCI PUT 이후 READY 갱신 실패 재현. 고정 500·PENDING 추적 유지, 트리거 제거 후 정리 확인. DB 연결 장애와 제약/갱신 오류를 같은 503으로 취급하지 않음.
- 검증 MySQL만 중단했을 때 첨부 조회 503 ProblemDetail, 응답 대기 30.0초. 복구 후 기존 로그인 유지, 첨부 행 0개·실행별 OCI 접두사 객체 0개 확인.
- Buildpacks 이미지 생성과 별도 Compose API·MySQL 기동 성공. 이미지에서도 실제 PNG 업로드·다운로드 바이트 일치·삭제·404, Swagger multipart 경로 확인.
- 첫 재시작 검증은 같은 JAR을 Buildpacks가 다시 패키징하는 시점과 겹쳐 기동 실패. 빌드 종료 후 고정된 산출물로 재실행하여 통과. 제품 코드 수정으로 처리한 오류 아님.
- 검증 API·MySQL·Compose 컨테이너와 전용 볼륨 정리 완료. 기존 VM 앱·Redis의 ID·이미지 ID·시작 시각 동일, healthy 유지.
- 라이트/다크 PNG 시각 확인, SVG 내장 아이콘·텍스트 경로 및 공개 복사본 일치 확인. 로컬 학습 자료는 Git 제외.

기존 VM은 새 API로 교체하지 않은 상태. 공개 HTTPS·도메인·브라우저 로그인·업로드 UI와 공개 이미지 경로는 후속 범위. 원격 CI·Pages 결과는 push 이후 별도 기록.

## 진행·기록 방식

이 계획 승인 후 구현 시작. 이전 P1-02A 승인이나 ‘다음’ 요청을 이 세부 구현 범위의 승인으로 간주하지 않음. 기존에 합의한 구현·리뷰 분담과 코드 기준 유지.

커밋은 저장소/메타데이터 기반, HTTP 흐름/실패 처리, 문서/도면 등 검토 가능한 변경 목적에 따라 구분. 같은 author date의 여러 커밋 허용. 개발 일정의 마지막 author date는 2026-06-02이며 후속 기능 기록은 여기서 이어서 배치. P1-02B의 정정·검증 문서 두 커밋은 예외적으로 실제 날짜인 2026-09-25 UTC를 사용한 기록. 실제 검증·push 날짜와 author date는 완료 보고에서 구분. 이번에는 기존 커밋 재작성·강제 푸시 없이 main에 새 커밋 추가.
