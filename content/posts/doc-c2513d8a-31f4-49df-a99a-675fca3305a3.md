화면 요청은 하나의 프로세스 안에서 권한 엔진을 거친 뒤 업무 모듈로 들어가고, 프로세스 밖으로 나가는 호출은 파일 저장소와 외부 ERP 두 곳뿐임.

## 품질 요구사항

| 품질 속성 | 요구 | 관련 문제 | 구조적 대응 |
| --- | --- | --- | --- |
| 인가의 일관성 | 요청이 한 곳의 규칙으로 판단됨 | P1 | 컨트롤러가 업무 모듈을 부르기 전에 권한 엔진 하나에 물음. 권한은 세션에 복사하지 않고 요청마다 원장에서 읽음. 여러 구역을 모은 홈과 캘린더는 같은 요청에서 읽은 권한 요약으로 구역을 고름 |
| 정책 변경의 안전성 | 동시에 고쳐도 덮어쓰지 않고, 권한을 관리할 사람이 남음 | P1 | 학원별 잠금, 정책 버전 비교, 마지막 관리자 보호 |
| 변경의 격리 | 모듈 내부를 바꿔도 다른 모듈이 바뀌지 않음 | P2 | 공개 계약과 내부 구현 분리, 의존 방향을 구조 테스트로 검사 |
| 외부 교체 가능성 | 저장소나 외부 ERP 연동을 바꿔도 업무 코드가 그대로임 | P2 | 두 경계에만 포트와 어댑터 |
| 외부 상태와의 정합성 | 중간 실패 뒤에 DB와 바깥이 어긋난 것을 찾아 마무리할 수 있음 | P3 | 작업 원장과 전송 상태, 멱등한 재실행과 대조 |

## 실행 구성

애플리케이션 한 프로세스와 PostgreSQL 하나로 동작함. 화면은 서버가 그리고, 별도의 API 서버나 프런트엔드 서버가 없음.

| 상태 | 저장 위치 |

| 자료실 파일 본문 | 저장소 포트 뒤의 디스크 |
| 로그인 세션 | 프로세스 메모리 |

### 포트를 둔 경계

| 포트 | 어댑터 | 포트를 둔 이유 |
| --- | --- | --- |
| `StorageGateway` | 로컬 파일시스템 | 파일 본문을 두는 곳은 배포 환경마다 달라짐 |
| `TngGateway` | 가상 데이터를 돌려주는 대역 | 외부 ERP는 계약과 가용성을 통제할 수 없음 |

DB 접근과 모듈 내부 서비스에는 포트를 두지 않고 JPA와 jOOQ를 직접 씀. 외부 ERP의 실제 연동 구현은 그 시스템의 비공개 계약과 계정에 묶여 있어 저장소에 두지 않았고, 포트가 주고받는 타입은 이 프로젝트가 정한 것만 씀.[* StorageGateway, TngGateway, 가상 구현(`MockTngGateway.java`)]

## 권한을 확인하는 두 층

권한 검사는 두 곳에서 일어남. 기능을 쓸 자격은 컨트롤러가 권한 엔진에 묻고, 대상이 본인의 것인지는 그 자료를 가진 업무일지가 확인함.

| 질문 | 확인하는 곳 | 예 |
| --- | --- | --- |
| 이 기능을 쓸 자격이 있는가 | 컨트롤러 → 권한 엔진 | 업무를 처리할 권한, 폴더에 올릴 권한과 허용 |
| 이 대상이 본인의 것인가 | 업무일지 | 본인에게 배정된 업무인지, 본인 담당 반인지, 본인이 올린 첨부인지 |
| 누가 대상 집합에 드는가 | 컨트롤러가 권한 원장에서 구해 넘김 | 업무를 받는 사람, 일일보고를 쓰는 사람 |

업무일지는 권한 엔진을 부르지 않음. 전원에게 배정한 업무의 담당자는 조회할 때 넘겨받은 집합으로 계산하므로, 역할이 바뀌면 다음 조회부터 담당자가 달라짐.[* 컨트롤러의 권한 확인(`Guard.java`), 업무일지의 공개 계약(`TaskBoard.java`)]

## 일관성 모델과 보장 범위

DB 트랜잭션은 바깥 시스템까지 묶지 못함. 바깥에 닿는 작업마다 "하려는 일"을 먼저 커밋해 두고, 그 기록을 기준으로 실패 뒤의 상태를 판정함.[* 자료실 변경(`DefaultStorageMutation.java`), 끊긴 작업 표시(`StorageOperationRecovery.java`), 정책 변경 잠금(`PolicyGuard.java`)]

| 경계 | 보장 | 방법 | 보장하지 않는 구간 |
| --- | --- | --- | --- |
| 권한 정책 변경끼리 | 갱신 손실 없음. 권한을 관리할 경로가 하나 이상 남음 | 학원별 잠금(비관적), 정책 버전 비교(낙관적), 변경 후 관리자 경로 확인 | 계정 정지는 다른 모듈의 일이라 유일한 관리자가 정지되면 막지 못함 |
| 권한 변경과 진행 중인 요청 | 커밋된 회수는 다음 판단부터 반영됨 | 요청마다 원장을 읽음 | 이미 판단을 통과해 진행 중인 요청은 중단하지 않음 |
| DB 트리와 파일 저장소 | 기록한 뒤에 끊긴 작업은 호출을 시작했든 아니든 원장에 남고, 같은 작업 ID로 다시 실행해 마무리할 수 있음 | 작업 원장, 작업 ID로 멱등한 저장소 연산 | 재실행은 운영자가 실행함. 그때까지 대상이 잠겨 있음. 올리던 파일은 되살리지 못하고 실패로 정리함 |
| 상담과 외부 ERP | 이 시스템이 같은 상담을 동시에 두 번 보내지 않음 | 전송 중 표시를 먼저 커밋. 포트가 확실한 거부라고 알린 실패만 되돌리고, 결과를 모르면 외부 기록과 대조 | 대조는 사람이 실행하고 내용이 같은지로 판정함. 같은 내용의 다른 기록이 있거나 외부가 내용을 바꿔 저장하면 틀릴 수 있음. 실제 외부 연동으로는 확인하지 못했음 |
| 일일보고의 제출 조건 | 제출된 보고는 그 순간의 조건을 채웠음 | 서버가 제출 시점에 계산하고 결과를 보고에 적어 둠 | 계산과 저장 사이에 바뀐 값은 반영되지 않음(TOCTOU) |

> 결과를 모르는 호출은 바깥이 멱등할 때만 다시 실행하고, 멱등하지 않으면 먼저 남겨 둔 기록을 바깥의 기록과 대조함.
