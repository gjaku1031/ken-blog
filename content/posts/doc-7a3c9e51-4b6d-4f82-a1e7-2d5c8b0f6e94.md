주문할 때 재고를 빼기로 하면서 미입금 주문을 회수하는 기한과 자동 취소가 필요해졌고(P1), 공개 사진에 캐시를 허용하면서(P2) CDN이 무엇을 저장하는지 확인하다가 저장되면 안 되는 응답을 찾았음(P3).

| 결정 | 해결한 문제 | 받아들인 비용 |
| --- | --- | --- |
| 주문할 때 재고를 빼고, 옵션 행을 잠근 뒤 수량을 확인 | P1 | 인기 옵션의 주문이 한 줄로 기다림. 5초를 넘기면 실패함 |
| 입금 기한을 주문에 저장하고, 기한이 지난 결제 대기 주문을 5분마다 취소 | P1 | 기한 동안은 입금하지 않은 주문이 재고를 잡음 |
| 사진을 올릴 때 서버가 WebP 세 벌을 만들고, 브라우저가 화면에 맞는 벌을 고름 | P2 | 업로드가 변환만큼 길어지고, 원본을 남겨 디스크가 더 듦 |
| API의 모든 응답에 "저장하지 말 것"(`Cache-Control: no-store`)을 기본으로 붙이고, 누구에게나 같은 공개 사진만 캐시를 허용 | P3 | 캐시를 허용할 응답마다 사람에 따라 달라지는지 확인해야 함 |

아래의 검증은 실제 PostgreSQL에 API를 띄우고 요청을 보내 확인한 것임. 같은 규칙을 그 뒤 자동 테스트로 옮겼음.[* 단위 테스트와 통합 테스트 129건, 2026-10-13 기준. 통합 테스트는 PostgreSQL 16 컨테이너에 마이그레이션을 모두 적용하고 API를 띄워 HTTP로 요청하며 CI에서 돎]

## P1. 재고 정합성

### 문제

결제 수단이 무통장 입금 하나라, 주문과 입금 사이가 몇 시간에서 며칠까지 비고 입금은 운영자가 통장을 보고 확인함. 수제품이라 옵션 하나의 재고가 1~3개인 경우가 많음. 마지막 한 개를 두 고객이 거의 동시에 주문하면 한 명만 성공해야 하고, 입금하지 않은 주문이 그 한 개를 계속 붙잡아서도 안 됨. 고객에게 알릴 수단은 화면뿐임.

### 검토한 대안

| 갈림길 | 고른 쪽 | 버린 쪽과 이유 |
| --- | --- | --- |
| 재고를 빼는 시점 | 주문할 때 | 입금 확인할 때. 재고 1개에 주문이 여러 건 쌓이고, 나머지 고객은 돈을 보낸 뒤에 품절을 알게 됨 |
| 동시 주문 | 옵션 행을 잠그고 확인한 뒤 차감 | 조건부 `UPDATE`는 실패 원인을 구분하려면 다시 조회해야 함. 낙관적 락은 한 명만 성공하는 경쟁에서 재시도가 낭비임 |
| 미입금 주문의 회수 | 입금 기한과 자동 취소 | 운영자가 직접 취소. 사람이 잊으면 재고가 계속 묶임 |
| 묶인 재고의 기록 | 재고 수량을 직접 차감 | 예약 테이블. 며칠짜리 점유는 주문의 결제 대기 상태와 같은 사실이라 두 곳에 적게 됨 |
| 기한이 지난 주문의 처리 | 5분마다 주기 실행 | 조회나 주문 요청이 올 때 처리. 아무도 보지 않으면 결제 대기로 남고, 조회가 재고를 바꾸게 됨 |
| 중복 취소 방지 | 주문 행 잠금과 잠근 뒤의 재확인 | 분산 락. 운영자의 입금 확인과 겹치는 경쟁은 풀지 못해 행 잠금이 어차피 필요함 |

- **결정**: 주문 트랜잭션이 옵션 행을 ID 순서로 잠그고 재고를 확인한 뒤 뺌. 주문에 입금 기한(주문일 + 설정 일수의 23:59, 한국 시간)을 저장함. 주기 작업은 기한이 지난 결제 대기 주문을 잠금 없이 고른 뒤, 한 건씩 새 트랜잭션에서 주문 행을 잠그고 상태를 다시 확인해 취소함. 운영자의 입금 확인도 같은 주문 행을 잠그므로, 둘이 겹치면 먼저 잠근 쪽만 반영됨
- **이중 방어**: 음수 재고는 애플리케이션의 검증과 DB의 `CHECK (stock >= 0)` 두 곳에서 막음. 재고 수량을 바꾸는 모든 경로는 같은 트랜잭션에서 이력을 남겨, 옵션마다 이력의 합이 현재 수량과 같음
- **대가**: 한 옵션의 주문이 한 줄로 기다리고, 잠금 대기를 포함해 5초를 넘긴 요청은 실패함. 기한 동안은 허수 주문이 재고를 잡을 수 있음(기본 2일, 길게는 약 3일). 회원 한 명의 결제 대기 주문을 5건으로 제한해 한 계정이 잡을 수 있는 양을 줄였음
- **보장하지 않는 것**: 잠금 순서(회원·주문 다음 옵션)와 잠근 뒤의 재확인, 수량과 이력의 동시 기록은 코드 규칙으로 지킴. 수량과 이력이 어긋나면 매시간의 대조가 운영자의 첫 화면과 오류 로그에 알리지만, 잠금 순서를 어긴 새 경로를 미리 잡는 장치는 없음.[* 운영자 대리 주문과 고객 취소는 회원 행을 잠그지 않고 옵션부터 잠근 뒤, 외래 키 검사로 회원 행에 `FOR KEY SHARE`를 요청함. 회원 행 잠금이 `FOR NO KEY UPDATE`라 같은 고객의 주문 생성과 서로 기다리지 않음. 이 잠금 모드가 바뀌면 교착이 생기는 것을 통합 테스트가 잡음(`OrderLockOrderTest`)] 결제 대기 주문의 제한은 회원 단위라 계정을 여러 개 만들면 넘을 수 있음

### 검증

| 확인한 것 | 결과 |
| --- | --- |
| 재고 2개인 옵션에 주문 20건을 동시에 요청(10회 반복) | 매번 2건 성공, 18건 재고 부족. 재고 0, 이력 합계 0. 잠금과 `CHECK`를 뺀 대조군에서는 매번 재고가 -18이 됨 |
| SQL로 재고를 -1로 바꾸기 | `CHECK` 위반으로 거부 |
| 같은 회원이 주문 12건을 동시에 요청 | 5건만 성공하고 7건은 409로 거절됨 |
| 기한을 과거로 바꾸고 주기 작업을 기다림 | 정각에 취소되고 재고가 돌아옴. 기한이 남은 주문은 그대로 |
| 입금 확인을 자동 취소 직전에 요청 | 입금 확인이 반영되고 주기 작업은 그 주문을 건너뜀 |
| 주기 작업이 먼저 주문을 잠근 뒤 입금 확인을 요청 | 자동 취소가 반영되고, 입금 확인은 기다린 뒤 409를 받음 |

갈림길 16곳의 비교와 나머지 확인 결과는 [무통장 입금 쇼핑몰의 재고 설계](/ken-blog/post/post-5d0f6c1e-7b3a-4c58-9e21-3f6a1d2b8c47/)에서 다룸.[* 2026-10-11 로컬 PostgreSQL에서 확인]

## P2. 사진 전송량

### 문제

운영자가 올린 사진을 받은 그대로 저장해, 120px 썸네일도 상세 화면의 큰 사진도 같은 원본을 받았음. 휴대폰 사진은 3~5MB이고 가로가 4000px 안팎이라, 사진 12장이 든 목록은 화면에 쓰지 않는 픽셀을 수십 MB 내려받게 됨. 사진 응답은 매번 다시 받게 돼 있었음. 운영 사이트의 사진은 17장이고 작아서 당장 느리지는 않았고, 운영자가 휴대폰 사진을 그대로 올리기 시작하면 생길 문제였음.

### 검토한 대안

| 갈림길 | 고른 쪽 | 버린 쪽과 이유 |
| --- | --- | --- |
| 줄이는 시점 | 올릴 때 미리 | 요청이 올 때 변환. 방문자의 요청 경로가 변환 비용을 치르게 됨 |
| 만드는 벌의 수 | 대·중·소 세 벌 | 압축한 한 벌. 목록은 가볍게, 상세는 선명하게를 함께 만족하지 못함 |
| 줄이는 곳 | 서버 | 올리기 전의 브라우저. 결과를 서버가 책임질 수 없고, 사진의 위치 정보를 지우는 일도 따로 해야 함 |
| 변환을 실행하는 시점 | 업로드 요청 안에서 | 뒤에서 따로. 큐가 없는 구성이고, 실패를 올린 사람이 바로 알 수 없게 됨 |
| 브라우저의 선택 | `srcset`으로 세 벌을 제시 | 화면마다 크기를 지정. 화면에 이미 적어 둔 `sizes`를 살리지 못함 |

- **결정**: 업로드 요청 안에서 서버가 가로 400·800·1600px의 WebP 세 벌을 만들고 원본도 남김. 세 벌은 사진 키에 붙는 이름 규칙으로 찾아 스키마를 바꾸지 않음. 공개된 상품과 글에 쓰인 사진은 하루 동안 캐시를 허용함. 사진 키는 올릴 때마다 새로 만들어져 같은 주소의 내용이 바뀌지 않음
- **대가**: 업로드가 변환 시간만큼 길어짐. 원본을 남겨 디스크가 사진 수만큼 더 듦. 캐시를 허용한 동안에는 사진을 숨겨도 이미 받아 간 쪽에 남음
- **보장하지 않는 것**: 사진을 올리는 사람이 운영자라는 전제에 기대고 있음. 방문자가 사진을 올리는 기능을 만들면 픽셀 수 제한부터 넣어야 함

### 검증

| 확인한 것 | 결과 |
| --- | --- |
| 4.8MB 사진 한 장의 업로드 | 요청 전체 2.1초. 세 벌은 29KB, 202KB, 793KB[* 4000×3000으로 키우고 잡음을 섞은 합성 사진 한 장을 개발용 VM의 ARM 컨테이너에서 운영 배포(2026-10-11) 전에 한 번 잰 값. 표본이 하나라 중앙값과 최댓값이 없고, 운영 서버에서는 재지 않았음] |
| 사진 두 장짜리 상품 목록의 전송량 | 5,063KB에서 PC 46KB, 화면 배율 3인 휴대폰 350KB |
| 운영 사이트의 상품 목록(사진 12장) | PC 119KB, 화면 배율 3인 휴대폰 432KB |
| 촬영 위치가 든 사진 | 변환본의 메타데이터 0개 |
| 앞부분만 있는 손상된 사진 | 400으로 거절하고 저장하지 않음 |

## P3. 개인 정보가 든 응답의 캐시

### 문제

CDN은 같은 주소의 요청이 다시 오면 서버에 묻지 않고 저장해 둔 응답을 돌려줌. 사진처럼 누구에게나 같은 응답에는 이득이지만, 주문 목록처럼 사람마다 다른 응답이 저장되면 다른 사람이 그 응답을 받게 됨.

공개 사진에 캐시를 허용한 뒤 CDN의 동작을 확인하다가 두 가지를 찾았음. 없는 사진 주소의 404가 CDN에 저장돼 4시간 동안 그대로 응답됨. 그리고 주소 끝에 `;x.jpg`를 붙이면 JSON 응답도 저장됨. 세 조건이 겹친 결과임.

- CDN은 주소가 `.jpg`처럼 끝나면 응답의 종류와 관계없이 정적 파일로 보고 저장함
- API는 주소의 `;` 뒤를 버리고 처리할 코드를 찾음. `/api/products;x.jpg`는 상품 목록이 응답함
- API가 캐시 지시를 보내지 않았음

로그인한 사용자가 `/api/orders/me;a.jpg` 같은 주소를 열면 그 사람의 주문 목록이 CDN에 저장되고, 같은 주소를 쿠키 없이 연 사람이 그 응답을 받게 됨(Web Cache Deception).

### 검토한 대안

| 갈림길 | 고른 쪽 | 버린 쪽과 이유 |
| --- | --- | --- |
| 막는 곳 | 원 서버가 캐시 지시를 보냄 | CDN 규칙에만 맡김. 사진이 공개인지는 원 서버만 알고, 저장소 밖의 설정은 바뀐 것을 추적하기 어려움 |
| 지시를 붙일 응답 | 모든 응답에 기본으로 | 오류 응답에만. 지시가 없는 성공 응답이 그대로 남음 |
| 붙이는 자리 | 요청을 처음 받는 필터 한 곳 | 응답을 만드는 곳마다. 빠뜨린 곳이 생김 |
| 404의 캐시 | 하지 않음 | 짧게 캐시. 같은 사진 주소가 비로그인에게는 404, 운영자에게는 200이라 공용 캐시에 넣을 수 없음 |
| `;`가 든 주소 | 거부하지 않음 | 400으로 거부. 재료 하나만 막는 것이라 같은 효과를 내는 다른 주소 형태에 다시 뚫림 |

- **결정**: 가장 먼저 실행되는 필터가 모든 응답에 `Cache-Control: no-store`를 적고, 캐시해도 되는 응답만 처리하는 코드가 직접 바꿈. 지금 캐시를 허용하는 응답은 공개 사진 하나임
- **대가**: 방어선이 원 서버 한 겹임. CDN 쪽의 보호 규칙은 아직 켜지 않았음. 캐시를 허용하는 응답이 늘 때마다 사람에 따라 달라지는 응답인지 확인해야 함

### 검증

| 확인한 것 | 결과 |
| --- | --- |
| 고치기 전의 운영 사이트에서 `/api/products;probe1.jpg`를 두 번 요청 | 두 번째 요청이 CDN에서 응답됨. 쿠키를 붙여도 같음 |
| 배포 뒤 같은 형태의 주소를 두 번 요청 | 두 번 모두 `no-store`이고 CDN이 저장하지 않음 |
| 배포 뒤 없는 사진 주소 | 404가 `no-store`로 응답됨 |
| 배포 뒤 공개 사진 | 하루 캐시가 유지되고 CDN에서 응답됨 |

로그인한 사용자의 응답이 실제로 저장되는 것까지는 운영에서 해 보지 않았고, 공개 상품 목록과 없는 주소로만 확인했음. 이 구멍은 API가 Spring으로 운영에 올라간 2026-10-08부터 `no-store`를 배포한 10-11까지 약 68시간 열려 있었고, 그동안 개인 정보가 든 응답이 CDN에 저장된 적이 있는지는 확인하지 못했음. 발견 경위와 나머지 확인 결과는 [사진 404를 쫓다가 찾은 CDN 캐시 구멍](/ken-blog/post/post-b4f19d3c-62a8-4e7d-95b1-0c8a7e3f5d26/)에서 다룸.[* 2026-10-11 운영 사이트에서 확인]
