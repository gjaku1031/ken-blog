# 학원 운영을 위한 사내 ERP: 인터뷰 요약

문서를 쓰며 확인한 사실과 판단의 이유를 정리한 기록. 블로그에는 게시하지 않음. 마지막 정리 2026-10-11.

## 개발 형태와 담당 범위

- 개발은 혼자 했음
- 요구사항은 기획을 맡은 실장 한 명, 운영진(대표와 원장), 각 팀의 팀장에게서 받았음
- 진행 방식: 먼저 시제품을 만들어 보여 주면 실장이 1차로 다듬고, 그 뒤에 팀장이나 원장이 확인했음
- 직접 정한 것
  - 권한 모델을 RBAC·ABAC·ACL로 나눠 쓴 방식
  - 모듈 경계와 포트를 둘 곳
  - 업무일지의 요구사항 정리와 운영
- 들어서 반영한 것: 권한 목록처럼 학원 안의 사정에 달린 세부 사항은 실장에게서 들었음
- 저장소: <https://github.com/gjaku1031/npr-erp>

## 개발 배경

학원은 기존 ERP에 딸린 업무일지를 쓰고 있었음. 표 하나로 된 화면이었고, 세 가지가 불편했음.

- **반복되는 업무를 날마다 다시 적음**: 상담일지 쓰기, 보충일지 작성처럼 매일 바뀌지 않는 업무도 표에 매번 들어가야 했음
- **같은 내용을 두 번 적음**: 상담일지를 쓴 뒤에 업무일지에도 상담한 학생의 이름을 다시 적어야 했음
- **팀장이 날마다 확인 항목을 손으로 적음**: 팀의 퇴근 시각이 밤 10시인데, 팀장이 그 전후로 그날 확인할 사항(시험지를 만들었는지, 처리할 업무를 했는지)을 적어야 했음. 월요일부터 목요일까지 이어지는 업무는 나흘 모두 적어야 했음

그래서 팀장이 항목을 빠뜨린 날에는 그 업무를 하지 않는 사람이 생겼고, 팀장이 작성을 잊거나 늦게 하면 팀의 퇴근이 늦어졌음. 팀장은 작성 부담이 컸고, 팀원은 퇴근이 늦어지는 데 불만이 있었음.

### 불편과 기능의 대응

코드에서 확인한 대응 관계.

| 불편 | 대응하는 기능 |
| --- | --- |
| 반복되는 업무를 날마다 다시 적음 | 업무에 시작일과 마감일을 두고, 그 기간에 드는 날의 일일보고 5단계에 자동으로 나타나게 함. 날짜별 체크리스트는 앞 날짜의 항목을 복사해 만듦 |
| 같은 내용을 두 번 적음 | 일일보고 3단계가 그날의 상담 기록을 외부 ERP에서 불러와 보여 줌. 강사는 확인만 함 |
| 팀장이 날마다 확인 항목을 손으로 적음 | 팀장은 업무와 체크리스트를 한 번 정하고, 제출 현황에서 누가 냈는지를 봄 |

## 시범 운영

업무일지는 ERP의 세부 기능을 먼저 떼어 시범 운영한 것임. 개발을 맡은 사람이 아직 검증받지 않은 상태였으므로, 업무일지가 실제 업무에서 통하는지를 먼저 확인하고 그 결과에 따라 다음 단계로 넘어가기로 했음. 권한 엔진과 자료실은 그다음 단계이고 운영에 올리지 않았음.

2026-10-11에 운영 화면의 자료를 집계한 값.

| 항목 | 값 |
| --- | --- |
| 등록 인원 | 13명(일일보고 대상 10명, 다른 팀 3명) |
| 일일보고를 연 날 | 55일(2026-07-13 ~ 2026-09-23) |
| 제출된 일일보고 | 493건(7월 167건, 8월 200건, 9월 126건) |

| 특강기간으로 연 날 | 16일 |

## 문서 방향으로 정한 것

- 저장소를 공개하고 근거를 코드 링크로 검
- 업무일지는 ERP의 일부를 먼저 시범 운영한 것으로 서술함. 시범 운영의 수치는 업무일지에만 붙이고, 권한 엔진과 자료실은 운영 전임을 밝힘
- API 설계 문서와 배포·운영 문서는 쓰지 않음. 화면을 서버가 그려 별도 HTTP API가 없고, 배포 경로를 정하지 않았기 때문

## 아직 확인하지 못한 것

- 근무하는 동안에는 계속 쓰였음. 그 뒤의 사용 여부는 알지 못함
- 외부 ERP의 이름을 문서에 쓸지
- RBAC·ABAC·ACL의 역할 분담 표를 본인의 말로 설명했을 때 어색한 칸이 있는지
