일반 JVM의 제한 자원 환경 부하·메모리 측정과 공개 스냅샷의 조회 수·응답 크기 검증. 2026-10-02의 과거 부하 결과와 현재 회귀 기준을 구분.

## 측정 질문과 환경

확인 대상은 ARM 1코어·약 4GB 서버에서 일반 JVM API와 Caddy를 유지할 수 있는지 여부. 당시 기능과 테스트 DB를 사용한 짧은 부하 관측이며, 현재 운영 DB의 성능 보장은 아님.

## 스냅샷 회귀 기준

`largeSnapshotsAreBoundedAndConsistent`는 같은 분류의 공개 글 300개를 사용하는 격리 MySQL 통합 검사. 다음 수치는 테스트 통과 조건이며 운영 실측값과 별개.

| 검증 대상 | 입력과 통과 조건 | 해석 범위 |
| --- | --- | --- |
| 공개 글 수 | 한 분류에 공개 글 300개 | 다양한 실사용 분류·태그 조합까지 대표하지 않음 |
| 조회 계수 | Hibernate `prepareStatementCount` + jOOQ SELECT 계수 ≤ 10 | 해당 snapshot 호출 구간의 DB 접근 기준. HTTP 지연 기준 아님 |
| 응답 형식 | `version == 3` | 현재 서버 스냅샷 계약 확인 |
| 탐색 중복 | `navigation` 그룹 1개, 해당 그룹 항목 300개 | 300개 그룹을 만드는 검사가 아님 |
| 응답 크기 | 전체 payload의 JSON 직렬화 결과 < 500,000바이트 | 네트워크 압축 전 바이트. 실제 반환 크기의 측정 보고서와 구분 |
| 관리자 읽기 | REPEATABLE_READ 안에서 외부 변경 전후 두 조회가 동일 | 한 읽기 트랜잭션의 일관성 확인 |
| 커밋 후 재조회 | 글 300개를 유지하고 외부에서 바꾼 제목을 확인 | 이전 트랜잭션 밖에서는 새 결과를 읽는지 확인 |

조회 계수는 Hibernate 통계와 jOOQ SELECT 리스너를 합산. 탐색 목록을 글마다 중복 직렬화하는 퇴행을 감시. 한 개의 큰 그룹을 사용하는 fixture이므로 모든 그룹·문자열·관계 조합에 동일 크기를 보장하지 않음.

공개 서비스의 응답 상한은 revision 추가 전 7,999,800바이트, 관리자 스냅샷은 8,000,000바이트. fixture의 500,000바이트 통과 조건과 서비스 한도를 구분.
