핵심 문제 P2(제한된 자원에서의 열람 성능)를 확인한 측정과 테스트 통과 기준을 모아 둔 목록임. 별도 글이 있는 측정은 결과만 적고, 없는 측정은 여기에 전체를 적음. 분류는 설계(실험·평가·관찰)와 목적(확증·탐색)의 두 축으로 적음.

## 제한 자원의 JVM 부하·메모리 측정

분류: 탐색적 실험(2026-10-02). API의 기본 런타임을 Native Image 대신 일반 JVM으로 정하면서, 측정 당시의 1코어·약 4GB 서버에서 JVM이 감당할 수 있는지 확인한 측정. 이전 구현에서 같은 코드·1 CPU·1GiB 조건으로 비교했을 때 읽기 요청 120회 후 메모리 중앙값이 JVM 684MiB, Native Image 136MiB였음[* 2026-09 측정, Native Image를 쓰던 이전 구현 기준. [인프라 ADR](https://github.com/gjaku1031/ken-blog/blob/1072a36/docs/ADR/ADR_infra.md)의 과거 Native Image 검증 이력]. JVM이 약 5배의 메모리를 쓰지만 약 4GB 서버에서는 감당할 수 있다고 보고, 리플렉션 설정 유지와 학습 비용이 큰 Native Image 대신 일반 JVM을 택함. 대가는 큰 메모리 사용과 긴 기동 시간.

> 측정한 요청 조합에서 API는 1.5GiB 컨테이너 한도 안에서 OOM과 재시작 없이 유지됐음. 200건/초 구간에서 p95 33.41ms, 호스트 평균 CPU 88.4%, API 메모리 최대 474.5MiB.

### 연구 질문

측정 당시의 1코어·약 4GB 서버에서 일반 JVM API가 메모리 한도 안에서 요청을 처리할 수 있는가(P2). 도착률과 요청 종류는 실행 전에 정했지만, 통과로 볼 지연·메모리 기준은 기록에 남아 있지 않음.

### 해석

- 측정한 요청 조합에서 API는 1.5GiB 한도 안에서 OOM과 재시작 없이 유지됐고, 메모리 최대는 474.5MiB로 한도의 약 31%였음
- 200건/초에서 호스트 CPU가 88.4%까지 올라, 이 서버에서 이 요청 조합의 여유는 크지 않았음
- 도착률이 오를 때 p95가 단조 증가하지 않았음(10건/초 23.55ms, 100건/초 10.17ms). 요약 결과만으로는 원인을 확정하지 못함

### 타당성과 한계

- **내적 타당성**: 테스트 MySQL이 같은 서버에서 돌았고, CPU는 API만이 아니라 MySQL·OS를 포함한 호스트 전체 값임
- **외적 타당성**: 2026-10-02 당시 이미지와 스냅샷 v2 결과임. 현재 운영 이미지·DB의 성능, 최대 처리량, 장기 메모리 안정성으로 확대하지 않음
- **구성 타당성**: 공개 상태·배지는 당시 API 요청 조합이며, Pages의 HTML 전송이나 브라우저 렌더링 측정이 아님
- **통계적 타당성**: 시나리오마다 30초 관측 한 번이고, 스냅샷 p95는 15회 관측에 한정됨

## 공개 스냅샷 회귀 기준

운영 실측이 아니라 격리 MySQL 통합 검사 `largeSnapshotsAreBoundedAndConsistent`의 통과 조건. 같은 분류의 공개 글 300개로 스냅샷을 만들어, 탐색 목록을 글마다 중복 직렬화하거나 조회가 글 수에 비례해 늘어나는 퇴행을 감시함.[* 조회 계수는 Hibernate `prepareStatementCount`와 jOOQ SELECT 리스너를 합산. 서비스의 실제 응답 상한은 공개 스냅샷 7,999,800바이트, 관리자 스냅샷 8,000,000바이트로 이 통과 조건과 별개]

| 검증 대상 | 입력과 통과 조건 | 해석 범위 |
| --- | --- | --- |
| 공개 글 수 | 한 분류에 공개 글 300개 | 다양한 실사용 분류·태그 조합까지 대표하지 않음 |
| 조회 계수 | Hibernate `prepareStatementCount` + jOOQ SELECT 계수 ≤ 10 | 해당 snapshot 호출 구간의 DB 접근 기준. HTTP 지연 기준 아님 |
| 응답 형식 | `version == 3` | 현재 서버 스냅샷 계약 확인 |
| 탐색 중복 | `navigation` 그룹 1개, 해당 그룹 항목 300개 | 300개 그룹을 만드는 검사가 아님 |
| 응답 크기 | 전체 payload의 JSON 직렬화 결과 < 500,000바이트 | 네트워크 압축 전 바이트. 실제 반환 크기의 측정 보고서와 구분 |
| 관리자 읽기 | REPEATABLE_READ 안에서 외부 변경 전후 두 조회가 동일 | 한 읽기 트랜잭션의 일관성 확인 |
| 커밋 후 재조회 | 글 300개를 유지하고 외부에서 바꾼 제목을 확인 | 이전 트랜잭션 밖에서는 새 결과를 읽는지 확인 |

큰 그룹 하나를 쓰는 fixture라 모든 그룹·문자열·관계 조합에서 같은 크기를 보장하지 않음.
