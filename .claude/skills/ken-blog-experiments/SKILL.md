# 실험 설계와 보고

독자는 컴퓨터공학 교수와 시니어 개발자다. 실험 글에서 이들이 먼저 보는 것은 결과 수치가 아니라 **실험 전에 무엇을 예측했고, 무엇이 나오면 틀렸다고 인정할지 미리 정했는가**다. 이 스킬은 소프트웨어공학 실험의 표준 틀(아래 '근거 문헌')을 포트폴리오 글 크기로 줄인 것이다. 문체·표현 요소·배포 절차는 `ken-blog-docs` 스킬을 따른다.

## 먼저 정할 것: 기록의 분류

기록은 서로 독립인 두 축으로 분류하고, 글에서 그 성격이 드러나게 한다. "분류: ○○" 같은 라벨 문장 대신 "미리 가설을 세우지 않고 잰 탐색적 실험임", "결과를 보기 전에 가설을 정해 두고 실행했음"처럼 문장으로 쓴다. 분류에 따라 주장할 수 있는 범위가 다르다.

**축 1. 설계: 무엇을 했나**

| 설계 | 정의 | 예 |
| --- | --- | --- |
| 실험 | 연구자가 조건(독립변수)을 일부러 바꾸고 나머지를 고정한 채 결과를 비교 | 렌더링 구조 3종, DB 2종, 임계값 여러 값 |
| 평가 | 조건을 바꾸지 않고 시스템 하나의 성능·정확도를 정해진 입력으로 잼 | 고정 질의 96개로 잰 검색 정확도 |
| 관찰 | 운영 중에 생긴 자료를 그대로 집계 | 운영 명단의 예약·입장 집계 |

**축 2. 목적: 왜 했나**

| 목적 | 정의 | 주장할 수 있는 것 |
| --- | --- | --- |
| 확증 | 가설·기각 기준·분석 방법을 결과를 보기 전에 고정하고 한 번 실행 | 가설의 지지·기각 |
| 탐색 | 무슨 일이 일어나는지 보고 가설 후보를 찾음. 사전에 고정한 판정 기준이 없음 | 관찰한 사실과 다음 가설. 가설을 검증했다고 쓰지 않음 |
| 기술 | 있는 그대로 요약(관찰에 주로 해당) | 집계된 사실 |

- 실험이 아닌 기록은 따로 부른다. **결함 재현**(추정한 결함이 실제로 일어나는지 조건을 만들어 확인, 재현 횟수와 함께), **회귀 기준**(테스트가 계속 지켜야 하는 수치 조건).
- 가설·기각 기준을 결과를 보기 전에 적어 두지 않았으면 목적은 **탐색**이다. 막연한 예상이 있었더라도 같다. 결과를 본 뒤 가설을 지어 원래 있던 것처럼 쓰지 않는다(HARKing, Kerr 1998).
- 탐색의 결과에서 세운 가설은 "이 결과에서 다음 가설을 세움"으로 쓰고, 확증은 **새 자료**로 한다. 가설을 만든 자료로 그 가설을 다시 검증하지 않는다(같은 자료로는 우연한 패턴도 맞아 보임).
- 이 구분은 탐색적 자료 분석(Tukey 1977)과 확증 연구의 사전 고정(Wagenmakers 외 2012)에서 온다.

## 설계 8단계

확증 실험·확증 평가는 1~7단계를 실행 전에 계획서로 쓰고 고정한다. 계획서 틀은 [references/plan-template.md](references/plan-template.md).

1. **연구 질문**: 답이 수치나 예/아니오로 나오게 좁힌다. 프로젝트의 핵심 문제(P1~Pn)와 연결한다. 목표 → 질문 → 지표 순서로 내린다(GQM).
   - 나쁜 예: "검색이 잘 되나"
   - 좋은 예: "임계값을 바꾸면 1위 정답률과 LLM 호출 비율이 어떻게 달라지나"
2. **가설과 기각 기준**: "A이면 B일 것이다. 왜냐하면 C이기 때문이다"로 쓴다. 근거 C는 이전 측정·코드·문헌에서 가져온다. 가설마다 **기각 기준**(어떤 결과가 나오면 틀렸다고 인정할지)을 수치로 적는다(반증 가능성, Popper).
3. **변수**
   - 독립변수: 바꾸는 것과 그 수준(예: 임계값 0.30~0.60, 0.05 간격)
   - 종속변수: 재는 것과 정의(예: 1위 정답 = 반환 1위가 사전 정답과 같음)
   - 통제변수: 고정하는 것(코드 커밋, 모델·버전, 데이터, 자원 한도, 실행 환경)
4. **비교 기준과 설계**
   - 비교 기준(baseline): 현재 구현, 기능을 끈 경우, 알려진 대안 중 최소 하나
   - 표본 크기와 그 이유, 반복 횟수, 워밍업, 실행 순서(교차·무작위)
   - 같은 입력을 모든 조건에 쓰면 짝지은 비교로 분석한다
5. **사전 고정**: 입력·정답·분석 스크립트·기각 기준을 실행 전에 커밋하거나 해시로 고정한다. 결과를 본 뒤 바꾼 것은 바꾼 이유와 함께 따로 기록하고, 바꾼 뒤의 결과는 탐색적 결과로 구분한다(사전 등록, Nosek 외 2018).
6. **타당성 위협**: 결과가 틀렸을 수 있는 이유를 실행 전에 적고, 막은 방법과 막지 못한 것을 구분한다(Shadish·Cook·Campbell 2002의 네 분류).
   - 내적 타당성: 다른 원인이 섞였을 가능성(공유 호스트, 외부 API 변동, 캐시, 실행 순서)
   - 외적 타당성: 일반화 범위(합성 데이터, 규모, 실제 사용자와의 차이)
   - 구성 타당성: 재는 지표가 묻고 싶은 것을 대표하는가(예: 1위 정답 ≠ 사용자 만족)
   - 통계적 타당성: 표본 크기, 반복, 분산, 다중 비교
7. **분석 계획**: 지표마다 요약 방법과 불확실성 표시를 미리 정한다(아래 '통계 최소 기준').
8. **결과·해석·한계**
   - 가설마다 지지·기각을 먼저 말하고, 근거 수치를 붙인다
   - 예상과 다른 결과는 숨기지 않고 따로 적는다. 기각된 가설도 결과다
   - 해석은 측정한 조건 안에서만 하고, 일반화하려면 6단계의 위협을 함께 쓴다

## 통계 최소 기준

포트폴리오 글은 검정력 분석이나 가설 검정까지 요구하지 않지만, 아래는 지킨다.

| 지표 | 보고 방식 |
| --- | --- |
| 비율(정답률·성공률) | 분자/분모와 백분율, Wilson 95% 신뢰구간 |
| 지연·처리 시간 | 중앙값과 p95, 표본 수. 반복 측정이면 반복 간 범위 |
| 두 조건 비교 | 같은 입력끼리 짝지어 비교하고, 차이의 크기를 함께 씀. "빠름"만 쓰지 않음 |
| 여러 조건 | 조건별 표를 접기로 넣고, 본문은 대표 조건과 전체 경향(예: 32개 군 중 32개) |
| 재현 | 재현 횟수/시도 횟수 |

- 성능 측정은 워밍업, 반복, 실행 순서 교차, 자원 한도, 측정 범위(무엇이 포함된 지연인가)를 적는다(Jain 1991, Hoefler·Belli 2015).
- 수치는 대상·환경·표본·시점과 함께 쓴다.

## 실행 규칙

- 확증 실험은 고정한 계획대로 **한 번** 실행한다. 결과가 마음에 들지 않아 다시 돌리지 않는다.
- 환경 문제로 실행이 실패하면(예: DB 플러그인 누락) 실패 기록을 지우지 않고 따로 보존한 뒤 원인을 고쳐 다시 실행한다. 글에 실패와 재실행 이유를 한 줄 남긴다.
- 원자료(요청별 결과·지연·오류)를 그대로 남기고, 집계는 스크립트로 만든다.
- API 키·비밀번호는 출력·로그·결과 파일에 남기지 않는다. 실행 전용 키는 최소 권한·짧은 만료로 만들고, 끝나면 파일을 지운다.
- 실험 코드와 원자료는 가능하면 공개 저장소(`docs/experiments/<날짜>-<이름>/`, README에 분류·파일 목록)에 두고, 글에서 커밋 해시로 링크한다. 확증 실험은 계획 고정 커밋과 결과 커밋을 따로 남겨 계획이 먼저였음을 보인다. 너무 큰 원자료는 집계·감사 결과와 해시로 대신하고 그 사실을 적는다.

## 실험 글 작성 규칙 (Posts)

실험·평가 하나는 Posts 글 하나가 원본이다. 여러 측정을 모은 목록 글에는 실험 본문을 두지 않고 결과 요약과 링크만 둔다(D-067). 대문·의사결정 문서에는 판정 한 줄과 대표 수치만 두고 이 글로 링크한다. 문체·표현 요소(주석·접기·인용)는 `ken-blog-docs`를 따른다.

| 절 | 확증 | 탐색 | 내용 |
| --- | :---: | :---: | --- |
| 첫머리 | 필수 | 필수 | 왜 궁금했는지와 결론을 2~3문장으로, 핵심 결론 인용 하나. 측정 일자·분류는 문장 속에 자연스럽게 |
| 질문과 가설 | 필수 | 질문만 | 연구 질문과 P 연결. 확증은 가설·근거·기각 기준 표와 계획 고정 위치. 탐색은 "가설과 판정 기준을 미리 정하지 않음"을 밝힘 |
| 설계 | 필수 | 필수 | 변수 표(독립·종속·통제), 비교 기준, 표본·반복·순서·워밍업, 정답·입력 고정 방법 |
| 결과 | 필수 | 필수 | 대표 표 하나. 전체 조건 표는 접기. 통계 최소 기준을 지킴 |
| 해석 | 필수 | 필수 | 확증은 가설마다 지지·기각을 먼저 씀. 예상 밖 결과를 따로 씀. 탐색은 관찰한 사실과 다음 가설 |
| 타당성과 한계 | 필수 | 필수 | 내적·외적·구성·통계적 네 분류로 막은 것과 남은 것. 해당 없는 분류는 생략 |
| 재현 자료 | 필수 | 필수 | 코드·원자료 위치(커밋 링크), 버전·환경 |

- 실험·평가를 담은 글에는 태그 `실험`을 단다. 요약과 링크만 있는 목록 글에는 달지 않는다(`post_tags`에 `tag_name`·`display_name` 모두 `실험`, 기존 태그 뒤 위치). DB 변경 뒤 Pages를 다시 배포해야 공개 화면에 보인다
- 제목은 무엇을 무엇과 비교했는지가 드러나게 쓴다(예: "Vowser 경로 저장소 재평가: Neo4j와 MySQL").
- 한 연구가 탐색 → 가설 → 확증으로 이어지면 한 글에 두 부분으로 싣고, 부분마다 분류를 밝힌다. 흐름 자체가 연구 과정을 보여 준다.
- 타당성 절 주석에 "Shadish·Cook·Campbell(2002)의 타당성 분류를 따름" 정도로 출처를 밝힌다. 문헌을 길게 인용하지 않는다.
- 실행 실패·재실행, 계획 변경은 숨기지 않고 해당 절에 한 줄로 쓴다.

### 이미 한 측정을 다시 쓸 때

- 실행 전에 적어 둔 가설·판정 기준이 기록(커밋·계획서)으로 남아 있지 않으면 **탐색**으로 분류한다. 가설 절을 새로 지어 넣지 않는다.
- 원래 있던 "측정 질문"은 연구 질문으로 그대로 쓴다. 질문 문구를 결과에 맞춰 고치지 않는다.
- 변수 표와 타당성 네 분류는 기록에 있는 사실로 채운다. 기록에 없는 조건은 "기록되지 않음"으로 쓴다.
- 결과 수치는 바꾸지 않는다. 해석에 "다음 가설"을 덧붙일 수 있고, 그 가설을 같은 자료로 검증했다고 쓰지 않는다.

## 그림 (D-069)

실험 글에는 설계를 보여 주는 그림 하나와 결과 그래프 한두 개를 넣는다. 블로그 렌더러가 글 안의 `<svg>`·`<script>`·`<iframe>`을 걸러 내므로, HTML/SVG로 그린 뒤 이미지로 구워 첨부한다.

1. `artifact-diagramming` 스킬의 지침을 따라 `docs/experiments/<실험>/figures/<이름>.html`에 그린다. 그림은 `<div id="figure">` 안(폭 1200px)에 inline SVG로, 밝은·어두운 테마는 CSS 변수와 `prefers-color-scheme`로 맞춘다. 이 세션에 스킬이 없으면 스킬이 있는 서브에이전트에게 맡긴다
2. 그래프 수치는 결과 파일에서 읽는다(`window.FIGURE_DATA`로 주입하거나, 손으로 옮겼으면 HTML 주석에 출처 파일을 적음)
3. `node .claude/skills/ken-blog-experiments/scripts/render-figure.cjs <그림.html> <접두어> [데이터.json]` → `<접두어>-light.png`, `-dark.png`. 두 장 모두 Read로 열어 겹침·잘림·빈 화면이 없는지 본다
4. 밝은 판을 기본 이미지, 어두운 판을 `dark=`로 첨부한다(구조도와 같이 페이지 테마를 따름). 그림 속 용어는 본문과 같게 쓴다
5. `figures/README.md`에 그림별 내용과 데이터 출처를 적는다

## 문장 쓰기 (D-068)

실험 글은 보고서 서식처럼 보이기 쉽다. 정보를 칸에 채우지 말고 사람이 설명하듯 쓴다. 문체는 `ken-blog-docs`의 간결체(~했음·~임)를 따른다.

| 하지 않을 것 | 예 | 대신 |
| --- | --- | --- |
| 라벨로 시작하는 메타 문장 | "~의 기록. 둘 다 2026-10-09 측정." / "분류: 확증 실험." | 왜 궁금했는지와 결론으로 시작. 날짜·분류는 문장 속에 |
| 문장 대신 명사 나열 | "원본 agent 서버(커밋 `d94eaf5`)를 고치지 않고 실행. `text-embedding-3-small`, `gpt-4o-mini`" | 주어·동사가 있는 문장. 커밋·모델·버전은 '재현 자료'나 주석으로 |
| 가운뎃점으로 명사 쌓기 | "가설·기각 기준·분석 스크립트를 … 고정" | 풀어서 쓰기("가설과, 어떤 결과면 틀렸다고 볼지를 적어 두고") |
| 한 문장에 숫자 몰아넣기 | "63건 중 41건(65%)… 17건 중 5건(29%)…" | 한 문장에 숫자 둘까지. 나머지는 표 |
| 번역투 신조어 | 정답형, 다의, 실행기, 판별력, 짝지은 | 정답이 있는 질문, 뜻이 애매한 질문, 실험 코드, 가려내는 힘, 같은 질문끼리 |
| 원칙을 가르치는 문장 | "가설을 만든 자료로 그 가설을 다시 검증할 수는 없음." | 한 일을 쓰기("그래서 질문을 새로 써서 다시 확인했음") |
| 접속사 연쇄·굵은 머리말 목록 | "다만… 또… 그래서…" / "**H1을 지지하지 못함.** …" | 문단으로 잇고, 판정은 결과 표에 |
| 무엇이든 표 | 설계·통제·한계를 모두 표로 | 표는 결과에. 설계·한계는 짧은 문단 |

- 개인 경험·감정은 지어내지 않는다. "1부 결과만 보면 ~처럼 보였음"처럼 실제로 일어난 흐름으로 쓴다.
- 가설과 판정 기준처럼 정확해야 하는 것은 표로 남겨도 되지만, 표 앞에 무엇을 왜 정했는지 한두 문장을 둔다.

## 점검 목록

- [ ] 설계(실험·평가·관찰)와 목적(확증·탐색·기술)을 정하고 글에서 문장으로 드러냈다
- [ ] '문장 쓰기'의 금지 패턴(라벨 문장, 명사 나열, 숫자 몰아넣기, 번역투 용어, 원칙 설명)이 없다
- [ ] (확증) 가설을 만든 자료와 다른 새 자료로 검증했다
- [ ] 연구 질문이 P1~Pn 중 하나와 연결된다
- [ ] (확증) 가설·근거·기각 기준을 실행 전에 고정했다
- [ ] 독립·종속·통제 변수와 비교 기준이 있다
- [ ] 표본 수·반복·순서·워밍업을 적었다
- [ ] 비율에 신뢰구간, 지연에 중앙값·p95와 표본 수를 붙였다
- [ ] 예상과 다른 결과와 실패한 실행을 숨기지 않았다
- [ ] 타당성 위협을 네 분류로 점검했다
- [ ] 원자료와 코드의 위치를 밝혔고, 비밀 값이 남지 않았다
