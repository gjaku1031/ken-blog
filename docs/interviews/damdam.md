# 담담공방 쇼핑몰: 인터뷰 요약

문서를 쓰며 확인한 사실과 판단의 이유를 정리한 기록. 블로그에는 게시하지 않음. 마지막 정리 2026-10-24.

## 개발 형태와 담당 범위

- 외주 프로젝트. 지인의 소개로 받았음
- 2인 팀: 프론트엔드 1명, 백엔드와 인프라 1명(본인)
- 본인이 한 일은 의뢰인과의 소통, 검수 의견 대응, 그리고 화면의 UI/UX를 뺀 개발 전부임. '팀 리더'라는 직함은 무엇을 했는지 드러내지 못해 문서에서 빼고, 한 일을 그대로 적음
- 팀 구성은 2인 팀으로 적음
- 2025년 9월에 시작했음. 저장소를 중간에 옮겨 지금 저장소의 이력은 그보다 짧음
- 운영 서버에 배포했고 정식 오픈 전임. 실제 고객의 주문이 없어 운영 DB와 업로드를 비우고 새로 시작했고, 상품과 사진은 예시 자료로 다시 넣었음. 문서에는 정식 오픈 전으로 씀
- 상호와 도메인은 문서에 그대로 씀

## 누가 정했는가

- **무통장 입금만 받음**: 의뢰인의 요구
- **별도의 관리자 화면을 두지 않고 편집 모드로 운영함**: 의뢰인의 요구
- **Redis를 쓰지 않음**: 백엔드와 인프라를 한 사람이 맡고, MAU가 50명에 못 미칠 것으로 예상해 정했음
- **자동 테스트**: 인터뷰 때는 없었고 뒤에 작성하기로 했음. 지금은 API 단위·통합 테스트 129건이 CI에서 돎
- **CSRF 토큰**: 인터뷰 때는 없었고 넣기로 했음. 지금은 상태를 바꾸는 모든 요청이 세션에 묶인 토큰을 실어야 함

## 직접 정한 것

- 재고 설계의 갈림길 16곳, 이미지 최적화, 응답 캐시의 선택은 모두 직접 고안했음. 재고는 비교안을 만들어 놓고 고르는 방식으로 정했음

## 문서 방향으로 정한 것

- 핵심 문제는 재고 정합성, 사진 전송량, 캐시된 응답의 노출 셋으로 잡음
- 기술 스택을 바꾼 이력은 쓰지 않고 현재 스택 기준으로 서술함
- 의뢰인이 이전에 어떻게 팔았는지 같은 개발 배경은 확인된 것이 없어 쓰지 않음. 의뢰 조건과 설계 제약만 적음

- 시스템 구조도는 따로 그리지 않음. 서버 한 대 구성이라 인프라 구성도와 요청 흐름도로 갈음함
- API 설계 문서를 둠. 경로 목록 대신 주문 요청, 상태가 맞지 않는 요청의 거절, 사진 업로드와 제공의 계약을 다룸
- 저장소는 이력을 정리해 공개했음(2026-10-13). 초기 구성까지의 이력은 첫 커밋 하나로 합쳤고, 서버 접속 정보가 적힌 문서는 이력에서 뺐음
- 대문의 사이트 링크가 열리지 않던 문제는 다시 생기지 않아 닫음

## 아직 하지 않은 것

- DB와 사진의 백업을 하지 않음
- 화면은 자동 테스트 대상이 아님. 저장소에 있던 브라우저 검사 묶음은 쓰지 않아 지웠음
