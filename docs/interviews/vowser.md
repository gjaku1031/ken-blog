# Vowser: 인터뷰 요약

문서를 쓰며 확인한 사실과 판단의 이유를 정리한 기록. 블로그에는 게시하지 않음. 마지막 정리 2026-10-24.

## 개발 형태와 담당 범위

- 4명 팀 프로젝트, 팀 리더. 2025년 4월부터 11월까지 진행했고 대회 본선에 진출했음
- 맡은 것
  - 서비스 아이디어 제안과 기획, 대회 발표
  - 인증·회원 백엔드 설계
  - AI 검색 프로토타입: Colab 노트북에서 LangChain·LangGraph로 만든 단계까지. FastAPI 서버로 옮긴 것은 다른 팀원
  - 인프라
- 맡지 않은 것
  - 음성 인식, 에이전트 연동, 제어 채널은 서버 담당 팀원의 작업
  - WebSocket을 단일 연결로 둔 것은 서버 담당 팀원의 결정
  - k6 부하 테스트는 팀 활동이었고 직접 실행하지 않았음

## 판단의 이유

- **경로 저장에 Neo4j를 쓴 이유**
  - 페이지 이동이 그래프로 표현됨
  - MySQL로 하면 자기 참조와 재귀 조회가 필요했음
  - 당시 데이터가 많을 때 Neo4j가 빠르다는 실험을 했음
  - 벡터 검색을 함께 쓸 수 있음
  - 그래프를 눈으로 볼 수 있음
- **검색 임계값 0.43**: 당시 실험으로 정했음
- **부하가 몰릴 때만 클라우드로 확장하는 구조**: 관공서와 소규모 사업장을 위한 접근성 오픈소스 앱이라 평소 부하는 작음. 명절 귀성 예매처럼 순간 부하가 몰릴 때 멈추면 안 되지만, 상시 비용은 부담이었음
- **클라이언트에 Kotlin Compose Multiplatform을 쓴 이유**: 키오스크와 관공서 태블릿으로 넓히는 것을 고려했음. React Native와 비교했고, 팀원이 모두 Java 개발자라 개발 속도를 위해 Kotlin을 골랐음
- **경로·음성 API를 로그인 없이 연 이유**: 로그인하지 않은 사용자도 쓸 수 있게 하려는 의도였음
- **검색 1위를 바로 실행한 이유**: 기간이 짧아 선택 화면을 생략했음. 컨설턴트의 조언을 따랐음

## 대안을 비교하지 않고 정한 것

- 경로를 기록하는 방식, 검색 방식, 실행 위치는 처음부터 정했고 대안을 비교하지 않았음

## 시연과 배포

- 시연은 한 사람이 순서대로 쓰는 방식이었음
- 시연 경로는 팀이 준비했음: KTX 예매(중간의 로그인은 사람이 처리하도록 기다림), 등본 발급, 날씨, 뉴스, 웹툰
- 배포는 GitHub Actions가 Proxmox의 서비스를 다시 띄우는 데까지 자동이었음. 롤백 절차는 없었음
- 클라우드 확장은 실습에서 Fargate의 서버가 실제로 켜지는 것을 보는 데까지 했음. 확장 상태의 부하·성능 시험은 하지 않았음
- 데스크톱 앱은 GitHub Releases로 배포하려 했고, 공개한 릴리스는 없음

## 기록이 남아 있지 않은 것

- Neo4j가 빠르다고 본 실험의 조건과 수치
- 임계값 0.43을 정한 실험의 자료. 2026년에 다시 실험했음
- 클라우드 확장의 비용 계산
- Fargate 실습의 세부 설정
- k6 부하 테스트의 결과

## 따로 공부하기로 한 것

- 의도 검색 실험 글과 경로 저장소 실험 글을 직접 설명할 수 있게 다시 읽기
