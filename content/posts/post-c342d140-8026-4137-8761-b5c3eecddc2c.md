ken-blog의 공개 화면을 브라우저의 API 호출 방식에서 빌드 시 정적 생성으로 바꾼 효과를, 같은 데이터로 재구성한 세 구조에서 측정한 기록. 2026-10-07 측정.

> 정적 생성이 20개 조합 모두에서 본문 표시가 가장 빨랐고, 열람 요청이 API 서버에 도달하지 않음. 이득은 전송량이 아니라 순차 왕복 제거에서 나옴.

## 측정 질문

- **Q1 열람 지연**: 첫 방문·재방문·앱 안 문서 이동에서 본문이 보이기까지의 시간이 줄었는가.
- **Q2 서버 부하**: 독자의 열람 요청이 API 서버의 부하로 이어지는가.

측정 당시 서버는 OCI 일본 리전의 ARM 1코어·약 4GB 단일 VM이었고, 주요 독자는 한국에 있음. 독자 기준 왕복 지연은 약 38.6ms[* 한국의 맥에서 측정 VM까지 ping 30회 평균. 측정 VM은 운영 서버와 같은 도쿄 리전].

## 비교한 세 구조

| 구조 | 커밋 | 본문 위치 | 열람 중 API 호출 |
| --- | --- | --- | --- |
| 순수 CSR | `f29ef35` | HTML에 없음. 스크립트가 API로 받아 렌더링 | 로그인 상태 확인 후 프로젝트·문서 조회, 역링크, 조회수 기록 |
| 하이브리드 | `135169f` | 빌드 시 HTML에 포함 | 순수 CSR의 호출을 그대로 유지 |
| 정적 생성 | `811c95f` | 빌드 시 HTML에 포함. 목록·역링크도 포함 | 로그인 상태 확인 1회 |

하이브리드는 정적 생성으로 전환하기 직전의 운영 구조. 검색엔진 노출을 위해 본문을 미리 렌더링했지만 런타임 API 호출은 남아 있었음.

## 실험 환경과 공정성

| 항목 | 조건 |
| --- | --- |
| 데이터 | 운영 공개 스냅샷과 Git 원고로 글 16개·프로젝트 6개 구성. 두 옛 구현은 같은 마이그레이션 24개와 같은 seed(SHA-256 동일) 사용 |
| 정적 파일 제공 | Caddy 하나로 세 구현 모두 제공. HTTPS·HTTP/2·압축, 운영 GitHub Pages와 같은 캐시 헤더(`max-age=600`, ETag, Last-Modified) |
| API·DB | 옛 API는 운영과 같은 1 CPU·1.5GiB 제한, 격리 MySQL 8.4. 옛 API의 JSON 응답은 원래대로 `no-store` |
| 네트워크 R (실측) | 맥 → 측정 VM 왕복 지연 30회 평균 38.6ms, 다운로드 처리량 5회 중앙값 16.3MB/s를 Chromium에 적용[* DevTools Protocol의 네트워크 조건 에뮬레이션. 업로드는 직접 재지 못해 다운로드와 같은 값 사용] |
| 네트워크 M (참고) | 왕복 지연 150ms, 다운로드 1.6Mbps, 업로드 750kbps[* Lighthouse 등에서 흔히 쓰는 저속 모바일 조건. 특정 망의 실측값이 아님] |
| 반복 | 구조 3개 × 시나리오 5개 × 캐시 2조건 × 네트워크 2조건 × 15회 = 900회. 조합마다 워밍업 2회, 구조 순서 교차 |
| 정적 구조의 로그인 확인 | 운영 API로 보내지 않고 브라우저에서 즉시 401로 응답 |

첫 방문(cold)은 매번 새 브라우저 컨텍스트, 재방문(warm)은 같은 컨텍스트에서 다시 연 경우.

## 지표

- **본문 표시 시각**: 탐색 시작부터 문서 본문의 표식 문장이 화면에 보일 때까지. 앱 안 이동은 링크 클릭부터.
- **서버 API 요청 수**: 실제 API 컨테이너까지 도달한 요청 수.
- **전송량**: 브라우저가 받은 압축 후 바이트.
- **API 서버 CPU**: 첫 방문 ERD 문서 한 번의 실제 요청 목록을 초당 5회씩 60초 재생할 때의 API 컨테이너 CPU(1 CPU 기준).

## 해석

- **순차 왕복이 지연의 주요인.** 순수 CSR은 스크립트 로드 → 로그인 상태 확인 → 본문 조회가 앞 단계 응답을 기다리며 이어져, 왕복 지연이 커질수록 차이가 벌어짐. ERD 첫 방문은 네트워크 R에서 1.6배, 왕복 지연 150ms의 M에서 4.1배 차이.
- **하이브리드는 절반의 개선.** 본문을 HTML에 넣어 첫 방문은 순수 CSR보다 빨라졌지만, 런타임 API 호출과 앱 번들이 남아 정적 생성보다 느렸음. 앱 안 이동은 네트워크 R에서 API를 7회 다시 호출해 순수 CSR보다도 느렸고(701ms 대 414ms), M에서는 반대로 빨라 조건에 따라 순위가 바뀜.
- **이득은 전송량이 아니라 왕복 제거에서 나옴.** 정적 생성의 ERD 첫 방문 전송량은 Mermaid 렌더러를 포함해 세 구조 중 가장 컸음(1,061KB). 그래도 본문 표시가 가장 빨랐던 것은 HTML 응답 하나로 본문이 확정되고 API 응답을 기다리는 단계가 없기 때문. 재방문은 캐시 적중으로 11KB만 전송.
- **열람량과 서버 부하의 분리.** 옛 두 구조는 열람 1회마다 API 요청 6~9회가 1코어 서버에 도달해 초당 5회 열람에서 CPU 최대 42~66%를 사용함. 정적 생성은 열람 요청이 API 서버에 도달하지 않아 열람량이 늘어도 서버 부하가 변하지 않는 구조.

## 1차 측정의 결함과 보정

같은 날 먼저 수행한 1차 측정(640회)은 다음 결함이 있어 결론에 사용하지 않음.

| 결함 | 영향 | 보정 |
| --- | --- | --- |
| 옛 구조로 하이브리드 하나만 비교 | 본문이 이미 HTML에 있어 API 왕복이 본문 표시에 미치는 영향을 측정하지 못함 | 순수 CSR을 추가하고, 앱 안 문서 이동 시나리오 추가 |
| 측정용 서버가 정적 파일에 `Cache-Control` 없이 응답 | 브라우저의 추정 캐시에 의존해 구현마다 재방문 캐시 동작이 달랐음. 정적 구조의 재방문 전송량이 첫 방문과 같아 "재방문은 옛 구조가 빠름"이라는 잘못된 결과가 나옴 | 운영 GitHub Pages의 응답 헤더를 확인해 세 구현에 같은 캐시 정책 적용, 재방문 캐시 적중 확인 |
| 옛 구조의 로그인 확인 요청에서 브라우저 완료 이벤트 누락 | API 순차 단계 수 계산 오류 | 응답 수신 이벤트 기준으로 계산 |

## 한계

- 로컬에 재구성한 환경의 측정. 운영 DB와 CDN을 거치지 않음. 참고로 맥에서 운영 GitHub Pages의 HTML 첫 바이트 시간은 중앙값 33~36ms였음.
- 네트워크 지연은 브라우저의 요청 단위 지연 주입으로 근사함. TCP·TLS 핸드셰이크의 왕복을 정확히 재현하지 않음.
- 세 구조는 화면 스크립트·Mermaid 구현·부가 기능도 다름. 결과를 정적 생성이라는 단일 변경의 효과로 분리할 수 없음.
- 조합당 표본 15회. 결과는 중앙값 중심으로 해석함.
