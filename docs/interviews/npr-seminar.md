# 입시설명회 예약·입장 시스템: 인터뷰 요약

문서를 쓰며 확인한 사실과 판단의 이유를 정리한 기록. 블로그에는 게시하지 않음. 마지막 정리 2026-10-11.

## 개발 형태와 담당 범위

- 3명 팀 프로젝트: 기획 1명, 프론트엔드와 디자인 1명, 백엔드와 인프라 1명(본인)
- 기획 담당은 사용자 관점의 흐름을 잡았고, 세부 화면 경험은 기획과 프론트엔드 담당이 함께 정했음
- 맡은 것
  - 백엔드와 인프라
  - 운영진(대표와 원장)과의 요구사항·일정 조율
  - 현장의 요구를 기능으로 옮기는 일: QR이 읽히지 않을 때를 위한 연락처 뒤 네 자리 수동 입장, 앱이 멈출 때를 걱정한 운영진을 위한 DB 명단의 Google Sheets 대체 명단
- 2026-08-21 설명회를 마친 뒤 서비스를 종료했음

## 개발 배경

- 이전에는 구글폼이나 전화로 예약을 받았음
- 당일에는 종이 명단에서 참석자를 확인했고, 한 명이 종이 기록을 스프레드시트로 옮겼음

## 직접 정한 것

- 예약과 QR을 가족 단위로 묶음
- 연락처를 암호문과 다이제스트로 저장함
- 학생 원천에는 실행마다 로그인을 한 번만 시도함
- 입구의 iPad는 페어링 코드로 연결함
- 운영 VM을 GCP 게이트웨이와 WireGuard로만 연결함

## 판단의 이유

- **같은 가정의 예약이 겹치는 경우**: 부모가 각자 기기로 예약하는 경우와 버튼을 여러 번 누르는 경우가 모두 있었음
- **정원 제한을 없앤 이유**: 행사장의 수용 인원이 충분했음
- **실제로 비교한 대안**: 메시지 큐(Kafka, BullMQ)뿐이었음. 그 밖의 설계는 처음부터 정했음
- **운영 VM**: 학원 안에 둔 개발용 Proxmox 서버였음

## 운영에서 있었던 일

- **입장 처리 500 오류**: 2026-08-16 리허설에서 발견해 바로 고쳤음
- **DB 연결 소진**: 실제 학부모를 대상으로 한 운영에서 일어났고, 문자 77건을 다시 보냈음
- **예약자 테이블 삭제**: 예약 접수를 시작한 첫날, 시트와 DB를 맞추는 작업이 비어 있던 시트를 기준으로 실행돼 예약자 테이블이 지워졌음. 서버 백업의 사본을 둔 학원 NAS에서 복구했음. 이후 운영 DB를 바꾸기 전에 백업을 확인하고 직접 허락하는 절차를 둠

## 기록이 남아 있지 않은 것

- 예약자 테이블 삭제의 정확한 날짜, 손실 범위, 복구에 걸린 시간
- 운영 DB는 서비스 종료로 남아 있지 않음. 스프레드시트는 개인정보가 있어 쓰지 않음

## 문서 방향으로 정한 것

- 학원의 실명과 도메인은 문서와 저장소에서 가림. 캠퍼스 지명은 "세 캠퍼스"처럼 일반화함
- 공개 저장소의 이력에서 공개 IP, 시트 ID, 클라우드 프로젝트 ID를 치환했음
