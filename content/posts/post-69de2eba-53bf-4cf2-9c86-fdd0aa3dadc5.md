[0편](/ken-blog/post/post-df978c72-44d3-4e81-b572-8834cd0646c3/)에서 지도를 그릴 때 "브라우저는 네트워크에 나가기 전에 저장된 응답부터 확인한다"고 적었다. 그런데 나는 API를 만들면서 응답 헤더에 `Cache-Control`을 직접 붙여 본 적이 없다. 안 붙이면 저장을 안 하는 건지, `no-cache`는 이름 그대로 저장하지 말라는 뜻인지부터 헷갈렸다. 그래서 응답을 "다시 묻지 않고 써도 되는지"를 누가, 무엇을 보고 정하는지 정리해 봤다.

## 학습 목표

- 브라우저 캐시와 공유 캐시가 어떻게 다른지, `private`와 `public`이 각각 누구에게 하는 말인지 설명할 수 있다
- `max-age`, `no-cache`, `no-store`, `must-revalidate`, `s-maxage`의 차이를 말할 수 있다
- `ETag`와 `If-None-Match`로 재검증하고 `304 Not Modified`를 받는 흐름을 직접 재현할 수 있다

## 캐시는 반찬 냉장고다

캐시는 한 번 받은 응답을 저장해 두었다가, 같은 요청이 오면 서버에 묻지 않고 저장본을 쓰는 것이다. 나는 이걸 반찬 냉장고로 생각하기로 했다. 엄마(서버)가 반찬(응답)을 보내 주면서 통에 "3일 안에 먹어"라고 적어 준다. 그 안에는 냉장고에서 꺼내 먹으면 되고, 엄마한테 다시 해 달라고 할 필요가 없다.

냉장고는 두 종류다.

| 종류 | 비유 | 실제 | 누가 꺼내 먹나 |
| --- | --- | --- | --- |
| 개인 캐시(private cache) | 우리 집 냉장고 | 브라우저 캐시 | 나 혼자 |
| 공유 캐시(shared cache) | 회사 탕비실 냉장고 | CDN, 프록시의 캐시 | 그곳을 지나는 모든 사람 |

우리 집 냉장고에는 내 이름이 적힌 반찬을 넣어도 괜찮다. 탕비실 냉장고에 넣으면 다른 사람이 꺼내 먹는다. 내 장바구니나 주문 목록 같은 응답이 공유 캐시에 들어가면 다음 사람이 그걸 받는 사고가 난다. 이 이야기는 [6편](/ken-blog/post/post-5b5ec693-9a31-4a67-9053-0381b98c9ddf/)에서 CDN과 함께 다시 본다.

## Cache-Control: 반찬통에 붙이는 쪽지

서버는 응답 헤더 `Cache-Control`로 "이 응답을 어떻게 보관해도 되는지"를 적어 보낸다.[* HTTP 캐시의 표준은 RFC 9111(HTTP Caching)이다. 아래 설명도 이 문서의 정의를 따랐다] 처음 볼 때 가장 헷갈린 값들을 반찬통 쪽지로 바꿔 보면 이렇다.

| 값 | 반찬통 쪽지로 치면 | 실제 뜻 |
| --- | --- | --- |
| `max-age=60` | 60초 안에는 그냥 꺼내 먹어 | 응답이 만들어진 뒤 60초 동안은 신선(fresh)하다. 그동안은 서버에 묻지 않고 쓴다 |
| `no-cache` | 넣어 둬도 되는데, 먹기 전에 매번 전화해서 물어봐 | 저장은 해도 된다. 쓰기 전마다 서버에 재검증해야 한다 |
| `no-store` | 냉장고에 넣지 마 | 어떤 캐시도 저장하면 안 된다 |
| `private` | 우리 집 냉장고에만 | 개인 캐시(브라우저)만 저장할 수 있다 |
| `public` | 탕비실 냉장고에도 넣어도 돼 | 공유 캐시도 저장할 수 있다 |
| `s-maxage=300` | 탕비실 냉장고는 5분 | 공유 캐시에만 적용되는 유효 기간. 공유 캐시는 `max-age`보다 이 값을 먼저 본다 |
| `must-revalidate` | 기한 지나면 반드시 물어보고 먹어 | 유효 기간이 지난(stale) 응답을 재검증 없이 쓰면 안 된다. 서버와 연결이 안 돼도 마찬가지 |

### 헷갈렸던 것: no-cache는 "저장하지 마"가 아니다

이름만 보고 `no-cache`가 저장 금지인 줄 알았다. 저장 금지는 `no-store`이고, `no-cache`는 저장은 하되 쓸 때마다 서버에 확인하라는 뜻이다. 그럼 매번 묻는데 캐시가 무슨 소용인가 싶었는데, 아래에서 볼 재검증 덕분에 내용이 그대로면 본문을 다시 받지 않아도 된다. 묻는 비용은 들지만 받는 비용은 아낀다.

### 헷갈렸던 것: 쪽지가 없으면 저장하지 않는다?

그렇지도 않다. `Cache-Control`이 없고 `Last-Modified` 같은 정보만 있으면, 캐시가 스스로 유효 기간을 어림해서 저장할 수 있다.[* RFC 9111의 heuristic freshness. 표준은 구체적인 계산법을 정하지 않고, 흔히 마지막 수정 뒤 지난 시간의 10%쯤을 쓴다고 예를 든다. 실제 값은 브라우저와 CDN마다 다르다] 쪽지를 안 붙이면 냉장고 주인이 알아서 유통기한을 정하는 셈이라, 저장되면 안 되는 응답에는 `no-store`를 직접 붙여야 한다.

## 재검증: "아직 그대로야?" 하고 묻기

유효 기간이 지났거나 `no-cache`라서 확인이 필요할 때, 브라우저는 응답을 처음부터 다시 받지 않고 "내가 가진 게 아직 최신이야?"라고 묻는다. 이걸 재검증(revalidation)이라고 하고, 조건부 요청(conditional request)으로 한다.[* 조건부 요청과 `304`의 정의는 RFC 9110(HTTP Semantics)에 있다]

- 서버는 처음 응답에 `ETag: "5e39b3ff"`처럼 그 내용을 가리키는 꼬리표를 붙인다. 반찬통 라벨 번호 같은 것이다.
- 브라우저는 다시 물을 때 `If-None-Match: "5e39b3ff"`를 붙인다. "이 번호랑 다르면 새로 줘"라는 뜻이다.
- 내용이 그대로면 서버는 본문 없이 `304 Not Modified`만 보낸다. "그대로야, 그거 먹어." 바뀌었으면 `200`과 새 본문을 보낸다.

`ETag` 대신 날짜로 비교하는 짝도 있다. 서버가 `Last-Modified`를 주면 브라우저는 `If-Modified-Since`로 묻는다. 날짜는 초 단위라 1초 안에 두 번 바뀌면 구분하지 못하므로, 둘 다 있으면 `ETag` 쪽이 먼저 쓰인다.

비유가 안 맞는 곳도 있다. 반찬은 기한이 지나면 상하지만, 응답은 기한이 지나도 내용이 그대로인 경우가 많다. 그래서 기한이 지나면 버리지 않고 재검증부터 하고, 그게 304 한 줄로 끝나는 경우가 많다.

![브라우저는 저장본이 없으면 보통 요청을 보내고, 저장본이 신선하면 서버에 묻지 않고 쓴다. 기한이 지났거나 no-cache면 꼬리표를 들고 재검증해, 내용이 그대로면 본문 없는 304를, 바뀌었으면 새 200을 받는다|dark=194|w=100|a=center](attachment:193)

## 직접 확인해 보기

파이썬으로 작은 서버를 띄워서 같은 본문에 `Cache-Control`만 다르게 붙인 파일 세 개를 만들었다. 서버는 받은 요청과 `If-None-Match`가 있었는지, 몇 번으로 답했는지를 한 줄씩 찍는다.[* 2026-10-23, Linux VM에서 Python 3.14.4의 `http.server`로 만든 서버를 127.0.0.1:18300에 띄우고, curl 8.18.0과 Playwright 1.63.0(Chromium 153)으로 요청했다. 서버 코드는 리소스마다 `Cache-Control`과 같은 `ETag`를 붙이고, `If-None-Match`가 맞으면 304로 답하는 40줄 남짓이다]

| 파일 | 붙인 `Cache-Control` |
| --- | --- |
| `/max-age.js` | `max-age=60` |
| `/no-cache.js` | `no-cache` |
| `/no-store.js` | `no-store` |

먼저 curl로 재검증을 흉내 냈다. 처음 받은 응답의 `ETag`를 그대로 `If-None-Match`에 넣어 다시 보냈다.

```bash
curl -si http://127.0.0.1:18300/no-cache.js
```

```text
HTTP/1.1 200 OK
Content-Type: text/javascript
Content-Length: 22
ETag: "5e39b3ff"
Cache-Control: no-cache

console.log('hello');
```

```bash
curl -si -H 'If-None-Match: "5e39b3ff"' http://127.0.0.1:18300/no-cache.js
```

```text
HTTP/1.1 304 Not Modified
ETag: "5e39b3ff"
Cache-Control: no-cache
```

| 출력 | 뜻 |
| --- | --- |
| 첫 응답의 `ETag: "5e39b3ff"` | 이 내용의 꼬리표 |
| 두 번째 요청의 `If-None-Match` | "이 꼬리표랑 같으면 안 줘도 돼" |
| `304 Not Modified`, 본문 없음 | 그대로이니 가진 걸 쓰라는 답. `Content-Length`도 본문도 없다 |

`Server`와 `Date` 줄은 지면을 아끼려고 지웠다. 같은 꼬리표를 `/no-store.js`에 보내면 내 서버는 304 대신 200과 본문을 돌려주게 만들었다. 저장하면 안 되는 응답이니 브라우저가 꼬리표를 들고 올 일도 원래는 없다.

다음은 진짜 브라우저다. 세 파일을 모두 불러오는 페이지 `/a`와 `/b`를 만들고, 같은 브라우저 창에서 `/a`를 연 다음 `/b`를 열었다. 서버 로그는 이렇게 찍혔다.

```text
--- 브라우저로 /a 열기
/a             -> 200
/no-store.js   (조건 없음) -> 200
/max-age.js    (조건 없음) -> 200
/no-cache.js   (조건 없음) -> 200
--- 브라우저로 /b 열기
/b             -> 200
/no-store.js   (조건 없음) -> 200
/no-cache.js   If-None-Match: "5e39b3ff" -> 304
```

| 파일 | 두 번째 방문에서 | 이유 |
| --- | --- | --- |
| `max-age.js` | 서버 로그에 아예 없음 | 60초가 안 지나 신선하므로 묻지도 않고 저장본을 씀 |
| `no-cache.js` | `If-None-Match`를 들고 와서 304를 받음 | 저장은 했지만 쓰기 전에 재검증함 |
| `no-store.js` | 조건 없이 다시 200을 받음 | 저장하지 않았으니 처음부터 다시 받음 |

표로 외울 때보다 로그 세 줄이 훨씬 잘 들어왔다. 특히 `max-age.js`는 요청이 서버에 오지도 않아서, 서버 쪽에서는 "브라우저가 캐시를 썼다"는 사실을 알 방법이 없다는 게 새로웠다. 반대로 말하면 `max-age`를 길게 준 파일을 고쳐 배포해도, 이미 받아 간 브라우저는 기한이 끝날 때까지 옛 파일을 쓴다. 그래서 정적 파일은 이름에 내용 해시를 넣고(`app.3f2a1c.js`) 내용이 바뀌면 주소 자체를 바꾸는 방식을 많이 쓴다고 한다.[* 이 방식은 확인한 것이 아니라 정리하면서 알게 된 관행이다. 주소가 바뀌면 캐시 입장에서는 다른 응답이라 옛 저장본과 겹치지 않는다]

마지막으로 실제 사이트 두 곳의 쪽지를 봤다.

```bash
curl -s -o /dev/null -D - https://github.com/ | grep -i cache-control
```

```text
cache-control: max-age=0, private, must-revalidate
```

```bash
curl -s -o /dev/null -D - https://developer.mozilla.org/en-US/ | grep -i cache-control
```

```text
cache-control: public, max-age=3600
```

로그인하면 사람마다 화면이 달라지는 GitHub 첫 화면은 `private`(우리 집 냉장고에만)에 `max-age=0`(바로 기한 지남)과 `must-revalidate`(반드시 물어보기)를 붙였다. 누구에게나 같은 문서인 MDN은 `public, max-age=3600`으로 공유 캐시에 1시간 저장을 허락한다. 응답이 사람마다 다른지가 쪽지를 고르는 기준이라는 걸 실제 사이트에서 확인했다.

> 캐시는 서버가 응답에 붙인 쪽지대로 움직인다. `max-age` 동안은 묻지 않고 쓰고, 그 뒤나 `no-cache`일 때는 `ETag`로 "아직 그대로야?"를 묻고, `no-store`면 아예 저장하지 않는다.

## 확인 질문

**1. `no-cache`와 `no-store`는 어떻게 다를까?**

<details><summary>답</summary>

`no-cache`는 저장은 해도 되지만 쓸 때마다 서버에 재검증하라는 뜻이고, `no-store`는 어디에도 저장하지 말라는 뜻이다. 실습에서도 두 번째 방문 때 `no-cache.js`는 `If-None-Match`를 들고 와서 304를 받았고, `no-store.js`는 조건 없이 처음부터 다시 받았다.

</details>

**2. `max-age=60`인 파일을 30초 뒤 다시 열면 서버는 그 사실을 알 수 있을까?**

<details><summary>답</summary>

알 수 없다. 응답이 아직 신선하면 브라우저는 서버에 요청을 보내지 않고 저장본을 쓰기 때문이다. 실습의 서버 로그에서도 두 번째 방문 때 `max-age.js` 줄이 아예 없었다.

</details>

**3. 304 응답에는 왜 본문이 없을까?**

<details><summary>답</summary>

304는 "네가 가진 것과 같다"는 답이라 본문을 보낼 필요가 없다. 브라우저는 이미 저장해 둔 본문을 그대로 쓰고, 304에 실려 온 헤더로 저장본의 정보(유효 기간 등)를 새로 고친다.

</details>

**4. 로그인한 사람마다 내용이 다른 응답에는 `public`과 `private` 중 무엇을 붙여야 할까?**

<details><summary>답</summary>

`private`. `public`이면 CDN 같은 공유 캐시가 저장해서 다른 사람에게 줄 수 있다. 아예 저장되면 안 되는 내용이면 `no-store`를 붙인다. 공유 캐시에서 생기는 사고는 [6편](/ken-blog/post/post-5b5ec693-9a31-4a67-9053-0381b98c9ddf/), 사람을 구분하는 쿠키는 [4편](/ken-blog/post/post-3af3de8c-228f-45d9-b316-c16924e45bd9/)에서 다룬다.

</details>

**5. 응답에 `Cache-Control`을 아예 붙이지 않으면 캐시되지 않을까?**

<details><summary>답</summary>

꼭 그렇지 않다. `Last-Modified` 같은 정보가 있으면 캐시가 유효 기간을 어림해서 저장할 수 있다(heuristic freshness). 저장되면 안 되는 응답이라면 `no-store`를 직접 붙여야 한다.

</details>
