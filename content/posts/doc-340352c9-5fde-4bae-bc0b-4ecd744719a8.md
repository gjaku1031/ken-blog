Git의 Markdown 원고, MySQL의 글 정보, 디스크의 이미지를 빌드 시 결합해 GitHub Pages로 공개하는 정적 블로그의 구조. 구성 요소의 책임과, 세 저장소에 나뉜 자료를 어느 범위까지 일관되게 발행하는지를 다룸. 핵심 문제 P1~P3는 [대문](/ken-blog/post/project-06840552-43a2-4870-83a9-d3e848c71d7e/)에서 정의함.

## 일관성 모델과 보장 범위

자료가 Git·DB·디스크 세 저장소에 나뉘어 있어 하나의 트랜잭션으로 묶을 수 없음. 대신 경계마다 보장 수준을 정하고, 보장하지 않는 구간을 명시함.

| 경계 | 보장 | 방법 | 보장하지 않는 구간 |
| --- | --- | --- | --- |
| 관리자 편집 | 갱신 손실(lost update) 방지 | 편집 버전 비교(불일치 시 409)와 글 행 비관적 잠금 | 첨부 연결 교체는 별도 트랜잭션 |
| 스냅샷 수집 | 한 시점의 공개 자료로 페이지 생성 | 스냅샷을 한 트랜잭션에서 조회하고, 이미지 수집 중 변경은 revision으로 감지 | — |
| Git 원고 | 빌드한 원고가 배포 시점의 `main`과 같음 | 배포 직전 `main`의 사이트 입력 재확인 | 마지막 확인부터 배포 완료까지[* 확인 시점과 사용 시점 사이에 상태가 바뀔 수 있는 TOCTOU(time-of-check to time-of-use) 구간] |
| DB → 공개 사이트 | 최종적 일관성 | 다음 Pages 배포에서 반영 | 자동 배포가 없어 반영 시점이 정해지지 않음 |
| 빌드 실패 | 마지막 정상 배포 유지 | 검증을 통과한 결과만 배포 | — |

> 관리 상태는 DB 트랜잭션으로 즉시 일관되고, 공개 상태는 배포 시점에 하나의 revision으로 맞춰짐.

### 관리자 편집: 편집 버전과 행 잠금

관리 화면은 글을 불러올 때 받은 편집 버전을 저장 요청에 함께 보냄. API는 글 행을 비관적 잠금(`PESSIMISTIC_WRITE`)으로 잡은 뒤 요청의 기준 버전과 현재 `edit_version`을 비교하고, 다르면 409로 거부함. HTTP 요청 사이에 생긴 충돌은 버전 비교(낙관적 동시성 제어)로 감지하고, 비교와 쓰기 사이에 다른 트랜잭션이 끼어드는 것은 행 잠금으로 막는 구조. [글 서비스](https://github.com/gjaku1031/ken-blog/blob/3074d80/src/main/java/io/github/gjaku1031/kenblog/post/service/PostService.java) · [잠금 조회](https://github.com/gjaku1031/ken-blog/blob/3074d80/src/main/java/io/github/gjaku1031/kenblog/post/repository/PostRepository.java)

메타데이터와 태그는 한 트랜잭션으로 바뀌지만, 첨부 연결 교체는 별도 트랜잭션이라 메타데이터 변경과 원자적으로 묶이지 않음.

통합 테스트에서 같은 버전으로 동시에 저장하면 하나만 성공하는지(`concurrentEditorsHaveOneWinner`), 낡은 버전의 저장이 거부되고 변경 전체가 롤백되는지(`atomicEditsRejectStaleVersionsAndRollback`) 확인함. [영속성 통합 테스트](https://github.com/gjaku1031/ken-blog/blob/3074d80/src/test/java/io/github/gjaku1031/kenblog/PostPersistenceIntegrationTest.java)

### 공개 사이트: revision 검증과 최종적 일관성

빌더는 공개 스냅샷 API에서 공개 글 정보·탐색 목록·revision을 한 번에 받음. API는 이를 한 트랜잭션 안에서 조회함. 이후 첨부와 기술 배지 이미지를 따로 내려받는 동안 관리자가 글 정보를 바꿀 수 있으므로, 페이지 생성을 마친 뒤 스냅샷을 다시 받아 revision[* 공개 글 정보 JSON과 글별 첨부의 ID·저장 위치·MIME·크기·상태·수정 시각을 합쳐 계산한 SHA-256]을 비교함. 다르면 생성 결과를 버리고 빌드를 실패로 끝냄. 잠금 없이 읽고, 결과를 확정하기 직전에 변경 여부를 검사하는 낙관적 검증 방식. [스냅샷 서비스](https://github.com/gjaku1031/ken-blog/blob/3074d80/src/main/java/io/github/gjaku1031/kenblog/pages/PagesSnapshotService.java) · [빌더](https://github.com/gjaku1031/ken-blog/blob/3074d80/.github/pages/build.mjs)

```mermaid caption="사이트 생성 순서. revision을 수집 시작과 페이지 생성 후 두 번 받아 비교하고, 배포 직전 main의 사이트 입력 변경을 다시 확인함. 실선은 요청, 점선은 응답"
sequenceDiagram
    participant Build as Build job
    participant API as Spring Boot API
    participant Git as Git main
    participant Deploy as Deploy job
    participant Pages as GitHub Pages
    Build->>Git: checkout manuscripts
    Build->>API: GET snapshot
    API-->>Build: metadata, navigation, revision r0
    Build->>API: GET attachments and badges
    API-->>Build: image files
    Note over Build: render and check pages in staging
    Build->>API: GET snapshot
    API-->>Build: revision r1
    alt r1 differs from r0
        Note over Build: discard staging and fail
    else r1 equals r0
        Note over Build: replace output with staging
    end
    Deploy->>Git: fetch main
    alt site inputs changed
        Note over Deploy: stop deploy
    else unchanged
        Deploy->>Pages: publish artifact
    end
```

원고·이미지 누락, 첨부 접근 거부, 잘못된 MIME·이미지 시그니처도 빌드 실패 조건. 실패하면 Pages 배포를 진행하지 않아 공개 중인 사이트가 그대로 유지됨.

DB의 변경은 Pages 배포를 자동으로 실행하지 않음. 배포는 원고·웹 소스가 `main`에 push되거나 운영자가 워크플로를 수동 실행할 때만 일어남. 따라서 글 정보 변경과 발행 취소는 다음 배포 전까지 공개 사이트에 반영되지 않고, 발행을 취소한 글도 그동안 공개된 채 남음. [Pages 워크플로](https://github.com/gjaku1031/ken-blog/blob/3074d80/.github/workflows/pages.yml)

## 장애 영향과 가용성

| 실패 지점 | 영향 |
| --- | --- |
| API·DB | 관리 기능과 새 사이트 빌드 중단. 이미 배포한 공개 사이트는 영향 없음 |
| 이미지 원본 | 해당 이미지를 요구하는 새 빌드 실패. 배포된 정적 복사본은 유지 |
| 사이트 빌드 | 이번 변경의 공개 반영 중단. 기존 배포는 유지 |
| GitHub Pages | 공개 사이트 열람 불가. API로 대체 제공하는 경로 없음 |

공개 글 열람은 GitHub Pages만 사용하므로 VM·API·DB 장애와 분리됨. 정적 생성 구조의 [열람 지연 측정](/ken-blog/post/post-c342d140-8026-4137-8761-b5c3eecddc2c/)은 API 서버에 요청을 한 번도 보내지 않고 수행했고, 모든 시나리오에서 본문이 표시됨.

반대로 관리 기능과 새 빌드는 단일 VM의 API에 의존해 이 VM이 단일 장애점. 원고는 Git, 글 정보는 관리형 DB, 이미지는 VM 디스크에 있어 저장소마다 백업 방식이 다르며, 세 자료를 같은 시점으로 함께 복구하는 것은 보장하지 않음.

## 영속 계층

쓰기·단일 조회·잠금은 JPA, 목록·검색·집계·공개 스냅샷 조회는 jOOQ가 담당하고 같은 데이터 소스와 Spring 트랜잭션을 공유함. 목록·검색·집계 조회는 선택 조건과 조인이 많아 JPQL 문자열로 유지하기 복잡했고, QueryDSL은 업데이트가 제대로 이어지지 않는다고 판단해 이 조회만 jOOQ로 작성함([기술적 의사결정과 검증](/ken-blog/post/doc-267e2237-7f38-4ea1-b04b-7c51d456c2b4/) 참조). jOOQ 타입은 JPA 엔티티에서 생성한 DDL로 만들어 스키마 정의를 한곳에 유지함. 코드 생성 순서와 대가는 [JPA 기반 코드 생성 ADR](/ken-blog/post/post-f69cf0bb-68a1-4b72-b6c9-6aea1ed04db9/) 참조.
