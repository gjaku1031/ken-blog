# 주석 컨벤션

상태: 적용. 작성일: 2026-10-03.

전체 코드에 적용한 주석 기준이다. 이후 코드를 추가하거나 수정할 때도 같은 기준을 따른다.

## 적용 범위

- Java 애플리케이션·테스트의 선언 문서는 Javadoc으로 작성한다.
- Java 구현 내부와 Gradle Groovy DSL의 설명에는 일반 주석을 사용한다.
- TypeScript·JavaScript·CSS·SQL·템플릿·배포 설정에도 아래의 내용·문체·유지보수 원칙을 적용한다. Javadoc 태그와 심볼 링크 문법은 Java에만 적용한다.
- 생성 코드, Gradle Wrapper, 외부 라이선스 고지는 컨벤션 정리를 위해 직접 수정하지 않는다. 게시글 본문과 본문의 각주는 코드 주석에 포함하지 않는다.

## 무엇을 설명하는가

각 선언과 의미 있는 코드 구간에 역할을 설명하는 주석을 반드시 붙인다. 이름이나 구현이 단순해도 생략하지 않고 짧게 작성한다. 복잡한 로직에는 처리 흐름과 그 순서가 필요한 이유를 추가한다.

- 호출자가 알아야 하는 입력 범위, `null`·빈 값·생략의 차이, 반환 순서, 단위, 공개 범위를 적는다.
- 트랜잭션 참여 조건, 잠금 순서, 실패 시 롤백 범위, 파일·스트림 해제 책임처럼 동작에 영향을 주는 조건을 적는다.
- 구현 내부에서는 특정 분기나 처리 순서를 유지해야 하는 이유를 해당 코드 가까이에 적는다.
- 단순한 선언은 짧은 역할 설명을 남긴다. 설명을 줄일 때도 선언의 주석 자체를 제거하지 않는다.
- 테스트 메서드에도 검증 대상과 기대 결과를 짧게 적는다. 준비 과정의 이유나 재현 조건이 복잡하면 흐름 설명을 추가한다.

## 주석 필수 대상

직접 작성하는 코드의 다음 단위에는 빠짐없이 주석을 작성한다. 접근 제어자, 선언 길이, 이름의 명확성에 따른 예외를 두지 않는다.

| 대상 | 설명할 내용 |
| --- | --- |
| 클래스·인터페이스·record | 타입의 역할 |
| enum과 각 항목 | 값의 종류와 각 항목의 의미 |
| 메서드·함수 | 수행하는 작업과 필요한 호출 조건. 정적·인스턴스 메서드, `private`, `@Override`, 테스트·헬퍼 메서드도 포함 |
| 프로퍼티·필드·상수 | 값의 역할. 엔티티·DTO·설정·record 구성요소·의존성 필드도 포함 |
| 생성자·초기화 블록 | 초기화 목적과 조건. 명시적인 생성자는 각각 Javadoc 작성. record·Lombok이 생성한 생성자는 타입·필드 주석으로 역할과 필요한 계약 설명. 초기화 블록은 바로 위에 일반 주석 작성 |
| 직접 구현한 접근자 | getter·setter의 계산이나 변경 역할 |
| 처리 구간·콜백·설정 구간 | 입력 검증, 조회, 변환, 저장, 응답 조립, 이벤트 처리 등 해당 구간의 목적 |

Java 선언에는 여러 줄 Javadoc을 사용하고, 구현 내부의 처리 구간에는 `//`를 사용한다. TypeScript·JavaScript 선언에는 여러 줄 문서 주석을 사용하며, 다른 파일은 해당 형식이 지원하는 주석을 사용한다. 주석 문법이 없는 JSON 등의 파일에는 주석을 억지로 삽입하지 않고 관련 문서에 설명한다.

클래스 주석으로 내부 메서드·프로퍼티 설명을 대신하지 않는다. 구현 내부는 함께 수행되는 문장들을 의미 단위로 묶어 설명하며, 같은 목적의 모든 대입문마다 같은 설명을 반복할 필요는 없다.

## 문체와 정확성

- 설명은 한국어로 작성하고 코드 식별자, 표준명, 프로토콜명은 원래 표기를 사용한다.
- 요약·상세 설명·태그는 명사구 또는 `~함`, `~됨`, `~임`, `~엶`처럼 간결한 형태로 쓴다. `~한다.`, `~이다.`로 문장을 길게 풀어 쓰지 않는다.
- 문맥상 의미가 명확하면 `ID`, `제목`, `생성 시각`처럼 짧게 적는다. 설명을 늘리기 위해 주어나 어노테이션의 의미를 반복하지 않는다. 짧은 설명 끝의 마침표는 생략한다.
- 간결하게 줄이더라도 입력 조건, 예외 조건, 자원 해제 책임처럼 필요한 정보는 남긴다.
- `원본처럼`, `이전과 동일`, `안전한`, `구체 서비스`만으로 설명을 끝내지 않는다. 현재 어떤 조건과 동작을 보장하는지 적는다.
- 보장 범위는 구현과 일치해야 한다. 예외 객체 생성, 예외 발생, HTTP 오류 응답 변환을 서로 구분한다.
- 과거 구조를 설명해야 하면 현재도 유지하는 호환 조건을 명시한다. 결정 배경과 변경 이력은 관련 [ADR](../ADR/README.md)에 두고 필요한 부분만 연결한다.
- 비밀번호·토큰·개인 경로를 예제로 넣지 않는다. 주석 처리한 폐기 코드를 남기지 않는다.

## Javadoc 형식

Javadoc을 문서화할 선언과 그 어노테이션 바로 위에 둔다. 첫 문단에는 그 선언의 책임을 요약하고, 상세 설명과 태그는 빈 줄로 구분한다. Javadoc의 `{@link Type#method()}`·`{@code value}`와 표준 태그를 사용한다.

### 선언 사이의 간격

- 앞선 선언·코드 구간과 다음 Javadoc 블록 사이에는 빈 줄 한 줄을 둔다. record 구성요소, DTO 필드, 의존성 필드, enum 항목, 메서드에도 같은 기준 적용.
- Javadoc의 닫는 ` */`와 해당 선언의 첫 어노테이션 또는 선언 사이에는 빈 줄을 넣지 않는다. 주석과 설명 대상은 하나의 묶음으로 유지.
- 파일 첫 선언이나 여는 `{`, `(`, `[` 바로 뒤의 첫 주석 앞에는 구분용 빈 줄을 추가하지 않는다.
- TypeScript·JavaScript의 문서 주석과 선언 사이에도 같은 간격 적용.

```java
/**
 * 공개 페이지 스냅샷 생성
 */
@RequiredArgsConstructor
public final class PagesSnapshotService {
    /**
     * 공개 글 메타데이터 서비스
     */
    private final PublicPostService posts;

    /**
     * 시리즈 서비스
     */
    private final SeriesService series;
}
```

위 예시는 `lombok.RequiredArgsConstructor`를 import하여 사용. 단순 주입 생성자는
[생성자 주입 규칙](CODE.md#생성자-주입)에 따라 자동 생성하고 각 의존성의 설명은 필드에 유지.
직접 작성한 생성자를 대체할 때 입력·예외 계약이 있었다면 관련 타입·필드 설명으로 보존.

### 여러 줄 작성

내용 길이나 태그 유무와 관계없이 항상 여러 줄로 작성한다. 한 단어뿐이어도 한 줄 Javadoc은 허용하지 않는다. 여는 `/**`와 닫는 ` */`는 각각 독립된 줄에 두고, 본문의 각 줄은 ` *`로 시작한다.

```java
/**
 * 게시글·첨부 연결 키
 */
```

상세 조건이나 태그도 같은 형식 안에 작성한다. `/**` 다음에 불필요한 빈 줄을 넣지 않는다. 요약 없이 `@return`, `@param`, `@throws`만 작성하지 않는다.

```java
/**
 * 저장 루트 내 이미지 파일을 읽기 전용으로 엶
 *
 * 심볼릭 링크 거부
 * 반환한 스트림은 호출자가 닫아야 함
 *
 * @param key 저장 루트를 기준으로 한 객체의 상대 경로
 * @return 호출자가 닫아야 하는 파일 스트림
 * @throws AttachmentFailure 경로가 허용되지 않거나 파일을 열 수 없을 때
 */
```

예시는 주석 구조를 보여준다. 실제로 적용할 때는 해당 함수의 입력·반환값·예외 조건과 대조한다.

## 엔티티 프로퍼티

엔티티의 각 프로퍼티에는 무엇을 나타내는 값인지 짧은 Javadoc을 붙인다. 가독성을 위해 `id`, `title`처럼 이름이 명확한 프로퍼티도 생략하지 않는다.

접근 제어자와 JPA 프록시 설정은 [CODE.md](CODE.md)의 엔티티 규칙 적용. 필드는 `private`, 조회용 getter는 `public`, setter는 `protected`로 두며 엔티티 클래스와 접근자에 `final`을 붙이지 않는다.

- PK, 일반 컬럼, FK·연관관계, 복합 키와 그 구성 프로퍼티를 포함한다. `private` 프로퍼티와 호환용 필드에도 적용한다.
- Javadoc은 해당 프로퍼티의 첫 어노테이션 바로 위에 둔다. 어노테이션이 없으면 프로퍼티 선언 바로 위에 둔다. record 구성요소도 같은 위치 규칙을 따른다.
- 짧은 명사구로 값의 역할을 설명하고, 해석에 필요한 경우에만 `null`의 의미, 단위, 생성 주체, 호환 목적을 덧붙인다.
- 엔티티 문맥에서 뜻이 분명하면 `ID`, `제목`만 적어도 된다. 다른 대상을 참조하면 `게시글 ID`, `시리즈 ID`처럼 구분한다. `DB 자동 생성` 등 어노테이션에서 드러나는 내용을 매번 풀어 설명하지 않는다.
- 각 프로퍼티를 읽는 위치에서 설명이 보이도록 작성한다. 클래스의 태그 목록으로 대신하거나 같은 설명을 중복하지 않는다.

```java
/**
 * ID
 */
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

## 태그와 참조

태그는 시그니처에 드러나지 않는 계약을 보완할 때 사용한다. 모든 인자·프로퍼티에 태그를 기계적으로 추가하거나 요약을 그대로 반복하지 않는다. 엔티티 프로퍼티의 짧은 설명에는 태그가 필요하지 않다.

`{@link Type#member}`·`@throws ExceptionType`의 타입은 [import 규칙](CODE.md#import와-타입-참조)에 따라 파일 상단의 import를 공유하고 단순 이름으로 작성한다. 주석에서만 사용하는 타입도 동일하게 적용한다.

| 문법 | 작성 기준 |
| --- | --- |
| `@param name` | 입력 범위, 단위, 생략·빈 값의 의미 등 추가 설명이 필요한 인자에 사용한다. 이름은 실제 인자와 일치해야 한다. |
| `@return` | 반환값의 의미, 정렬, `null`·빈 결과, 자원 소유권을 설명한다. `void` 메서드에 사용하지 않는다. |
| `@throws ExceptionType` | 호출자가 알아야 하는 예외 타입과 발생 조건을 적는다. HTTP 상태만 반환값처럼 적지 않는다. |
| `{@link Type#member}` | 실제로 참조할 수 있는 타입·함수·프로퍼티를 연결한다. 자기 자신을 연결하며 역할을 반복하지 않는다. |
| `{@code literal}` | 경로, 설정 키, SQL 열, 리터럴 등 코드 심볼이 아닌 값을 표시한다. |

태그는 각각 새 줄에 두고, 사용한 태그는 `@param` → `@return` → `@throws` 순서로 정리한다. `@param`은 선언의 인자 순서를 따른다. 이는 이 프로젝트의 정렬 기준이다.

항상 예외를 던지는 함수는 반환 설명을 만들지 않는다.

```java
/**
 * 기술 뱃지 입력 오류 발생
 *
 * @throws BusinessException 입력이 기술 뱃지 규칙을 벗어났을 때
 */
private void badInput() {
    throw new BusinessException(HttpStatus.BAD_REQUEST, "기술 뱃지 입력을 확인하세요.");
}
```

반대로 예외 객체를 만들어 반환하는 함수는 `@return`에 예외 객체라고 적는다. 직접 예외를 던지는 것처럼 문서화하지 않는다.

## 복잡한 처리 흐름

여러 단계의 처리, 중첩 분기·반복, 트랜잭션·잠금, 비동기 처리, 재시도·실패 복구처럼 순서나 조건을 따라가야 하는 코드에는 흐름 설명을 반드시 추가한다.

- 선언의 Javadoc에는 요약 뒤에 주요 처리 순서를 적는다. 단계가 여러 개면 번호 목록으로 정리한다.
- 구현 내부의 각 처리 구간 바로 위에는 `//`로 그 단계의 목적을 적는다. 분기 기준, 조기 종료 조건, 다음 단계로 넘어가는 조건도 필요한 위치에 설명한다.
- 순서가 중요하면 이유를 적는다. 예를 들어 검증을 삭제보다 먼저 수행하는 이유, 잠금 취득 순서, 실패 시 함께 롤백되는 범위를 명시한다.
- 요약만으로 내부 흐름 설명을 대신하거나 `1단계`, `처리 시작`처럼 내용 없는 구획 이름만 붙이지 않는다.
- 흐름 설명도 명사구·`~함` 형태로 짧게 쓰되, 중요한 조건과 실패 경로를 생략하지 않는다.

다음은 기존 첨부 연결 교체 로직에 흐름 설명을 붙인 예시이다.

```java
/**
 * 게시글 첨부 연결 전체 교체
 *
 * 호출자가 부모 글을 잠근 쓰기 트랜잭션 안에서 실행
 * 실패 시 호출자의 글 변경과 연결 교체가 함께 롤백됨
 *
 * 1. 첨부 ID 중복 제거 및 정렬
 * 2. ID 순서로 잠금 취득 후 READY 상태 확인
 * 3. 기존 연결 삭제 후 새 연결 저장, 빈 목록이면 해제만 수행
 */
private void replacePostInTransaction(long postId, List<Long> ids) {
    // 잠금 순서를 일정하게 유지하기 위해 중복 제거 후 정렬
    var normalized = ids.stream().distinct().sorted().toList();

    // 유효하지 않은 첨부가 있으면 기존 연결 삭제 전에 실패
    lockReady(normalized);

    // 검증 완료 후 전체 교체, 빈 목록이면 기존 연결만 해제
    posts.deleteByPostId(postId);
    if (!normalized.isEmpty()) {
        posts.saveAllAndFlush(normalized.stream()
            .map(id -> new PostAttachmentEntity(postId, id)).toList());
    }
}
```

## 일반 주석과 다른 언어

- Java·TypeScript·JavaScript의 처리 단계와 이유는 `//`로 작성한다. `/** ... */`를 구획 구분선이나 실행문 묶음의 제목으로 사용하지 않는다.
- TypeScript·JavaScript 선언 문서도 항상 여러 줄로 작성하되, 태그와 참조는 해당 언어의 문서 주석 문법을 사용한다. Java의 `{@link Type#member}` 참조 문법을 그대로 옮기지 않는다.
- 짧은 `/* ... */`는 빈 `catch`처럼 코드 내부에서 설명이 필요한 곳에 사용할 수 있다. 실패를 무시해도 되는 이유와 그 뒤의 대체 동작을 적는다.
- CSS는 `/* ... */`, SQL은 `--`, YAML·환경 설정은 `#`, Nunjucks는 `{# ... #}` 등 파일 형식에 맞게 작성한다.
- `TODO`·`FIXME`가 필요하면 남은 작업, 필요한 이유, 해소 조건이나 관련 이슈를 함께 적는다. 완료되면 제거한다.

## 변경 시 확인

- 동작·이름·책임이 바뀌면 관련 주석도 함께 갱신하거나 제거한다.
- 요약, 태그, 심볼 링크가 현재 선언과 일치하는지 확인한다.
- 추가·수정한 모든 선언과 처리 구간에 역할 설명이 있는지 확인한다. `private`·`@Override`·테스트·헬퍼도 빠뜨리지 않는다.
- 앞선 선언과 다음 문서 주석 사이에 빈 줄 한 줄이 있고, 문서 주석과 설명 대상 선언·어노테이션은 붙어 있는지 확인한다.
- 엔티티를 추가하거나 프로퍼티를 수정할 때 해당 프로퍼티의 어노테이션 위에 역할을 설명하는 Javadoc이 있는지 확인한다.
- 복잡한 로직에는 Javadoc의 전체 흐름과 구현 내부의 단계·분기 설명이 모두 있는지 확인한다.
- 주석 안의 중복 설명은 줄이되 필수 주석과 잠금·자원 해제·공개 범위·호환 조건의 근거는 보존한다. 선언이 남아 있으면 주석도 현재 역할에 맞게 유지한다.
- 컨벤션 준수 여부와 코드 동작 검증을 구분한다. 주석 형식 확인만으로 동작이나 링크 해석까지 검증했다고 보고하지 않는다.
