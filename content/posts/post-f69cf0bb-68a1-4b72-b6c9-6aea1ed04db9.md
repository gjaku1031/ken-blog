ken-blog는 저장과 단건 조회, 행 잠금은 JPA로, 목록과 집계, 공개 스냅샷 조회는 jOOQ로 처리한다. jOOQ는 테이블마다 Java 타입을 만들어 쓰는데, 그 타입을 무엇에서 만들지가 문제였다. JPA 엔티티에서 Hibernate로 뽑은 DDL로 만들기로 했고, 그러려면 앱과 생성 타입이 서로를 기다리는 컴파일 순서를 풀어야 했다. 엔티티만 먼저 컴파일하는 단계를 따로 두어 해결했다.

## 계기: 같은 테이블을 두 번 적지 않으려면

JPA와 jOOQ는 같은 MySQL을 쓴다. 그래서 엔티티의 매핑과 jOOQ가 만든 테이블 타입이 어긋나면 안 된다.[* jOOQ 코드 생성: 스키마를 읽어 테이블과 열마다 Java 클래스를 만드는 단계다. 조회 코드는 이 클래스로 열 이름과 타입을 컴파일 시점에 검사받는다] jOOQ 타입을 만들 재료를 어디서 가져올지 세 가지를 비교했다.

| 재료 | 좋은 점 | 판단 |
|---|---|---|
| 손으로 쓴 `schema.sql` | 입력이 단순하고 직접 읽을 수 있다 | 엔티티와 SQL을 늘 함께 고쳐야 해서 뺐다 |
| 실제 DB를 읽기(역공학) | 반영된 DB 구조를 그대로 읽는다 | 빌드가 DB 접속, 네트워크, 스키마 준비 순서에 기대게 되어 뺐다 |
| 앱의 Hibernate로 엔티티에서 DDL을 뽑기(고른 쪽) | 앱과 같은 매핑과 이름 정책을 쓰고, DB 없이 만든다 | 먼저 컴파일하는 단계와 생성 태스크를 계속 유지해야 한다 |

jOOQ가 제공하는 `JPADatabase`도 엔티티를 바로 읽을 수 있지만, 당시 jOOQ 3.21.8 확장과 앱의 Hibernate 7.4, MySQL 매핑을 맞추는 비용이 있어 고르지 않았다. 그때의 조합에 대한 판단이고, 이후 버전에도 같은 제약이 있다고 보지는 않는다.

## 걸림돌: 앱과 생성 타입이 서로를 기다렸다

고른 방법에는 순서 문제가 있었다. 앱은 jOOQ가 만든 타입이 있어야 컴파일되는데, 그 타입은 DDL에서 나오고, DDL은 컴파일된 엔티티에서 나온다. 엔티티는 앱과 같은 소스에 있다. 그래서 앱 전체를 먼저 컴파일하려 하면 순환이 생긴다.

![앱 전체를 한 번에 컴파일할 때의 순환. 앱은 jOOQ 타입이 있어야 컴파일되고, jOOQ 타입은 DDL에서, DDL은 엔티티에서 나오는데 엔티티는 앱과 함께 컴파일된다|dark=219|w=100|a=center](attachment:220)

## 푼 방법: 엔티티만 먼저 컴파일한다

엔티티만 따로 먼저 컴파일하고, 거기서 DDL과 jOOQ 타입을 만든 뒤 앱 전체를 컴파일하도록 Gradle 단계를 나눴다.[* DDL(Data Definition Language)은 `CREATE TABLE`처럼 테이블 구조를 정의하는 SQL이다. Gradle 태스크는 빌드를 이루는 한 단계이고, 앞 단계의 결과를 입력으로 받는다]

![빌드의 네 단계. 도메인 클래스와 도메인 예외의 공통 부모만 먼저 컴파일하고, Hibernate가 그 매핑으로 DDL을 쓰고, jOOQ가 DDL에서 테이블 타입을 만든 뒤 앱 전체를 컴파일한다. DDL과 타입은 Git에 올리지 않고 빌드마다 다시 만든다|dark=221|w=100|a=center](attachment:222)

먼저 컴파일하는 대상에는 도메인 클래스와 도메인 예외의 공통 부모만 넣고, 서비스와 HTTP 변환기는 뺐다. 엔티티는 복사본을 두지 않고 앱과 같은 원본을 쓴다. DDL과 jOOQ 타입은 Git에 올리지 않는 빌드 산출물이다.

DDL을 뽑는 Hibernate는 앱과 같은 Spring Boot BOM으로 버전을 맞추고, MySQL dialect와 snake_case 이름 정책을 똑같이 적용한다.[* BOM(Bill of Materials)은 함께 쓰는 라이브러리들의 버전을 한곳에서 정해 두는 목록이다. dialect는 Hibernate가 DB 종류에 맞춰 SQL을 만드는 규칙이다] DB에 접속하지 않고 파일만 쓰도록 JDBC 메타데이터 조회와 스키마 변경은 끄고, 성공하든 실패하든 클래스 로더와 레지스트리를 정리한다. 그래서 코드 생성에는 DB가 필요 없다. 의존성을 내려받을 때만 네트워크가 필요하다.

생성 타입을 쓰는 조회 쪽에도 몇 가지를 맞췄다. MySQL enum은 jOOQ 조회 경계에서 문자열로 받고, JOIN은 쿼리에 직접 적으며 필요한 메타데이터 열만 고른다. JPA 엔티티와 프록시 접근자는 `final`로 선언하지 않고 보호된 기본 생성자와 setter를 둔다. 일반 타입과 복합 키 클래스는 상속을 막는다.

## 받아들인 비용

엔티티를 바꾸면 Gradle이 의존 관계를 따라 DDL과 테이블 타입을 다시 만든다. 코드 생성용 스키마를 손으로 고칠 일도, 빌드 중에 운영 DB에 접속할 일도 없어졌다. 대신 지켜야 할 경계가 생겼다.

- 도메인 클래스가 서비스나 생성된 jOOQ 타입에 기대기 시작하면 먼저 컴파일하는 단계가 깨진다.
- 엔티티 위치, 이름 정책, dialect, Spring Boot 버전이 바뀌면 생성 설정을 다시 봐야 한다.
- 생성 태스크가 도메인 클래스를 읽으므로, Gradle을 실행하는 JDK도 프로젝트 기준과 맞아야 한다.

## 운영 스키마는 따로 다룬다

생성 DDL은 코드 생성의 입력일 뿐이고, 운영 DB에 자동으로 실행하지 않는다. 운영 API는 스키마가 엔티티와 맞는지 검증만 하고(validate), 초기화 SQL은 실행하지 않도록 기동한다. 운영 DB를 바꿀 때는 검토한 이관 SQL을 따로 반영한다. `posts.edit_version`과 `admin_login_sources`도 그렇게 들어갔다.[* 당시 이관 SQL(`review-2026-10-03.sql`)이다. 적용한 뒤 2026-10-08 정리 커밋에서 저장소에서 지웠다]

![생성 DDL과 운영 DB의 경계. 엔티티에서 나온 DDL은 jOOQ 타입을 만드는 데만 쓰고, 운영 MySQL은 검토한 이관 SQL로 바꾼다. API는 기동할 때 스키마가 엔티티와 맞는지 검증만 한다|dark=217|w=100|a=center](attachment:218)

JDBC 세션이나 인증 상태처럼 JPA 밖에 있는 테이블도 별도 SQL로 관리한다. 기존 DB를 옮길 때와 빈 DB에 처음 설치할 때의 절차도 다르다. 그래서 엔티티만으로 운영 DB 전체를 다시 만들 수 있는 구조는 아니다.

## 남은 위험

- Hibernate, jOOQ, MySQL이 바뀌면서 매핑을 제대로 만들지 못하게 될 수 있다. 실제 DB와 생성 DDL의 차이가 되풀이되면 이 방식을 다시 본다.
- 먼저 컴파일하는 대상이 서비스나 웹까지 넓어지면 단계를 나눈 의미가 줄어든다.
- 명시적인 마이그레이션 파일을 스키마의 원본으로 바꾸거나, 다른 생성 방식의 호환성이 확인돼 유지 비용이 줄면 다시 고른다. 그때는 생성에 걸리는 시간, 매핑이 일치하는지, 빌드가 DB 접속에 기대는지, 스키마 원본이 두 곳으로 나뉘는지, 운영 이관을 누가 맡는지를 비교한다.
