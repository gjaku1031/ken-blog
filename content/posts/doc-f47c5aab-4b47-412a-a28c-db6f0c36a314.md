한 언어 풀스택과 관리형 플랫폼을 고른 결과 요청마다 함수 인스턴스가 달라질 수 있게 됐고, P2는 그 결과로 생긴 문제를 푸는 결정임. P1은 되돌릴 수 없는 외부 쓰기에서, P3는 외부 원장이 달마다 바뀌는 데서 나온 결정임.

| 결정 | 해결한 문제 | 대가 |
| --- | --- | --- |
| Next.js 풀스택을 Vercel에, 데이터는 SQLite 계열의 Turso에 둠 | 한 사람의 개발·운영 부담 | 인스턴스마다 리플리카가 생겨 P2가 생김. 규모가 커지면 PostgreSQL로 옮겨야 함 |
| 상담 전송을 원본 DB에서 선점하고, 보내기 전후의 건수를 대조해 확정함 | P1 | 결과를 모르는 상담은 사람이 종결함. 같은 내용을 다른 경로로 쓰면 대조가 틀릴 수 있음 |
| 조회 전 원본 당겨 오기, 겨루는 변경은 원본 트랜잭션, 반 정보는 잠금 행과 상태 지문 | P2 | 조회마다 원본과 한 번 더 왕복함. 원본에 닿지 못하면 요청이 실패함 |
| 특강기간 여부와 특강상담의 대상을 만든 시점에 복사함 | P3 | 같은 명단을 업무마다 저장함. 만든 뒤의 명단 변화는 반영되지 않음 |

## 기술 스택 선택

### 문제

화면과 API를 모두 개발자 한 사람이 유지해야 했고, 화면을 함께 볼 수 있는 동료는 JavaScript와 TypeScript만 다룰 수 있었음. 쓰는 사람은 100명 안쪽이었음.

### 검토한 대안

| 항목 | Spring Boot + PostgreSQL, AWS나 Proxmox에 직접 배포 | **Next.js 풀스택 + Vercel + SQLite 계열(Turso)** |
| --- | --- | --- |
| 언어 | 화면과 API가 다른 언어. 둘 사이의 API 계약(OpenAPI 명세)을 따로 관리해야 함 | 화면과 API가 TypeScript 하나. 동료도 같은 코드를 다룸 |
| 운영 | 서버, 배포, DB를 직접 꾸림 | 빌드·배포·함수 실행은 Vercel이, DB 운영은 Turso가 맡음 |
| DB | PostgreSQL | SQLite 계열로 작게 시작하고, 필요해지면 PostgreSQL로 옮김 |
| 실행 모델 | 서버 프로세스 하나가 DB 연결을 가짐 | 요청마다 함수 인스턴스가 달라질 수 있고, 인스턴스마다 DB 리플리카를 가짐 |

- 선택 이유: 화면과 API를 한 언어로 두면 API 계약을 두 코드베이스에서 맞추는 일이 없어지고, 사용자 규모에서는 인프라를 꾸리는 것보다 완성된 관리형 플랫폼으로 시작하는 편이 초기 부담이 작다고 판단함

### 대가

- 인스턴스마다 리플리카를 가지므로, 한 서버의 트랜잭션이면 끝날 일을 인스턴스 사이에서 다시 맞춰야 함. 이것이 P2가 됨
- 규모가 커지면 DB를 옮겨야 함. 스키마는 날짜를 ISO 문자열로, 목록을 JSON 문자열로 두는 SQLite 방식이라 옮길 때 열 형식도 함께 바꿔야 함

## P1. 외부 ERP에 상담을 한 번만 쓰기

### 문제

외부 ERP의 상담 쓰기는 멱등하지 않고, 쓴 기록을 가리킬 식별자를 돌려주지 않음. 응답이 늦어 강사가 다시 누르거나, 서로 다른 인스턴스가 같은 상담을 동시에 받으면 두 번 기록될 수 있었음. 반대로 응답이 끊겼을 때 실패로 보고 다시 보내면, 실제로는 기록된 상담을 한 번 더 쓰게 됨.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 외부 ERP에 요청 식별자를 붙여 같은 요청을 무시하게 함 | 외부 ERP의 상담 저장 요청에 같은 요청을 알아볼 키가 없어 쓸 수 없음 |
| 응답을 보고 완료로 표시하고, 실패하면 다시 보내게 함 | 응답이 끊기면 기록 여부를 모르므로, 다시 보내는 순간 중복이 생길 수 있음 |
| 인스턴스의 리플리카에서 트랜잭션으로 선점 | 리플리카는 인스턴스마다 따로라서, 다른 인스턴스의 동시 요청을 막지 못함[* 원본 연결을 따로 둔 이유(`src/db/db.service.ts`)] |
| **원본 DB의 조건부 갱신으로 선점하고, 보내기 전후 건수를 대조함** | 채택 |

- 선점: 원본에서 읽은 상태 전체(단계, 토큰, 지문, 날짜, 완료 여부)를 `WHERE`에 넣은 `UPDATE` 한 문장이 실제 선점점임. 두 요청이 같은 행을 동시에 읽어도 바뀐 행이 1인 요청 하나만 보냄(compare-and-set)
- 단계 구분: 선점 직후(`claimed`)에는 외부 ERP에 닿지 않았음이 확실하므로, 이 구간에서 끊기면 선점을 풀고 작성 내용만 남김. 보내기 직전에 외부 ERP의 같은 상담 수를 원본에 기록하고(`posting`), 이 기록이 성공한 뒤에만 보냄
- 확정: 보낸 뒤 다시 읽어 같은 상담 수가 늘었을 때만 완료로 바꿈. 같은 상담은 학생, 날짜, 주제, 본문 앞부분이 같은 기록임[* 건수 대조와 결과 확인(`src/ttt/counsel-write.ts`), 외부 ERP 포트(`src/ttt/ttt.gateway.ts`)]
- 결과를 모를 때: 다시 보내지 않고 "결과 확인 중"으로 남김. 이후의 결과 확인은 외부 ERP를 읽기만 함. 외부 쓰기가 확인된 뒤 원본 반영만 실패한 경우도 전송 실패로 보고하지 않음[* 확인 뒤 저장 실패의 처리(`src/api/external-write-sync.ts`)]
- 사람의 종결: 다시 읽어도 확인되지 않으면 담당 강사가 외부 ERP를 직접 보고 "보낸 것으로 종결"하거나 "한 번 다시 보내기"를 고름. 자동 조회로는 저장 거부와 조회 실패를 구분할 수 없기 때문임

### 대가

- 결과를 모르는 상담은 사람이 종결할 때까지 그 학생의 상담을 고치거나 다시 보낼 수 없음
- 대조는 같은 상담의 수로 판정하므로, 보내기 전후 사이에 내용이 같은 상담을 외부 ERP에서 직접 쓰면 이 시스템이 보낸 것으로 잘못 판정할 수 있음
- 보장 범위는 이 시스템 안의 경쟁까지임. 외부 ERP 쪽에서 생긴 중복은 막지 못함
- 선점 뒤 3분 동안은 원래 요청이 아직 보내는 중일 수 있어 다른 요청이 선점을 회수하지 못함
- 알림장 게시에는 이 선점과 대조를 쓰지 않음. 게시 전에 그 반의 그날 글을 조회해, 있으면 그 글을 고치는 방식임

### 검증

| 확인한 것 | 근거 |
| --- | --- |
| 원본을 공유하는 두 연결이 같은 상담을 동시에 선점하면 하나만 성공함 | `counsel-delivery-store.test.cjs` |
| 같은 내용의 재요청은 외부 ERP를 부르지 않고, 확인 중에 내용을 바꾼 요청은 거부됨 | `counsel-delivery-store.test.cjs` |
| 선점 기한이 끝나기 전에는 회수하지 않고, 회수된 뒤에는 이전 소유자의 단계 전환이 거부됨 | `counsel-delivery-store.test.cjs` |
| 결과 확인은 다시 읽어 건수가 늘지 않으면 확인 중으로 남고, 외부 ERP에 다시 쓰지 않음 | `counsel-api-reconcile.test.cjs` |
| 팀장은 강사의 상담 전송을 대조하거나 종결할 수 없음 | `counsel-api-reconcile.test.cjs` |

- 2026-08-18: 외부 ERP가 저장을 거부한 상담이 결과 확인 중에 갇혀, 다시 보내지도 고치지도 못했음. 거부 안내문은 그 응답에만 있어 이후 조회로는 알 수 없으므로 응답에서 보존하고, 사람의 종결 경로를 더함

같은 상담이 외부 ERP에 두 번 기록된 사례는 운영 기간의 수정 기록에서 찾지 못했음. 전송 건수는 상담 업무를 지우면 전송 기록도 함께 지워져 집계하지 못했음.

> 외부 ERP에 쓰는 일은 되돌릴 수 없으므로, 결과를 모르면 다시 보내지 않고 사람이 확인할 때까지 남겨 둠.

## P2. 인스턴스 사이의 읽기 일관성과 갱신 손실

### 문제

함수 인스턴스는 요청마다 다를 수 있고, 각자 리플리카 파일로 읽고 씀. 그래서 두 가지가 깨질 수 있었음.

- 다른 인스턴스가 방금 만든 업무나 공지가 다음 조회에서 사라진 것처럼 보이고, 오래된 리플리카로 로그인하면 있는 계정을 "계정 없음"으로 판정함
- 강사의 반 묶음은 JSON 열 하나라서, 반 동기화·강사 등록·외부 ERP 계정 변경이 동시에 읽고 고치면 한쪽의 변경이 사라짐(갱신 손실). 정규반 전체 교체는 외부 ERP를 오래 읽는 동안 다른 요청이 강사 정보를 바꿀 수 있음

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 동기화 실패를 무시하고 리플리카로 응답 | 방금 만든 업무가 사라져 보이거나 계정 판정이 틀림. 상태·보고 조회와 로그인에서는 쓰지 않음 |
| 리플리카의 트랜잭션만으로 읽고 고침 | 인스턴스마다 다른 리플리카를 고치므로 서로의 오래된 JSON이 덮어씀 |
| 모든 요청을 원본에 직접 | 리플리카를 두는 의미가 없어지고 모든 조회가 원본을 왕복함 |
| **조회 전 엄격 당겨 오기, 겨루는 변경만 원본에서 판정** | 채택 |

- 조회: 상태·보고 조회와 로그인 전에 원본을 당겨 오고, 실패하면 오래된 상태를 돌려주지 않고 요청을 실패시킴. 학생 연락처가 담긴 상담 상세는 원본에서 한 업무, 한 강사의 것만 직접 읽음
- 변경: 중요한 변경은 앞뒤로 원본과 동기화하고, 실패하면 세 번까지 바로 다시 시도한 뒤 오류로 돌려줌
- 원본 트랜잭션: 상담 전송의 선점, 특강상담과 명단 복사, 명단 반영은 원본 DB의 한 트랜잭션에서 커밋함
- 잠금 행: 강사 반 묶음을 고치는 요청(반 동기화, 강사 등록·삭제, 외부 ERP 계정 저장, 담당 반 적용)은 원본의 설정 행에 3분짜리 잠금을 걸어 줄 세움. 잠금이 있으면 409로 거부함
- 상태 지문: 정규반 전체 교체는 외부 ERP를 읽기 전에 강사 행들의 SHA-256 지문을 재고, 적용할 때 원본 트랜잭션 안에서 다시 재서 다르면 적용하지 않음(낙관적 동시성 제어)
- 업무 생성: 화면이 만든 요청 식별자의 해시로 업무 ID를 만들어, 같은 요청이 다시 와도 업무가 하나만 생김[* 업무 생성의 멱등(`src/api/store.service.ts`)]

### 대가

- 상태 조회마다 원본과 한 번 더 왕복함. 지연은 측정하지 않았음
- 원본에 닿지 못하면 화면이 오래된 내용 대신 오류를 보여 줌
- 잠금이 걸린 동안의 반 변경은 거부되고, 다시 시도는 사람이 함. 잠금을 건 요청이 죽으면 3분 뒤에 풀림

### 검증

| 확인한 것 | 근거 |
| --- | --- |
| 원본을 당기지 못하면 상태·보고 조회와 로그인이 오래된 리플리카로 답하지 않음 | `read-consistency-api.test.cjs` |
| 외부 ERP를 읽은 뒤 바뀐 강사 정보가 있으면 정규반 전체 교체가 거부됨 | `regular-class-sync.test.cjs` |
| 반 동기화, 강사 변경, 계정 저장이 같은 잠금으로 줄 세워짐 | `regular-class-sync.test.cjs` |

## P3. 만든 시점의 대상을 고정하기

### 문제

반과 명단의 원장은 외부 ERP이고 달마다 바뀜. 지금의 명단을 매번 따라가면 특강상담의 대상 학생과 진행률이 업무 도중에 바뀌고, 특강기간 설정을 끄면 이미 특강으로 보고한 날짜가 일반 보고처럼 보이게 됨.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 조회할 때마다 지금의 명단과 설정으로 계산 | 저장은 줄지만 지난 보고와 진행 중인 업무의 대상이 바뀜 |
| **만들 때 대상을 복사해 저장** | 채택 |

- 일일보고: 날짜를 만들 때 그때의 특강기간 여부를 함께 저장하고, 보고에는 그날 실제로 다룬 반 목록을 저장함
- 특강상담: 만들 때 대상 월, 담당자 목록, 담당자별 학생 명단을 원본의 한 트랜잭션에서 복사함. 전원 배정도 그때의 강사로 고정하고, 고정한 업무의 종류와 배정 범위는 바꿀 수 없음
- 명단 반영: 다시 가져온 명단에서 빠진 학생은 행을 지우지 않고 대상에서만 뺌. 명단이 비어 오면 조회 실패로 보고 지우지 않고, 정규반에서 학생을 빼는 변경은 외부 ERP를 두 번 읽어 결과가 같을 때만 적용함

### 대가

- 같은 학생 명단을 업무마다 복사해 저장함
- 만든 뒤에 들어온 학생은 그 특강상담에 들어가지 않으므로, 필요하면 업무를 새로 만들어야 함

### 검증

| 확인한 것 | 근거 |
