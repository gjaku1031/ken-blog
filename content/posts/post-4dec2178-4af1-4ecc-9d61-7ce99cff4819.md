관리 화면은 여러 탭에서 열 수 있어, 같은 글을 두 화면에서 열고 차례로 저장하면 늦게 저장한 화면이 먼저 저장된 변경을 덮어쓰는 갱신 손실(lost update)이 생길 수 있음. ken-blog는 이를 편집 버전 비교와 글 행 잠금을 함께 써서 막음. 둘 중 하나만으로는 막지 못하는 구간이 있음.

## 두 종류의 충돌

| 구간 | 예 | 막는 장치 |
| --- | --- | --- |
| HTTP 요청 사이 | 화면 A가 글을 연 뒤 화면 B가 저장함. A가 나중에 저장함 | 편집 버전 비교 |
| 트랜잭션 사이 | 두 저장 요청이 거의 동시에 도착해 둘 다 같은 버전을 읽음 | 글 행 잠금 |

화면은 글을 불러올 때 받은 `editVersion`을 저장 요청의 `baseVersion`으로 보냄. 서버는 현재 버전과 다르면 409로 거부함. 이 비교만 있으면 첫 번째 구간은 막지만 두 번째 구간은 남음.

```mermaid caption="잠금 없이 버전만 비교하면 두 요청이 모두 같은 버전을 읽고 비교를 통과해, 뒤에 커밋한 쪽이 앞의 변경을 덮어씀"
sequenceDiagram
    %% legend: solid=요청·쓰기; dotted=결과
    participant A as 저장 요청 A
    participant DB as posts 행(version 3)
    participant B as 저장 요청 B
    A->>DB: 읽기 → version 3
    B->>DB: 읽기 → version 3
    Note over A,B: 둘 다 baseVersion 3과 일치
    A->>DB: 제목 갱신, version 4
    B->>DB: 제목 갱신, version 4
    DB-->>A: A의 변경이 사라짐
```

MySQL InnoDB의 기본 격리 수준(REPEATABLE READ)에서 일반 `SELECT`는 잠금 없이 스냅샷을 읽으므로, 두 트랜잭션이 같은 버전을 읽는 것을 막지 않음. 그래서 서비스는 비교 전에 글 행을 `PESSIMISTIC_WRITE`(`SELECT ... FOR UPDATE`)로 잠금. 뒤에 온 요청은 앞 트랜잭션이 커밋할 때까지 기다린 뒤 최신 버전을 읽고, 비교에 실패해 409를 받음.[* [글 서비스](https://github.com/gjaku1031/ken-blog/blob/b768152/src/main/java/io/github/gjaku1031/kenblog/post/service/PostService.java) · [잠금 조회](https://github.com/gjaku1031/ken-blog/blob/b768152/src/main/java/io/github/gjaku1031/kenblog/post/repository/PostRepository.java)]

비교와 쓰기를 `UPDATE ... SET edit_version = edit_version + 1 WHERE id = ? AND edit_version = ?` 같은 조건부 갱신 한 문장으로 묶어도 같은 구간을 막을 수 있음. 이 프로젝트는 엔티티를 읽어 도메인 메서드로 바꾸는 JPA 방식에 맞춰, 먼저 잠근 뒤 비교하는 쪽을 씀. 대가는 같은 글에 대한 저장이 잠금을 기다리는 것임.

## 저장 순서

1. 분류를 지정했으면 분류 행을 공유 잠금으로 읽어 존재를 확인
2. 관련 시리즈 행을 ID 오름차순으로 잠금. 두 요청이 같은 시리즈 쌍을 반대 순서로 잠가 생기는 교착 상태를 막음
3. 글 행을 잠그고 `baseVersion`과 현재 버전을 비교. 다르면 409
4. 글 정보·소속·순서·태그를 같은 트랜잭션에서 저장하고 버전을 1 올림
5. 커밋. 중간에 실패하면 전체 롤백

분류 삭제의 일괄 이동도 분류 행을 먼저 잠근 뒤 글 행을 갱신하므로, 두 경로 모두 분류 → 글 순서로 잠가 순서가 뒤집히지 않음. 시리즈 쌍을 반대 순서로 지정한 두 요청이 교착하지 않는지는 `oppositeSeriesAssignmentsDoNotDeadlock`이 확인함. 분류 삭제와 글 편집이 겹치는 경우의 교착 검사는 없음.

## 버전을 올리는 작업

버전은 JPA `@Version`이 아니라 서비스 코드가 직접 올림. 그래서 어떤 작업이 버전을 올리는지가 코드에 명시됨.

| 작업 | 버전 비교 | 버전 증가 | 이유 |
| --- | --- | --- | --- |
| 글 정보 저장 | 함 | 함 | 여러 필드를 함께 바꾸므로 앞선 저장을 덮어쓰지 않게 함 |
| 발행·발행 취소 | 안 함 | 함 | 누른 대로 적용하되, 열린 편집 화면이 옛 상태를 기준으로 저장하지 않게 함 |
| 분류 삭제에 따른 일괄 이동 | 안 함 | 함 | JPQL 일괄 `UPDATE`가 `edit_version + 1`을 함께 실행해 열린 편집 화면의 다음 저장을 409로 만듦 |

`@Version`은 엔티티를 저장할 때 `UPDATE ... WHERE version = ?`로 검사하는 방식이라, 일괄 `UPDATE` 쿼리는 버전을 자동으로 올리지 않음. 분류 이동처럼 엔티티를 거치지 않는 변경도 편집 화면을 무효화해야 해서, 버전 증가를 쿼리에 직접 적음.

## 대가

- 자동 병합은 없음. 409를 받은 화면은 입력을 보존하고, 사용자가 글을 다시 열어 최신 값과 비교한 뒤 다시 저장해야 함. 기준 버전만 바꿔 자동으로 다시 보내지 않음. 자동 재전송은 앞선 저장을 덮어쓰는 것과 같기 때문임
- 같은 글에 대한 저장은 잠금 때문에 직렬로 처리됨. 관리자가 한 명이라 대기가 문제 되지 않는 규모임. 잠금 대기 시간(InnoDB 기본 50초)을 넘기거나 교착으로 롤백되면 409 "동시 변경이 충돌했습니다."로 응답함
- 버전을 올려야 하는 새 작업을 추가할 때 개발자가 직접 챙겨야 함. 빠뜨리면 그 작업 뒤의 낡은 편집이 409 없이 저장됨

## 검증

| 검사 | 확인하는 것 |
| --- | --- |
| `concurrentEditorsHaveOneWinner` | 두 스레드가 같은 버전으로 동시에 저장하면 하나만 성공. `CountDownLatch`로 두 요청을 같은 시점에 출발시킴 |
| `atomicEditsRejectStaleVersionsAndRollback` | 태그만 바꿔도 버전이 올라 낡은 화면의 저장이 거부되고, 잘못된 요청 뒤에도 제목·태그·버전이 그대로임 |
| `categoryMovesInvalidateEditors` | 분류 삭제로 글이 옮겨진 뒤 이전 버전의 저장이 거부됨 |
| 브라우저 검사 | 409를 받은 뒤 편집 중인 입력과 창이 유지됨 |
