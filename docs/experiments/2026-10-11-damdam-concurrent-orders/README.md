# 담담공방 동시 주문 실험 (2026-10-11)

재고 2개인 옵션에 주문 20건을 동시에 보냈을 때, 주문 트랜잭션의 옵션 행 잠금이 초과 판매를 막는지 확인함. 결과를 보기 전에 가설과 기각 기준을 아래에 적어 두고 한 번 실행하는 확증 실험임.

## 계획 (실행 전에 고정)

### 조건

| 조건 | 내용 | 실행 방법 |
| --- | --- | --- |
| A. 옵션 행 잠금 | 실제 API. 주문 트랜잭션이 옵션 행을 잠근 뒤 재고를 확인하고 뺌. 재고에 `CHECK (stock >= 0)`이 있음 | 로그인한 회원 10명이 2건씩, HTTP 주문 20건을 동시에 보냄 |
| B. 잠금 없음, `CHECK` 있음 | 같은 테이블에서 "재고를 읽고, 1 이상이면 1을 뺌"을 잠금 없이 실행 | DB 세션 20개가 같은 시각에 시작 |
| C. 잠금 없음, `CHECK` 없음 | B와 같고 `CHECK` 제약을 뗌 | B와 같음 |

B와 C는 API 코드를 고치지 않고, 잠금을 뺀 절차를 같은 스키마에 SQL로 재현한 대조군임. 읽기와 차감 사이에 20ms를 둠(애플리케이션이 DB를 한 번 다녀오는 시간을 넉넉히 잡은 값). 격리 수준은 세 조건 모두 PostgreSQL의 기본값 READ COMMITTED임.

### 고정한 값

- 재고 2, 동시 요청 20, 조건마다 10회 반복. 반복마다 새 옵션을 씀
- 대상: damdam 커밋 `3b57c18`로 만든 API 이미지, PostgreSQL 16, 한 대의 개발용 VM(aarch64, 2 vCPU)에서 컨테이너로 실행
- 판정에 쓰는 값: 성공한 주문 수(A는 201 응답 수, B·C는 차감에 성공한 세션 수), 실행 뒤의 재고, 재고 이력의 합(A만)

### 가설과 기각 기준

- **H1**: A에서는 모든 반복에서 성공이 정확히 2건이고, 재고가 0이며, 재고 이력의 합이 재고와 같음
  - 기각: 10회 가운데 한 번이라도 성공 수가 2가 아니거나, 재고가 0이 아니거나, 이력의 합이 재고와 다름
- **H2**: C에서는 재고가 음수가 되는 반복이 있음(초과 판매)
  - 기각: 10회 모두 재고가 0 이상임. 이 경우 대조군이 문제를 재현하지 못한 것이므로, 이 실험으로 잠금의 효과를 말할 수 없음
- **H3**: B에서는 재고가 음수가 되지 않고, 차감을 시도한 세션 가운데 일부가 `CHECK` 위반 오류로 끝남
  - 기각: 재고가 음수인 반복이 있거나, 10회 모두 `CHECK` 위반이 한 건도 없음

### 요청이 실제로 겹쳤는지

A는 요청마다 보낸 시각과 응답을 받은 시각을 기록함. 반복마다 "가장 먼저 끝난 요청이 끝나기 전에 시작한 요청의 수"를 겹친 요청 수로 보고함. 이 값이 20보다 작은 반복이 있으면 결과와 함께 밝힘.

### 이 실험이 말하지 못하는 것

- 대조군은 API의 코드 경로가 아님. "잠금을 뺀 API"가 아니라 "잠금 없는 같은 절차"의 결과임
- 요청 20건, 재고 2, 옵션 하나의 주문만 봄. 옵션 여러 개를 담은 주문의 교착, 5초 제한에 걸리는 긴 대기 줄은 보지 않음
- 주기 작업의 자동 취소와 입금 확인의 경쟁은 이 실험의 범위가 아님

## 파일

- `run.py`: 세 조건을 실행하고 `results/`에 요청별 원자료를 남김
- `results/`: 실행 결과(실행 뒤에 추가)
- `figures/result.html`: 결과 그림의 원본. 수치는 `results/summary.json`에서 옮김

## 결과 (2026-10-11 실행)

계획을 커밋한 뒤(`0b0ec9d`) 한 번 실행했음. 다시 돌리지 않았음.

| 조건 | 성공 | 나머지 18건 | 실행 뒤 재고 | 10회 가운데 |
| --- | --- | --- | --- | --- |
| A. 옵션 행 잠금(실제 API) | 2건(201) | 재고 부족으로 거절(400) | 0. 재고 이력의 합도 0 | 10회 모두 같음 |
| B. 잠금 없음, `CHECK` 있음 | 2건 차감 | `CHECK` 위반 오류 | 0 | 10회 모두 같음 |
| C. 잠금 없음, `CHECK` 없음 | 20건 차감 | — | -18 | 10회 모두 같음 |

- **H1 지지**: A는 10회 모두 성공 2건, 재고 0, 이력의 합 0
- **H2 지지**: C는 10회 모두 재고가 -18이 됨. 대조군이 초과 판매를 재현했음
- **H3 지지**: B는 재고가 음수가 되지 않았고, 10회 모두 18건이 `CHECK` 위반으로 끝남

A의 요청 20건은 10회 모두 서로 겹쳤음(가장 먼저 끝난 요청이 끝나기 전에 20건이 모두 시작됨). 요청을 보낸 시각의 차이는 가장 컸던 반복에서 0.081초였음. 요청 200건의 응답 시간은 중앙값 0.22초, 최대 0.61초였고 5초 제한에 걸린 요청은 없었음.

B에서 눈여겨볼 점은 재고는 지켜지지만 거절의 모양이 다르다는 것임. A의 18건은 "재고 부족"이라는 안내를 받고, B의 18건은 제약 위반 오류로 끝남. `CHECK`는 잠금이 빠진 경로가 생겼을 때의 마지막 방어선이고, 고객에게 보여 줄 안내는 잠금 뒤의 확인이 만듦.

### 환경

- API: damdam 커밋 `3b57c18`의 `Dockerfile`로 만든 이미지(Java 25), 컨테이너 한 개
- DB: PostgreSQL 16.15(aarch64), 격리 수준 READ COMMITTED, API의 연결은 `statement_timeout` 5초
- 실행 장비: 개발용 VM 한 대(aarch64, 2 vCPU). 요청을 보내는 스크립트, API, DB가 같은 장비에서 돎
- 조건 B·C의 읽기와 차감 사이 간격: 20ms

### 해석할 때 조심할 것

- B와 C는 API의 코드 경로가 아니라 같은 테이블에 SQL로 재현한 절차임
- 요청을 보내는 쪽과 서버가 같은 장비라 네트워크 지연이 없음. 실제 운영에서는 요청이 이만큼 촘촘히 겹치기 어려움
- 재고 2, 요청 20, 옵션 하나짜리 주문만 봤음

### 원자료

- `results/raw.json`: 조건 A의 요청별 상태 코드와 시작·종료 시각, 조건 B·C의 반복별 집계
- `results/summary.json`: 반복별 집계
