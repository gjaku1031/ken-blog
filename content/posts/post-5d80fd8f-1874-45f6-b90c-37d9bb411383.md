## 학습 목표

- Tomcat이 연결을 받아 요청 객체를 만들고 작업 스레드에 맡기는 과정을 설명할 수 있다
- 필터, DispatcherServlet, 인터셉터, 컨트롤러를 요청이 지나는 순서대로 말할 수 있다
- 필터에 닿기도 전에 Tomcat이 거절하는 요청의 예를 들 수 있다

## Tomcat: 바이트를 요청 객체로 바꾸는 정문

Spring Boot로 웹 앱을 만들면 Tomcat이 함께 들어 있다. Tomcat은 네트워크로 들어온 바이트를 읽어 HTTP 요청으로 해석하고, 그것을 Java 객체(`HttpServletRequest`)로 만들어 내 코드에 넘겨주는 서블릿 컨테이너다.[* 서블릿 컨테이너: 서블릿 규격(Jakarta Servlet)에 맞춰 요청을 받고 서블릿을 실행하는 프로그램. Tomcat, Jetty, Undertow 등이 있고 Spring Boot의 기본값은 Tomcat이다]

건물 정문에 비유하면 이해가 쉬웠다. 경비실이 문 앞에서 손님을 들이고, 로비 관리인이 누가 용건을 꺼냈는지 지켜보다가, 용건을 꺼낸 손님에게 직원을 한 명 붙여 준다. 직원은 손님의 말을 정해진 서류 양식에 옮겨 적고 그 서류를 들고 안으로 들어간다.

| 비유 | Tomcat 안에서 | 스레드 이름 |
| --- | --- | --- |
| 경비실 | 새 TCP 연결을 받아들임 | `http-nio-포트-Acceptor` |
| 로비 관리인 | 열린 연결 여러 개를 지켜보다가 읽을 데이터가 생긴 연결을 작업 스레드에 넘김 | `http-nio-포트-Poller` |
| 직원 | HTTP를 해석해 요청 객체를 만들고, 필터와 서블릿을 거쳐 응답을 쓰기까지 요청 하나를 맡음 | `http-nio-포트-exec-N` |

직원(작업 스레드)은 스레드 풀에서 빌려 쓴다. Spring Boot 기본값은 최소 10개, 최대 200개이고, 동시에 열어 둘 수 있는 연결은 8192개다.[* Spring Boot 4.1.1의 설정 기본값 `server.tomcat.threads.min-spare=10`, `server.tomcat.threads.max=200`, `server.tomcat.max-connections=8192`. 설정 메타데이터(`spring-configuration-metadata.json`)에서 확인했다] 처음엔 "연결 하나에 스레드 하나"라고 생각했는데 그렇지 않았다. [1편](/ken-blog/post/post-adf39eb5-c2bf-4064-b443-e89613393020/)에서 본 것처럼 연결은 한동안 열려 있을 수 있는데, 아무 말도 하지 않는 연결은 로비 관리인이 지켜보기만 하고 직원을 붙잡지 않는다. 그래서 연결 수가 스레드 수보다 훨씬 클 수 있다.[* 여기서 말하는 것은 요청 하나를 한 스레드가 처음부터 끝까지 처리하는 일반적인 서블릿 방식이다. 서블릿 비동기 처리나 가상 스레드를 쓰면 스레드를 쓰는 방식이 달라진다]

## 필터와 DispatcherServlet: 겹겹이 싼 포장과 안내 데스크

직원이 들고 들어간 요청은 먼저 필터를 지난다. 필터는 서블릿 규격에 있는 장치라 Spring MVC보다 바깥에 있고, 모든 요청이 지나가므로 인코딩, 로그, 보안 검사, 공통 응답 헤더 같은 일을 하기 좋다.[* Spring Security도 필터 여러 개를 이어 붙인 필터 체인으로 동작한다]

필터는 겹겹이 싼 포장 같았다. 요청은 들어갈 때 바깥 포장부터 하나씩 벗기며 안으로 가고, 응답은 나올 때 안쪽부터 다시 싸며 밖으로 나온다. 필터 코드에서 `chain.doFilter()` 앞에 쓴 것은 들어갈 때, 뒤에 쓴 것은 나올 때 실행된다.

필터를 다 지나면 Spring MVC의 `DispatcherServlet`이 요청을 받는다. Spring MVC 앱에는 보통 이 서블릿 하나뿐이고, 모든 요청을 받아 어디로 보낼지 정하는 안내 데스크 역할을 한다.

1. **핸들러 매핑**: 메서드와 경로(`GET /hello/kim`)를 보고 어떤 컨트롤러 메서드가 맡을지 찾는다
2. **인터셉터**: 맡을 메서드가 정해진 뒤, 그 메서드를 부르기 전과 후에 끼어든다
3. **컨트롤러**: 내가 쓴 메서드가 실행된다
4. **응답 변환**: 반환값을 응답 본문으로 바꾼다(문자열은 그대로, 객체는 보통 JSON으로)[* 이 변환은 `HttpMessageConverter`가 맡는다. [2편](/ken-blog/post/post-3afb11d0-e0ac-40ec-b062-a66775e3264b/)에서 본 `Content-Type` 헤더도 이때 정해진다]

필터와 인터셉터는 둘 다 "컨트롤러 앞뒤에 끼어든다"는 점이 같아서 헷갈렸다. 차이는 위치다.

| | 필터 | 인터셉터 |
| --- | --- | --- |
| 속한 곳 | 서블릿 규격(Tomcat이 부름) | Spring MVC(`DispatcherServlet`이 부름) |
| 실행 시점 | `DispatcherServlet`보다 앞 | 맡을 컨트롤러 메서드가 정해진 뒤 |
| 아는 것 | 요청과 응답 | 요청, 응답, 그리고 어느 메서드가 맡는지 |

### 헷갈렸던 것: 모든 요청이 필터를 지나지는 않는다

"모든 요청이 필터를 지난다"고 외웠는데, 정확히는 "Tomcat이 요청으로 받아들인 것만" 지난다. Tomcat은 바이트를 요청 객체로 옮겨 적다가 형식이 틀린 요청을 만나면 그 자리에서 400을 돌려보낸다. 경비실에서 돌려보낸 손님은 안내 데스크에 오지 않는 것과 같다. 아래 확인에서 깨진 퍼센트 인코딩(`%zz`)과 너무 긴 헤더가 그런 경우였다.[* 퍼센트 인코딩은 [3편](/ken-blog/post/post-fd94afc2-46b7-4f0a-a470-42d13a147cd3/)에서 다룬다. 헤더 크기 한도는 Spring Boot 기본값 `server.max-http-request-header-size=8KB`]

그래서 필터에서 붙이는 공통 응답 헤더는 이런 400 응답에는 붙지 않는다. 필터에서 "모든 응답에 이 헤더를 붙인다"고 해도, Tomcat에서 끝난 응답은 예외다.

![요청은 Tomcat이 HTTP로 해석한 뒤에야 필터 체인과 DispatcherServlet 안으로 들어가고, 응답은 같은 길을 거꾸로 나온다. 해석하다 거절한 요청은 필터를 지나지 않고 그 자리에서 400으로 끝난다|dark=200|w=100|a=center](attachment:199)

## 직접 확인해 보기

필터 하나, 인터셉터 하나, 컨트롤러 하나만 있는 아주 작은 Spring Boot 앱을 만들고, 각 단계에서 지금 스레드 이름과 함께 로그를 찍게 했다.[* 2026-10-23, Linux VM에서 OpenJDK 25.0.4.1, Spring Boot 4.1.1(Tomcat 11.0.24, Spring MVC 7.0.9)로 실행했다. 의존성은 `spring-boot-starter-webmvc` 하나. 아래 출력에서 `Date` 헤더와 로그의 시각·INFO 줄은 생략했다]

```java
@Component
static class LogFilter implements Filter {
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        var r = (HttpServletRequest) req;
        log("filter", "들어옴 " + r.getMethod() + " " + r.getRequestURI());
        chain.doFilter(req, res);   // 여기서 안쪽(DispatcherServlet)으로 들어감
        log("filter", "나감 status=" + ((HttpServletResponse) res).getStatus());
    }
}

// 인터셉터: preHandle에서 "컨트롤러 앞", afterCompletion에서 "응답 뒤"를 찍음

@RestController
static class HelloController {
    @GetMapping("/hello/{name}")
    String hello(@PathVariable String name) {
        log("controller", "hello(" + name + ")");
        return "hello " + name;
    }
}
```

정상 요청부터 보냈다.

```text
$ curl -i localhost:18500/hello/kim
HTTP/1.1 200
Content-Type: text/plain;charset=UTF-8
Content-Length: 9

hello kim
```

```text
[http-nio-18500-exec-2] filter      들어옴 GET /hello/kim (REQUEST)
[http-nio-18500-exec-2] interceptor 컨트롤러 앞 handler=demo.App$HelloController#hello(String)
[http-nio-18500-exec-2] controller  hello(kim)
[http-nio-18500-exec-2] interceptor 응답 뒤
[http-nio-18500-exec-2] filter      나감 status=200
```

| 로그 | 개념 |
| --- | --- |
| 모든 줄의 `http-nio-18500-exec-2` | 요청 하나를 작업 스레드 하나가 처음부터 끝까지 맡음 |
| `filter 들어옴`이 맨 처음, `filter 나감`이 맨 끝 | 필터는 겹겹이 싼 포장의 바깥쪽 |
| `handler=…HelloController#hello` | 핸들러 매핑이 맡을 메서드를 정한 뒤에 인터셉터가 불림 |
| `controller hello(kim)` | 내가 쓴 코드는 가장 안쪽에서 한 번 실행됨 |

같은 요청을 한 번 더 보내자 이번에는 `exec-3` 스레드가 맡았다. 요청마다 풀에서 비어 있는 직원을 빌려 쓴다는 뜻이다.

다음은 Tomcat이 돌려보내는 요청이다. 경로에 깨진 퍼센트 인코딩을 넣었다.

```text
$ curl -i localhost:18500/hello/%zz
HTTP/1.1 400
Content-Type: text/html;charset=utf-8
Content-Language: en
Content-Length: 435
Connection: close

<!doctype html><html lang="en"><head><title>HTTP Status 400 – Bad Request</title>…
```

앱 로그에는 아무것도 찍히지 않았다. 필터의 "들어옴"조차 없다. 응답 본문도 Spring의 오류 응답이 아니라 Tomcat의 기본 오류 페이지였다.[* 응답의 `Date` 헤더와 HTML 본문의 스타일 부분은 생략했다]

헤더를 9000바이트로 키워 보내도 마찬가지였다. 7000바이트일 때는 200이었다.

```text
$ curl -s -o /dev/null -w '%{http_code}\n' -H "X-Big: (a를 9000개)" localhost:18500/hello/kim
400
```

```text
INFO … [io-18500-exec-8] o.apache.coyote.http11.Http11Processor : Error parsing HTTP request header
java.lang.IllegalArgumentException: Request header is too large
	at org.apache.coyote.http11.Http11InputBuffer.fill(Http11InputBuffer.java:768)
```

이번에는 Tomcat 자신이 "헤더를 해석하다 실패했다"고 남겼다. 예외가 난 곳도 `org.apache.coyote.http11`, 즉 HTTP를 해석하는 Tomcat 코드였다.[* 로그의 시각과 스택 트레이스 나머지 줄은 생략했다. 같은 종류의 오류는 처음 한 번만 INFO로 남기고 그 뒤로는 DEBUG로 낮춘다는 안내도 함께 찍혔다]

없는 주소(`/nothing`)는 달랐다. 이건 HTTP로서는 멀쩡한 요청이라 필터를 지나 Spring까지 갔다가 404가 됐다.

```text
[http-nio-18500-exec-5] filter      들어옴 GET /nothing (REQUEST)
[http-nio-18500-exec-5] interceptor 컨트롤러 앞 handler=ResourceHttpRequestHandler […]
[http-nio-18500-exec-5] interceptor 응답 뒤
[http-nio-18500-exec-5] filter      나감 status=404
[http-nio-18500-exec-5] interceptor 컨트롤러 앞 handler=…BasicErrorController#error(HttpServletRequest)
[http-nio-18500-exec-5] interceptor 응답 뒤
```

맞는 컨트롤러가 없으니 정적 파일을 찾는 핸들러가 맡았다가 못 찾았고, 그 뒤 Spring Boot가 오류 응답을 만드는 `/error`로 요청을 안에서 다시 보냈다. 이 두 번째 길에서는 인터셉터만 찍히고 내 필터는 다시 불리지 않았다.[* 이 재전달은 서블릿의 ERROR 디스패치다. 핸들러 목록은 일부 생략했다]

| 요청 | 결과 | 필터 로그 | 끝난 곳 |
| --- | --- | --- | --- |
| `/hello/kim` | 200 | 있음 | 컨트롤러 |
| `/nothing` | 404 | 있음 | Spring MVC |
| `/hello/%zz` | 400 | 없음 | Tomcat |
| 9000바이트 헤더 | 400 | 없음 | Tomcat |

마지막으로 직원이 정말 풀에서 나오는지 보려고 스레드를 셌다. `jcmd <pid> Thread.print`로 스레드 목록을 뽑아 이름별로 셌다.

```text
기동 직후(요청 0건):
      1 "http-nio-18500-Acceptor
      1 "http-nio-18500-Poller
     10 "http-nio-18500-exec
요청 1건 뒤:
     10 "http-nio-18500-exec
동시 50건 뒤:
     44 "http-nio-18500-exec
```

경비실과 로비 관리인은 하나씩이고, 직원은 기본값대로 10명으로 시작해 요청이 한꺼번에 몰리자 44명까지 늘었다.[* 요청 1건 뒤와 동시 50건 뒤의 Acceptor, Poller 줄은 기동 직후와 같아 생략했다. 50건은 `curl`을 백그라운드로 동시에 띄워 보냈다]

> 요청은 Tomcat이 해석한 뒤에야 필터, DispatcherServlet, 인터셉터, 컨트롤러를 차례로 지나고, 응답은 그 길을 거꾸로 나간다. Tomcat이 해석하다 거절한 요청은 내 코드에 한 번도 닿지 않는다.

## 확인 질문

**1. Tomcat에서 Acceptor, Poller, 작업 스레드는 각각 무슨 일을 할까?**

<details><summary>답</summary>

Acceptor는 새 TCP 연결을 받아들이고, Poller는 열린 연결들을 지켜보다가 읽을 데이터가 생긴 연결을 작업 스레드에 넘긴다. 작업 스레드는 HTTP를 해석해 요청 객체를 만들고 필터, 서블릿, 컨트롤러를 거쳐 응답을 쓰기까지 그 요청 하나를 맡는다.

</details>

**2. 필터 코드에서 `chain.doFilter()` 뒤에 쓴 코드는 언제 실행될까?**

<details><summary>답</summary>

안쪽(DispatcherServlet, 인터셉터, 컨트롤러)이 모두 끝나고 응답이 밖으로 나올 때 실행된다. 확인 로그에서 `filter 나감 status=200`이 컨트롤러와 인터셉터 로그보다 뒤에 찍힌 것이 그 예다.

</details>

**3. 인터셉터는 알지만 필터는 모르는 정보는 무엇일까?**

<details><summary>답</summary>

이 요청을 어느 컨트롤러 메서드가 맡는지다. 인터셉터는 핸들러 매핑이 맡을 메서드를 정한 뒤에 불려서 `handler` 인자로 그 메서드를 받는다. 필터는 그보다 바깥에서 불리므로 요청과 응답만 안다.

</details>

**4. 필터에서 모든 응답에 공통 헤더를 붙이게 했는데, 어떤 400 응답에는 그 헤더가 없었다. 왜 그럴 수 있을까?**

<details><summary>답</summary>

그 400을 필터가 아니라 Tomcat이 만들었을 수 있다. 깨진 퍼센트 인코딩이나 한도를 넘는 헤더처럼 HTTP를 해석하는 단계에서 실패한 요청은 필터까지 오지 않고 Tomcat이 바로 400으로 돌려보낸다. 필터를 지나지 않았으니 필터가 붙이는 헤더도 없다.

</details>

**5. 동시에 열린 연결이 수천 개인데 작업 스레드는 200개뿐이어도 괜찮은 이유는?**

<details><summary>답</summary>

열려만 있고 아무 요청도 보내지 않는 연결은 Poller가 지켜보기만 하고 작업 스레드를 붙잡지 않기 때문이다. 작업 스레드는 실제로 요청을 처리하는 동안에만 쓰인다. 다만 처리 시간이 긴 요청이 몰려 200개가 모두 바쁘면 그다음 요청은 기다려야 한다.

</details>
