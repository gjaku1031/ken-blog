Git의 Markdown 원고와 MySQL의 공개 메타데이터를 빌드 시 결합하는 정적 블로그. 공개 화면은 GitHub Pages, 인증·관리·빌드 자료 제공은 Spring Boot API가 담당.

## 요구사항과 설계 경계

| 요구사항 | 반영한 구조 |
| --- | --- |
| 프로젝트 경험과 학습 문서 통합 | 공통 Post 모델과 프로젝트·일반 시리즈 탐색 |
| 작성자와 에이전트의 원고 공동 활용 | Git Markdown을 본문 정본으로 사용 |
| 공개 글 열람 시 일본 리전 API 호출 최소화 | 본문·이미지를 빌드 단계에서 수집해 Pages로 제공 |
| 제목·분류·소속·발행 상태 관리 | 관리자 API와 MySQL에 메타데이터 저장 |
| 설계 도식을 원문으로 관리 | Markdown 내 Mermaid, Architecture·ERD별 공용 렌더링 |
| 서로 다른 저장소의 자료를 함께 배포 | 원고·이미지 검증, 공개 스냅샷 revision 재확인 |

## 인프라·시스템 통합 구성도

```mermaid
architecture-beta
  %% layout: ken-blog-infrastructure
  group people[Users]
  group github[GitHub]
  group site[Pages workflow] in github
  group ci[API workflow] in github
  group ops[Manual operation]
  group oci[OCI ARM VM]
  group compose(ken:docker)[Docker Compose] in oci
  group data[External database]

  service writer(ken:user)[Author and agent] in people
  service repo(ken:git)[Git repository] in github
  service sitebuild(ken:github-actions)[Site build] in site
  service pages(ken:github)[GitHub Pages] in site
  service apibuild(ken:github-actions)[API CI] in ci
  service archive(ken:docker)[JVM image] in ci
  service operator(ken:user)[Operator] in ops
  service reader(ken:user)[Reader] in people
  service admin(ken:user)[Admin] in people
  service caddy(ken:caddy)[Caddy] in compose
  service api(ken:spring)[Java Spring Boot API] in compose
  service disk(ken:disk)[Image disk] in oci
  service db(ken:mysql)[MySQL] in data

  writer:R -[Push]-> L:repo
  repo:R -[Web changes]-> L:sitebuild
  repo:B -[API changes]-> L:apibuild
  sitebuild:R -[Publish]-> L:pages
  sitebuild:B -[Public API]-> T:caddy
  apibuild:R -[Archive]-> L:archive
  archive:B -[Review]-> R:operator
  operator:B -[Manual deploy]-> T:api
  reader:R -[Read]-> R:pages
  admin:T -[Manage UI]-> B:pages
  admin:R -[Admin API]-> L:caddy
  caddy:R -[HTTP]-> L:api
  api:R -[JDBC]-> L:db
  api:B -[Read only]-> T:disk
```

실선은 요청·데이터 접근, 초록 점선은 빌드·산출물 전달, 보라 점선은 검토 후 수동 운영 반영. API 응답은 요청의 반대 경로로 전달. 외부 MySQL과 OCI VM, VM 내부 Compose의 배포 경계 구분.

## 데이터의 정본과 파생 결과물

| 자료 | 정본 | 변경 주체 | 공개 반영 |
| --- | --- | --- | --- |
| 글 본문 | `content/posts/{slug}.md` | 작성자·에이전트 | Pages 빌드 |
| 글 정보·분류·태그·소속·발행 상태 | MySQL | 관리자 API | 스냅샷 수집 후 Pages 빌드 |
| 프로젝트 상태·기간·기술 선택 | MySQL | 관리자 API | 스냅샷 수집 후 Pages 빌드 |
| 이미지 원본·기술 아이콘 | 영속 디스크, 메타데이터는 MySQL | 운영자 | API 조회 후 정적 복사 |
| 첨부 ID·위키 대상 선언 | MySQL | 관리자 API | 첨부 접근 조건 등에 사용 |
| 계정·인증 상태·세션 | MySQL | 운영자·인증 처리 | 정적 산출물에 포함하지 않음 |
| HTML·검색 자료·역링크 | 빌드 산출물 | Node 빌더 | Pages에 배포 |

DB의 옛 `body`·`body_sha256` 열은 이관 호환용으로 보존. 현재 API의 본문 저장·조회에는 사용하지 않음. 본문의 위키 링크와 역링크는 빌더가 원고에서 계산하며, DB 위키 선언과 자동 동기화하지 않음.

## 주요 실행 흐름

### 공개 글 열람

독자 → Pages의 HTML·자산 → 브라우저의 검색·목차·도식 처리. 본문과 이미지 열람에 API 요청 불필요. 로그인 상태 확인과 관리자 작업은 별도 API 호출.

프로젝트 문서는 `seriesId`로 PROJECT 시리즈에 소속. 문제 해결·ADR·실험 글은 일반 글로 유지하고 `relatedSeriesId`로 프로젝트에 연결. 프로젝트 문서 목록과 관련 Posts 목록을 별도로 구성.

### 관리자 변경

관리자 화면 → Caddy → Spring Security → Controller·Service → MySQL. 세션·권한·CSRF 검사를 거쳐 저장. 글 편집은 부모 글 잠금 안에서 기준 버전을 비교하고 메타데이터·관계를 한 트랜잭션으로 변경.

DB 저장 성공은 관리 상태 반영을 의미. 공개 화면은 이후 Pages 재배포로 갱신.

### 사이트 생성

1. Git 원고와 웹 소스 체크아웃.
2. 공개 스냅샷의 메타데이터·탐색 목록·revision 수집.
3. slug에 대응하는 원고 확인, 첨부와 기술 아이콘 다운로드·검증.
4. 임시 디렉터리에 HTML·검색 자료·역링크·정적 자산 생성.
5. 공개 revision 재확인. 수집 도중 변경되었으면 결과 확정 중단.
6. 검증된 산출물로 교체하고 배포 직전 `main`의 사이트 입력 재확인.
7. Pages artifact 발행.

원고 누락·첨부 접근 실패·잘못된 이미지도 빌드 실패 조건. 마지막 revision 확인부터 실제 배포 완료까지를 DB 트랜잭션으로 묶는 구조는 아님.

## 영속 계층

JPA는 저장·단일 조회·변경 잠금, jOOQ는 목록·검색·집계·공개 조회와 일부 연결 검증용 잠금 담당. 같은 MySQL과 Spring 트랜잭션을 공유.

JPA 엔티티 선행 컴파일 → Hibernate DDL 생성 → jOOQ 타입 생성 → 애플리케이션 컴파일 순서. 코드 생성에 실제 DB 접속 불필요. 운영 스키마는 별도 이관·검증 대상으로 유지. 상세 결정은 [JPA 기반 코드 생성 ADR](/ken-blog/post/post-f69cf0bb-68a1-4b72-b6c9-6aea1ed04db9/) 참조.

## 장애 영향과 제약

| 실패 지점 | 영향 |
| --- | --- |
| API·DB | 관리자 기능과 새 사이트 빌드 영향. 이미 배포한 정적 본문·이미지는 별도 제공 |
| 이미지 원본 | 해당 원본을 요구하는 API 조회·새 빌드 실패 가능. 기존 정적 복사본은 유지 |
| 사이트 빌드 | 이번 변경의 공개 반영 중단. 기존 배포는 유지 |
| Pages 제공 | 독자 화면 열람 영향. API 가용성만으로 공개 사이트 대체 불가 |

발행 취소 후에도 재배포 전에는 이전 HTML·이미지가 남을 수 있음. 원고·DB·이미지의 복구 시점도 함께 관리 필요.
