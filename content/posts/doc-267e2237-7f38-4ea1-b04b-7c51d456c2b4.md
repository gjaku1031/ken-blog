대문에서 정의한 핵심 문제 P1~P3에 대한 설계 결정과, 그 밖의 주요 결정의 상세 원본. 결정마다 문제, 검토한 대안, 대가, 검증을 기록함. 핵심 문제의 정의는 [대문](/ken-blog/post/project-06840552-43a2-4870-83a9-d3e848c71d7e/), 구조와 일관성 보장 범위는 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)에서 다룸.

## P1. Git Markdown을 원고의 정본으로

### 문제

초기에는 Next.js 화면의 웹 블록 편집기로 본문을 작성해 DB에 저장했음. 원고가 바뀐 내용을 diff로 검토하거나 수정 이력을 추적하기 어려웠고, 사람과 에이전트가 같은 원고를 같은 방식으로 다루기 어려웠음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 웹 편집기와 DB 저장 유지 | 변경 검토와 이력 추적 문제가 그대로 남음 |
| DB에 버전 이력 테이블 추가 | 이력 저장은 가능하지만 diff 검토 화면과 되돌리기 기능을 별도로 구현해야 함 |
| **Git 저장소의 Markdown을 정본으로 사용 (채택)** | diff·검토·되돌리기를 Git이 제공하고, 사람과 에이전트가 같은 파일을 같은 도구로 수정함 |

아키텍처·ERD 도식도 Mermaid 원문으로 원고에 포함해 설명과 같은 커밋으로 관리함.

### 대가

본문(Git)과 글 정보(DB)가 서로 다른 저장소에 있게 되었고, 둘을 일관되게 발행하는 문제가 P3로 이어짐.

### 검증

현재 API에는 본문을 저장하거나 조회하는 경로가 없음. 본문 변경은 모두 Git 커밋으로만 발생하며, 이 프로젝트 문서들의 개정도 커밋 단위로 검토함. 본문이 담긴 키를 보낸 요청은 400으로 거부됨([API 명세](/ken-blog/post/doc-6bf82223-5b13-49ae-894b-5da5a0de6ddf/) 참조).

## P2. 빌드 시 정적 생성으로 열람 경로에서 API 제거

### 문제

옛 구조에서는 브라우저가 화면 스크립트를 받은 뒤 API를 호출해 본문을 받아 그렸음. 프로젝트 문서 하나를 열 때 로그인 상태 확인 → 프로젝트 조회 → 문서 조회가 앞 단계 응답을 기다리는 순차 호출로 이어졌고, 이미지를 빼고도 문서 한 편에 API 요청이 6~9회(로그인 상태·프로젝트·문서·역링크·CSRF 토큰·조회수 기록 등) 발생했음. 응답은 모두 캐시 금지(`no-store`)라 재방문에도 같은 요청이 반복됨. 순차 단계마다 왕복 지연(약 38ms)과 1코어 서버의 처리 시간이 더해지는 구조.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 브라우저의 API 호출(CSR) 유지 | 순차 3단계 왕복과 요청 6회가 열람마다 반복됨 |
| Redis 캐시로 본문 조회 가속 | 실측에서 외부 Redis 조회가 DB 직접 조회보다 느렸음[* 본문 약 1KB 기준 중앙값 Redis 20.51ms, DB 12.26ms, 각 10회. 전환 전 격리 환경 측정]. 서버 처리 시간을 줄여도 순차 왕복은 남음 |
| 요청마다 서버에서 렌더링(SSR) | 순차 왕복은 서버 안으로 옮겨지지만 모든 열람 요청이 1코어 서버의 렌더링 부하가 됨 |
| **빌드 시 정적 생성 (채택)** | 본문을 포함한 HTML 한 번의 응답으로 열람이 끝나고, 독자 요청이 API 서버에 도달하지 않음 |

### 대가

글과 공개 상태의 변경은 Pages 재배포 후 반영되며, 발행 취소 후 재배포 전까지 이전 페이지가 남음.

### 검증

같은 데이터를 넣은 세 구조를 로컬에 재구성해 비교함. 비교 대상은 본문을 API로만 받는 순수 CSR, 본문을 HTML에 미리 넣고 API도 호출하는 전환 직전의 하이브리드, 현재 정적 생성. 맥에서 잰 실제 왕복 지연(38.6ms)과 처리량을 브라우저에 적용하고, 세 구조 모두 GitHub Pages와 같은 캐시 정책으로 제공함. 시나리오 5개 × 캐시 2조건 × 네트워크 2조건의 20개 조합에서 각 15회 측정한 결과, 정적 구조가 모든 조합에서 본문 표시가 가장 빨랐음.

| 측정 항목(중앙값) | 순수 CSR | 하이브리드 | 정적 생성 |
| --- | ---: | ---: | ---: |
| ERD 문서 첫 방문, 본문 표시 | 747ms | 625ms | 463ms |
| 같은 조건, 모바일 네트워크(150ms·1.6Mbps) | 3,536ms | 1,582ms | 869ms |
| 대문에서 ERD 문서로 이동, 클릭 후 본문 표시 | 414ms | 701ms | 216ms |
| ERD 문서 한 번 열 때 서버 API 요청 | 6회 | 9회 | 0회 |
| 초당 5회 ERD 열람 60초, API 서버 CPU 평균/최대 | 17.1% / 42.2% | 25.6% / 66.0% | 요청 없음 |

> 정적 생성은 첫 방문 전송량이 가장 컸지만 API 응답을 기다리는 순차 단계가 없어 모든 조합에서 가장 빨랐음. 이득은 전송량이 아니라 왕복 제거에서 나옴.

로컬 재구성 환경의 브라우저 측정이며, 네트워크 지연은 브라우저의 요청 단위 지연 주입[* Chromium DevTools Protocol의 네트워크 조건 에뮬레이션. TCP·TLS 핸드셰이크 왕복은 정확히 재현하지 않음]으로 근사함. 측정 방법과 전체 결과는 [정적 생성 전환 전후의 글 열람 지연 측정](/ken-blog/post/post-c342d140-8026-4137-8761-b5c3eecddc2c/) 참조. 본문이 초기 HTML에 있어 검색엔진이 본문을 수집할 때 스크립트 실행과 추가 API 호출을 기다리지 않아도 됨. [Google의 JavaScript SEO 가이드](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

## P3. revision 재검증으로 서로 다른 시점의 자료 혼합 방지

### 문제

공개 페이지는 Git의 원고, DB의 글 정보, 디스크의 이미지를 빌드 시 결합해 만듦. 빌드가 자료를 수집하는 동안 관리자가 글 정보를 바꾸면 서로 다른 시점의 자료가 섞인 사이트가 발행될 수 있고, 원고 누락이나 손상된 이미지가 있으면 일부만 깨진 사이트가 배포될 수 있음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 검증 없이 수집한 그대로 빌드 | 서로 다른 시점의 자료가 섞이거나 일부가 깨진 사이트가 배포될 수 있음 |
| 빌드하는 동안 DB 쓰기 잠금 | 빌드 시간 동안 관리 기능이 멈추고, 빌드 실패 시 잠금 해제를 따로 보장해야 함 |
| **revision 기반 낙관적 검증 (채택)** | 관리 기능을 멈추지 않고, 수집 도중의 변경을 빌드 결과 확정 전에 감지함 |

API가 공개 메타데이터와 첨부 상태의 SHA-256 revision[* 공개 글 메타데이터 JSON과 글별 첨부 연결·상태를 합쳐 계산한 해시. Git 원고는 포함하지 않으며, 원고 쪽 변경은 배포 직전 `main` 재확인으로 검사]을 제공하고, 빌더가 수집 시작 때와 페이지 생성 후의 revision을 비교해 다르면 결과를 폐기함. Git 쪽은 배포 직전 `main`의 사이트 입력 변경 여부를 다시 확인함. 페이지는 임시 디렉터리에서 생성·검사하고, 수집·생성·검증 중 하나라도 실패하면 새 결과를 확정하지 않고 Pages 배포도 진행하지 않아 공개 중인 사이트가 그대로 유지됨.

### 대가

빌드 중 관리자 변경이 있으면 빌드를 다시 실행해야 하며, 마지막 검증부터 배포 완료까지의 구간은 원자적으로 묶이지 않음.

### 검증

빌드 파이프라인 회귀 검사에서 아래 실패 상황마다 새 결과를 확정하지 않고 기존 산출물을 유지하는지 확인함. 수집·검증 순서와 보장하지 않는 구간은 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)의 일관성 모델 절에서 다룸. [파이프라인 검사](https://github.com/gjaku1031/ken-blog/blob/3074d80/.github/pages/pipeline.test.mjs)

## 편집 충돌: 편집 버전과 행 잠금

### 문제

같은 글을 두 관리 화면에서 열고 차례로 저장하면, 늦게 저장한 화면이 먼저 저장된 변경을 덮어쓰는 갱신 손실(lost update)이 생길 수 있음.

### 구조

화면은 글을 불러올 때 받은 `editVersion`을 저장 요청의 `baseVersion`으로 보냄. 서비스는 글 행을 비관적 잠금으로 잡은 뒤 두 값을 비교하고, 다르면 409로 거부함. 같으면 글 정보·소속·순서·태그를 한 트랜잭션으로 저장하고 버전을 올림. HTTP 요청 사이의 충돌은 버전 비교로, 비교와 쓰기 사이에 끼어드는 트랜잭션은 행 잠금으로 막음.

버전은 JPA `@Version`이 아니라 서비스가 직접 관리함. 그래서 버전을 올리는 작업을 코드에서 명시함. 글 정보 저장과 발행 전환이 버전을 올리고, 분류를 삭제해 글을 부모 분류로 한꺼번에 옮기는 일괄 UPDATE도 `edit_version + 1`을 함께 실행해 열려 있던 편집 화면의 다음 저장을 409로 만듦. 발행 전환에는 버전 비교를 두지 않았고, 작업별 정책은 [기능과 사용자 흐름](/ken-blog/post/doc-4cfccbd2-1972-4ad8-893a-6a8bf45744e1/)의 동시성 정책 절에서 다룸.

### 대가

자동 병합은 없음. 409를 받은 화면은 입력을 보존하고, 사용자가 글을 다시 열어 최신 값과 비교한 뒤 다시 저장해야 함.

### 검증

영속성 통합 테스트에서 같은 버전으로 동시에 저장하면 하나만 성공하는지(`concurrentEditorsHaveOneWinner`), 낡은 버전의 저장이 거부되고 변경 전체가 롤백되는지(`atomicEditsRejectStaleVersionsAndRollback`), 분류 이동 뒤 이전 버전의 저장이 거부되는지(`categoryMovesInvalidateEditors`) 확인함. 브라우저 검사에서는 409 뒤 입력이 보존되는지 확인함. [영속성 통합 테스트](https://github.com/gjaku1031/ken-blog/blob/3074d80/src/test/java/io/github/gjaku1031/kenblog/PostPersistenceIntegrationTest.java) · [브라우저 검사](https://github.com/gjaku1031/ken-blog/blob/3074d80/.github/pages/browser.spec.mjs)

## 반영 시점: 자동 배포 대신 배포 대기 표시

### 문제

글 정보·발행 상태는 DB에 있고 공개 사이트는 배포 때 만들어지므로, DB 변경이 언제 공개 사이트에 반영되는지 정해야 함.

### 선택과 대가

DB 변경을 감지해 Pages 배포를 자동으로 실행하는 경로를 두지 않음. 글 정보를 바꿀 일이 드물어, 원고 push와 운영자의 수동 실행으로 배포함. 그 대가로 다음 배포 전까지 공개 사이트가 DB와 어긋나는 구간이 생김.

이 구간은 관리 화면의 배포 대기 표시로 드러냄. 빌드가 공개 글마다 메타데이터 지문을 배포 결과에 기록하고, 관리 화면이 이를 현재 공개 스냅샷과 글 단위로 비교해 '발행 후 배포 대기', '수정 후 배포 대기', '발행 취소 · 배포 대기' 등을 표시함. 상태 목록과 판정 규칙은 [기능과 사용자 흐름](/ken-blog/post/doc-4cfccbd2-1972-4ad8-893a-6a8bf45744e1/)의 배포 대기 표시 절에서 다룸. [배포 상태 판정 테스트](https://github.com/gjaku1031/ken-blog/blob/3074d80/.github/pages/deployment.test.mjs)

## 조회 계층: JPQL 대신 jOOQ

### 문제

쓰기와 단일 조회는 JPA로 충분했지만, 목록·검색·집계 조회는 선택 조건과 조인이 많았음. JPQL 문자열로 쓰면 선택 조건을 `:값 is null or ...` 형태로 나열하고, 정렬 기준을 바꾸려고 `CASE`를 반복하고, 같은 조건을 건수 조회에 한 번 더 복사해야 했음.

<details><summary>jOOQ 전환 전 공개 글 목록 JPQL</summary>

분류·태그 필터와 두 가지 정렬을 한 문자열에 담은 쿼리. 같은 `where` 조건을 건수 조회 쿼리에 한 번 더 작성함.

```sql
select new PublishedPostRow(p.id, p.title, p.slug, p.publishedAt, p.categoryId)
from PostEntity p
where p.section = PostSection.TECH
  and p.status = :published
  and (:includePrivate = true or p.visibility = :publicVisibility)
  and (:categoryPath is null or exists (
        select c.id from CategoryEntity c
        where c.id = p.categoryId and (c.path = :categoryPath or c.path like :descendantPath)))
  and (:tag is null or exists (
        select t.id from PostTagEntity t where t.postId = p.id and t.name = :tag))
order by case when :seriesOrder = true and p.techSeriesOrder is null then 0
              when :seriesOrder = true then 1 else null end asc,
         case when :seriesOrder = true then p.techSeriesOrder else null end asc,
         case when :seriesOrder = true then p.publishedAt else null end asc,
         case when :seriesOrder = true then p.id else null end asc,
         case when :seriesOrder = false then p.publishedAt else null end desc,
         case when :seriesOrder = false then p.id else null end desc
```

</details>

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| JPQL만 사용 | 위와 같은 조건부 조회를 문자열로 유지하기 복잡함 |
| QueryDSL | 더 이상 제대로 된 업데이트가 이어지지 않는다고 판단함 |
| **jOOQ (채택)** | 조건과 정렬을 코드로 조립하고, 스키마에서 생성한 타입으로 열 이름·타입을 컴파일 시점에 검사함 |

쓰기·단일 조회·잠금은 JPA에 남기고, 목록·검색·집계·공개 스냅샷 조회만 jOOQ로 옮김. 두 기술은 같은 데이터 소스와 Spring 트랜잭션을 공유함.

### 대가

영속 기술 두 개와 코드 생성 단계를 함께 유지해야 함. jOOQ 타입은 JPA 엔티티에서 만든 DDL로 생성해 스키마 정의를 한곳에 둠. 생성 순서와 검증은 [JPA 기반 코드 생성 ADR](/ken-blog/post/post-f69cf0bb-68a1-4b72-b6c9-6aea1ed04db9/)에서 다룸. jOOQ와 JPA의 속도를 비교해 내린 결정은 아님.
