## 공개 스냅샷 회귀 기준

운영에서 잰 값이 아니라, 격리된 MySQL에서 도는 통합 검사(`largeSnapshotsAreBoundedAndConsistent`)가 지켜야 하는 조건임. 같은 분류에 공개 글 300개를 넣어 스냅샷을 만들고, 탐색 목록을 글마다 중복해 담거나 조회 수가 글 수만큼 늘어나는 퇴행이 생기지 않는지 봄.[* 조회 계수는 Hibernate `prepareStatementCount`와 jOOQ SELECT 리스너를 합산. 서비스의 실제 응답 상한은 공개 스냅샷 7,999,800바이트, 관리자 스냅샷 8,000,000바이트로 이 통과 조건과 별개]

| 검증 대상 | 입력과 통과 조건 | 해석 범위 |
| --- | --- | --- |
| 공개 글 수 | 한 분류에 공개 글 300개 | 다양한 실사용 분류·태그 조합까지 대표하지 않음 |
| 조회 계수 | Hibernate `prepareStatementCount` + jOOQ SELECT 계수 ≤ 10 | 해당 snapshot 호출 구간의 DB 접근 기준. HTTP 지연 기준 아님 |
| 응답 형식 | `version == 3` | 현재 서버 스냅샷 계약 확인 |
| 탐색 중복 | `navigation` 그룹 1개, 해당 그룹 항목 300개 | 300개 그룹을 만드는 검사가 아님 |
| 응답 크기 | 전체 payload의 JSON 직렬화 결과 < 500,000바이트 | 네트워크 압축 전 바이트. 실제 반환 크기의 측정 보고서와 구분 |
| 관리자 읽기 | REPEATABLE_READ 안에서 외부 변경 전후 두 조회가 동일 | 한 읽기 트랜잭션의 일관성 확인 |
| 커밋 후 재조회 | 글 300개를 유지하고 외부에서 바꾼 제목을 확인 | 이전 트랜잭션 밖에서는 새 결과를 읽는지 확인 |

한 분류에 글 300개를 넣은 단일 자료로 잰 것이라, 그룹 수나 문자열 길이, 관계가 다른 자료에서도 같은 크기라고 볼 수는 없음.[* [영속성 통합 테스트](https://github.com/gjaku1031/ken-blog/blob/b768152/src/test/java/io/github/gjaku1031/kenblog/PostPersistenceIntegrationTest.java) · [공개 스냅샷](https://github.com/gjaku1031/ken-blog/blob/b768152/src/main/java/io/github/gjaku1031/kenblog/pages/PagesSnapshotService.java)]

## 측정하지 않은 것

- 지금 운영 중인 이미지로는 JVM 부하를 다시 재지 않았음
- 스냅샷의 글 수, 그룹 수, 문자열 길이를 바꿨을 때 조회 수와 응답 크기, 지연이 어떻게 변하는지 재지 않았음
- 원고와 이미지가 늘거나 번들 캐시가 없을 때 정적 빌드의 수집과 렌더링 시간이 얼마나 늘어나는지 재지 않았음
