# 관리자 글쓰기 화면 — P2-02B

이 문서는 P2-02B의 정적 관리자 화면 계약과 2026-09-26 격리 브라우저 검증 기록. API 주소 미설정 빌드의 화면 확인까지 완료했고 main·CI·Pages 반영 전. 기반인 [관리자 편집본 API](editor-drafts.md)는 main `19b884a`와 CI·Pages에 반영 완료. 공개 Pages에는 API HTTPS 주소가 없어 실사이트의 관리자 로그인·작성·출간 연결은 아직 없음. 상세 범위와 완료 조건은 [P2-02B 계획](../planning/issues/P2-02B.md) 참고.

## 진입과 권한

| 정적 경로 | 동작 |
| --- | --- |
| `/write/` | 새 Tech 글 작성 |
| `/write/?postId=양수` | 기존 글의 별도 편집본 작성 또는 기존 편집본 이어쓰기 안내 |
| `/write/?draftId=양수` | 저장된 편집본 재개 |
| `/admin/drafts/` | 수동 저장 편집본 목록·이어쓰기·삭제 |

GitHub Pages 하위 경로에서는 앞에 `/ken-blog`를 붙이고 끝 슬래시를 유지. `postId`와 `draftId`를 함께 보내거나 잘못된 ID를 주면 조용히 새 글로 처리하지 않고 입력 안내. 없는 글·편집본, API 주소 미설정, 통신 장애도 각각 구분. 익명은 사이트 내부의 안전한 `returnTo`로 로그인 화면에 이동하고, 로그인한 `USER`에게는 권한 없음 안내. 화면 조회와 쓰기는 모두 유효한 `ADMIN` JDBC 세션 필요. 공개 전용 origin의 CORS나 단순 화면 링크는 관리자 권한을 부여하지 않음.

새 글은 기존 `posts`의 `DRAFT` 행을 바로 만들지 않고 별도 `editor_drafts` 편집본에 수동 저장. 기존 공개 글도 원본 PUT 없이 편집본을 만들어 수정. 같은 원본에 편집본이 이미 있으면 그 편집본을 다시 열도록 안내하고 새 편집본으로 덮지 않는 계약. 첫 저장 성공 뒤 URL에 `draftId`를 반영해 새로고침·직접 진입에서 서버 저장본 복원. 브라우저 `localStorage`에 원고·비밀번호·쿠키·CSRF 토큰을 보관하지 않음. 저장 전 화면에만 있는 변경은 새로고침이나 탭 종료로 복원되지 않음.

## 기본 블록과 원문 보존

편집 범위는 문단, 제목 1~3단계, 글머리·번호·할 일 목록, 인용, 코드, 구분선의 기본 블록. 제목·분류·태그 입력, 수동 저장과 출간 버튼 제공. 편집 중인 블록에만 입력 영역을 두고 나머지는 안전한 읽기 표시. 헤더는 유지하고 글쓰기 화면의 푸터는 숨기며, 편집 열은 최대 760px.

Enter의 문단 분할과 빈 목록 탈출, Backspace의 빈 블록 변환·안전한 이웃 블록 합치기, 화살표·Escape의 초점 이동, 코드 블록의 Ctrl/⌘+Enter, 블록 순서의 손잡이·키보드 위아래 이동 제공. 모바일에서는 손잡이에 의존하지 않는 위아래 버튼 제공. 한글 조합 중에는 단축키가 조합 문자를 가로채지 않도록 처리. 제목·목록·할 일·인용 블록의 Shift+Enter는 입력 전에 차단하고 도움말로 안내하며, 문단·코드 블록의 줄바꿈과 구분.

표, 중첩 접기(`details`), 이미지, 수식, Mermaid, 참조 정의 등은 이번 단계의 전용 편집·렌더링 범위 밖. 읽어 온 Markdown에서 지원하지 않는 부분은 원문 블록으로 보존하고, 다른 블록을 수정해 수동 저장해도 해당 원문을 삭제하거나 평탄화하지 않는 계약. 원문 블록 경계에서 Backspace를 눌러도 내용이 의도 없이 삭제되지 않아야 함. 아무것도 고치지 않은 로드→저장 원문 보존과 일부 수정→재로드 후 내용 유지가 검증 대상. 원문 보존은 이미지 업로드·표 편집·고급 Markdown 표시의 완료를 뜻하지 않음. 공개 글 읽기 화면도 기존의 외부 이미지 자동 요청 차단과 raw HTML 미실행 경계를 유지.

## 수동 저장과 출간

수동 저장은 편집본 API의 POST 또는 `revision`을 포함한 PUT을 사용. 저장 중 중복 요청 방지와 저장 직후 추가한 화면 입력의 보존 필요. 저장 성공 응답의 새 revision이 화면의 출간 기준이며, 저장 이후 아직 수동 저장하지 않은 변경을 성공한 저장으로 표시하거나 출간에 포함했다고 안내하지 않는 계약. 기존 글 편집본의 `baseUpdatedAt`은 원본 조회 때의 UTC `updatedAt`을 사용. 수동 저장만으로 공개 원문·분류·태그·가시성·본문 캐시는 변하지 않음.

출간 시트에서 slug와 `PUBLIC`/`PRIVATE`를 확인하고, 제목·길이·본문/태그 제한을 안내. 출간은 저장된 편집본의 revision을 담아 `POST /api/v1/admin/editor-drafts/{id}/publish` 호출. 성공하면 원본 게시글과 분류·태그·범위를 한 번에 반영하고 편집본을 제거한 뒤 정적 `/post/?slug=...` 주소로 이동. 기존 글 최초 출간 시각은 유지. 출간 실패 시 공개 글 원문과 편집본은 이전 커밋 상태로 유지되는 API 계약. 화면의 미저장 입력도 자동으로 버리거나 서버 응답으로 덮지 않는 계획.

오래된 revision·원본 변경·중복 slug의 `409`, 잘못된 입력 `400`, 없는 원본·편집본·분류 `404`, DB 장애 `503`와 네트워크 오류를 구분해 안내. 충돌에서 자동 재조회·강제 덮어쓰기 없음. 사용자가 명시적으로 다시 조회하기 전까지 현재 입력 보존. ADMIN 세션 만료·로그아웃·계정 전환에서는 관리자 원문을 즉시 화면에서 제거하고, 앞선 계정이나 요청의 늦은 응답이 다시 표시되지 않아야 함. 쓰기 요청에는 현재 세션의 `X-CSRF-TOKEN` 필요. API 응답의 `no-store`와 브라우저 메모리 폐기는 서로 다른 보호 경계.

## 편집본 목록

`/admin/drafts/`는 실제 API의 본문 없는 10개 단위 번호 페이지를 조회하고, 각 항목에서 이어쓰기 또는 revision 조건 삭제를 제공. 삭제 전에 확인을 받고, 삭제 성공 후 마지막 항목이 사라진 페이지는 유효한 이전 페이지로 복귀. 저장 시각은 서버 UTC 시각을 명시적으로 해석해 한국 시간으로 표시. 분류는 관리자 분류 API의 실제 경로를 사용하고 삭제된 분류와 조회 실패를 구분. 빈 목록, 권한 없음, API 미설정·오류도 구분. 편집본 삭제는 연결된 원본 게시글이나 OCI Object Storage 객체를 삭제하지 않음.

## 로컬 실행·검증 경계

로컬 정적 서버 `http://127.0.0.1:14000/ken-blog/`와 API `http://127.0.0.1:18081`의 쿠키·CORS 설정은 [런타임 안내](runtime.md) 참고. 포트는 다르지만 호스트는 같은 `127.0.0.1`을 사용. `APP_AUTH_CORS_ALLOWED_ORIGINS`에 정확한 로컬 정적 origin을 명시해야 하며, 관리자 글·분류·태그의 추가 CORS는 GET만 허용. 편집본 쓰기는 기존 API의 세션·CSRF 계약을 사용. 2026-09-26 API `clean verify`의 기존 검사 28개와 격리 JAR GET에서 관리자 글·분류·태그의 인증 origin credential 응답을 확인. 같은 경로 쓰기 메서드와 공개 전용 origin GET의 preflight는 `403` 확인. 이는 화면이나 공개 HTTPS 배포 검증의 근거가 아님. 공개 API 주소가 비어 있는 별도 정적 빌드에서는 관리자 API 요청 성공이나 가짜 편집본 데이터를 표시하지 않는 것이 검증 대상.

## 실제 검증과 남은 경계

2026-09-26 기존 API 검사 28개·웹 검사 7개·타입 검사·정적 빌드 통과. 격리 Chrome 153에서 새 글 기본 블록 작성, 분류·태그 선택, 수동 저장→`draftId` URL 변경→새로고침 복원→출간과 편집본 제거 확인. 기존 공개 글의 편집본 저장 중 공개 원문 불변, 성공 출간 뒤 반영 확인. 중첩 `details`, 표, 이미지, 수식, Mermaid, 참조 정의, script를 포함한 원문은 무수정 왕복에서 정확히 보존했고 다른 문단만 수정한 뒤 출간해도 해당 원문이 보존됨을 확인. 별도 원문 16개와 결정적 비정상 입력 300개도 왕복 보존 확인.

실제 PUT 응답을 지연한 동안 추가 입력하면 저장 요청 당시 내용만 저장되고 화면의 추가 입력·미저장 표시가 남으며 다음 revision 저장에 반영됨을 확인. SQL에서 세션 CSRF 속성을 제거한 뒤 쓰기 `403`에서도 입력 유지, 새 토큰으로 재시도 성공. 다른 수정이 먼저 들어간 `409`와 중복 slug 출간 `409`에서는 입력·출간 시트 유지. 쿼리 이동을 취소하면 미저장 원고·원래 주소 유지, 이동을 확인하면 다른 편집본 정상 로드. Chrome 뒤로가기 취소에서도 원고 보존. 같은 문서의 뒤로가기 개입은 Navigation API `navigate` 이벤트가 `canIntercept`와 `cancelable` 조건을 만족할 때 사용하며, [MDN의 `canIntercept` 설명](https://developer.mozilla.org/en-US/docs/Web/API/NavigateEvent/canIntercept)은 개입 가능 범위와 구형 브라우저 지원 차이를 설명. 실제 확인은 Chrome 153 한정이고 다른 브라우저의 뒤로가기 보호 완료 근거는 없음. SQL 세션 만료 뒤 원고 제거, 실제 편집본 상세 응답을 지연한 상태에서 로그아웃한 뒤 이전 원고가 다시 나타나지 않음을 확인.

11개 편집본의 10개 단위 번호 페이지와 마지막 페이지 삭제 뒤 첫 페이지 복귀, 삭제 취소·확인, 저장 시각의 한국 시간 표시와 실제 분류 명칭 확인. 다른 탭에서 revision을 올린 뒤 목록의 오래된 revision으로 삭제하면 `409`, 행과 서버 원고 유지. 잘못된 동시 `postId`·`draftId`, 없는 편집본, 음수 목록 페이지의 안내도 확인. 문단 분할·합치기·커서 위치, 빈 목록 탈출, 구분선, 코드 Ctrl+Enter, 제목 Shift+Enter 차단·문단 줄바꿈, Escape, 키보드 블록 이동과 저장·재로드 확인. ⌘+Enter는 구현했지만 실제 키보드 검증 범위 밖. 한글 조합은 합성 IME 229 이벤트로 확인했으며 실제 운영체제 IME 입력 검증은 아직 아님.

라이트·다크의 글쓰기·출간 시트·목록을 320~1440px 일곱 너비에서 확인하고 페이지 가로 넘침·미처리 브라우저 오류·오버레이 없음 확인. 자체 MySQL 중단의 오류와 입력 유지, 재시작 후 수동 저장 성공 확인. 자체 API 중단의 네트워크 오류와 입력 유지, 재시작 후 기존 JDBC 로그인으로 저장·새로고침 원고 복원 확인. 이는 격리 환경의 JAR·브라우저 결과이며 운영 API 교체나 공개 HTTPS API 연결 결과가 아님. API 주소를 비운 별도 정적 빌드에서 `/write/`는 관리자 세션/API 설정 안내, `/admin/drafts/`와 Home은 API 미설정 안내 확인. API 요청 0건, 가짜 원고·목록 0건 확인.
