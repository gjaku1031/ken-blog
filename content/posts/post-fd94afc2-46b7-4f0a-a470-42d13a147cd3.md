[0편](/ken-blog/post/post-df978c72-44d3-4e81-b572-8834cd0646c3/)에서 요청의 첫 단계는 브라우저가 주소를 해석하는 일이었다. 컨트롤러에서 `@RequestParam`으로 한글 검색어를 받아 쓰기만 했지, 주소창에 친 "커피"가 서버에 어떤 모양으로 도착하는지는 생각해 본 적이 없었다. 그래서 주소 한 줄을 칸별로 나눠 보고, 한글과 특수 문자가 어떻게 바뀌어 나가는지 직접 찍어 봤다.

## 학습 목표

- URL을 스킴, 호스트, 포트, 경로, 쿼리, 프래그먼트로 나누고 각 칸의 역할을 말할 수 있다
- 한글이 퍼센트 인코딩으로 바뀌는 과정을 UTF-8 바이트로 설명할 수 있다
- 공백이 `%20`과 `+`로 다르게 적히는 이유와, 프래그먼트가 서버로 가지 않는다는 것을 설명할 수 있다

## URL은 칸이 정해진 송장이다

택배 송장에는 칸이 정해져 있다. 건물 주소, 출입문, 층과 호실, 배송 메모를 각자 자기 칸에 적어야 기사님이 헷갈리지 않는다. URL도 같다. 아래 주소 하나를 칸별로 나눠 보면 이렇다.[* URL의 문법은 RFC 3986(URI 일반 문법)이 정한다. 브라우저가 실제로 주소를 해석하는 방식은 WHATWG URL 표준을 따른다]

`https://shop.example.com:8443/search/커피?q=원두 200g&sort=new#review`

| 칸 | 이 주소에서 | 택배로 치면 | 하는 일 |
| --- | --- | --- | --- |
| 스킴 | `https` | 배송 방식(일반, 보안 배송) | 어떤 규약으로 이야기할지 정함 |
| 호스트 | `shop.example.com` | 건물 이름 | 어느 서버인지. [1편](/ken-blog/post/post-adf39eb5-c2bf-4064-b443-e89613393020/)의 DNS가 이 이름을 IP로 바꿈 |
| 포트 | `8443` | 출입문 번호 | 그 서버의 어느 프로그램인지. `https`는 443, `http`는 80이 기본이라 보통 생략함 |
| 경로 | `/search/커피` | 층과 호실 | 서버 안에서 어떤 자원인지. 컨트롤러의 `@GetMapping`이 이 칸을 봄 |
| 쿼리 | `q=원두 200g&sort=new` | 배송 메모 | `이름=값`을 `&`로 이어 붙인 추가 조건 |
| 프래그먼트 | `review` | 내가 붙여 둔 책갈피 | 페이지 안의 위치. **서버로 보내지 않음** |

칸을 가르는 기호도 정해져 있다. `://` 뒤가 호스트, `:` 뒤가 포트, 첫 `/`부터 경로, `?` 뒤가 쿼리, `#` 뒤가 프래그먼트다. 문제는 이 기호들이 내용 안에도 나올 수 있다는 점이다. 검색어가 `a&b=c`라면 서버는 `&`를 보고 쿼리가 둘로 나뉜다고 읽어 버린다.

## 퍼센트 인코딩: 쓸 수 있는 글자로 옮겨 적기

URL에는 영문자, 숫자, 몇몇 기호만 그대로 쓸 수 있다. 해외로 보내는 송장에 한글을 못 쓰니 정해진 표에 따라 옮겨 적는 것처럼, URL에 쓸 수 없는 글자는 퍼센트 인코딩으로 옮겨 적는다. 규칙은 단순하다.

1. 글자를 UTF-8 바이트로 바꾼다. "담"은 `EB 8B B4` 세 바이트다
2. 바이트 하나를 `%`와 16진수 두 자리로 적는다. "담"은 `%EB%8B%B4`가 된다

한글 한 글자가 UTF-8로 3바이트라서, 인코딩하면 `%XX`가 세 개씩 붙는다. "커피"는 `%EC%BB%A4%ED%94%BC`로 여섯 덩어리다.

칸을 가르는 기호(`/ ? # & =` 등)가 내용 안에 들어갈 때도 같은 방법으로 옮겨 적는다. 그러면 서버는 `&`는 구분자로, `%26`은 내용 안의 `&`로 구별할 수 있다.[* RFC 3986은 이런 기호를 예약 문자(reserved characters)로 부르고, 영문자·숫자·`-._~`를 인코딩하지 않아도 되는 비예약 문자로 정한다]

### 헷갈렸던 것: 공백은 `%20`일까 `+`일까

둘 다 본 적이 있어서 헷갈렸다. 퍼센트 인코딩 규칙대로라면 공백은 `%20`이다. `+`는 HTML 폼을 보낼 때 쓰는 방식(`application/x-www-form-urlencoded`)에서 공백을 줄여 쓰는 표기다. 그래서 쿼리에서는 서버 대부분이 `+`를 공백으로 읽어 주지만, 경로에서 `+`는 그냥 더하기 기호다.[* `/search/a+b`의 경로에서 `+`는 공백이 아니다. 쿼리의 `+`를 공백으로 읽는 것도 폼 형식의 관례이지 RFC 3986의 규칙은 아니어서, 서버 프레임워크마다 처리가 같은지 확인해야 한다]

### 헷갈렸던 것: `#` 뒤는 서버가 모른다

프래그먼트는 브라우저가 페이지 안에서 위치를 찾을 때만 쓴다. 요청을 보낼 때는 떼어 내고 보낸다. 서버 로그에서 `#review`를 찾을 수 없는 이유이고, 서버가 프래그먼트 값으로 무언가를 하려 해도 받을 방법이 없다.

## 직접 확인해 보기

### 파이썬으로 칸 나누기와 인코딩

```text
$ python3
>>> from urllib.parse import urlsplit, quote, quote_plus, urlencode, unquote
>>> u = urlsplit("https://shop.example.com:8443/search/커피?q=원두 200g&sort=new#review")
>>> u.scheme, u.hostname, u.port, u.path, u.query, u.fragment
('https', 'shop.example.com', 8443, '/search/커피', 'q=원두 200g&sort=new', 'review')
>>> "담".encode("utf-8")
b'\xeb\x8b\xb4'
>>> quote("커피")
'%EC%BB%A4%ED%94%BC'
>>> quote("원두 200g"), quote_plus("원두 200g")
('%EC%9B%90%EB%91%90%20200g', '%EC%9B%90%EB%91%90+200g')
>>> urlencode({"q": "원두 200g", "tag": "a&b=c"})
'q=%EC%9B%90%EB%91%90+200g&tag=a%26b%3Dc'
>>> unquote("%zz")
'%zz'
```

출력은 한 세션처럼 모아 적었다.[* 2026-10-23, Linux VM의 Python 3.14.4. 실제로는 스크립트로 실행했고 출력 형식만 대화형으로 정리했다] `quote`는 공백을 `%20`으로, `quote_plus`와 `urlencode`는 `+`로 적었다. `a&b=c`의 `&`와 `=`는 `%26`, `%3D`로 바뀌어 쿼리 구분자와 섞이지 않는다. 깨진 표기 `%zz`는 `unquote`가 오류 없이 그대로 돌려줬다.

### 서버가 실제로 받은 요청줄

받은 요청줄을 그대로 출력하는 작은 파이썬 서버를 띄우고, 같은 한글 주소를 curl과 브라우저로 보내 봤다.[* 서버는 `http.server.BaseHTTPRequestHandler`로 만들고 `self.requestline`을 출력했다. 브라우저는 Playwright로 띄운 Chromium 153.0.8010.12, curl은 8.18.0]

```text
# curl로 보냄
$ curl 'http://127.0.0.1:18201/search/커피?q=원두#review'
받은 요청줄: GET /search/%EC%BB%A4%ED%94%BC?q=ìë HTTP/1.1

# 브라우저(Chromium)로 보냄
page.goto("http://127.0.0.1:18201/search/커피?q=원두 200g#리뷰")
location.href = http://127.0.0.1:18201/search/%EC%BB%A4%ED%94%BC?q=%EC%9B%90%EB%91%90%20200g#%EB%A6%AC%EB%B7%B0
받은 요청줄: GET /search/%EC%BB%A4%ED%94%BC?q=%EC%9B%90%EB%91%90%20200g HTTP/1.1
```

| 보낸 쪽 | 경로의 한글 | 쿼리의 한글 | 공백 | 프래그먼트 |
| --- | --- | --- | --- | --- |
| curl | `%EC%BB%A4…`로 인코딩함 | 인코딩하지 않고 UTF-8 바이트 그대로 보냄 | 주소에 공백이 있으면 보내지 않고 오류로 끝냄 | 보내지 않음 |
| Chromium | 인코딩함 | 인코딩함 | `%20` | 보내지 않음 |

curl 줄의 `ìë`가 깨져 보여서 바이트를 직접 떠 봤다. `nc`로 받은 요청의 첫 줄을 16진수로 보면 `?q=` 뒤에 `ec 9b 90 eb 91 90`, 즉 "원두"의 UTF-8 바이트가 인코딩 없이 들어 있었다. 파이썬 서버는 요청줄을 ISO-8859-1로 읽기 때문에 이 바이트가 엉뚱한 글자로 보인 것이다.[* `curl 'http://…/search/a b'`는 요청을 보내지 않고 종료 코드 3(잘못된 URL)으로 끝났다] 쓰는 도구에 따라 같은 주소가 다른 바이트로 나간다는 게 의외였다. 브라우저는 주소창 표시와 상관없이 보낼 때는 전부 인코딩하고, `#리뷰`는 `location.href`에만 남고 서버에는 가지 않았다.

### 깨진 인코딩 `%zz`는 누가 막을까

`%` 뒤에는 16진수 두 자리가 와야 하는데 `zz`는 16진수가 아니다. 같은 `%zz`를 세 곳에 보내 봤다. Tomcat은 Spring Boot에 들어 있는 것과 같은 내장 Tomcat으로 서블릿 하나만 띄웠다.[* Tomcat 11.0.24(`tomcat-embed-core`), 기본 설정. 서블릿은 `getRequestURI()`, `getPathInfo()`, `getParameter("q")`를 출력한다. 경로에 `%zz`를 그대로 보내려고 curl에 `--path-as-is`를 붙였다]

| 받는 곳 | 요청 | 결과 |
| --- | --- | --- |
| 직접 만든 파이썬 서버 | `/files/%zz` | 200. 경로를 그대로 받음 |
| example.com(앞에 CDN) | `/%zz` | 400. CDN 서버가 응답함(`server: cloudflare`) |
| Tomcat | `/files/%zz` | 400. 서블릿이 실행되지 않음 |
| Tomcat | `/search/x?q=%zz` | 400. 서블릿은 실행됐고, `getParameter("q")`를 부르는 순간 400이 됨 |

정상 주소를 보냈을 때 Tomcat은 `getRequestURI()`로 인코딩된 원문(`/search/%EC%BB%A4%ED%94%BC`)을, `getPathInfo()`로 디코딩한 `/search/커피`를, `getParameter("q")`로 `+`를 공백으로 바꾼 `원두 200g`을 돌려줬다. 컨트롤러가 받는 한글은 이렇게 서버가 한 번 풀어 준 값이었다.

`%zz`는 받는 곳마다, 그리고 같은 Tomcat 안에서도 칸마다 다르게 처리됐다. 경로의 `%zz`는 Tomcat이 요청을 읽는 단계에서 바로 거절해 서블릿까지 오지 않았다. 반면 쿼리는 요청을 읽을 때 풀어 보지 않고 있다가, 코드가 파라미터를 꺼낼 때 풀다가 실패했다. 서블릿 앞에 필터가 있었다면 경로의 `%zz`는 필터도 거치지 않고, 쿼리의 `%zz`는 필터를 거친 뒤에 실패한다는 뜻이다. 이 순서는 [9편](/ken-blog/post/post-5d80fd8f-1874-45f6-b90c-37d9bb411383/)에서 Tomcat, 필터, 컨트롤러를 볼 때 다시 확인한다.

> URL은 칸이 정해진 송장이고, 칸에 그대로 쓸 수 없는 글자는 UTF-8 바이트를 `%XX`로 옮겨 적는다. 무엇을 인코딩해 보내고 어디서 풀어 읽는지는 도구와 서버마다 달라서, 서버가 실제로 받은 원문을 직접 확인해 봐야 한다.

## 확인 질문

**1. `https://example.com/docs#install`로 접속하면 서버가 받는 경로는 무엇일까?**

<details><summary>답</summary>

`/docs`다. `#install`은 프래그먼트라서 브라우저가 요청을 보낼 때 떼어 낸다. 페이지를 받은 뒤 브라우저가 그 위치로 스크롤할 때만 쓴다.

</details>

**2. "담"을 퍼센트 인코딩하면 왜 `%XX`가 세 개 붙을까?**

<details><summary>답</summary>

퍼센트 인코딩은 글자가 아니라 바이트 단위로 적기 때문이다. "담"은 UTF-8로 `EB 8B B4` 세 바이트라서 `%EB%8B%B4`가 된다.

</details>

**3. 검색어 `a&b`를 쿼리에 인코딩하지 않고 `?q=a&b`로 보내면 서버는 어떻게 읽을까?**

<details><summary>답</summary>

`q=a`와 값이 없는 `b`, 두 개의 파라미터로 읽는다. `&`가 쿼리의 구분자이기 때문이다. 내용 안의 `&`는 `%26`으로 적어 `?q=a%26b`로 보내야 `q`가 `a&b` 하나로 읽힌다.

</details>

**4. 쿼리의 `+`와 경로의 `+`는 같은 뜻일까?**

<details><summary>답</summary>

아니다. 쿼리의 `+`는 HTML 폼 형식의 관례에 따라 서버 대부분이 공백으로 읽는다(Tomcat의 `getParameter`도 그랬다). 경로의 `+`는 더하기 기호 그대로다. 어느 칸에서나 공백이라는 뜻을 분명히 하려면 `%20`을 쓴다.

</details>

**5. 내장 Tomcat에 경로 `/files/%zz`와 쿼리 `?q=%zz`를 보냈을 때 결과가 어떻게 달랐을까?**

<details><summary>답</summary>

둘 다 400이었지만 멈춘 곳이 달랐다. 경로의 `%zz`는 Tomcat이 요청을 읽는 단계에서 거절해 서블릿이 실행되지 않았다. 쿼리의 `%zz`는 서블릿이 실행된 뒤 `getParameter`로 값을 꺼내는 순간 실패했다.

</details>
