# 주석 전수 조사

조사일: 2026-10-03 (Asia/Seoul). 조사 시점 HEAD: `ec1aabc`.

기존 Git 추적 파일 147개를 대상으로 주석을 추출하고 전체 주석 내용을 읽었다. 아래 정확성 지적은 관련 구현과 대조했다. 최초 조사에서는 소스 주석을 수정하지 않았다. 아래 집계·행 번호·개선 후보는 정리 전 스냅샷이며, [주석 컨벤션](../convention/KDoc.md) 확정 후 전체 적용 결과는 문서 마지막에 기록했다.

## 범위와 집계 기준

- 애플리케이션·테스트·프론트·빌드·CI·배포·설정·템플릿을 포함했다. 이번에 추가한 지침·컨벤션·조사 문서는 기존 주석 수에서 제외했다.
- `/* ... */`·`/** ... */`·템플릿 주석은 블록당 1개, `//`·`#`·`--`는 줄당 1개로 셌다. 같은 줄의 코드 뒤에 있는 주석도 포함했다.
- 문자열·정규식·URL·glob 안의 기호는 주석에서 제외했다. 예를 들어 `https://`, `"/api/v1/admin/**"`, Markdown 파서가 찾는 `"<!--"`는 주석이 아니다.
- `rg`로 후보를 검색하고 임시 어휘 스캐너로 위치·유형을 집계했다. 원문 검색과 대조하여 추출되지 않은 블록 시작 기호는 문자열의 경로 패턴임을 확인했다. 컴파일러나 Dokka로 문서 구조·링크 해석을 검증한 결과는 아니다.
- Markdown 11개는 ADR·게시글 본문으로 분류했다. 본문 각주는 코드 주석에서 제외했다. 라이선스 텍스트 2개와 바이너리 1개도 별도 분류했다.
- Gradle Wrapper의 생성 주석은 별도 집계했다. 라이선스·shellcheck 지시문·생성 원본 설명을 포함하며 컨벤션 정리 대상으로 보지 않는다. 첫 줄 shebang은 주석 수에서 제외했다.

## 구현과 대조한 정확성 보정 대상

### 1. 반환값·예외·HTTP 변환을 구분해야 한다

- [StackBadgeService.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/stack/service/StackBadgeService.kt) 79행은 `@return 입력 실패의 안전한 400.`이지만 `badInput(): Nothing`은 항상 `BusinessException`을 던진다. 반환 설명을 제거하고 예외 발생 조건으로 표현해야 한다.
- 같은 파일 66행은 `badge()`의 반환값에 엔티티와 `404`를 함께 적었다. 반환값은 `StackBadgeEntity`이며 조회 실패는 예외이다.
- [AttachmentIds.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/attachment/dto/AttachmentIds.kt) 27행, [PostAttachmentDeliveryService.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/attachment/service/PostAttachmentDeliveryService.kt) 30행, [LocalAssetStorage.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/attachment/storage/LocalAssetStorage.kt) 98행의 헬퍼는 HTTP 응답 대신 `AttachmentFailure` 객체를 반환한다. 이 경우 `@return`은 가능하지만 반환 객체와 나중의 HTTP 변환을 구별해야 한다.

### 2. 저장소에서 옮겨진 책임이 주석에 남아 있다

- [PostAttachmentRepository.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/attachment/repository/PostAttachmentRepository.kt) 10행은 공개 전달 권한 조회를 책임으로 적었다. 현재 선언은 연결 ID 조회와 연결 삭제이며 공개 전달 권한 조회는 [PostQueries.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/post/repository/PostQueries.kt)의 `readableAttachment()`에 있다(83행).
- [PostTagRepository.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/post/repository/PostTagRepository.kt) 13행은 권한별 SQL 사용량 집계를 책임으로 적었다. 현재 선언은 이름·행 조회와 삭제이며 집계는 `PostQueries.tagCounts()`에 있다(59행).

### 3. 분류·태그 집계의 권한 설명이 현재 조회 조건과 다르다

- [CategoryDtos.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/category/dto/CategoryDtos.kt) 46~47행은 현재 역할로 읽을 수 있는 글 수라고 설명한다. [CategoryService.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/category/service/CategoryService.kt) 20행·119행에도 권한별 집계라는 표현이 있다.
- 실제 `CategoryService.tree()`는 초안을 포함하는 관리자 트리를 만들고, `PostQueries.categoryCounts()`는 분류가 있는 글을 역할·공개 상태 필터 없이 센다(56~58행).
- [TagDtos.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/post/dto/TagDtos.kt) 3행의 관리자 또는 공개 권한 설명도 현재 관리자 집계 경로에 맞게 좁힐 필요가 있다. `PostQueries.tagCounts()`에는 공개 조건이 없다.
- 이는 현재 관리자 API 설명의 정확성 문제이다. 이 조사만으로 공개 데이터 노출 결함이라고 판단하지 않는다.

### 4. 첨부 응답의 본문 전송·자원 해제 설명을 보완해야 한다

[PostAttachmentController.kt](../../src/main/kotlin/io/github/gjaku1031/kenblog/attachment/controller/PostAttachmentController.kt) 16행은 헤더만 반환한다고 읽힐 수 있다. 실제 `content()`는 같은 요청에서 헤더를 설정하고 본문을 스트리밍하며 `use`로 입력 스트림을 닫는다(23~30행). 파일을 여는 시점, 본문 전송, 해제 책임을 포함하는 설명이 적절하다.

## 보존하거나 보완할 계약 설명

- 보존: `AttachmentIds.parse()`의 생략·null·빈 배열 구분, `AttachmentLinkService`의 부모→첨부 ID 잠금 순서, `LocalAssetStorage.open()`의 스트림 해제 책임은 호출자가 알아야 하는 계약이다.
- 보존: Markdown 파서의 코드·수식 제외 범위, CRLF 위치 복원, Mermaid SVG 외부 참조 제한은 코드 변경 시 깨지기 쉬운 이유를 설명한다. 단순히 길다는 이유로 제거하지 않는다.
- 보존: 엔티티 5곳의 동일한 FK 주석은 쓰기용 ID 필드와 관계 매핑을 구분하는 설명이다. 반복을 발견했지만 자동 삭제 대상은 아니다.
- 보완 후보: `SeriesService.update()`의 `baseUpdatedAt` 일치 조건과 `delete()`의 비어 있는 시리즈 조건, `PublicPostService.detailMetadata()`의 시리즈 우선·3단계 분류 대체 탐색 조건은 함수 이름만으로 알기 어렵다. 이 파일들은 현재 클래스 KDoc이 각각 1개뿐이다.
- 보완 후보: `PagesSnapshotService.snapshot()`의 revision에는 공개 메타데이터와 첨부 정보가 들어가고 Git 원고 내용은 들어가지 않는다. 클래스 설명을 유지하면서 호출 계약에 이 범위를 명시할 수 있다.
- 직접 관리하는 주석에서 `TODO`·`FIXME`·`HACK`·`XXX`, 검사 억제용 주석, 주석 처리한 폐기 코드는 발견하지 못했다. Gradle Wrapper의 shellcheck 지시문은 생성 원본으로 별도 취급했다.

## 후속 정리 순서

1. 반환·예외 설명, 옮겨진 저장소 책임, 집계 범위, 첨부 전송 설명을 먼저 바로잡는다.
2. 한 줄 KDoc 238개를 여러 줄 형식으로 바꾸고, 요약 없는 KDoc 46개와 문서 주석의 잘못된 위치를 정리한다. 두 집계에는 중복이 있다.
3. 클래스·메서드·프로퍼티·테스트·헬퍼 등 모든 선언과 의미 있는 처리 구간의 누락 주석을 보완한다. 복잡한 로직에는 전체 흐름과 내부 단계·분기·실패 조건도 설명한다. 필수 주석은 유지하며 설명만 간결하게 정리한다.
4. 마지막으로 문체를 맞추고 링크·태그를 다시 확인한다.

주석 수는 품질이나 선언별 문서화율이 아니다. 특히 모든 Kotlin 파일에 주석이 있어도 모든 선언과 처리 구간에 주석이 있다는 뜻은 아니다. 최초 조사는 기존 주석의 집계이며, 후속 적용에서는 주석이 없는 선언과 복잡한 흐름도 빠짐없이 점검해야 한다. 이번 작업에서는 실행 코드 변경, 앱 테스트 실행, Dokka 빌드, 주석 일괄 수정을 하지 않았다.

### 주석 문법이 없는 JSON 파일

| 파일 | 역할 |
