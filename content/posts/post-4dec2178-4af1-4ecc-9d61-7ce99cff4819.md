관리 화면은 여러 탭에서 열 수 있다. 같은 글을 두 화면에서 열고 차례로 저장하면, 늦게 저장한 화면이 먼저 저장된 변경을 덮어쓰는 갱신 손실(lost update)이 생길 수 있다. ken-blog는 편집 버전을 비교해 이를 막는데, 버전 비교만으로는 거의 동시에 도착한 두 저장 요청을 막지 못한다. 그래서 비교하기 전에 글 행을 잠그는 단계를 함께 둔다.

## 계기: 늦게 저장한 화면이 앞의 변경을 지운다

화면은 글을 불러올 때 받은 `editVersion`을 저장 요청의 `baseVersion`으로 보낸다. 서버는 현재 버전과 다르면 409로 거부한다.[* 409 Conflict는 요청이 서버의 현재 상태와 충돌해 처리할 수 없다는 HTTP 상태 코드다] 화면 A가 글을 연 뒤 화면 B가 저장하면 버전이 올라가므로, A가 나중에 저장할 때 거부된다.

![HTTP 요청 사이의 충돌. 두 화면이 같은 버전 3으로 글을 열고, B가 먼저 저장해 버전이 4가 되면 A의 저장은 baseVersion 3이라서 409로 거부된다|dark=239|w=100|a=center](attachment:240)

## 남은 구간: 거의 동시에 온 두 저장

버전 비교가 막는 것은 HTTP 요청 사이의 충돌이다. 두 저장 요청이 거의 동시에 도착하면 이야기가 다르다. 두 트랜잭션이 모두 버전 3을 읽고, 둘 다 `baseVersion` 3과 같으니 비교를 통과하고, 뒤에 커밋한 쪽이 앞의 변경을 덮어쓴다.

MySQL InnoDB의 기본 격리 수준(REPEATABLE READ)에서 일반 `SELECT`는 잠금 없이 스냅샷을 읽는다.[* 격리 수준은 동시에 도는 트랜잭션이 서로의 변경을 얼마나 보는지 정한 규칙이다. 스냅샷 읽기는 트랜잭션이 시작한 시점의 데이터를 잠금 없이 읽는 방식이라, 다른 트랜잭션이 같은 행을 읽는 것을 막지 않는다] 그래서 두 트랜잭션이 같은 버전을 읽는 것 자체를 막지 못한다.

## 메운 방법: 비교 전에 글 행을 잠근다

서비스는 버전을 비교하기 전에 글 행을 `PESSIMISTIC_WRITE`(`SELECT ... FOR UPDATE`)로 잠근다. 뒤에 온 요청은 앞 트랜잭션이 커밋할 때까지 기다린 뒤 최신 버전을 읽고, 비교에 실패해 409를 받는다.[* `SELECT ... FOR UPDATE`는 읽은 행에 쓰기 잠금을 걸어, 트랜잭션이 끝날 때까지 다른 트랜잭션이 그 행을 잠그거나 바꾸지 못하게 한다. 글 서비스(`PostService.java`), 잠금 조회(`PostRepository.java`)]

![트랜잭션 사이의 충돌. 버전만 비교하면 두 요청이 모두 버전 3을 읽고 통과해 A의 변경이 덮인다. 글 행을 먼저 잠그면 B는 A가 커밋할 때까지 기다린 뒤 버전 4를 읽고 409를 받는다|dark=241|w=100|a=center](attachment:242)

같은 구간을 막는 방법은 이것 말고도 있었다.

| 방법 | 동작 | 판단 |
|---|---|---|
| 잠근 뒤 비교(쓰는 쪽) | 글 행을 `FOR UPDATE`로 잠그고 읽은 다음 버전을 비교한다 | 엔티티를 읽어 도메인 메서드로 바꾸는 JPA 방식에 맞는다. 같은 글에 대한 저장이 잠금을 기다린다 |
| 조건부 갱신 한 문장 | `UPDATE ... SET edit_version = edit_version + 1 WHERE id = ? AND edit_version = ?`로 비교와 쓰기를 묶는다 | 같은 구간을 막을 수 있지만, 여러 필드와 관계를 엔티티로 바꾸는 흐름과는 맞지 않는다 |
| JPA `@Version` | 엔티티를 저장할 때 `UPDATE ... WHERE version = ?`로 검사한다 | 일괄 `UPDATE` 쿼리는 버전을 자동으로 올리지 않아, 엔티티를 거치지 않는 변경이 편집 화면을 무효로 만들지 못한다 |

## 저장 한 번의 순서

저장 요청 하나는 아래 순서로 잠근다. 모든 경로가 같은 순서로 잠가야 서로를 기다리며 멈추는 교착 상태가 생기지 않는다.[* 교착 상태(deadlock)는 두 트랜잭션이 서로 상대가 쥔 잠금을 기다려 둘 다 진행하지 못하는 상태다. InnoDB는 이를 감지해 한쪽을 롤백한다]

![저장 한 번의 잠금 순서. 분류를 공유 잠금으로 확인하고, 시리즈를 ID 오름차순으로 잠근 뒤, 글 행을 잠그고 버전을 비교한다. 분류 삭제의 일괄 이동도 분류 → 글 순서로 잠근다|dark=237|w=100|a=center](attachment:238)

1. 분류를 지정했으면 분류 행을 공유 잠금으로 읽어 있는지 확인한다.
2. 관련 시리즈 행을 ID 오름차순으로 잠근다. 두 요청이 같은 시리즈 쌍을 반대 순서로 잠가 교착되는 것을 막는다.
3. 글 행을 잠그고 `baseVersion`과 현재 버전을 비교한다. 다르면 409다.
4. 글 정보, 소속, 순서, 태그를 같은 트랜잭션에서 저장하고 버전을 1 올린다.
5. 커밋한다. 중간에 실패하면 전부 롤백한다.

분류를 지울 때 그 분류의 글을 옮기는 일괄 이동도 분류 행을 먼저 잠근 뒤 글 행을 바꾼다. 그래서 두 경로 모두 분류 → 글 순서로 잠근다.

## 버전을 올리는 작업

버전은 JPA `@Version`이 아니라 서비스 코드가 직접 올린다. 그래서 어떤 작업이 버전을 올리는지가 코드에 드러난다.

- **글 정보 저장**은 버전을 비교하고 올린다. 여러 필드를 함께 바꾸므로 앞선 저장을 덮어쓰지 않게 한다.
- **발행과 발행 취소**는 비교하지 않고 버전만 올린다. 누른 대로 적용하되, 열려 있는 편집 화면이 옛 상태를 기준으로 저장하지 못하게 한다.
- **분류 삭제에 따른 일괄 이동**도 비교하지 않고 버전만 올린다. JPQL 일괄 `UPDATE`가 `edit_version + 1`을 함께 실행해, 열려 있는 편집 화면의 다음 저장을 409로 만든다. `@Version`이었다면 이 쿼리는 버전을 올리지 않았을 것이다.

## 받아들인 비용

- 자동 병합은 없다. 409를 받은 화면은 입력을 그대로 두고, 사용자가 글을 다시 열어 최신 값과 비교한 뒤 다시 저장해야 한다. 기준 버전만 바꿔 자동으로 다시 보내지 않는다. 자동 재전송은 앞선 저장을 덮어쓰는 것과 같기 때문이다.
- 같은 글에 대한 저장은 잠금 때문에 하나씩 처리된다. 관리자가 한 명이라 기다림이 문제 되지 않는 규모다. 잠금 대기 시간(InnoDB 기본 50초)을 넘기거나 교착으로 롤백되면 409 "동시 변경이 충돌했습니다."로 답한다.

## 확인

동시성 검사는 영속성 통합 테스트에 있다. 두 스레드를 `CountDownLatch`로 같은 시점에 출발시켜 같은 버전으로 저장하면 하나만 성공하는지 보고, 태그만 바꿔도 버전이 올라 낡은 화면의 저장이 거부되는지, 분류 삭제로 글이 옮겨진 뒤 이전 버전의 저장이 거부되는지도 본다. 시리즈 쌍을 반대 순서로 지정한 두 요청이 교착하지 않는지도 확인한다.

## 남은 위험

- 버전을 올려야 하는 새 작업을 더할 때 개발자가 직접 챙겨야 한다. 빠뜨리면 그 작업 뒤의 낡은 편집이 409 없이 저장된다.
- 분류 삭제와 글 편집이 겹칠 때의 교착 검사는 없다. 두 경로가 같은 순서로 잠근다는 것은 코드의 순서로 확인한 것이다.
