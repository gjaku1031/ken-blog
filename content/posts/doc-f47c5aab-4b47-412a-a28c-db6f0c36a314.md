권한 판단을 한 엔진에 모았기 때문에(P1) 업무 모듈은 역할을 몰라도 되고(P2), 모듈이 프로세스 밖과 만나는 두 포트에서는 DB 트랜잭션 밖에서 호출한 뒤 결과를 따로 확정함(P3).

| 결정 | 해결한 문제 | 대가 |
| --- | --- | --- |
| 역할의 권한과 리소스의 허용을 함께 요구하는 권한 엔진 | P1 | 요청마다 원장을 읽음. 명시적 거부와 상속 차단이 없음 |
| 정책 변경을 학원별 잠금과 정책 버전으로 직렬화 | P1 | 같은 학원의 정책 변경은 동시에 하나만 진행됨 |
| 업무 모듈이 권한 엔진에 의존하지 않음. 포트는 바깥 경계에만 | P2 | 권한 검사가 두 층으로 나뉨. 모듈 내부는 JPA·jOOQ에 묶임 |
| 외부 호출을 기록·호출·확정으로 나누고, 끊긴 작업은 멱등한 재실행이나 대조로 마무리 | P3 | 마무리 전까지 대상이 잠김. 마무리는 사람이 실행함 |

## P1. 권한 판단을 한 엔진으로

### 문제

시범 운영에서는 역할을 팀장·강사·다른 팀 세 가지로 코드에 고정했음. 이 방식에서는 기능마다 역할을 보는 조건문이 생기고, 여기에 자료실이 더해지면 "강사는 교재 폴더에만 올릴 수 있다" 같은 규칙이 기능과 폴더의 조합만큼 늘어남. 역할 이름을 바꾸거나 역할을 하나 더 만들 때마다 배포가 필요하고, 검사가 빠진 기능을 찾으려면 모든 기능을 읽어야 함.

### 세 가지 방식을 어떻게 나눠 썼는가

RBAC, ABAC, ACL은 서로 다른 질문에 답함. 하나만으로는 요구를 다 표현하지 못해서 질문마다 맞는 방식을 배치했음.

| 방식 | 답하는 질문 | 이 방식만 썼을 때 표현하지 못하는 것 | 이 프로젝트에서 맡은 일 |
| --- | --- | --- | --- |
| RBAC | 어떤 기능을 쓸 수 있는가 | "교재 폴더에만"처럼 대상에 따라 달라지는 허용. 폴더마다 역할을 새로 만들어야 함 | 소속에 배정된 역할의 권한 키로 기능의 자격을 판단 |
| ACL | 이 리소스에서 무엇이 허용되는가 | 폴더가 없는 기능(업무 배정, 역할 관리). 사람마다 허용을 따로 줘야 해서 역할이 바뀔 때 일괄로 바꿀 수 없음 | 폴더마다 계정이나 역할에 목록·읽기·쓰기·권한 관리를 허용. 하위로 내려가게 할지 고름 |
| ABAC | 지금 이 조건이 맞는가 | 관리자가 읽고 고칠 수 있는 목록. 조건식이 늘면 왜 허용됐는지 추적하기 어려움 | 소속이 활성인지, 대상이 그 학원의 것인지, 역할이 활성인지 같은 고정된 조건만 코드로 확인. 관리자가 쓰는 조건식은 두지 않음 |

리소스에 대한 요청은 역할의 권한과 리소스의 허용이 **둘 다** 있어야 통과함. 개인에게 폴더 읽기 허용을 줘도 역할에 읽기 권한이 없으면 열리지 않고, 읽기 권한이 있는 역할도 허용이 걸리지 않은 폴더는 열지 못함. 학원 전체를 대상으로 하는 기능(업무 배정, 역할 관리)은 허용 목록 없이 권한만 봄.

허용은 폴더에 직접 걸린 것을 먼저 보고, 없으면 하위로 내려가게 한 허용 가운데 가장 가까운 조상의 것을 봄.

"담당 반의 학생", "본인에게 배정된 업무"처럼 사용자와 대상 사이의 관계로 정해지는 조건(ReBAC)은 엔진에 넣지 않았음. 그 관계의 원장을 가진 업무 모듈이 직접 확인함. 이유는 P2에서 다룸.

### 검토한 대안

| 대안 | 내용 | 판단 |
| --- | --- | --- |
| 고정 역할과 고정 권한 표 | 역할과 권한 조합을 코드와 초기 데이터로 고정 | 학원마다 다른 업무 분담을 표현하기 어렵고, 역할을 보는 조건문이 코드에 퍼짐 |
| 전역 역할 템플릿 | 공통 템플릿을 두고 학원이 일부만 바꿈 | 템플릿을 고쳤을 때 이미 바꾼 학원에 어떻게 반영할지 정해야 함. 규모에 비해 모델이 복잡해짐 |
| **권한 키는 코드가, 역할과 허용은 학원이 구성** | 코드는 권한 키의 뜻과 판단 순서만 가짐. 역할, 역할의 권한, 배정, 폴더의 허용은 학원의 데이터 | 채택 |
| 외부 정책 엔진, 범용 조건식 | OPA·Cedar·OpenFGA 같은 엔진이나 관리자가 쓰는 조건식 | 지금 요구를 넘는 표현력이고 운영할 구성 요소가 늘어남. 실제 요구가 생기면 다시 검토하기로 하고 보류 |
| 명시적 거부, 상속 차단, 파일별 허용 | 허용 목록에 거부 행을 두거나 하위에서 상속을 끊음 | 허용과 거부가 섞이면 우선순위 규칙이 필요해짐. 폴더 단위 허용과 "허용이 없으면 거부"로 충분하다고 보고 보류 |

플랫폼 전체를 관리하는 슈퍼유저를 어떻게 둘지도 따로 비교했음.

| 대안 | 판단 |
| --- | --- |
| 예약된 역할로 둠 | 슈퍼유저는 권한을 평가하지 않으므로 역할이 실제 의미를 설명하지 못하고, 학원 권한 코드에 예외가 남음 |
| 계정에 불리언 열을 둠 | 계정 모듈이 권한 정책을 가지게 됨. 부여와 회수의 이력을 표현하기 어려움 |
| **권한 모듈 안의 별도 등록부** | 학원의 역할 모델과 섞이지 않고, 두 정책은 판단을 조립하는 한 곳에서만 만남. 채택 |

슈퍼유저도 권한 키와 대상의 짝이 맞는지는 먼저 검사받고, 통과한 요청은 매번 감사 기록에 남음.

### 정책 변경의 동시성

두 관리자가 같은 역할의 권한 목록을 동시에 고치면 늦게 저장한 쪽이 앞의 변경을 덮어씀(갱신 손실). 또 두 관리자가 서로 다른 경로로 마지막 관리 권한을 동시에 빼면, 각자의 변경은 관리자가 남는 것으로 보이지만 합쳐지면 아무도 권한을 고칠 수 없게 됨.

- **결정**: 정책을 바꾸는 모든 요청을 학원 단위로 직렬화함
  - 학원별 트랜잭션 advisory lock을 먼저 잡음. 정책 행이 아직 없는 초기화 경쟁도 같은 잠금으로 막음
  - 정책 행을 `FOR UPDATE`로 잠그고, 요청이 들고 온 정책 버전을 현재 값과 비교함. 다르면 거부함
  - 변경을 적용한 뒤 "권한 관리 권한과 루트 폴더의 권한 관리 허용을 함께 가진 활성 경로"가 하나 이상 남는지 확인함. 없으면 전체를 취소함
  - 실제로 바뀐 것이 있을 때만 버전을 올리고, 변경 전후 상태를 같은 트랜잭션에서 감사 기록에 씀
- **대가**: 같은 학원의 정책 변경은 한 번에 하나만 진행됨. 버전이 어긋난 쪽은 화면을 다시 읽고 변경을 다시 해야 함
- **보장하지 않는 것**: 마지막 관리자 보호는 권한 원장만 봄. 계정 정지는 계정 모듈의 일이라, 유일한 관리자의 계정이 정지되면 막지 못함

### 권한 관리 권한의 범위

역할을 고치는 권한, 역할을 배정하는 권한, 소속을 관리하는 권한은 서로를 막지 않음. 역할을 고칠 수 있는 사람은 자기 역할에 다른 권한을 넣을 수 있음. 셋 가운데 하나를 가진 사람은 그 학원 안에서는 관리자와 같다고 보고 부여해야 함. 이 권한들이 닿지 않게 막은 것은 학원 밖임: 플랫폼 슈퍼유저 자격은 화면으로 줄 수 없고, 비밀번호는 이 학원에만 활성 소속이 있는 계정의 것만 바꿀 수 있음.

### 옮기기와 허용 범위

옮긴 폴더는 옮겨 간 곳의 허용을 물려받음. 쓰기만 허용된 사람이 자기 폴더를 읽을 수 있는 폴더 아래로 옮기면 읽기가 생기므로, 옮기려면 원본과 그 아래 전부를 이미 읽을 수 있어야 하게 했음. 옮긴 뒤 다른 사람에게 보이는 범위가 달라지는 것은 막지 않음.

### 검증

- 판단 규칙(소속, 학원 일치, 권한, 직접·상속 허용, 가장 가까운 허용 선택)은 DB를 읽지 않는 순수 함수로 분리해 단위 테스트로 확인함[* [AuthorizationPolicyEngineTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/accesscontrol/internal/authorization/AuthorizationPolicyEngineTest.java)]
- 버전이 어긋난 변경의 거부, 마지막 관리자가 사라지는 변경의 취소, 두 요청을 스레드로 겹쳐 실행했을 때 하나만 통과하는 것을 실제 PostgreSQL에서 확인함[* [AccessControlLockoutIntegrationTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/integration/accesscontrol/AccessControlLockoutIntegrationTest.java), [AuthorizationBehaviorIntegrationTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/integration/accesscontrol/AuthorizationBehaviorIntegrationTest.java), [ResourceAclIntegrationTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/integration/accesscontrol/ResourceAclIntegrationTest.java). 임베디드 PostgreSQL 18]
- 화면 요청에서 같은 주소가 역할에 따라 열리거나 거부되는 것, 폴더 목록이 허용으로 걸러지는 것, 올리기 권한이 있어도 쓰기 허용이 없는 폴더에는 올릴 수 없는 것을 요청 단위 테스트로 확인함[* [WebAccessIntegrationTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/integration/web/WebAccessIntegrationTest.java)]
- 코드의 권한 키 목록과 DB의 `permission` 행이 같은지 테스트가 확인함

## P2. 업무 모듈을 권한에서 떼어 내고, 포트는 바깥에만

### 문제

업무일지에는 "업무를 받는 사람 전원에게 배정", "일일보고를 쓰는 사람 가운데 몇 명이 제출했나"처럼 역할에 기대는 규칙이 많음. 업무일지가 권한 엔진을 직접 부르면 두 모듈이 서로의 타입을 알게 되고, 역할 없이 업무 규칙만 따로 시험하기 어려워짐. 반대로 모든 계층에 인터페이스를 끼우면 구현이 하나뿐인 곳까지 간접 호출이 늘어남.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 업무일지가 권한 엔진을 직접 호출 | 모듈이 서로를 알게 됨. 업무 규칙의 테스트가 권한 원장을 준비해야 함 |
| 업무와 보고마다 허용 목록을 부여 | 담당자가 바뀔 때마다 허용을 맞춰야 함. 담당 관계는 이미 업무 원장에 있어 같은 사실을 두 곳에 두게 됨 |
| 권한 엔진에 "소유자" 개념 추가 | 소유의 뜻이 자료마다 다름(담당자, 작성자, 담당 반). 공통 규칙으로 묶이지 않음 |
| **호출자가 대상 집합을 넘기고, 소유 조건은 업무일지가 확인** | 채택 |

- **결정**: 컨트롤러가 권한 원장에서 "업무 수행 권한을 가진 계정", "일일보고 작성 권한을 가진 계정"을 구해 업무일지의 메서드에 넘김. 업무일지는 받은 집합으로 담당자와 분모를 계산하고, 대상이 요청한 사람의 것인지는 계정 ID로 직접 확인함
- **대가**: 기능을 쓸 자격은 컨트롤러에서, 대상이 본인의 것인지는 업무일지에서 확인하므로 한쪽이 빠지면 구멍이 됨. 업무일지 쪽은 통합 테스트로, 컨트롤러 쪽은 대표 경로의 요청 단위 테스트로 확인함
- **부수 효과**: 전원 배정 업무의 담당자가 조회 시점의 집합으로 정해지므로, 역할을 바꾸면 담당자가 따라 바뀜. 만들 때의 담당자를 고정해야 하는 특강상담은 담당자를 따로 저장함

포트는 파일 저장소와 외부 ERP 두 곳에만 둠. 둘 다 프로세스 밖에 있고 구현이 바뀔 수 있는 경계임. 외부 ERP의 실제 연동은 그 시스템의 비공개 계약과 계정에 묶여 있어 저장소에 두지 않고, 포트 하나와 가상 데이터를 돌려주는 대역 어댑터만 둠.

### 검증

- 모듈의 의존 방향과 내부 패키지 침범은 구조 테스트가 빌드에서 검사함[* [ModularityTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/architecture/ModularityTest.java). Spring Modulith의 검증을 실행]
- 업무일지의 통합 테스트는 권한 원장 없이 계정 ID의 집합만 넘겨 실행함. 담당자가 아닌 사람의 처리 거부, 다른 담당자의 보고가 응답에서 빠지는 것, 후보 집합이 바뀌면 담당자가 달라지는 것을 확인함[* [WorklogTaskIntegrationTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/integration/worklog/WorklogTaskIntegrationTest.java)]

## P3. 바깥 시스템과의 기록

### 문제

폴더 이동은 DB의 트리와 디스크를 함께 바꾸고, 상담 전송은 DB의 상태와 외부 ERP를 함께 바꿈. DB 트랜잭션 안에서 바깥을 호출하면 호출이 늦을 때 연결과 잠금을 오래 잡고, 그래도 커밋 직전에 끊기면 바깥만 바뀐 채로 남음. 실패한 호출을 그대로 다시 보내면 상담이 두 번 기록됨.

시범 운영에서 고친 문제도 이 경계에 몰려 있었음. 수정 23건 가운데 18건이 외부 ERP에서 가져오거나 보내는 자료(상담, 반 명단, 출결)에 관한 것이었고[* 2026-07-17부터 2026-09-05까지의 수정 기록을 제목으로 분류한 값], 그중 두 가지가 아래 결정의 근거가 됨.

- **보낸 상담을 확인하지 못함**: 전송 뒤에 외부 ERP의 목록에서 같은 내용을 찾아 성공을 확인했는데, 외부 ERP가 긴 본문을 잘라 돌려주는 길이가 예상한 10자가 아니라 9자인 경우가 있어 실제로 보낸 상담이 확인되지 않았음
- **거부된 상담이 전송 중에 갇힘**: 외부 ERP가 저장을 거부해도 뒤의 조회로는 그 사실을 알 수 없어, 상담이 전송 중 상태에 남아 다시 보내지도 고치지도 못했음. 저장 응답에 담긴 거부 사유를 보존하고, 외부 ERP를 직접 확인한 담당자가 "보냄"이나 "안 보냄"으로 종결하는 경로를 두어 풀었음

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| DB 트랜잭션 안에서 바깥을 호출 | 바깥의 지연이 DB 연결과 잠금을 붙잡음. 커밋 실패 시 바깥만 바뀜 |
| 실패하면 자동으로 다시 보냄 | 바깥에서는 성공했는데 응답만 잃은 경우 같은 변경이 두 번 들어감 |
| 분산 트랜잭션, 범용 작업 큐 | 한 사람이 운영하는 구성에 구성 요소를 더해야 함 |
| **기록 → 호출 → 확정. 끊기면 멱등한 재실행 또는 대조** | 채택 |

- **결정**: 바깥에 닿는 작업을 세 단계로 나눔. 먼저 하려는 일을 짧은 트랜잭션으로 커밋하고, 트랜잭션 밖에서 호출한 뒤, 결과를 다시 짧은 트랜잭션으로 커밋함
  - 자료실은 `storage_operation` 원장에 작업을 적고 대상 노드를 변경 중으로 표시함. 저장소 포트의 연산은 작업 ID를 받아 같은 요청을 다시 받아도 결과가 같음
  - 상담은 행의 상태를 `IDLE`에서 `PENDING`으로 바꾸는 것이 기록 단계임. 이 커밋 뒤로는 같은 상담을 다시 보낼 수 없음
  - 바깥이 명확히 거부하면 되돌림. 끊겨서 결과를 모르면 그대로 두고 바깥의 성질에 따라 마무리함
    - 파일 저장소는 멱등함: 재시작할 때 끝나지 않은 작업을 확인 대상으로 표시하고, 운영자가 같은 작업 ID로 다시 실행함. 이미 끝난 변경은 그대로이고 덜 끝난 변경만 마저 됨. 올리던 파일은 본문을 다시 구할 수 없어 실패로 정리함
    - 외부 ERP의 상담 기록은 멱등하지 않음: 다시 보내지 않고, 그날 기록에서 같은 학생·주제·내용을 찾아 있으면 보낸 것으로, 없으면 보내기 전으로 정리함
- **대가**: 마무리되기 전에는 대상이 잠겨 있음. 재실행과 대조 모두 사람이 화면에서 실행함
- **보장하지 않는 것**: 대조는 내용이 같은지로 판정함. 같은 학생·주제·내용의 기록이 이미 있었다면 보내지 않은 상담도 보낸 것으로 판정되고, 외부가 내용을 바꿔 저장하면 보낸 상담을 찾지 못함. 외부 ERP의 대역은 실패하지 않으므로, 지연과 장애에 대한 동작은 포트를 대역으로 바꾼 단위 테스트로만 확인했음

### 검증

- 자료실: 호출 전과 호출 뒤 확정 전에 멈춘 상황을 준비 단계와 확정 단계를 따로 불러 만들고, 재시작 표시와 재실행 뒤 원장과 디스크의 상태를 확인함[* [StorageIntegrationTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/integration/storage/StorageIntegrationTest.java). 테스트용 로컬 디렉터리와 임베디드 PostgreSQL 18]
- 상담: 전송 중으로 표시만 하고 외부에 쓰지 않은 경우는 대조 뒤 보내기 전으로, 외부에 쓴 뒤 확정하지 못한 경우는 보낸 것으로 정리되는지 확인함. 전송 중과 보낸 상담의 재전송이 거부되는지도 확인함[* [WorklogTaskIntegrationTest](https://github.com/gjaku1031/npr-erp/blob/c90b28a/src/test/java/com/npr/erp/integration/worklog/WorklogTaskIntegrationTest.java)]
- 측정하지 않은 것: 동시 사용자가 늘었을 때 요청마다 원장을 읽는 비용, 큰 파일이 애플리케이션을 지날 때의 부하
