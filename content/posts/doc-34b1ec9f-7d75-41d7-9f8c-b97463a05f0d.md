로그인한 직원이 자기 권한 밖의 기능과 남의 자료에 닿지 못하게 하는 것이 이 시스템 보안의 중심이고, 그 판단은 서버의 권한 엔진과 업무 모듈이 함.

## 위협 모델

사내 직원만 쓰는 시스템이라 로그인한 내부 사용자를 가장 현실적인 위협으로 봄. 지키려는 자산과 상정한 행위자는 아래와 같음.

| 자산 | 상정한 위협 |
| --- | --- |
| 학생 이름과 보호자 연락처(외부 ERP에서 읽어 옴) | 담당하지 않는 반의 명단과 출결을 조회 |
| 다른 직원의 업무 보고, 첨부, 상담 내용 | 주소의 ID를 바꿔 남의 것을 읽거나 고침 |
| 자료실의 파일 | 허용되지 않은 폴더의 파일을 주소로 직접 내려받음 |
| 권한 정책 | 학원 관리자가 자기 권한을 넘어 플랫폼 전체의 권한을 얻음. 실수로 관리자가 모두 사라짐 |
| 로그인 세션 | 다른 사이트가 로그인한 사용자의 브라우저로 변경 요청을 보냄 |

## 위협별 대응

| 위협 | 대응 | 남은 위험 |
| --- | --- | --- |
| 권한 없는 기능 호출 | 컨트롤러가 업무 모듈을 부르기 전에 권한 엔진에 물음. 메뉴와 버튼을 숨기는 것과 별개로 요청마다 검사함 | 새 컨트롤러 메서드에서 검사를 빠뜨리면 막을 장치가 테스트뿐임 |
| 주소의 ID를 바꿔 남의 자료에 접근 | 모든 조회가 학원 ID를 조건에 포함함. 업무·상담·첨부·일정·개인 상담일정은 업무일지가 계정 ID로 소유를 확인함 | 소유 조건은 메서드마다 따로 구현돼 있음 |
| 다른 학원의 자료를 자기 학원 주소에 끼워 넣기 | 대상과 조상을 서버가 원장에서 읽어 권한 엔진에 넘김. 클라이언트가 보낸 경로나 조상을 쓰지 않음 | — |
| 허용되지 않은 폴더의 파일 | 폴더 목록은 허용된 항목만 남기고, 내려받기는 그 파일에 대한 읽기 권한과 허용을 다시 확인함 | 이미 내려받은 파일은 회수할 수 없음 |
| 담당하지 않는 반의 학생 정보 | 알림장·출결·명단은 가져온 본인 담당 반 안에서만 열림 | 담당 반 목록은 마지막으로 가져온 시점의 것임 |
| 학원 관리자의 권한 상승 | 플랫폼 슈퍼유저는 학원의 역할과 분리된 등록부에 있고 화면으로는 부여할 수 없음 | 역할·배정·소속을 관리하는 권한 가운데 하나를 가진 사람은 자기 학원 안에서 모든 권한을 스스로 가질 수 있음 |
| 비밀번호 변경으로 다른 학원의 계정 가로채기 | 계정은 플랫폼 전체에서 하나임. 학원 관리자는 이 학원에만 활성 소속이 있는 계정의 비밀번호만 바꿀 수 있고, 종료된 소속·다른 학원에도 소속된 계정·슈퍼유저는 바꿀 수 없음 | 비밀번호를 바꿔도 이미 열린 세션은 회수되지 않음 |
| 옮기기로 읽기 권한 얻기 | 옮긴 항목은 옮겨 간 폴더의 허용을 물려받으므로, 옮기려면 원본과 그 아래 전부를 이미 읽을 수 있어야 함 | 읽을 수 있는 자료를 공유 폴더로 옮겨 다른 사람에게 보이게 하는 것은 막지 않음 |
| 관리자가 모두 사라짐 | 정책 변경 뒤 권한을 관리할 경로가 남는지 확인하고 없으면 취소함 | 유일한 관리자의 계정 정지는 막지 못함 |
| 사이트 간 요청 위조 | 모든 변경 요청에 CSRF 토큰을 요구함. 세션 쿠키는 HttpOnly, SameSite=Lax | — |
| 저장된 글에 든 스크립트 | 사용자가 넣은 글은 이스케이프해서 출력함. 마크다운은 전체를 이스케이프한 뒤 굵게·목록·링크만 태그로 바꾸고 링크는 http와 https만 받음 | — |
| 올린 파일이 브라우저에서 실행됨 | 올린 파일은 항상 내려받기로 응답하고 내용 유형 추측을 끔 | — |
| 저장 경로 벗어나기 | 디스크 경로는 서버가 내부 ID로 만들고, 학원 디렉터리 밖으로 나가는 경로를 거부함 | — |

> 화면에서 버튼을 감추는 것과 서버가 요청을 거부하는 것을 따로 구현했고, 테스트는 버튼이 없는 요청을 직접 보내 거부되는지를 확인함.

## 인증과 세션

아이디와 비밀번호로 로그인하고 서버 세션을 씀. 토큰을 브라우저에 맡기지 않음.

- 비밀번호는 BCrypt 해시로만 저장하고 원문을 로그나 세션에 두지 않음
- 로그인에 성공하면 세션 ID를 교체하고, 원래 요청하던 임의의 주소로 돌려보내지 않고 첫 화면으로 보냄
- 세션에는 계정 ID만 의미가 있음. 역할과 권한을 세션에 넣지 않고 요청마다 원장에서 읽으므로, 역할 회수와 소속 종료가 다음 요청부터 반영됨
- 학원 경로의 요청마다 계정이 활성인지와 그 학원에 소속돼 있는지를 다시 확인함

<details><summary>세션 쿠키와 비밀번호 규칙</summary>

| 항목 | 값 |
| --- | --- |
| 세션 쿠키 | HttpOnly, SameSite=Lax, HTTPS에서는 Secure, 비활동 만료 8시간 |
| 세션 저장 | 프로세스 메모리. 재시작하면 다시 로그인함 |
| 비밀번호 | 8자 이상, UTF-8 72바이트 이하 |
| 가입, 비밀번호 찾기 | 없음. 계정은 학원 관리자의 직원 등록이나 서버의 운영 명령으로만 만듦 |

</details>

## 권한 경계

권한 판단의 규칙은 주요 기술적 의사결정 문서의 P1에, 요청별 연결은 아키텍처 문서에 있음. 보안 관점에서 눈여겨볼 성질만 적음.

- **기본은 거부**: 권한 키가 목록에 없거나, 권한과 대상의 짝이 맞지 않거나, 일치하는 허용이 없으면 거부함. 슈퍼유저도 앞의 두 검사는 통과해야 함
- **권한 관리도 같은 엔진을 통과함**: 역할을 고치는 요청, 폴더의 허용을 바꾸는 요청도 각자의 권한을 요구함. 역할 이름을 보고 관리자를 판정하지 않음
- **거부는 기록됨**: 거부된 요청과 슈퍼유저의 우회는 업무 트랜잭션이 취소돼도 남도록 별도 트랜잭션으로 감사 기록에 씀. 정책 변경은 변경 전후 상태와 정책 버전을 함께 적음
- **화면에는 거부 사유를 보여 주지 않음**: 사유 코드는 감사 기록에서만 확인함

## 검증

| 확인한 것 | 방법 |
| --- | --- |
| 로그인하지 않은 요청이 로그인 화면으로 가는지 | 요청 단위 테스트 |
| 소속이 없는 학원의 주소가 열리지 않는지 | 요청 단위 테스트 |
| 같은 주소가 역할에 따라 열리거나 403이 되는지 | 시연 구성의 세 역할로 같은 주소를 요청 |
| 허용되지 않은 폴더가 목록에서 빠지고 주소로도 열리지 않는지 | 요청 단위 테스트 |
| 올리기 권한이 있어도 쓰기 허용이 없는 폴더에는 올릴 수 없는지 | 요청 단위 테스트 |
| 쓰기만 허용된 사람이 읽을 수 없는 파일을 옮길 수 없는지 | 요청 단위 테스트 |
| 종료된 소속의 계정 비밀번호를 바꿀 수 없는지, 파일에 허용 목록을 걸 수 없는지 | 요청 단위 테스트 |
| CSRF 토큰이 없는 변경 요청이 거부되는지 | 요청 단위 테스트 |
| 담당자가 아닌 사람의 업무 처리, 남의 상담·첨부·개인일정 접근이 거부되는지 | 업무일지 통합 테스트 |
| 정책 버전 불일치와 마지막 관리자 제거가 거부되는지 | 권한 통합 테스트(스레드를 겹친 실행 포함) |

| 확인하지 않은 것 | 상태 |
| --- | --- |
| 로그인 시도 제한, MFA | 구현하지 않음 |
| 모든 컨트롤러 메서드에 권한 검사가 있는지의 자동 점검 | 없음. 대표 경로만 테스트함 |
| 마크다운 변환기와 돌아갈 주소 계산의 단위 테스트 | 없음 |
| 외부에 공개된 환경에서의 점검(HTTPS, 헤더, 접근망) | 배포 환경을 정하지 않아 하지 않음 |
