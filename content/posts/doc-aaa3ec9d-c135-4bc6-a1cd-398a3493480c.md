공개 사이트·API·DB를 서로 다른 경로로 배포하고 운영하는 방식. 배포 경계를 나눠 독자의 열람이 API 배포와 무관하게 유지되고(P2), 공개 사이트에는 검증을 통과한 산출물만 올라감(P3). 배포 경계와 구성 요소는 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)에서 정의함.

| 변경 | 반영 경로 | 완료 확인 | 관련 문제 |
| --- | --- | --- | --- |
| Markdown 원고 | `main` push → Pages 자동 빌드·배포 | 공개 주소의 새 HTML | P1 |

| 템플릿·CSS·TypeScript | Frontend 검사, Pages 자동 빌드·배포 | 새 정적 자산 | — |
| API 소스·런타임 설정 | API CI → JVM 이미지 artifact → 운영자 수동 교체 | health·공개 스냅샷·로그 확인 | — |

## Pages 배포

빌드는 공개 스냅샷과 Git 원고를 수집하고 revision을 두 번 비교한 뒤, 검증을 통과한 결과만 배포함. 단계와 보장 범위는 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)의 일관성 모델 절에서 다룸. 운영에서 지키는 규칙은 세 가지.

- **직렬 실행**: 워크플로가 `github-pages` 동시성 그룹 하나로 묶여 배포가 겹치지 않고, 진행 중인 배포를 새 실행이 취소하지 않음.
- **실패 시 유지**: 수집·생성·검증 중 하나라도 실패하면 배포하지 않아 공개 중인 사이트가 그대로 남음. 성공한 빌드는 이전 출력의 옛 파일을 복사하지 않아, 발행 취소한 글은 다음 성공 배포에서 사라짐.
- **번들 재사용**: 브라우저 JS·CSS 번들은 입력 해시와 산출물 검사를 통과하면 재사용하고, 페이지는 매번 전체를 다시 생성함.

## API 배포와 롤백

API CI는 Gradle·MySQL 통합 검사를 통과한 커밋으로 ARM64 JVM 이미지를 만들고, 실제 HTTP 동작을 검사한 뒤 이미지 아카이브와 SHA-256을 90일 보관함. 운영 서버 교체는 CI가 하지 않고 운영자가 수동으로 반영함.

수동 반영은 설계로 고른 방식이 아니라 자동화하지 못한 부분임. 배포마다 수동 절차를 밟아야 해 절차 실수가 생길 수 있고, 아래 중단 사례도 이 수동 단계에서 일어남. 검증된 이미지를 운영 서버에 자동으로 반영하는 단계를 추가하는 것이 남은 과제.

```mermaid caption="주황은 운영자 행동, 회색은 시스템 처리. 둥근 노드는 시작·끝, 마름모는 판단. 모든 Compose 명령에 운영 설정과 DB TLS 설정 두 파일을 함께 지정함"
flowchart TD
    start(["CI 이미지 artifact 선택"]) --> record["현재 이미지 태그·ID와 스냅샷 revision 기록"]
    record --> verify{"아카이브 SHA-256과 이미지 ID 일치"}
    verify -->|불일치| stop(["배포 중단"])
    verify -->|일치| tag["환경 파일의 이미지 태그만 변경"]
    tag --> recreate["두 Compose 파일로 API만 재생성"]
    recreate --> check{"health UP, revision 유지, CSRF·아이콘 200, ERROR 없음"}

    check -->|하나라도 실패| rollback["기록한 이전 태그로 되돌려 재생성"]
    rollback --> health["health 확인"]

    classDef admin fill:#fff7ed,stroke:#ea580c,color:#7c2d12,stroke-width:2px

```

배포 전후로 공개 스냅샷의 revision이 같아야 API 교체가 공개 데이터 계약을 바꾸지 않았다고 판단함. 이미지 태그는 바뀔 수 있으므로 재현의 기준은 이미지 ID와 아카이브 해시로 둠. [API 교체 절차](https://github.com/gjaku1031/ken-blog/blob/3074d80/deploy/API-RELEASE.md) · [API CI](https://github.com/gjaku1031/ken-blog/blob/3074d80/.github/workflows/ci.yml)

## 운영 사례: truststore 누락으로 인한 API 중단

2026-10-07 API 이미지를 교체하고 되돌리는 과정에서 API가 약 6분간 중단됨. 이미지 교체 명령에 Compose 파일을 하나만 지정해, DB TLS 연결에 필요한 truststore 마운트가 빠졌음. API는 JPA 초기화 단계에서 DB 연결에 실패해 재시작을 반복했음. 공개 사이트는 Pages에서 제공되므로 열람에는 영향이 없었고, 관리 기능과 새 빌드만 멈췄음.

배포 실행은 에이전트가 했고, 재발 방지 기준은 본인이 정함.

- 절차서에 운영 설정과 DB TLS 설정 두 파일을 함께 지정하는 명령을 고정함.
- 재생성 후 실행 중인 컨테이너의 `com.docker.compose.project.config_files` 라벨로 두 파일이 모두 적용됐는지 확인하는 단계를 추가함.

> 배포 경계를 나눈 덕분에 API가 멈춘 동안에도 독자는 영향을 받지 않았지만, 수동 절차의 누락 하나가 관리 기능 전체를 멈췄음. 그래서 명령을 절차서에 고정하고 적용 결과를 확인하는 단계를 둠.

## 스키마 변경을 동반한 전환

API와 DB 스키마가 함께 바뀔 때는 확장-축소(expand/contract) 순서를 따름. 새 열·테이블을 먼저 추가하고 새 API를 배포한 뒤, 옛 구조는 더 이상 쓰이지 않음을 확인하고 나중에 지움. 교체 도중 옛 API와 새 API가 같은 DB에서 잠시 함께 동작해도 깨지지 않게 하고, 문제가 생기면 API 이미지만 되돌릴 수 있게 하기 위함.

1. 복사 DB에서 이관 SQL과 새 API 기동, 자료 보존을 확인함.
2. 관리자 쓰기를 멈추고 백업과 복원 가능성을 확인함.
3. 검토한 SQL을 적용하고 검증된 API 이미지를 반영함.
4. Pages를 배포하고 관리 화면을 새로 고침.
5. 인증·글 조회·편집 충돌·발행·이미지·공개 스냅샷을 확인한 뒤 작업을 재개함.

2026-10-07의 위키 선언 기능 삭제가 축소 단계의 사례. 먼저 이 테이블을 쓰지 않는 API를 배포하고, Caddy 허용 메서드에서 쓰지 않게 된 PATCH를 제거함. 이어서 테이블의 데이터가 빌드에 쓰이지 않음을 확인한 뒤, 운영 테이블 `post_wiki_links`와 현재 코드가 쓰지 않는 이관 전 테이블·열을 [정리 SQL](https://github.com/gjaku1031/ken-blog/blob/main/deploy/sql/drop-legacy-tables-2026-10-07.sql)로 삭제함. 백업 없이 삭제하기로 한 것은 본인 결정. Caddy 설정처럼 운영 파일을 바꾸기 전에는 서버의 백업 디렉터리에 이전 파일을 복사해 둠. [전환 절차](https://github.com/gjaku1031/ken-blog/blob/3074d80/deploy/REVIEW-ROLLOUT.md)

## CI 결과의 의미

| 검사 | 확인하는 범위 | 운영에서 추가로 확인할 것 |
| --- | --- | --- |
| API verify | 빌드, 격리 DB 통합 검사, 인증·배포 계약 | 실제 운영 DB·TLS·네트워크 |
| JVM 이미지 | ARM64 컨테이너 기동과 HTTP 동작 | 운영 반영 후 공개 진입점 |
| Frontend | 타입 검사, Node 검사, 모의 API 브라우저 검사 | 운영 계정과 실제 API 연동 |
| Pages build | 공개 자료 수집과 정적 생성 | 실제 호스팅 반영 |
| Pages deploy | 해당 artifact 발행 | 공개 화면의 본문·이미지·탐색 |

Frontend 검사는 Pages 배포의 선행 조건이 아니므로, Pages 성공이 브라우저 검사 통과를 뜻하지 않음.

## 점검과 백업

운영 점검은 `/actuator/health`, 공개 스냅샷의 `version`·`revision`, 기동 이후 로그의 ERROR 여부로 함. 구성 요소별 장애 영향은 [아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/)의 장애 영향 절에서 다룸.

| 자료 | 백업 |
| --- | --- |
| Git 원고·웹 소스 | Git 저장소의 커밋 이력 |
| MySQL | OCI 관리형 DB 기본 설정의 자동 백업, 보존 기간 1일. 시점 복구(PITR)는 꺼져 있음[* 2026-10-07 OCI CLI로 DB System 설정 확인] |
| 운영 설정 파일 | 변경 전 서버의 백업 디렉터리에 수동 복사 |
| 이미지 디스크·서버 | 백업 방식 미확인 |

## 한계

- 백업 정책을 따로 정하지 않았음. 이미지 디스크와 서버의 백업 방식은 확인하지 못했고, 실제 복구 소요 시간과 허용 데이터 손실 범위도 정하지 않음.
- DB 자동 백업의 보존 기간이 1일이라 하루가 지난 시점으로는 되돌릴 수 없음.
- 원고(Git)·글 정보(DB)·이미지(디스크)를 같은 시점으로 함께 복구하는 절차는 없음.
- API 교체가 아직 자동화되지 않아, 절차를 고정해도 사람이나 에이전트의 실행 실수 가능성이 남음.
