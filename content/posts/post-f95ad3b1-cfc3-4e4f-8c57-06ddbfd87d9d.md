기술 목록을 정리하고 실제 HTTP 요청으로 응답을 확인하다가 기술 아이콘과 본문 첨부 이미지가 가끔 중간에 끊기거나 헤더가 깨진 채로 오는 것을 보게 됐다. 따라가 보니 이미지 본문을 별도 스레드에서 보내는 방식과, 응답이 나가기 직전에 보안 헤더를 쓰는 Spring Security 필터가 같은 응답을 서로 다른 스레드에서 건드릴 수 있는 구조였다. 그래서 이미지를 보내는 세 곳 모두 요청 스레드 안에서 헤더를 다 쓴 뒤 본문을 보내도록 바꿨다.

## 처음 본 것: 대부분 성공하고 가끔 끊겼다

같은 요청을 되풀이하면 대부분은 정상이었고, 가끔 연결이 끊기거나 헤더가 깨져 왔다. 경로나 파일이 잘못됐다면 매번 실패했을 테니, 그런 문제는 아니었다.

직전에 바꾼 기능 탓인지 보려고 변경 전에 빌드한 JAR로도 돌려 봤다. 거기서도 아이콘 요청 150번 중 1번이 끊겼다.[* 1/150은 당시 반복 검사에서 본 값이고, 운영에서의 실패율을 추정한 값은 아니다] 직전 변경이 만든 문제가 아니라 그 전부터 있던 문제였다.

## 더 찾아본 것: 헤더를 쓰다가 난 오류였다

로그에는 Tomcat의 `MimeHeaders` 예외가 남아 있었다.[* `MimeHeaders`는 Tomcat이 응답 헤더 목록을 담아 두는 내부 객체다] 본문이 아니라 헤더를 쓰는 시점에 난 오류였다. API를 직접 불렀을 때와 Caddy를 거쳤을 때 모두 재현됐으므로, 프록시가 아니라 API 안쪽의 문제였다.[* Caddy는 이 블로그에서 API 앞에 둔 리버스 프록시다]

## 원인: 두 스레드가 같은 헤더 목록을 건드렸다

당시 이미지 응답은 `StreamingResponseBody`로 본문을 보냈다.[* `StreamingResponseBody`는 Spring MVC에서 응답 본문을 비동기로 흘려보내는 반환 타입이다. 컨트롤러 메서드가 끝난 뒤 다른 스레드가 본문을 쓴다] 같은 응답에서 Spring Security의 `HeaderWriterFilter`는 응답이 커밋되기 직전에 보안 헤더를 쓴다.[* 커밋은 상태 줄과 헤더가 클라이언트로 나가기 시작한 상태다. 그 뒤로는 헤더를 바꿀 수 없다. 보안 헤더는 `X-Content-Type-Options: nosniff`, `X-Frame-Options`처럼 브라우저의 동작을 제한하는 헤더다] 본문 쓰기와 헤더 쓰기가 서로 다른 스레드에서 같은 응답 객체의 헤더를 건드릴 수 있었고, `MimeHeaders` 예외는 헤더 목록이 동시에 바뀔 때 나는 오류와 맞았다.

![비동기 전송일 때의 구조. 컨트롤러는 본문 쓰기를 별도 스레드에 넘기고 끝나고, 보안 헤더 작성과 응답 커밋이 서로 다른 스레드에서 같은 헤더 목록을 건드릴 수 있다. 어느 쪽이 먼저인지는 정해져 있지 않다|dark=215|w=100|a=center](attachment:216)

비동기 본문 쓰기와 `HeaderWriterFilter`가 부딪히는 비슷한 구조는 다른 서버와 응답 방식(Jetty, SSE)에서 Spring Security 이슈로 보고된 적이 있다.[* [Spring Security 이슈 #9175](https://github.com/spring-projects/spring-security/issues/9175)]

다만 스레드 순서를 고정해 경합을 매번 재현하는 최소 프로그램은 만들지 않았다. 그래서 이 판단은 이 서비스에서 본 현상의 설명이고, 비동기 스트리밍 전체의 결함이라고 넓혀 말하지 않는다.

## 고친 방법

이미지 응답에서 `StreamingResponseBody`를 없애고, 같은 요청 스레드에서 헤더를 모두 정한 뒤 본문을 보냈다. 기술 아이콘, 관리자 첨부, 공개 첨부의 세 응답을 모두 같은 방식으로 바꿨다.[* 관리자 첨부 API는 이후 업로드 기능과 함께 없앴다] 아래는 공개 첨부 컨트롤러를 줄인 것이다(보안 헤더 두 줄은 뺐다).

```java
var content = service.open(postId, id);      // 발행·연결·경로 검사 후 파일 열기
try (var stream = content.stream()) {
    response.setContentType(content.contentType());
    response.setContentLengthLong(content.byteSize());
    response.setHeader(HttpHeaders.CACHE_CONTROL, "private, no-store");
    stream.transferTo(response.getOutputStream());
}
```

![고친 뒤의 순서. 한 요청 스레드에서 검사하고 파일을 연 뒤 헤더를 모두 정하고 본문을 흘려보낸다. 검사에서 실패하면 아직 헤더가 나가지 않아 404·503으로 답할 수 있지만, 보내는 중에 실패하면 오류 응답으로 바꿀 수 없다|dark=213|w=100|a=center](attachment:214)

권한 확인과 파일 열기는 헤더를 정하기 전에 끝난다. 그래서 여기서 실패하면 전과 같은 404·503 오류 응답을 보낼 수 있다. 파일은 메모리에 통째로 올리지 않고 스트림으로 복사하며, 성공하든 실패하든 try-with-resources가 스트림을 닫는다. 본문을 보내기 시작한 뒤의 실패는 헤더가 이미 나갔기 때문에 오류 응답으로 바꿀 수 없다.

고칠 방법은 세 가지를 놓고 비교했다. 보안 헤더를 끄는 방법도 있었지만 응답의 보안 계약이 바뀌므로 처음부터 뺐다.

| 방법 | 헤더와 본문 | 판단 |
|---|---|---|
| 비동기 전송 유지 | 두 스레드에 나뉜다 | 필터와 전송 스레드가 헤더를 쓰는 순서를 따로 맞춰야 한다 |
| 파일 전체를 메모리에 올려 응답 | 한 스레드 | 동시 요청 수 × 파일 크기만큼 메모리가 들어, 1.5GiB로 제한한 API 컨테이너에 부담이 된다 |
| 요청 스레드에서 흘려보내기(고른 쪽) | 한 스레드에서 차례로 | 보내는 동안 요청 스레드를 붙잡아 둔다 |

받아들인 비용은 마지막 줄이다. 본문 이미지는 최대 10MiB, 기술 아이콘은 64px라서 지금 용도에서는 감당할 만하다고 봤다. 세 방법의 성능을 따로 재서 비교하지는 않았다.

지금도 공개 첨부와 기술 아이콘은 이 구조로 보낸다. 캐시 정책만 다르다. 첨부는 `private, no-store`, 기술 아이콘은 `public, max-age=300`이다.

## 확인

고쳤다고 보는 근거는 구조다. 헤더와 본문을 한 스레드에서 차례로 쓰니 두 쓰기가 겹칠 수 없다. 부하 검사는 고친 뒤에 다른 문제가 생기지 않았는지 본 것이다. API 직접 호출, Caddy 경유, 공개·관리자 첨부를 섞어 동시에 4개씩 모두 750번 요청했고 오류는 없었다.

750번 무오류로 말할 수 있는 것에는 한계가 있다. 오류가 한 번도 없었을 때 실패율의 95% 신뢰 상한은 약 3/750, 곧 0.4%다.[* 3의 법칙: n번 시도해 한 번도 실패하지 않으면 실패율의 95% 신뢰 상한은 약 3/n이다] 고치기 전에 본 1/150(약 0.67%)보다는 낮은 범위지만, 실패가 아주 드물게라도 남아 있는지까지 가리지는 못한다.

## 남은 위험

- 경합을 매번 재현하는 시험이 없다. 원인은 구조와 예외의 모양으로 판단한 것이다. `AttachmentDeliveryTest`는 잘못된 MIME, 0·음수·상한 초과 크기, 실제 크기 불일치를 보내기 전에 거부하는지 보는 입력 검사이고, 헤더 경합을 오래 재현하는 시험은 아니다.[* 근거: 결정·검증 기록(`ADR_application.md`), 공개 첨부 컨트롤러(`PostAttachmentController.java`), 기술 아이콘 컨트롤러(`StackBadgeController.java`), 전달 검사(`AttachmentDeliveryTest.java`)]
- 750번 성공과 두 시점의 파일 디스크립터 수만으로는 오래 돌려도 오류나 누수가 없다고 말할 수 없다.
- 큰 파일, 느린 연결, 동시 다운로드가 늘면 요청 스레드를 붙잡는 시간이 문제가 될 수 있다. 그때는 요청 스레드 점유와 대기 시간을 먼저 재고, 비동기 방식으로 돌아갈지는 헤더 경합을 재현하고 부하를 비교한 뒤에 정한다.
