# 문서 유형별 구성

프로젝트 문서 묶음의 기본형과 유형별 구성. 각 유형의 'ken-blog 예시'는 사용자 검토를 마친 실제 게시 문서다. 구성을 바꾸면 결정을 [decisions.md](decisions.md)에 기록한다.

## 목차

- 문서 묶음: 순서·독자가 얻을 답·적용 조건·상태, 공통 규칙
- 1. 대문 ~ 8. 보안 설계: 유형별 절 순서, 넣지 않음, ken-blog 예시
- 저장소 README: 작성 시점, 독자, 구성 순서 표, 이미지

## 문서 묶음

| 순서 | 문서 | 독자가 얻을 답 | 적용 조건 |
| --- | --- | --- | --- |
| 1 | 대문 | 무엇을 왜 만들었고, 본인이 무엇을 했고, 핵심 판단이 무엇인가 | 항상 |
| 2 | 아키텍처 | 어디서 돌아가고, 어떻게 처리되고, 어디까지 보장하는가 | 항상 |
| 3 | 기능과 사용자 흐름 | 누가 무엇을 어떤 순서·규칙으로 하는가 | 항상 |
| 4 | 데이터 모델과 ERD | 무엇을 저장하고 어떤 관계·제약을 지키는가 | DB가 있을 때 |
| 5 | API 설계 | API를 어떤 원칙으로 나눴고, 핵심 계약이 왜 그런 모양인가 | HTTP API가 있을 때 |
| 6 | 주요 기술적 의사결정 | 대문의 주요 결정마다 어떤 대안을 비교해 무엇을 택했고 어떻게 확인했는가 | 항상 |
| 7 | 배포와 운영 | 변경이 어떤 경로로 반영되고, 실패하면 어떻게 되는가 | 배포 경로가 둘 이상일 때 |
| 8 | 보안 설계 | 무엇을 무엇으로부터 어떻게 지키는가 | 인증·공개 경계가 있을 때 |
| — | Posts(실험·트러블슈팅·개별 ADR) | 개별 기록 | 필요할 때, 관련 프로젝트로 연결 |
| — | 저장소 README | 이 저장소가 무엇이고, 무엇을 하며, 문서는 어디에 있는가 | 모든 문서의 작성·검토·검증이 끝난 뒤(D-044) |

공통 규칙: 한계 절은 필요할 때만(D-030), 첫머리 핵심 주장 한 줄(D-006), 판단 기록은 목록(D-007), 상세 원본은 한 곳(D-005), P 번호 연결(D-002), 아키텍처는 '어떻게 동작하나'·06은 '왜'(D-027), 유동적인 절만 도입 문장(D-024).

## 1. 대문

- 순서: 개요 표 → 요약 문단 → 담당 범위 절(본인 항목만, D-059) → 개발 배경과 핵심 문제 → 주요 기능 → 전체 아키텍처(통합 구성도·설계 결정 요약·주요 흐름) → 핵심 문제별 설계와 검증
- 개발 배경: 실제 불편 한 문단, 설계 제약 2~4개(수치는 측정 방법 주석), 핵심 문제 `P1 품질 속성: 보장할 것` 2~4개
- 주요 기능: `기능 / 사용자가 할 수 있는 일` 표 4~6행, 대표 화면 1~2장(반대 테마, 캡션)
- 설계 결정 요약: `결정 / 해결한 문제(P 번호) / 받아들인 비용`. 기술 스택 이름 표는 두지 않음(헤더 배지가 대신함)
- 주요 흐름: 표 대신 3~4문장 서술과 아키텍처 링크. 흐름 표의 원본은 아키텍처 문서(D-056)
- 핵심 문제별: P마다 문제·결정·대가·검증 한 줄씩(하위 목록 없음, D-052), 대표 수치 표 1개와 인용 1개, 끝에 의사결정 문서 링크
- 넣지 않음: 한계 절, 대안 비교 표 전체, 기술 선택 일반론
- 복사용 틀: [landing-template.md](landing-template.md)
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/project-06840552-43a2-4870-83a9-d3e848c71d7e/

## 2. 아키텍처

- 첫 줄: 구조의 결론 한 문장(예: "독자의 열람은 GitHub Pages에서 끝나고, 서버는 관리 요청과 사이트 빌드에만 쓰임")
- 품질 요구사항: `품질 속성 / 요구 / 관련 문제 / 구조적 대응`. P에 연결된 행만
- 인프라 구성도: 중제목 바로 아래 배포 경계 한 줄(예: "배포 경계는 GitHub, OCI ARM VM, 관리형 MySQL의 세 영역.") → 로고 구성도 한 장(고정 배치, 범례는 그림 안 오른쪽 아래 상자, 캡션은 설명만) → `배포 경계 / 구성 요소 / 책임` 표(경계별로 정렬). 그림 뒤에 설명 문단을 두지 않음
- 주요 흐름: 인프라 구성도 바로 다음 절. `흐름 / 처리 경로 / 실패하면 / 관련 문제` 표. 사용자 요청·쓰기·빌드·배포·확장 흐름을 모두 넣고, 배포·확장은 한 줄 요약과 배포 문서 링크만(D-056)
- 시스템 구조: 로고 구성도(고정 배치)로 계층(사용자·표현·빌드·애플리케이션·데이터)과 경로(열람 굵은 선·관리 실선·빌드 점선)를 한 장에(경로별 처리는 주요 흐름 표가 맡아 따로 경로 표를 두지 않음), API 내부 계층도(flowchart, 보안 필터 → 컨트롤러 → 서비스 → 저장소)
- 데이터의 정본과 파생 결과물: `자료 / 정본 / 변경 주체 / 공개 반영`. 같은 자료가 여러 저장소에 있어 정본을 정하는 것이 핵심 문제와 이어지는 프로젝트만 씀(ken-blog의 Git·DB·디스크). 저장소마다 자료가 겹치지 않으면 절을 빼고, 파생값(임베딩 등)의 재계산 같은 특이점만 일관성 표에 한 행으로 둠(D-055)
- 일관성 모델과 보장 범위: 도입 1~3문장, `경계 / 보장 / 방법 / 보장하지 않는 구간` 표, 핵심 결론 인용, 가장 중요한 경계의 실행 순서(시퀀스, 범례 상자) 한 장과 한두 문장. 선택 이유·대안·실패 사례 목록은 06
- 넣지 않음: 장애 영향 표, 영속 계층(ORM 선택), 배포 절차, 보안 세부
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/

## 3. 기능과 사용자 흐름

- 기능 범위: 개별 기능을 나열하지 않고 `역할 / 기능 묶음 / 내용` 표로 전체를 묶음. 로그인·테마 같은 기본 기능은 뺌
- 그 밖의 절: 콘텐츠 모델(관계 규칙, 작은 flowchart), 상태와 공개 조건(stateDiagram), 대표 유저 플로우, 관리 작업의 동시성 정책 표
- **대표 유저 플로우는 2~4개만**(D-031). 고르는 기준: 여러 저장소·모듈을 가로지름, 상태 전이·실패 분기가 많음, 정합성·동시성·권한 같은 기술 문제가 걸림, 대문의 핵심 문제와 이어짐. 블로그·관리 화면이라면 어디에나 있는 흐름(목록·검색으로 찾기 등)과 단순한 규칙(409 후 다시 저장 등)은 흐름도 대신 한 문장이나 표로
- 유저 플로우 표기: `flowchart TD`, 시작·끝은 둥근 노드, 화면·행동은 사각형, 판단은 마름모, 분기 선에 조건, 역할별 색(classDef)
- 넣지 않음: 시스템 간 호출 시퀀스(아키텍처 문서), 동시성의 원리·선택 이유(Posts 결정 글), 한계 절(D-030)
- **규모가 큰 프로젝트**(예: ERP): 기능 범위를 `모듈 / 기능 묶음 / 사용 역할` 모듈 지도로, `역할 × 모듈` 권한 표, 중심 엔티티 1~2개의 상태도, 모듈을 가로지르는 대표 흐름 2~4개, 기술적으로 의미 있는 업무 규칙(재고 차감 동시성, 마감 후 수정 금지 등)만. 단순 CRUD 화면은 기능 묶음 한 칸으로 끝내고, 이야기할 거리가 있는 기능은 Posts 글로. 전체 기능 명세가 필요하면 블로그가 아닌 레포 문서로
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/doc-4cfccbd2-1972-4ad8-893a-6a8bf45744e1/ (독자 흐름 1개, 발행 흐름 1개)

## 4. 데이터 모델과 ERD

- 첫 줄: DB에 두는 것과 두지 않는 것
- 전체 ERD(영역별 색, 범례 상자) → 스키마의 특징(짧게 3~5개, 핵심 문제와 이어지는 특징은 P 번호와 06 링크) → 주요 관계 상세 → 스키마 변경과 운영 대조(운영과 생성 DDL 차이는 접기. 운영 DB와 대조한 결과가 없으면 절을 빼고, 이관 도구·구조 재설계 이야기는 배포 문서·의사결정 문서에만 둠, D-058)
- **상세 ERD는 프로젝트의 특징이 드러나는 관계 2~3개만**(D-037). 고르는 기준: 이 프로젝트의 콘텐츠·업무 모델을 설명함(예: 같은 테이블을 가리키는 두 관계), 핵심 문제(P)의 규칙이 걸림(예: 공개 조건·revision에 들어가는 연결). 분류·태그·계정·세션처럼 흔한 영역은 그리지 않고 '그 밖의 영역' 필드 표(접기)로
- **쓰지 않는 열을 문서에 나열하지 않음**(D-037). 발견하면 코드·DB에서 지우는 작업을 제안하고, 문서에는 지금 쓰는 호환 열만 '쓰는 곳'과 함께 둠
- 기준을 한 문장으로 밝힘(예: 운영 DB의 실제 정의 기준). 운영 대조는 읽기 전용 조회 결과로
- DB 설계의 이유도 코드·ADR에서 확인한 사실로 씀. 사용자가 잘 모르는 부분은 비공개 학습 목록에(D-028)
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/post-f9235d74-4d5b-4705-8f59-ba3511bd50e9/

## 5. API 설계

- 명세가 아니라 설계 판단과 핵심 계약만 다룸(D-039). 경로 목록·필드 계약·오류 상태 표는 쓰지 않고, 첫 줄 주석에 컨트롤러·입력 DTO 코드 링크로 원본을 가리킴
- 첫 줄: API의 종류와 각자의 책임, P 연결 → 설계 원칙(`결정 / 내용 / 이유·대가` 표, 인용 1) → 핵심 계약 2~3개
- 핵심 계약 고르는 기준: 동시성·일관성이 걸린 계약(예: 편집 버전 409, 잠금 순서로 교착 방지), 다른 구성 요소가 의존하는 계약(예: 빌더가 쓰는 공개 스냅샷의 구조·크기 상한), 정보 노출을 막는 규칙(예: 비공개 첨부를 없는 것과 같은 404로)
- 인증 순서·쿠키 속성은 보안 설계 문서에만 두고 여기서는 링크
- 정확한 시도 제한 수치처럼 공격자에게만 쓸모 있는 값은 쓰지 않음
- 코드가 비공개인 프로젝트는 관리 API 경로 목록을 공개하지 않음. 전체 명세가 필요하면 저장소 안 OpenAPI 등으로
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/doc-6bf82223-5b13-49ae-894b-5da5a0de6ddf/

## 6. 주요 기술적 의사결정

- 대문의 주요 결정(P1~Pn)만 다룸. 선정 기준은 [decisions.md](decisions.md)의 '주요 결정과 Posts의 분배'
- 첫 줄: 결정들이 어떻게 이어지는지 한 문장 → 결정 요약 표(`결정 / 해결한 문제 / 대가`) → P마다 문제 / 검토한 대안(표, 채택안 굵게) / 대가 / 검증. 한계 절은 필요할 때만(D-030)
- 검증은 요약과 링크. 측정 원자료·실패 사례 전체는 Posts 실험 글로. 실험 글의 설계·보고 형식은 `ken-blog-experiments` 스킬
- 넣지 않음: P에 속하지 않는 결정(Posts로), '지금 어떻게 동작하나'의 설명(아키텍처 문서로)
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/doc-267e2237-7f38-4ea1-b04b-7c51d456c2b4/

## 7. 배포와 운영

- CI/CD 구성도(flowchart, D-042) → 변경별 반영 경로 표(관련 문제 열) → 사이트 배포 운영 규칙 → API 배포와 롤백(flowchart, 수동이면 그 사실과 대가) → 실제 운영 사례(무엇이 빠졌고, 증상, 중단 시간, 재발 방지, 담당 구분) → 스키마 변경 전환(확장-축소, 값을 바꾸는 이관과 단순 삭제를 구분) → CI 결과의 의미 → 운영 점검
- 실제로 하지 않는 절차는 쓰지 않음. 백업·복구는 정책을 정한 프로젝트만 '점검과 백업' 절로 씀(D-041). 작은 프로젝트에서 정하지 않았다면 절과 한계 항목 모두 생략
- 설정값은 기본값과 운영값을 구분
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/doc-aaa3ec9d-c135-4bc6-a1cd-398a3493480c/

## 8. 보안 설계

- 위협 모델 → 위협별 대응 표(인용 1) → 배포 구조가 만든 보안 설계 → 인증·세션(계약은 접기) → 반복 시도 제한 → 공개 자료 경계 → 렌더링 경계 → 검증 표(검증하지 않은 항목 포함)
- 한계 절은 두지 않고 위협별 대응 표의 '남은 위험' 열로 대신함. 로그인 제한 임계값 같은 세부 수치는 쓰지 않고 방식만 씀(D-043)
- 설정은 실제 코드·운영 값과 대조(예: CORS 출처 목록이 공개·인증 모두 같은지)
- ken-blog 예시: https://gjaku1031.github.io/ken-blog/post/doc-b707888f-a270-4aef-a617-f3345644a3f3/

## 저장소 README

- 작성 시점: 문서 묶음(대문~보안 설계)과 연결된 Posts의 작성·사용자 검토·사실 검증이 모두 끝난 뒤에만 씀(D-044). 문서가 바뀌는 중에 쓰면 README가 요약하는 내용과 어긋남
- 독자: 대문의 GitHub 링크로 온 교수·시니어 개발자. 블로그 문서를 다시 쓰지 않고 저장소 안내에 집중하며, 상세는 블로그 문서로 링크(D-005). 공개 실행을 전제로 한 오픈소스가 아니면 실행·설치 방법 절은 두지 않음(D-047)
- 언어·문체: 한국어 간결체(블로그와 같음)
- 구성 순서

| 순서 | 절 | 내용 |
| --- | --- | --- |
| 1 | 제목·한 줄 소개 | 무엇을 만든 저장소인지, 블로그 대문 링크 |
| 2 | 주요 기능 | 대문의 주요 기능 표(기능 / 할 수 있는 일)를 그대로 옮김. 이 블로그·서비스가 무엇을 하는지 첫 화면에서 보이게 함(D-048) |
| 3 | 화면 | 스크린샷 1~2장. 공개 화면(설계 문서와 도식)과 관리 화면(글 정보 편집). 모의 데이터면 캡션에 밝힘 |
| 4 | 핵심 문제와 결정 | P1~Pn 한 줄씩, 상세는 주요 기술적 의사결정 문서로 링크 |
| 5 | 아키텍처 | 블로그의 전체 구성도를 이미지로 넣고, 배포 경계와 주요 경로를 2~3줄로 설명. 상세는 아키텍처 문서로 링크 |
| 6 | 기술 스택 | `영역 / 기술` 표(API·DB·사이트 빌드·배포 등 영역별). 주력 기술만 넣고 라이브러리·테스트 도구는 넣지 않음(버전은 언어·프레임워크·런타임만)(D-050) |
| 7 | 문서 | 블로그 문서 묶음·Posts·ADR·컨벤션 링크 |
| 8 | 작업 방식 | 본인·에이전트 역할 한 줄씩, 상세는 대문 링크 |

저장소 구조(디렉터리 표) 절은 두지 않음(D-049).

- 이미지: 구성도와 스크린샷은 README를 쓰는 시점에 새로 캡처해 저장소(`docs/images/` 등)에 PNG로 둠. 블로그 첨부(DB·서버 디스크)는 GitHub에서 쓸 수 없음. 라이트·다크 두 장을 `<picture>`와 `prefers-color-scheme`로 바꿔 보여 주고, GitHub 테마와 같은 테마의 캡처를 씀(블로그의 반대 테마 규칙은 같은 사이트 안에서 화면이 겹쳐 보이는 문제 때문이라 README에는 적용하지 않음)
- 구성도는 블로그의 고정 배치 도식을 캡처함. 아이콘·고정 배치를 쓰는 도식은 GitHub Mermaid로 그려지지 않으므로 원문을 다시 그리지 않음. 원문이 바뀌면 이미지를 다시 캡처함
