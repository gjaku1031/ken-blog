# 학원 강사 업무일지: 인터뷰 요약

문서를 쓰며 확인한 사실과 판단의 이유를 정리한 기록. 블로그에는 게시하지 않음. 마지막 정리 2026-10-23.

## 개발 형태와 담당 범위

- 개발 1인, 기획 1인
- 요구사항은 실장, 운영진(대표와 원장), 각 팀의 팀장에게서 받았음
- 진행 방식: 먼저 시제품을 만들어 보여 주면 실장이 1차로 다듬고, 그 뒤에 팀장이나 원장이 확인했음
- 직접 설계하고 구현한 것
  - 요구사항 정리
  - 업무와 일일보고의 모델(업무 종류와 완료 판정, 날짜별 체크리스트, 다섯 단계 작성 흐름)
  - 외부 ERP로 상담을 보낼 때의 선점과 대조
  - 서버리스 인스턴스 사이의 일관성 처리
  - 시범 운영
- 저장소: <https://github.com/gjaku1031/npr-erp>. 실제로 운영한 코드를 정리해 공개했고, 외부 ERP 연동은 포트와 모의 구현으로 대체했음

## 개발 배경

학원은 기존 ERP에 딸린 업무일지를 쓰고 있었음. 표 하나로 된 화면이었고, 세 가지가 불편했음.

- **반복되는 업무를 날마다 다시 적음**: 상담일지 쓰기, 보충일지 작성처럼 매일 바뀌지 않는 업무도 표에 매번 들어가야 했음
- **같은 내용을 두 번 적음**: 상담일지를 쓴 뒤에 업무일지에도 상담한 학생의 이름을 다시 적어야 했음
- **팀장이 날마다 확인 항목을 손으로 적음**: 팀의 퇴근 시각이 밤 10시인데, 팀장이 그 전후로 그날 확인할 사항(시험지를 만들었는지, 처리할 업무를 했는지)을 적어야 했음. 월요일부터 목요일까지 이어지는 업무는 나흘 모두 적어야 했음

그래서 팀장이 항목을 빠뜨린 날에는 그 업무를 하지 않는 사람이 생겼고, 팀장이 작성을 잊거나 늦게 하면 팀의 퇴근이 늦어졌음. 팀장은 작성 부담이 컸고, 팀원은 퇴근이 늦어지는 데 불만이 있었음.

### 불편과 기능의 대응

코드에서 확인한 대응 관계.

| 불편 | 대응하는 기능 |
| --- | --- |
| 반복되는 업무를 날마다 다시 적음 | 일일보고의 체크리스트가 됨. 날짜별 체크리스트를 만들 때 오늘(없으면 직전 날짜)의 항목을 복사하므로 다시 적지 않음 |
| 같은 내용을 두 번 적음 | 일일보고 3단계가 그날의 상담 기록을 외부 ERP에서 불러와 보여 줌. 강사는 확인만 함 |
| 팀장이 날마다 확인 항목을 손으로 적음 | 업무에 시작일과 마감일을 두어, 그 기간에 드는 날의 일일보고 5단계에 자동으로 나타남. 팀장은 한 번 정하고 제출 현황에서 누가 냈는지를 봄 |

## 기술 선택

검토한 대안은 Spring Boot 백엔드와 PostgreSQL, AWS나 Proxmox 가상화 서버에 직접 배포하는 구성이었음.

- **TypeScript 풀스택(Next.js)**: 화면과 API를 모두 개발자 한 사람이 유지해야 했고, 화면을 함께 볼 수 있는 동료는 JavaScript·TypeScript만 다룰 수 있었음. 두 언어 사이의 API 계약(OpenAPI 명세)을 꼼꼼히 관리하는 것보다 한 언어로 화면과 API를 함께 두는 편이 유지보수가 쉽다고 판단했음
- **Vercel**: 인프라를 다뤄 본 경험은 있지만 사용자가 100명 안쪽이었음. 인프라를 규모 있게 꾸리기보다 완성된 관리형 플랫폼으로 시작하는 편이 초기에 낫다고 판단했음
- **SQLite(libSQL, Turso)**: PostgreSQL도 고려했지만 작고 유지보수할 수 있는 크기로 시작하고, 필요해지면 PostgreSQL로 옮기기로 했음

## 시범 운영

시범 운영에서 기존 업무일지를 완전히 대체했음. 퇴근 전에 업무일지를 마치는 데 필요한 클릭은 기존에 평균 50번쯤이었고 새 업무일지에서는 10번 안으로 줄었음. 강사로도 일했기 때문에 실제 업무를 하면서 직접 세어 본 값이고, 한 사람의 기록임.

운영은 2026-09-23의 일일보고가 마지막이고, 지금은 종료됐음.

### 시범 운영에서 겪은 문제

2026-07-17부터 2026-09-05까지의 수정 기록에서 확인한 것.

- 수정 23건 가운데 18건이 외부 ERP에서 가져오거나 보내는 자료(상담, 반 명단, 출결)에 관한 것이었음. 제목으로 분류한 값
- 2026-07-25: 보낸 상담을 확인하는 기준이 외부 ERP의 실제 응답과 달라, 보낸 상담이 확인되지 않았음. 외부 ERP가 긴 본문을 10자가 아니라 9자로 잘라 돌려주는 경우가 있었음
- 2026-08-18: 외부 ERP가 저장을 거부한 상담이 전송 중 상태에 갇혀 다시 보내지도 고치지도 못했음. 거부 사유를 보존하고, 외부 ERP를 직접 확인한 담당자가 종결하는 경로를 추가했음
- 같은 상담이 두 번 기록된 사례는 수정 기록에서 찾지 못했음
