## 개발 배경

### 프로젝트 경험과 학습 문서의 통합

포트폴리오 작성 과정에서 GitHub에 축적된 자료만으로 개발 경험을 정리하기 어려운 문제 확인. 관련 정보가 여러 곳에 분산되어 있어, 수행한 작업과 학습 내용을 정리할 때마다 자료 수집 반복.

프로젝트 중 작성한 학습 문서도 이후 작업에서 재사용하고 팀원과 공유할 필요. 프로젝트 소개·설계·문제 해결 기록과 학습 자료를 한곳에 모아 본인이 다시 참고하고, 에이전트에도 정리할 자료로 제공하는 것이 목적.

### 아키텍처와 데이터 모델의 문서화

시스템 구성과 데이터 관계를 기록할 때 문서화 도구와 표현 방식을 직접 선택·구성할 수 있는 환경 필요. 서버·배포 구조는 Mermaid Architecture, 테이블·키·관계는 ERD로 표현하고 설계 설명과 함께 관리.

다이어그램 원문을 Markdown에 포함해 본문과 같은 Git 변경 이력으로 관리. 구조 변경 시 설명과 그림을 함께 수정하고, 에이전트도 원문을 읽고 수정할 수 있도록 구성.

### 에이전트를 통한 문서 갱신

기술 버전 변경에 따른 기존 문서의 검토·수정 부담 완화가 목표. Spring Security 버전 변경을 예로 들면, 기존 방식은 관련 글을 기억해 내고 발행된 내용을 다시 읽은 뒤 수정하는 순서. 검토 대상의 발견이 작성자의 기억에 의존함.

Git에 보관한 문서를 블로그를 통해 에이전트에 제공하고, 전체 글에서 갱신 대상과 수정안을 도출하는 흐름 검토. 제안된 변경은 작성자가 검토한 뒤 반영하는 방향. 에이전트용 문서 제공과 갱신 기능은 향후 개발 범위.

## 전체 아키텍처

### 인프라·시스템 통합 구성도

```mermaid
architecture-beta
  %% layout: ken-blog-infrastructure
  group people[Users]
  group github[GitHub]
  group site[Pages workflow] in github
  group ci[API workflow] in github
  group ops[Manual operation]
  group oci[OCI ARM VM]
  group compose(ken:docker)[Docker Compose] in oci
  group data[External database]

  service writer(ken:user)[Author and agent] in people
  service repo(ken:git)[Git repository] in github
  service sitebuild(ken:github-actions)[Site build] in site
  service pages(ken:github)[GitHub Pages] in site
  service apibuild(ken:github-actions)[API CI] in ci
  service archive(ken:docker)[JVM image] in ci
  service operator(ken:user)[Operator] in ops
  service reader(ken:user)[Reader] in people
  service admin(ken:user)[Admin] in people
  service caddy(ken:caddy)[Caddy] in compose
  service api(ken:spring)[Spring Boot API] in compose
  service disk(ken:disk)[Image disk] in oci
  service db(ken:mysql)[MySQL] in data

  writer:R -[Push]-> L:repo
  repo:R -[Web changes]-> L:sitebuild
  repo:B -[API changes]-> L:apibuild
  sitebuild:R -[Publish]-> L:pages
  sitebuild:B -[Public API]-> T:caddy
  apibuild:R -[Archive]-> L:archive
  archive:B -[Review]-> R:operator
  operator:B -[Manual deploy]-> T:api
  reader:R -[Read]-> R:pages
  admin:T -[Manage UI]-> B:pages
  admin:R -[Admin API]-> L:caddy
  caddy:R -[HTTP]-> L:api
  api:R -[JDBC]-> L:db
  api:B -[Read only]-> T:disk
```

실선은 요청·데이터 접근, 초록 점선은 빌드·산출물 전달, 보라 점선은 검토 후 수동 운영 반영. API 응답은 요청의 반대 경로로 전달.

원고 작성, 정적 사이트 생성, 공개 글 열람, 관리자 요청, API 배포를 하나의 구성도로 표현. GitHub의 빌드·호스팅 영역, OCI VM의 Caddy·API·이미지 디스크, 외부 MySQL의 배포 경계와 각 시스템의 책임을 함께 구분.

공개 화면은 GitHub Pages에서 제공하고, API는 인증·메타데이터 관리·공개 데이터 조회를 담당. 원고는 Git, 글 정보와 관계·세션은 MySQL, 이미지 원본은 영속 디스크에서 관리. Node 빌더가 이 자료를 결합해 공개 페이지 생성.

### 주요 기술 스택과 선택 이유

| 기술 | 적용 영역 | 선택 이유 |
| --- | --- | --- |
| Kotlin·Spring Boot·JPA | 인증·관리 API, 공개 데이터 조회와 엔티티 영속성 관리 | — |
| GitHub Actions·Pages | 사이트 빌드와 정적 파일 배포 | 공개 글 열람을 API 처리에서 분리해 서버 부하와 API 왕복 의존 축소 |
| Mermaid | 아키텍처·ERD 등 설계 도식 | 구조에 맞는 도식을 선택하고 다이어그램 원문을 문서와 함께 관리 |

### 주요 인프라 흐름

| 흐름 | 처리 경로 |
| --- | --- |
| 공개 글 열람 | 독자 브라우저 → GitHub Pages의 HTML·이미지. 본문 열람에 API 조회 불필요 |
| 관리자 작업 | Pages의 관리 화면 → Caddy의 HTTPS 진입점 → API의 인증·메타데이터 처리 → 외부 MySQL |
| 사이트 생성·배포 | Git 원고와 웹 소스 → GitHub Actions의 Node 빌더. Caddy·API를 통해 공개 메타데이터와 이미지를 수집하고 정적 산출물을 Pages에 배포 |
| API 배포 | Kotlin 소스 → API CI의 검사·JVM 이미지 생성 → 이미지 아카이브 보관 → 운영자 확인 후 OCI VM의 Docker Compose에 수동 반영 |

## 중요한 선택과 문제 해결

### 정적 페이지 생성으로 API의 글 열람 처리 분리

일본 리전 API의 처리 부하와 글 열람 시 API 왕복 지연에 대한 의존을 줄이는 것이 목적. 글을 읽을 때마다 API에서 데이터를 조회하고 화면을 생성하는 작업을 줄이기 위해 공개 페이지를 빌드 시 미리 생성하는 방식 선택.

Git 원고와 공개 메타데이터·이미지를 빌드 단계에서 수집하고, 생성한 HTML과 이미지를 GitHub Pages에서 제공. 공개 본문과 이미지 열람에 필요한 API 요청을 빌드 단계로 이동. 로그인·관리 기능과 새 사이트 빌드에는 API 사용 유지.

본문을 초기 HTML에 포함하므로 검색엔진이 본문을 확인하기 위해 클라이언트의 추가 API 호출과 JavaScript 실행을 기다릴 필요도 줄어듦. 검색엔진의 콘텐츠 수집을 고려한 구조. [Google의 JavaScript SEO 가이드](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

대신 글과 공개 상태의 변경은 Pages 재배포 후 반영. 매 요청의 동적 처리 대신 빌드·배포 단계에서 변경 내용을 반영하는 비용 수용.

### API·벡터 저장소 기반 RAG 검색 (예정)

에이전트가 브라우저로 글 목록과 본문을 모두 탐색하는 방식은 문서가 늘어날수록 탐색 단계와 입력 토큰이 증가. 질문과 관계없는 내용까지 읽는 비용을 줄이고, 필요한 문서에 바로 접근하는 것이 목적.

문서를 구간별로 나누어 벡터 저장소에 색인하고, 질문과 관련된 내용을 API로 검색·조회하는 RAG 흐름 도입 예정. 검색 결과에 원문 위치를 함께 제공하고, 추가 맥락이 필요한 경우 본문 조회.

반복적인 브라우저 탐색과 불필요한 본문 입력을 줄여 토큰 사용량과 응답 시간 절감 목표. 실제 절감 효과와 검색 정확도는 구현 후 검증 예정.
