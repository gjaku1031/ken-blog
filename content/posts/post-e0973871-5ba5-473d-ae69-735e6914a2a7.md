ken-blog는 쓰기·단건 조회·행 잠금을 JPA로, 목록·집계·공개 스냅샷 조회를 jOOQ로 처리함. 두 영속 기술을 함께 쓰게 된 출발점은 공개 조건과 정렬을 함께 다루는 목록 조회의 JPQL이었음.

## 문제: 문자열 JPQL의 조건부 조회

당시 공개 글 목록은 발행 상태·공개 범위·구획·분류·태그 조건을 선택적으로 걸고, 시리즈 순서와 최신순 중 하나로 정렬해야 했음.[* 공개 범위(`visibility`)와 구획(`section`)은 값이 하나로 고정되어 이후 열을 지웠고, 지금 공개 조건은 발행 상태뿐임] JPQL 문자열 하나로 쓰면 아래와 같은 모양이 됨.

<details><summary>jOOQ 전환 전 공개 글 목록 JPQL</summary>

```sql
select new PublishedPostRow(p.id, p.title, p.slug, p.publishedAt, p.categoryId)
from PostEntity p
where p.section = PostSection.TECH
  and p.status = :published
  and (:includePrivate = true or p.visibility = :publicVisibility)
  and (:categoryPath is null or exists (
        select c.id from CategoryEntity c
        where c.id = p.categoryId and (c.path = :categoryPath or c.path like :descendantPath)))
  and (:tag is null or exists (
        select t.id from PostTagEntity t where t.postId = p.id and t.name = :tag))
order by case when :seriesOrder = true and p.techSeriesOrder is null then 0
              when :seriesOrder = true then 1 else null end asc,
         case when :seriesOrder = true then p.techSeriesOrder else null end asc,
         case when :seriesOrder = true then p.publishedAt else null end asc,
         case when :seriesOrder = true then p.id else null end asc,
         case when :seriesOrder = false then p.publishedAt else null end desc,
         case when :seriesOrder = false then p.id else null end desc
```

</details>

- 선택 조건을 `(:값 is null or ...)`로 나열해, 조건을 걸지 말지가 쿼리 문자열 안에서 분기함
- 정렬 기준 하나를 바꾸려고 `CASE`를 여섯 번 반복함
- 같은 `where` 조건을 건수 조회 쿼리에 한 번 더 복사해야 함
- 공개 조건(당시 발행·공개 범위·구획)이 쿼리마다 따로 적혀, 목록·단건·첨부 조회의 공개 기준이 어긋나도 알아채기 어려움

이 가운데 마지막 문제가 가장 컸음. 공개 사이트는 공개 스냅샷과 첨부 전달이 같은 공개 기준을 써야 일관되게 만들어지기 때문임([아키텍처](/ken-blog/post/doc-340352c9-5fde-4bae-bc0b-4ecd744719a8/) 참조).

## 검토한 대안

| 기준 | JPQL 유지 | Criteria API | QueryDSL(JPA 모듈) | jOOQ |
| --- | --- | --- | --- | --- |
| 조건 조립 | 문자열 안의 null 분기 | Java 코드로 조립 | Java 코드로 조립 | Java 코드로 조립(`Condition`) |
| 읽기 쉬움 | 조건이 늘면 분기가 문자열에 쌓임 | 조건 하나에도 빌더 호출이 길게 이어짐 | SQL과 비슷한 문장 | SQL과 비슷한 문장 |
| 타입의 원천 | 엔티티 | 엔티티(메타모델) | 엔티티에서 Q타입 생성(APT) | DB 스키마에서 테이블 타입 생성 |
| 표현 범위 | JPQL·HQL | JPQL·HQL | JPQL·HQL로 변환되므로 그 범위 안 | SQL 그대로(`FOR UPDATE`, 방언별 기능 포함) |
| 유지 상태[* 2026-10 확인. QueryDSL 원 저장소의 마지막 릴리스는 5.1.0(2024-01). 이후 OpenFeign 조직의 포크가 릴리스를 이어 가고 있음. QueryDSL에도 JPQL을 거치지 않는 SQL 모듈이 있지만 유지 상태는 같음. jOOQ는 이 프로젝트가 쓰는 3.21 계열까지 정기 릴리스, Spring Boot가 `spring-boot-starter-jooq`를 제공] | 표준 | 표준 | 원 저장소 정체, 포크로 유지 | 정기 릴리스 |

- Criteria API는 코드가 장황하고 복잡해 유지보수가 어렵다고 보고 제외함[* Spring Data JPA의 Specification도 Criteria API 위에서 조건을 조합하는 방식]
- QueryDSL은 원 저장소의 업데이트가 멈춘 상태라 제외함. OpenFeign 포크가 릴리스를 이어 가고 있지만 원 저장소 조직의 릴리스가 아니어서, 핵심 조회 계층을 맡기기에는 유지 주체가 불확실하다고 봄
- JPQL로 복잡한 조회를 쓰기 어려웠던 문제는 JPQL로 변환되는 도구를 써도 그 범위에 머문다고 보고, SQL을 직접 다루는 jOOQ를 택함
- 쓰기·단건 조회·잠금은 JPA에 남김. 두 기술은 같은 데이터 소스와 Spring 트랜잭션을 공유함

## 전환 후의 조회

공개 조건을 `Condition` 하나로 정의하고, 공개 스냅샷의 글 목록·시리즈 문서 목록·첨부 전달·첨부 revision 계산이 모두 이 조건을 씀. 공개 기준을 바꾸면 네 조회가 함께 바뀜.[* [조회 코드](https://github.com/gjaku1031/ken-blog/blob/b768152/src/main/java/io/github/gjaku1031/kenblog/post/repository/PostQueries.java)]

```java
public Condition readable() {
    return p.STATUS.eq("PUBLISHED");
}

public AttachmentDeliveryRow readableAttachment(long postId, long attachmentId) {
    return sql.select(ATTACHMENTS.OBJECT_KEY, ATTACHMENTS.CONTENT_TYPE, ATTACHMENTS.BYTE_SIZE)
            .from(joined().join(POST_ATTACHMENTS).on(POST_ATTACHMENTS.POST_ID.eq(p.ID))
                    .join(ATTACHMENTS).on(ATTACHMENTS.ID.eq(POST_ATTACHMENTS.ATTACHMENT_ID)))
            .where(readable().and(p.ID.eq(postId)).and(ATTACHMENTS.ID.eq(attachmentId)))
            .fetchOne(...);
}
```

- 조건과 정렬을 `Condition`·`SortField` 값으로 조합하므로, 옛 JPQL의 null 분기와 `CASE` 정렬이 사라짐
- 첨부 연결을 바꿀 때 첨부 행을 ID 순서로 잠그는 `SELECT ... FOR UPDATE`도 같은 조회 계층에서 씀

## 대가

- 영속 기술 두 개와 코드 생성 단계를 함께 유지해야 함. 스키마 정의를 두 곳에 두지 않으려고 jOOQ 타입은 JPA 엔티티에서 만든 DDL로 생성함. 생성 순서는 [JPA 엔티티를 원본으로 jOOQ 타입 생성](/ken-blog/post/post-f69cf0bb-68a1-4b72-b6c9-6aea1ed04db9/)에서 다룸
- 상태 열은 DDL에서 문자열 열로 생성되어, `"PUBLISHED"` 같은 값은 컴파일러가 검사하지 않음. 열 이름과 타입은 컴파일 시점에 검사되지만 값의 오타는 테스트로만 잡힘(예: 초안이 공개 목록에서 빠지는지 검사하는 `secondLevelNavigationKeepsOrderAndExcludesDrafts`)
- 같은 트랜잭션에서 JPA로 쓰고 jOOQ로 읽으면, JPA가 아직 flush하지 않은 변경은 jOOQ 조회에 보이지 않음. 두 기술을 섞는 메서드에서는 flush 시점을 의식해야 함
- 속도를 비교해 내린 결정은 아님. JPQL·jOOQ의 조회 성능은 측정하지 않음

## 검증

공개 스냅샷 회귀 검사는 Hibernate의 쿼리 수와 jOOQ SELECT 리스너의 계수를 합산해, 글 300개에서 조회가 10회 이하인지 확인함. jOOQ로 옮긴 뒤에도 조회 수가 글 수에 비례해 늘지 않는다는 기준임.[* [측정과 회귀 기준](/ken-blog/post/post-b46d1115-97ad-4d25-a9d9-1801b56857db/) · [조회 계수 설정](https://github.com/gjaku1031/ken-blog/blob/b768152/src/test/java/io/github/gjaku1031/kenblog/fixture/SqlCountConfig.java)]
