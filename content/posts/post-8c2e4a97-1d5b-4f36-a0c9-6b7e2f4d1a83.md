[담담공방 쇼핑몰](/ken-blog/post/project-a3d53a55-de01-4888-9e9a-02e34f2579bb/)은 사진을 올릴 때 서버가 대·중·소 세 크기의 WebP를 만들어 두고, 목록과 썸네일에는 작은 것을 내려보냄. 1~3번이 처음 결정이고, 4~11번은 그 결정을 구현하면서 함께 정한 것임.

## 바꾸기 전 상태

- 운영자가 JPG·PNG·WebP를 5MB까지 올리고, 서버는 받은 바이트를 그대로 디스크에 저장함.
- 사진은 한 벌뿐임. 120px짜리 썸네일도, 장바구니의 작은 사진도, 상세 화면의 큰 사진도 같은 원본 파일을 받음.
- 웹은 `next/image`를 쓰지만 `unoptimized: true`라서 크기 변환이 일어나지 않음. `sizes`를 적어 두었어도 고를 후보가 원본 하나뿐임.
- 사진 응답은 모두 `Cache-Control: no-store`이고, 요청마다 "이 사진이 공개 글·상품에 쓰였는가"를 DB에서 확인함. 같은 사진을 볼 때마다 다시 내려받음.
- 운영 서버의 사진은 17장(옛 사진 15장은 중앙값 80KB, 새로 올린 2장은 각 490KB)이라 당장 느리지는 않았음. 운영자가 휴대폰 사진(3~5MB, 가로 4000px 안팎)을 그대로 올리기 시작하면 달라짐.

상품 목록 한 화면에 카드가 12장이면 원본 12장을 받음. 장당 4MB라면 48MB이고, 그중 화면에 쓰이는 픽셀은 1%가 안 됨. 가로 4000px 사진을 가로 400px 자리에 넣으면 픽셀 수는 100분의 1만 필요하기 때문임.

## 1. 줄이는 시점

| 기준 | A. 올릴 때 미리 만들어 둠 | B. 요청이 올 때 변환(Next 이미지 최적화, imgproxy, CDN 변환) |
|---|---|---|
| 첫 요청 속도 | 파일을 읽어 보내기만 함 | 첫 요청은 변환을 기다림. 이후는 캐시 |
| 서버 부하가 생기는 때 | 운영자가 올릴 때 한 번 | 방문자가 볼 때. 캐시가 비면 한꺼번에 몰림 |
| 크기 종류 | 정해 둔 세 가지 | 주소로 아무 크기나 요청 가능 |
| 크기를 바꾸고 싶을 때 | 다시 일괄 변환 | 주소만 바꾸면 됨 |
| 저장 공간 | 사진당 원본 + 세 벌 | 원본 + 변환 캐시(지워도 됨) |
| 악용 | 없음. 만들 수 있는 크기가 고정 | 크기를 바꿔 가며 요청해 CPU와 캐시를 채울 수 있음. 허용 크기 제한이 필요 |
| 필요한 부속 | 변환 코드 | 변환 서버나 유료 CDN 기능, 변환 캐시 저장소 |

**선택: A.** API가 1대이고 사진을 올리는 사람은 운영자 한 명이라, 변환 비용을 올리는 순간에 한 번 치르는 편이 방문자 요청 경로를 가볍게 둠. B의 장점인 "아무 크기나"는 화면 종류가 몇 개 안 되는 이 쇼핑몰에서 쓸 일이 없음.

**A가 치르는 비용.** 크기 기준을 바꾸면 모든 사진을 다시 변환해야 함. 그래서 원본을 남겨 둠(6번).

## 2. 만드는 벌의 수

| 기준 | A. 대·중·소 세 벌 | B. 압축한 한 벌만 |
|---|---|---|
| 목록·썸네일 전송량 | 작은 벌만 받음 | 상세용 크기를 그대로 받음 |
| 상세 화면 화질 | 큰 벌로 유지 | 한 벌의 크기를 어디에 맞추든 한쪽이 손해 |
| 저장 공간 | 한 벌 대비 약 1.3배(작은 벌들은 픽셀 수가 적음) | 가장 적음 |
| 구현 | 변환 세 번, 고르는 규칙 필요 | 변환 한 번 |
| 고해상도 화면 | 한 단계 큰 벌을 골라 선명하게 | 대응 불가 |

**선택: A.** 한 벌로는 "목록은 가볍게, 상세는 선명하게"를 동시에 만족할 수 없음. 세 벌의 추가 저장 공간은 작음. 가로를 절반으로 줄이면 픽셀 수가 4분의 1이 되므로, 큰 벌 하나에 중간·작은 벌을 더해도 큰 벌의 3분의 1 남짓만 늘어남.

크기는 가로 기준 **소 400px, 중 800px, 대 1600px**. 원본이 그보다 작으면 키우지 않고 원본 크기까지만 만듦.

| 벌 | 가로 | 쓰는 곳 |
|---|---|---|
| 소 | 400px | 상품 카드, 장바구니·주문 내역 썸네일, 글 목록 작은 표지, 상세 화면의 작은 미리보기 |
| 중 | 800px | 고해상도 화면의 상품 카드, 휴대폰의 상세 사진, 글 목록 큰 표지 |
| 대 | 1600px | PC 상세 사진, 글 본문 사진 |

**A가 치르는 비용.** 세 가지보다 촘촘한 선택지는 없음. 가로 500px 자리에는 800px짜리가 가서 필요보다 조금 큼. 다섯 벌, 여섯 벌로 늘리면 줄일 수 있지만 얻는 것이 작아 세 벌에서 멈춤.

## 3. 썸네일에 주는 사진

| 기준 | A. 작은 벌을 내려보냄 | B. 큰 벌을 내려보내고 CSS로 줄임 |
|---|---|---|
| 전송량 | 필요한 만큼 | 필요의 수십 배 |
| 화질 | 서버가 좋은 방식으로 줄여 둠 | 브라우저가 실시간으로 줄임. 결과는 비슷하거나 조금 못함 |
| 휴대폰 메모리·배터리 | 작은 사진만 풀어 냄 | 큰 사진을 다 풀어 낸 뒤 줄임 |
| 상세로 넘어갈 때 | 큰 벌을 새로 받음 | 이미 받아 둔 것을 씀 |

**선택: A.** 바꾸기 전이 B였음. 목록에서 상세로 들어가는 방문자는 일부인데 B는 모든 방문자가 모든 상품의 큰 사진을 받게 함.

**A가 치르는 비용.** 상세로 들어가면 큰 벌을 새로 받는 동안 잠깐 비어 보일 수 있음. 작은 벌을 먼저 깔아 두고 큰 벌이 오면 바꾸는 방식으로 메울 수 있음.

## 4. 줄이는 곳

| 기준 | A. 서버가 변환 | B. 브라우저가 올리기 전에 변환(canvas) |
|---|---|---|
| 업로드 시간 | 원본을 통째로 올림. 느린 회선에서는 김 | 줄인 것만 올림. 빠름 |
| 결과의 일관성 | 서버 한 곳의 설정으로 항상 같음 | 브라우저·기기마다 압축 결과와 지원 형식이 다름 |
| 믿을 수 있는가 | 서버가 만든 것이므로 크기·형식을 믿어도 됨 | 클라이언트가 보낸 것이라 서버가 다시 검사해야 함. 조작된 요청은 큰 파일을 "작은 벌"이라고 보낼 수 있음 |
| 서버 자원 | 올릴 때 CPU와 메모리 사용 | 없음 |
| 원본 보관 | 가능 | 원본이 서버에 오지 않음 |
| 회전·위치 정보 | 서버가 한 번에 정리 | 브라우저마다 처리 차이 |

**선택: A.** 올리는 사람이 운영자 한 명이라 업로드가 몇 초 더 걸리는 것은 감당할 만하고, 결과를 서버가 책임지는 편이 단순함. 휴대폰 사진에는 촬영 위치가 들어 있는 경우가 많아, 변환하면서 회전 정보를 반영하고 나머지 정보는 지우는 일도 서버에서 한 번에 처리함.

**A가 치르는 비용.** 사진을 푸는 데 메모리가 들고, 여러 장을 동시에 변환하면 그만큼 겹침. 그래서 한 번에 한 장만 변환하고 나머지는 줄을 세움. 변환은 API 프로세스 안이 아니라 별도 프로세스(libvips)에서 하므로 사진이 잘못돼도 API가 죽지 않음.

## 5. 저장 형식

| 기준 | A. WebP로 통일 | B. 올린 형식 그대로(JPG는 JPG, PNG는 PNG) |
|---|---|---|
| 같은 화질에서의 크기 | JPG보다 대체로 4분의 1에서 3분의 1가량 작음 | 기준 |
| 투명 배경 | 지원 | PNG만 지원. PNG 사진은 매우 큼 |
| 브라우저 지원 | 현재 쓰이는 브라우저 전부 | 전부 |
| 서버 구현 | Java 기본 도구에 WebP 저장 기능이 없음. 별도 라이브러리나 변환 프로그램 필요 | 기본 도구로 가능 |
| 파일 이름 | 확장자가 하나로 정리됨 | 형식별로 나뉨 |

AVIF는 더 작지만 변환이 훨씬 느리고 서버 쪽 도구 준비가 더 까다로워 지금은 후보에서 뺌.

**선택: A.** 사진이 대부분 나무 결을 담은 실물 사진이라 압축 효율 차이가 그대로 전송량 차이가 됨. 운영자가 PNG로 올린 사진도 WebP가 되면 크게 줄어듦.

**A가 치르는 비용.** 변환 도구를 하나 더 들여야 함. libvips의 `vips thumbnail` 명령을 골랐고, 줄이기·회전 반영·메타데이터 제거·색 공간 맞추기·WebP 저장을 한 번에 함. 대신 API 실행 이미지가 약 160MB 커짐(딸려 오는 패키지 118개). 도구가 없는 환경(컨테이너 밖에서 띄운 개발 서버)에서는 변환 없이 원본만 저장하고 원본을 그대로 보내도록 해서 개발은 막지 않음. 운영 이미지는 빌드할 때 `vips --version`을 실행해 도구가 빠지면 빌드가 실패하게 함.

화질은 80으로 둠. 옛 사진 15장으로 재 보니 72·76·80에서 큰 벌 합계가 655KB·709KB·837KB였고, 가장 높은 80에서도 원본 합계(1,325KB)의 63%였음.

## 6. 원본 보존

| 기준 | A. 원본 보관 | B. 변환 후 삭제 |
|---|---|---|
| 크기 기준을 바꿀 때 | 원본에서 다시 만듦 | 이미 줄인 것에서 다시 줄여야 함. 키울 수는 없음 |
| 더 좋은 형식이 나올 때 | 원본에서 새로 변환 | 손실이 겹침 |
| 저장 공간 | 사진당 최대 5MB 추가 | 변환본만 |
| 노출 위험 | 원본에 위치 정보가 남아 있음. 밖으로 내보내면 안 됨 | 없음 |

**선택: A.** 사진 수가 수백 장 규모라 원본을 다 남겨도 몇 GB를 넘지 않음. 원본은 내려받는 주소를 만들지 않고 서버 안에만 둠.

**A가 치르는 비용.** 디스크 사용량이 변환본만 둘 때보다 몇 배가 됨. 백업 대상도 그만큼 커짐. 그리고 "원본을 내보내지 않는다"를 코드가 지켜야 함. 크기를 지정하지 않은 예전 주소로 요청해도 큰 벌을 보내고, 원본은 변환본이 없는 사진에만 대신 보냄.

## 7. 변환을 실행하는 시점

| 기준 | A. 업로드 요청 안에서 바로 | B. 일단 저장하고 뒤에서 변환 |
|---|---|---|
| 업로드 응답 시간 | 변환이 끝날 때까지 기다림(장당 1초 안팎 예상) | 바로 응답 |
| 올린 직후 화면 | 세 벌이 이미 있음 | 아직 없을 수 있음. "준비 중" 상태와 대체 표시가 필요 |
| 실패 처리 | 그 자리에서 오류로 알림 | 나중에 실패하면 알릴 길이 필요. 재시도 관리 |
| 필요한 부속 | 없음 | 작업 대기열과 상태 컬럼 |
| 동시 업로드가 많을 때 | 요청이 줄을 섬 | 대기열이 흡수 |

**선택: A.** 큐도 Redis도 없는 구성이고, 올리는 사람이 한 명이라 줄 설 일이 드묾. 실패를 올린 사람이 바로 아는 것이 가장 단순한 오류 처리임.

**A가 치르는 비용.** 여러 장을 한꺼번에 올리면 마지막 장은 몇 초를 기다림. 그리고 변환하는 동안 DB 연결과 행 잠금을 쥐고 있지 않도록 순서를 잡아야 함. 업로드는 세 단계로 나눔. 먼저 잠금 없이 업로드 티켓과 파일을 확인하고, 트랜잭션 밖에서 변환하고, 마지막에 티켓 행을 잠가 다시 확인한 뒤 저장함. 다시 확인하는 이유는 변환하는 사이에 같은 티켓으로 다른 요청이 먼저 끝났을 수 있기 때문임.

## 8. 세 벌을 가리키는 방법

| 기준 | A. 파일 이름 규칙(`product/<id>-s.webp`, `-m`, `-l`) | B. DB에 변환본 목록 저장 |
|---|---|---|
| 조회 | 원래 키에서 이름을 계산. DB를 읽지 않음 | 사진마다 한 번 더 읽거나 조인 |
| 기존 데이터 | 상품·글·주문에 저장된 키를 바꾸지 않아도 됨 | 키를 참조하는 모든 곳에 연결 필요 |
| 크기 종류 변경 | 규칙을 바꾸고 일괄 변환 | 행을 추가 |
| 벌마다 다른 정보(실제 크기 등) | 저장할 곳이 없음 | 저장 가능 |
| 없는 벌 처리 | 파일이 없으면 원본으로 대체하는 규칙 필요 | 목록에 없으면 없음이 분명 |

**선택: A.** 상품 사진, 글 본문, 주문 스냅샷이 이미 사진 키 문자열을 들고 있음. 키는 그대로 두고 "이 키의 작은 벌"을 이름으로 찾게 하면 기존 데이터에 손을 대지 않음. 스키마 변경도 없음.

- 저장: `product/<id>.jpg` 옆에 `product/<id>-s.webp`, `-m.webp`, `-l.webp`.
- 주소: 원래 주소에 `?size=s|m|l`을 붙임. 붙이지 않으면 큰 벌. 접근 권한은 지금처럼 원래 키로 판단하므로 권한 코드는 바뀌지 않음.
- 웹: `storageUrl(key)`를 `storageUrl(key, 's')`로 넓힘.
- 옛 사진(`/images/a.jpg`)의 변환본은 업로드 저장소의 `legacy/a.jpg-s.webp`에 둠. 확장자만 다른 파일끼리 겹치지 않게 원래 확장자를 이름에 남김.

글 본문 HTML 안의 사진 주소에는 `size`를 붙이지 않음. 공지·FAQ 사진의 공개 여부를 본문의 `src` 문자열과 그대로 비교해 판단하고 있어서, 주소가 달라지면 그 판단이 깨짐. 본문 사진은 큰 벌을 받음.

**A가 치르는 비용.** 사진의 실제 가로·세로를 알 수 없어 자리 비율을 미리 잡지 못함. 필요해지면 그때 크기 컬럼을 추가함.

## 9. 브라우저가 고르는 방식

| 기준 | A. `srcset`으로 세 벌을 후보로 주고 브라우저가 선택 | B. 화면마다 벌을 하나 정해 줌 |
|---|---|---|
| 고해상도 화면 | 한 단계 큰 벌을 자동으로 고름 | 흐리거나, 모두에게 큰 것을 줘야 함 |
| 휴대폰과 PC | 실제 표시 크기에 맞춰 고름 | 한 가지로 고정 |
| 코드 | 사진 컴포넌트 하나에 규칙을 모음 | 화면마다 `'small'`·`'large'`를 적음 |
| 예측 가능성 | 어떤 벌이 갈지 기기에 따라 다름 | 항상 같음 |

**선택: A.** 웹에는 이미 `sizes`가 적혀 있고 후보만 없었음. 세 벌을 후보로 넣으면 지금 코드가 그대로 살아남. 주문 내역의 작은 썸네일처럼 크기가 고정된 자리는 B처럼 작은 벌을 직접 지정함.

Next의 이미지 설정에서 자체 변환을 끄는 대신 로더를 직접 지정함. 후보 폭을 400·800·1600 세 가지로 맞추고, 로더는 요청 폭을 `size=s|m|l`로 바꿔 줌. 그러면 `next/image`가 만드는 `srcset`이 `...?size=s 400w, ...?size=m 800w, ...?size=l 1600w`가 됨. 화면 쪽 코드는 사진마다 붙어 있던 `unoptimized`를 떼는 것으로 끝남.

**A가 치르는 비용.** 화면 폭의 2배 밀도를 가진 휴대폰은 카드 사진으로 중간 벌을 고름. "썸네일은 항상 작은 벌"보다 전송량이 늘지만 화질을 위해 받아들임.

## 10. 캐시

세 벌을 만들어도 볼 때마다 다시 받으면 효과가 절반임. 지금은 모든 사진이 `no-store`임.

| 기준 | A. 공개된 사진은 오래 캐시, 비공개는 지금처럼 | B. 전부 지금처럼 매번 확인(`no-store`) |
|---|---|---|
| 다시 방문할 때 | 받지 않음 | 전부 다시 받음 |
| 요청마다 DB 확인 | 공개 사진은 CDN·브라우저가 대신 응답 | 매번 실행 |
| 비공개 글의 사진 | 공개 전에는 캐시하지 않음 | 보호됨 |
| 숨긴 뒤의 사진 | 이미 받아 간 사람의 캐시에는 남음 | 바로 막힘 |
| 사진 교체 | 새로 올리면 키가 새로 생겨 주소가 바뀜. 캐시가 꼬이지 않음 | 해당 없음 |

**선택: A.** 사진 키는 올릴 때마다 새로 만들어지는 UUID라 같은 주소의 내용이 바뀌지 않음. 그래서 공개 사진은 길게 캐시해도 안전함. 접근 확인은 유지하되, 공개로 판정된 응답에만 캐시를 허용함.

**A가 치르는 비용.** 상품이나 글을 숨겨도 이미 사진을 받은 브라우저와 CDN에는 캐시 기간 동안 남음. 숨기는 즉시 사라져야 하는 사진이 있다면 이 방식은 맞지 않음. 그래서 캐시 기간은 하루(`public, max-age=86400`)로 시작함. 운영자만 볼 수 있는 사진(아직 붙이지 않았거나 숨긴 상품의 사진)과 본인 주문 내역으로만 볼 수 있는 사진은 지금처럼 `no-store`임.

접근 확인 순서도 바뀜. 전에는 운영자면 바로 통과시켰는데, 이제는 공개 여부를 먼저 봄. 운영자가 공개 사진을 요청했을 때도 캐시할 수 있는 응답인지 알아야 하기 때문임.

## 11. 이미 올린 사진

| 기준 | A. 한 번 일괄 변환 | B. 새로 올리는 사진부터만 |
|---|---|---|
| 적용 직후 | 모든 사진에 세 벌이 있음 | 옛 사진은 원본으로 대체 표시 |
| 코드 | 벌이 없을 때의 대체 규칙이 필요 없거나 단순 | 대체 규칙을 계속 유지 |
| 실행 부담 | 지금은 17장. 몇 초 | 없음 |
| 옛 사진(`/images/...`) | 같은 규칙으로 변환해 둠 | 그대로 |

**선택: A.** 사진이 적은 지금이 일괄 변환 비용이 가장 쌈. 다만 변환이 실패한 사진이 있어도 화면이 깨지지 않도록, 작은 벌이 없으면 원본을 보내는 대체 규칙은 함께 둠.

일괄 변환은 API의 일회성 명령(`optimize-images`)으로 만듦. 세 벌이 모두 있는 사진은 건너뛰므로 여러 번 돌려도 결과가 같고, 한 장이 실패해도 나머지를 계속 처리함.

**A가 치르는 비용.** 변환 명령을 한 번 돌려야 하고, 돌리는 동안 서버 CPU를 씀. 사진이 수천 장으로 늘어난 뒤에 기준을 바꾸면 이 비용이 커짐.

## 측정 결과

실행 이미지(libvips 8.18, ARM 컨테이너)로 API를 띄우고 실제 요청으로 확인함. 휴대폰급 사진은 구하지 못해 옛 사진을 4000×3000으로 키우고 잡음을 섞어 만든 4.8MB JPG를 씀. 잡음 때문에 실제 사진보다 잘 줄지 않는 쪽으로 치우친 값임.

## 남는 위험

- 크기 세 가지는 지금 화면 구성에 맞춘 값임. 화면이 바뀌면 다시 재야 함.
- 이미 강하게 압축된 작은 사진은 같은 크기의 WebP가 원본보다 조금 커질 수 있음. 옛 사진 15장 중 한 장이 그랬음(259KB → 274KB). 원본을 내보내지 않기로 했으므로 그대로 둠.
- 공유 미리보기(카카오톡 등)에 쓰는 대표 사진 주소도 이제 WebP를 받음. WebP를 읽지 못하는 서비스가 있으면 미리보기 사진이 비어 보일 수 있음. 배포 후 실제 공유로 확인이 필요함.
- 변환 도구가 사진을 읽다가 생기는 문제는 프로세스 분리와 20초 제한으로 막지만, 사진을 올리는 사람이 운영자라는 전제에 기대고 있음. 방문자가 사진을 올리는 기능을 만들면 픽셀 수 제한을 먼저 넣어야 함.
- 원본을 남기므로 디스크와 백업 용량이 사진 수에 비례해 늘어남. 붙이지 않고 버린 업로드 파일이 쌓이는 문제(코드 리뷰에서 나온 항목)와 함께 정리 작업이 필요함.
- 캐시를 켜면 숨김이 즉시 반영되지 않음. 캐시 기간이 그 지연의 상한임.
- 운영 앞단의 CDN은 사진 주소(`.jpg` 등으로 끝나는 주소)의 404도 캐시함. 오류 응답에 캐시 지시가 없어서 CDN이 브라우저에 `max-age=14400`(4시간)을 붙이고, 로그인 쿠키가 있어도 같은 404를 돌려줌. 공개 전이나 숨긴 사진을 한 번 요청한 브라우저는 공개된 뒤에도 최대 4시간 동안 사진이 비어 보일 수 있음. 이미지 최적화 전부터 있던 동작이며, 모든 응답의 기본값을 `no-store`로 바꿔 고침([CDN 뒤의 응답 캐시: 기본값을 저장 금지로](/ken-blog/post/post-b4f19d3c-62a8-4e7d-95b1-0c8a7e3f5d26/)).
