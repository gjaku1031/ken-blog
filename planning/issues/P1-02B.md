# P1-02B: Spring Data JPA Repository 전환과 도입 이력 정정

상태: **구현·로컬 검증·이력 재작성 완료 — 원격 반영 대기**

## 문제와 목적

“인터페이스 없이 작성”의 적용 범위를 Service뿐 아니라 JPA Repository까지 확대한 상태. 직접 구현한 `EntityManager` 기반 저장소를 Spring Data JPA 인터페이스로 전환하고, 해당 구현·규칙이 처음 들어간 커밋부터 정정. Service는 구체 클래스, Swagger Controller 계약은 인터페이스 유지. 후속 수정 커밋만 추가하고 끝내는 방식 아님.

이번 공유 이력 재작성과 필요한 main 강제 푸시는 사용자 명시적 허용 범위. 실제 실행은 이 계획 승인 후 진행. 저장소 삭제·재생성·무관한 커밋 정리 없음.

## 구현 범위

### 저장소와 호출부

- `PostRepository : JpaRepository<PostEntity, Long>`와 `AccountRepository : JpaRepository<UserEntity, Long>` 인터페이스 사용.
- 직접 작성한 `persist`, `flush`, 기본키 조회, `count` 구현 제거. 상속받는 기본 CRUD를 설명용으로 재선언하거나 래핑하지 않음.
- `findBySlug(slug: String): PostEntity?`, `findByUsername(username: String): UserEntity?` 파생 쿼리 선언. 현재 조건에서는 별도 `@Query` 필요 없음. 사용자명 대소문자 비교는 기존 스키마의 collation과 정확 일치 조건 유지.
- `PostService`, `AccountService`는 구체 클래스 유지. 인증의 `SecurityUserDetailsService` 조회 경로와 Swagger 계약 유지.
- Custom Repository, 공통 Repository 부모 인터페이스, Service 인터페이스, 엔티티 `Persistable` 구현 추가 없음.
- Kotlin·기능별 패키지 유지. 인터페이스와 직접 선언한 조회 메서드 및 변경한 Service 선언에 한국어 KDoc 작성. 상속 메서드의 설명은 KDoc 심볼 링크로 연결.

### 저장 의미·flush·트랜잭션

현재 두 `save`는 항상 `persist` 후 즉시 `flush`. 단순히 Spring Data의 `save` 호출로 바꾸면 예외를 관찰하는 위치가 달라질 수 있으므로 다음과 같이 유지.

| 항목 | 변경 후 계약 |
| --- | --- |
| 신규 여부 | 두 엔티티는 nullable `Long` ID와 `IDENTITY`, Version 필드 없음. 서비스에서 새 엔티티의 ID가 null인 현재 생성 흐름 유지 |
| persist / merge | Spring Data는 신규 엔티티에 persist, 기존 엔티티에 merge 사용. 기존 서비스는 생성만 제공하므로 신규 경로 유지. ID를 가진 분리 엔티티의 새 수정 API 추가 없음 |
| 반환 객체 | 저장 메서드가 반환한 엔티티 사용. merge까지 항상 입력과 동일 객체를 반환한다고 문서화하지 않음 |
| 저장 시점 | 게시글 생성과 초기 관리자 생성에서 `saveAndFlush` 사용. IDENTITY의 조기 INSERT 가능성과 별개로 제약 검사 경계를 명시 |
| flush와 commit | flush는 SQL 동기화이며 커밋 아님. 같은 영속성 컨텍스트의 다른 변경도 flush될 수 있음. 기존 동작과 외부 트랜잭션 롤백 유지 |
| 오류 번역 | `PostService.createDraft`의 try/catch 안에서 `saveAndFlush` 호출. MySQL 1062 및 `uk_posts_slug`만 `DuplicatePostSlugException`으로 변환, 다른 DB 오류는 기존대로 전파 |
| 트랜잭션 경계 | 쓰기 Service의 `@Transactional`, 조회 Service·인증 조회의 `readOnly = true` 유지. 파생 쿼리는 호출부 트랜잭션 안에서 실행. `REQUIRES_NEW`나 수동 트랜잭션 추가 없음 |
| Optional | 상속 `findById` 결과를 Kotlin `findByIdOrNull` 확장으로 변환. Service의 잘못된 ID·없는 행 → null 계약 유지. `Optional.get()`·강제 non-null 사용 없음 |

`saveAndFlush`로 모든 DB 오류가 커밋 전에 발생한다고 보장하지 않음. 여기서 보존할 계약은 현재 MySQL 고유 제약 위반의 번역 시점과 트랜잭션 롤백. 계정 초기화의 충돌·실패에 따른 기동 중단 및 기존 비밀번호 해시 보존도 유지.

Flyway V1~V3·엔티티 스키마·Spring Session JDBC·세션 정리·쿠키·CSRF·권한·ProblemDetail 계약 변경 없음. Spring Data REST와 게시글 HTTP 경로 추가 없음.

각 기존 커밋의 author 이름·이메일·author date·영어 Conventional Commit 메시지와 기능별 구분 유지. committer date는 실제 재작성 시각 사용. 이번 계획·검증 기록을 남기는 추가 문서 커밋은 가능하나, 구현 수정을 그 커밋에만 몰아넣지 않음. 추가 기록 커밋은 실제 작업일 사용, 기존 5~6월 author date와 구분.

GitHub의 과거 Actions 실행·push 이벤트·기존 SHA 링크는 새 이력으로 바뀌지 않음. 과거 실행 링크는 원래 코드의 증거로 남기고, 새 SHA에 대한 결과는 실제 재검증 시각으로 별도 기록. 과거 커밋에 서명이 있다면 재작성 후 기존 서명이 유지되지 않으므로 실행 전 유무 확인. 다른 로컬 clone/브랜치는 기존 이력에 남으므로 자동 병합하지 않도록 전환 안내 포함.

## 백업·재작성·원격 반영 절차

아래는 승인 후 수행할 절차이며 현재 실행 결과 아님.

1. 원격 main·HEAD·index·worktree 상태 재확인. 계획의 예상 원격 SHA와 달라지면 이력 재작성·덮어쓰기 중단 후 변경 내용 보고.
2. 저장소 밖의 날짜별 백업 디렉터리 생성, 접근 권한 제한. 기존 main을 가리키는 로컬 backup ref와 전체 기존 이력을 포함한 Git bundle 생성 후 `git bundle verify` 실행. 기존 ref·31개 커밋 순서·author 정보·서명 여부 목록 저장. 백업 ref를 원격에 푸시하지 않음.
3. index/worktree의 binary diff, 미추적 계획 파일 및 P1-03·tasks·roadmap 원본 사본 보관. 로컬 AGENTS·학습 문서와 Git 제외 설정도 별도 보관. `git bundle`에 미커밋·Git 제외 파일이 포함되지 않는 점을 구분. 외부 비밀 설정은 읽거나 백업에 수집하지 않음.
4. 깨끗한 별도 worktree와 `codex/p1-02b-spring-data-jpa` 브랜치에서 구현·검증. 현재 작업 디렉터리의 미완료 변경은 그대로 보존. 완성한 수정은 검토 가능한 패치로 확보.
5. 검토한 패치를 도입 시점별로 나누고 별도 재작성 브랜치에서 root부터 순서대로 재구성. 최초 도입 당시 패키지 경로로 수정한 뒤 후속 패키지 이동을 재적용. 최종 파일을 과거 커밋에 통째로 덮어써 후속 기능이 먼저 들어가지 않도록 관리.
6. 기존 SHA→새 SHA 매핑과 커밋별 변경 비교 생성. 최종 tree를 검증한 구현 tree와 비교하고, 각 시점에서 불필요한 변경이 섞이지 않았는지 원래 patch와 대조. 코드 도입·패키지 이동·최종 상태의 빌드 확인. 전체 과거 커밋을 모두 테스트했다고 기록하지 않음.
7. 최종 로컬 검증 통과 후, 현재 계획·이번 실제 결과 문서만 목적별로 기록. 기존 P1-03 미완료 패치는 커밋 대상에서 제외. 최종 후보 SHA 고정.
8. 푸시 직전 `git ls-remote origin refs/heads/main` 재확인. 예상 SHA가 정확히 일치할 때 아래 명시적 lease로 main 한 ref만 갱신. 일반 `--force`, 인자 없는 lease, `--mirror`, 백업 ref 동시 푸시 사용 없음.

```bash
git push origin <검증한-새-HEAD>:refs/heads/main \
  --force-with-lease=refs/heads/main:daf74882d2a71e9a568b9cc4fa21a74e8992ae2d
```

9. lease 거절 시 새 SHA로 기대값만 바꿔 재시도하지 않음. 원격의 다른 변경을 먼저 확인·보고. 사전 확인 뒤 발생한 경쟁 변경도 lease로 보호.
10. 성공 후 원격 SHA·새 CI·Pages 확인. 로컬 main을 새 이력에 맞추되, 보관한 P1-03 작업을 파일별 3-way 비교로 복원. 작업 목록·로드맵의 이번 작업 상태만 갱신하고 이미지 계획의 미완료 내용은 계속 미커밋 유지. 무조건 `reset --hard`·`stash pop`으로 덮어쓰지 않음.

### 복구

- 푸시 전: 별도 worktree의 작업을 멈추고 기존 main·원본 작업 디렉터리 사용. bundle에서 새 디렉터리로 clone 가능한지와 미완료 패치/사본 복구 가능 여부 확인.
- 푸시 후: 백업 ref에서 기존 main 복구 가능. 원격을 되돌려야 한다면 그때의 원격 SHA가 이번 푸시 결과인지 확인하고, 그 SHA를 기대값으로 한 명시적 lease만 사용. 다른 사람의 후속 변경이 있으면 자동 복구 푸시 중단.
- 실패 증거와 백업은 완료 보고까지 보존. 검증 실패를 해결하지 않은 상태에서 재작성 이력을 밀어 넣지 않음.

## 검증 계획

신규 테스트 코드·테스트 메서드·새 HTTP probe 작성 없음. 기존 테스트는 저장소 전환에 필요한 참조·반환 처리만 수정. 기존 배포 앱·DB·Redis 컨테이너와 외부 운영 설정 변경 없음.

1. 기존 MySQL Testcontainers 구성을 사용해 API `./mvnw -B clean verify` 실행. 기존 게시글·계정·인증·HTTP 계약 검사 확인. 리소스는 직렬 실행 등으로 조절하며 실행하지 않은 검사는 명시.
2. 게시글 기존 검사로 정규화·ID/slug 조회·고유 제약 예외·같은 외부 트랜잭션 전체 롤백 확인. ID nullable 조건·saveAndFlush 반환값·Optional 변환·프록시 예외 번역은 코드와 실제 검사 결과 함께 리뷰.
3. 기존 계정 검사로 관리자 초기 생성·기존 해시 유지·권한 자동 승격 거부 확인. 계정 조회 및 로그인에 파생 쿼리가 실제 사용되는지 확인.
4. 별도 MySQL·API 프로세스·계정·포트에서 실제 HTTP health/status, CSRF 발급, 로그인, 세션 ID 교체, 현재 사용자, 잘못된 인증/CSRF, 로그아웃과 이전 쿠키 거부 확인. 실제 배포 컨테이너를 재시작하지 않음.
5. 격리 API만 재시작해 동일 세션 유지 확인. 격리 MySQL만 일시 중단해 기존 503 ProblemDetail 확인 후 복구. 토큰·해시·비밀값 로그 기록 없음.
6. 게시글 HTTP API는 아직 없으므로 HTTP로 게시글 저장을 확인했다고 기록하지 않음. 저장·조회 검증은 기존 통합 테스트의 증거로 보고.
7. 재작성된 게시글 도입 커밋·계정 도입 커밋·패키지 이동 커밋은 컴파일/패키징 확인. 최종 재작성 후보가 검증한 코드와 일치하는지 확인하고 새 원격 CI·Pages 성공 및 공개 홈 HTTP 응답 확인.
8. 작업 전후 기존 컨테이너 ID·이미지·StartedAt·상태 비교. 이번에 만든 컨테이너·볼륨·임시 파일만 정리. AGENTS·study가 Git 추적에 들어가지 않았는지 확인.
