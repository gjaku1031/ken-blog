[0편](/ken-blog/post/post-df978c72-44d3-4e81-b572-8834cd0646c3/)에서 "서버가 보는 상대방은 바로 앞 칸"이라는 말이 계속 걸렸다. 그렇다면 내가 만든 API에서 `request.getRemoteAddr()`로 IP를 읽으면 사용자 IP가 아니라 프록시 IP가 나오는 걸까. 그리고 사용자 IP를 대신 알려 준다는 `X-Forwarded-For`는 믿어도 되는 값일까. 이번 편은 그 두 질문을 따라갔다.

## 학습 목표

- 포워드 프록시와 리버스 프록시를 "누구 편에 서 있는가"로 구분할 수 있다
- 리버스 프록시 뒤의 서버가 보는 연결 상대 주소와 `X-Forwarded-For`가 어떻게 만들어지는지 설명할 수 있다
- `X-Forwarded-For`에서 믿을 수 있는 칸을 오른쪽부터 골라낼 수 있다

## 프록시: 대신 전달해 주는 서버

프록시(proxy)는 "대리인"이라는 뜻이다. 요청을 받아서 자기가 대신 다른 서버에 보내고, 받은 응답을 다시 돌려준다. 처음엔 프록시가 하나의 물건인 줄 알았는데, 어느 쪽 편에 서 있느냐에 따라 두 가지로 나뉜다.

| 구분 | 누구 편 | 상대가 모르는 것 |
| --- | --- | --- |
| 포워드 프록시 | 사용자 | 서버는 진짜 손님이 누군지 모름 |
| 리버스 프록시 | 서버 | 사용자는 안쪽 담당자(서버)가 몇 명이고 어디 있는지 모름 |

회사나 학교 망에서 밖으로 나갈 때 거치는 프록시가 포워드 프록시이고, 서비스 앞에 세워 두는 nginx 같은 서버가 리버스 프록시다. 이 시리즈에서 따라가는 길에 나오는 건 리버스 프록시다.[* 포워드 프록시는 사용자가 브라우저나 운영체제에 "이 프록시를 거쳐라"라고 설정해서 쓴다. 리버스 프록시는 사용자가 존재를 모르는 채로 거친다. DNS가 프록시의 주소를 알려 주기 때문이다]

### 리버스 프록시가 하는 일

리버스 프록시는 요청을 넘기기만 하지 않고, 넘기면서 여러 일을 한다.

- **나눠 주기(로드 밸런싱)**: 같은 일을 하는 서버 여러 대에 요청을 골고루 나눈다.
- **자물쇠 풀기(TLS 종료)**: HTTPS의 암호화를 프록시에서 풀고, 뒤쪽 서버에는 평문 HTTP나 다시 암호화한 연결로 넘긴다. 자물쇠를 다는 일은 [8편](/ken-blog/post/post-fe24a8b3-892f-4e3f-aeb6-13437ed47aaa/)에서 다룬다.
- **직접 응답하기**: 이미지, CSS 같은 정적 파일은 뒤로 넘기지 않고 프록시가 바로 돌려줄 수 있다.
- **안쪽 숨기기**: 뒤쪽 서버의 주소와 개수가 바깥에 드러나지 않고, 바깥에서 직접 들어올 길을 막을 수 있다.

[6편](/ken-blog/post/post-5b5ec693-9a31-4a67-9053-0381b98c9ddf/)의 CDN도 넓게 보면 원 서버 앞에 선 리버스 프록시다. 사본을 들고 있다는 점이 다를 뿐이다.

## 서버가 보는 "상대방"

서버 프로그램이 "상대방 주소"라고 알 수 있는 건 TCP 연결을 맺은 상대의 주소뿐이다.[* 연결 상대 주소(remote address, peer address): TCP 연결의 반대편 IP와 포트. Servlet에서는 `HttpServletRequest#getRemoteAddr()`, nginx에서는 `$remote_addr`가 이 값이다] 리버스 프록시 뒤에 있으면 그 상대는 언제나 프록시다.

그래서 프록시는 "원래 보낸 사람"을 헤더에 적어서 넘긴다.

| 헤더 | 담는 것 | 왜 필요한가 |
| --- | --- | --- |
| `X-Forwarded-For` | 지나온 주소 목록. 프록시마다 자기가 본 연결 상대 주소를 오른쪽 끝에 덧붙임 | 뒤쪽 서버가 실제 사용자 IP를 알려고 |
| `X-Forwarded-Proto` | 원래 요청의 스킴(`http`, `https`) | 프록시가 TLS를 풀면 뒤쪽은 늘 `http`로 받기 때문 |
| `X-Forwarded-Host` | 원래 요청의 `Host` | 프록시가 `Host`를 바꿔 넘길 때 |
| `Forwarded` | 위 세 가지를 한 헤더에 담은 표준 형식. `for=203.0.113.7;proto=https` | `X-` 헤더들이 표준이 아니어서 RFC 7239로 정리함 |

`X-` 헤더들은 원래 표준이 아니었는데 워낙 널리 쓰여서 사실상 표준이 됐다. 표준인 `Forwarded`가 따로 있지만 실제로는 `X-Forwarded-For`를 더 많이 보게 된다.[* `Forwarded` 헤더는 RFC 7239(2014)에서 정의했다. 프록시와 프레임워크마다 어느 헤더를 읽고 쓰는지가 다르므로 설정을 확인해야 한다]

Spring에서 `getRemoteAddr()`가 이 헤더를 반영할지는 설정에 달려 있다. 아무 설정이 없으면 연결 상대, 즉 프록시 주소가 나온다.[* Spring Boot의 `server.forward-headers-strategy` 설정. `native`면 Tomcat이, `framework`면 Spring의 `ForwardedHeaderFilter`가 전달 헤더를 반영한다. 지정하지 않으면 클라우드 플랫폼에서 실행될 때만 반영한다] 내가 처음 품었던 의문의 답은 "설정하기 전에는 프록시 IP가 나온다"였다.

### 헷갈렸던 것: 왼쪽 첫 칸이 사용자 IP가 아니다

`X-Forwarded-For: 203.0.113.7, 198.51.100.10` 같은 값을 보고 처음엔 "맨 왼쪽이 원래 사용자구나" 하고 끝냈다. 그런데 이 헤더는 그냥 글자다. 사용자가 요청을 보낼 때 아무 값이나 적어 넣을 수 있고, 프록시는 받은 값의 **오른쪽에 덧붙일** 뿐 왼쪽에 있던 걸 지우지 않는다.

![클라이언트가 X-Forwarded-For에 1.2.3.4를 적어 보내면, 프록시 A와 B는 각자 본 연결 상대 주소를 오른쪽에 덧붙인다. 애플리케이션 서버에 닿은 목록에서 믿을 수 있는 건 믿는 프록시들이 적은 오른쪽 칸뿐이다|dark=176|w=100|a=center](attachment:175)

그래서 믿을 수 있는 값을 고르는 방법은 오른쪽부터 읽는 것이다.

1. 맨 오른쪽 칸은 바로 앞 프록시(B)가 적었다. B가 본 연결 상대, 즉 A의 주소다.
2. A도 내가 믿는 프록시라면 한 칸 더 왼쪽으로 간다. 그 칸은 A가 본 연결 상대, 즉 실제 사용자 주소다.
3. 믿는 프록시가 아닌 쪽이 적은 칸이 나오면 거기서 멈춘다. 그보다 왼쪽은 누가 적었는지 알 수 없다.

그럼 믿는 프록시가 적은 칸은 왜 믿어도 될까. 프록시가 적는 값은 받은 글자가 아니라 자기와 TCP 연결을 맺은 상대의 주소다. [1편](/ken-blog/post/post-adf39eb5-c2bf-4064-b443-e89613393020/)의 handshake에서 서버의 SYN-ACK는 SYN에 적힌 보낸 주소로 간다. 보낸 주소를 남의 것으로 적으면 답장이 그쪽으로 가 버려서, 위조한 쪽은 서버의 시작 번호를 모르고 마지막 ACK를 맞게 보낼 수 없다. 그래서 연결이 열렸다면 상대 주소는 진짜다.[* 답장이 지나는 길목에서 패킷을 엿볼 수 있는 위치라면 이야기가 다르다. TCP가 시작 번호를 짐작하기 어렵게 고르는 것도 이런 위조를 막기 위해서다] 이 논리는 요청이 반드시 그 프록시를 거칠 때만 성립한다. 프록시를 건너뛰고 서버에 바로 닿을 수 있으면 사용자가 목록 전체를 마음대로 쓸 수 있다.

## 직접 확인해 보기

nginx 컨테이너 두 개로 실험했다. 하나(`app`)는 뒤쪽 서버 역할로, 받은 요청의 연결 상대 주소와 전달 헤더를 그대로 돌려준다. 다른 하나(`proxy`)는 리버스 프록시 역할로, 받은 요청을 `app`으로 넘긴다.[* 2026-10-23, Linux VM의 Docker에서 `nginx:alpine` 이미지(nginx 1.31.8)로 실행했고 요청은 curl 8.18.0으로 보냈다. 두 컨테이너는 Docker가 만든 가상 네트워크 안에 있다]

```text
# app: 받은 요청의 연결 상대와 전달 헤더를 그대로 돌려줌
server {
    listen 80;
    default_type text/plain;
    return 200 "remote_addr: $remote_addr\nX-Forwarded-For: $http_x_forwarded_for\nX-Forwarded-Proto: $http_x_forwarded_proto\n";
}

# proxy: app으로 넘기며 전달 헤더를 붙임
server {
    listen 80;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    location / { proxy_pass http://series-ep7-app:80; }
}
```

`$proxy_add_x_forwarded_for`는 "받은 `X-Forwarded-For` 뒤에 내가 본 연결 상대 주소를 덧붙인 값"이다. 이 컨테이너들 사이에서 `172.20.0.1`은 내 컴퓨터 쪽(curl), `172.20.0.3`은 프록시 컨테이너의 주소다.[* Docker의 포트 연결을 거쳐 들어온 요청은 컨테이너에서 보면 가상 네트워크의 게이트웨이 주소(`172.20.0.1`)에서 온 것으로 보인다]

```bash
curl -s http://127.0.0.1:18401/        # app에 직접
```

```text
remote_addr: 172.20.0.1
X-Forwarded-For:
X-Forwarded-Proto:
```

```bash
curl -s http://127.0.0.1:18402/        # proxy를 거쳐서
```

```text
remote_addr: 172.20.0.3
X-Forwarded-For: 172.20.0.1
X-Forwarded-Proto: http
```

```bash
curl -s -H 'X-Forwarded-For: 1.2.3.4' http://127.0.0.1:18402/    # 헤더를 위조해서
```

```text
remote_addr: 172.20.0.3
X-Forwarded-For: 1.2.3.4, 172.20.0.1
X-Forwarded-Proto: http
```

| 경우 | `app`이 본 연결 상대 | `X-Forwarded-For` | 알게 된 것 |
| --- | --- | --- | --- |
| 직접 | `172.20.0.1`(나) | 없음 | 프록시가 없으면 연결 상대가 곧 사용자 |
| 프록시 경유 | `172.20.0.3`(프록시) | `172.20.0.1` | 연결 상대는 프록시로 바뀌고, 내 주소는 헤더로만 전달됨 |
| 위조 헤더 | `172.20.0.3`(프록시) | `1.2.3.4, 172.20.0.1` | 프록시는 내가 쓴 `1.2.3.4`를 지우지 않고 오른쪽에 덧붙임 |

마지막 줄을 보고 확신이 들었다. 맨 왼쪽만 읽는 서버라면 나를 `1.2.3.4`로 믿었을 것이다.

nginx에는 이 헤더로 연결 상대 주소를 바꿔 주는 기능이 있어서, "누구를 믿을지"만 바꿔 같은 위조 요청을 보내 봤다.[* nginx의 `ngx_http_realip_module`. `set_real_ip_from`에 믿는 프록시 주소를, `real_ip_header`에 읽을 헤더를 적는다. `real_ip_recursive on`이면 오른쪽부터 믿는 주소를 건너뛰며 읽는다. `$realip_remote_addr`에는 바꾸기 전의 원래 연결 상대가 남는다]

```text
# 81번: 프록시(172.20.0.3)만 믿음
set_real_ip_from 172.20.0.3;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# 82번: 모든 주소를 믿음(잘못된 설정)
set_real_ip_from 0.0.0.0/0;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

```bash
curl -s -H 'X-Forwarded-For: 1.2.3.4' http://127.0.0.1:18402/trust-proxy
```

```text
remote_addr: 172.20.0.1 (realip_remote_addr: 172.20.0.3)
```

```bash
curl -s -H 'X-Forwarded-For: 1.2.3.4' http://127.0.0.1:18402/trust-all
```

```text
remote_addr: 1.2.3.4 (realip_remote_addr: 172.20.0.3)
```

프록시만 믿게 하면 위조한 `1.2.3.4`를 건너뛰고 실제 내 주소 `172.20.0.1`을 골라냈다. 모든 주소를 믿게 하면 오른쪽부터 읽어도 끝까지 믿고 넘어가서 위조 값이 사용자 IP가 됐다. 오른쪽부터 읽는 것만으로는 부족하고, **몇 칸까지 믿을지를 실제 프록시 구성에 맞춰 정해야** 한다는 걸 알게 됐다.

> 리버스 프록시 뒤의 서버가 보는 연결 상대는 늘 프록시다. 사용자 IP는 `X-Forwarded-For`로 전해지지만, 그 값은 누구나 적을 수 있으므로 믿는 프록시가 적은 오른쪽 칸만 골라 읽어야 한다.

## 확인 질문

**1. 포워드 프록시와 리버스 프록시는 무엇으로 구분할까?**

<details><summary>답</summary>

누구 편에 서 있는지로 구분한다. 포워드 프록시는 사용자 쪽에 서서 사용자를 대신해 밖으로 나가고, 리버스 프록시는 서버 쪽에 서서 서버를 대신해 요청을 받는다. 앞은 서버가 진짜 사용자를 모르고, 뒤는 사용자가 진짜 서버를 모른다.

</details>

**2. 리버스 프록시 뒤의 Spring 서버에서 아무 설정 없이 `getRemoteAddr()`를 부르면 누구의 IP가 나올까?**

<details><summary>답</summary>

프록시의 IP다. `getRemoteAddr()`는 TCP 연결 상대의 주소이고, 그 연결을 맺은 건 프록시이기 때문이다. 사용자 IP를 얻으려면 `server.forward-headers-strategy` 같은 설정으로 전달 헤더를 반영하게 해야 한다.

</details>

**3. 믿는 프록시가 두 대(바깥쪽 A, 안쪽 B)일 때, 서버에 `X-Forwarded-For: 1.2.3.4, 203.0.113.7, 198.51.100.10`이 왔다. 실제 사용자 IP는 무엇일까?**

<details><summary>답</summary>

`203.0.113.7`이다. 맨 오른쪽 `198.51.100.10`은 B가 적은 A의 주소이므로 건너뛰고, 그다음 칸은 A가 적은 값이라 믿을 수 있다. 맨 왼쪽 `1.2.3.4`는 누가 적었는지 알 수 없는 값이다.

</details>

**4. 프록시가 TLS를 풀어 주는 구성에서 `X-Forwarded-Proto`가 없으면 무엇이 곤란할까?**

<details><summary>답</summary>

뒤쪽 서버는 모든 요청을 `http`로 받기 때문에, 원래 요청이 `https`였는지 알 수 없다. 그러면 리다이렉트 주소를 `http://`로 만들거나, "HTTPS로만 허용" 같은 검사를 잘못 판단할 수 있다.

</details>

**5. 프록시 없이 인터넷에 바로 열려 있는 서버가 `X-Forwarded-For`의 값을 사용자 IP로 쓰면 어떤 일이 생길까?**

<details><summary>답</summary>

누구나 헤더에 원하는 IP를 적어 자기 IP인 척할 수 있다. 앞에 믿는 프록시가 없으니 그 헤더를 적은 건 사용자 자신이다. 이런 서버는 연결 상대 주소를 그대로 써야 한다.

</details>
