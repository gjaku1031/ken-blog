Next.js 웹과 Spring Boot API, PostgreSQL을 서버 한 대의 Docker Compose로 운영하는 쇼핑몰임. 결제 수단은 무통장 입금 하나이고, 운영자는 별도의 관리자 화면 없이 고객이 보는 화면에서 편집 모드를 켜 상품과 글을 고침. 사이트는 Cloudflare 뒤에 있음.

## 담당 범위

- **백엔드**: 주문, 재고, 계정, 게시글, 사진 저장을 맡는 API와 DB 스키마
- **인프라**: 서버 구성, 배포 절차, 운영 중 점검
- **설계 결정**: 재고를 빼는 시점과 미입금 주문의 회수, 사진 변환 방식, CDN 뒤의 응답 캐시 정책

## 의뢰 조건과 핵심 문제

의뢰인이 정한 조건은 두 가지였음. 결제는 무통장 입금만 받고, 운영자가 쓰는 관리자 화면을 따로 두지 않음.

설계 제약은 4가지.

- **주문과 입금 사이가 며칠 빔**: 고객이 주문한 뒤 계좌로 입금하고, 운영자가 통장을 보고 직접 확인함. 그사이 주문은 결제 대기 상태로 남음
- **재고가 적음**: 수제품이라 옵션 하나의 재고가 1~3개인 경우가 많음. 한 개 차이로 품절이 갈림
- **한 사람이 백엔드와 인프라를 맡음**: 예상 이용자가 월 50명에 못 미쳐, 서버 한 대와 PostgreSQL 하나로 구성하고 Redis와 메시지 큐를 두지 않음. 로그인 세션도 PostgreSQL에 저장함
- **고객에게 알릴 수단이 화면뿐임**: 가입할 때 이메일을 받지 않고 문자도 보내지 않음

이 제약에서 다음 3개 문제를 핵심 문제로 정의함.

- **P1 재고 정합성**: 마지막 한 개를 두 고객이 동시에 주문해도 한 명만 성공하고, 입금하지 않은 주문이 재고를 계속 붙잡지 않아야 함
- **P2 사진 전송량**: 운영자가 휴대폰으로 찍어 올린 사진을 목록, 썸네일, 상세 화면이 같은 원본으로 받지 않아야 함
- **P3 캐시된 응답의 노출**: CDN이 개인 정보가 든 응답이나 오류 응답을 저장해 다른 사람에게 돌려주지 않아야 함

## 핵심 문제별 설계와 검증

API의 자동 테스트는 아직 없고 뒤에 작성할 예정임. 아래의 검증은 실제 PostgreSQL에 API를 띄우고 요청을 보내 확인한 것임.

### P1. 주문할 때 재고를 빼고, 미입금 주문은 기한 뒤에 취소함

- **문제**: 입금을 확인할 때 재고를 빼면, 재고 1개에 주문이 여러 건 쌓이고 먼저 확인된 한 건만 성공함. 나머지 고객은 돈을 보낸 뒤에 품절을 알게 됨. 주문할 때 빼면 이 문제는 없지만, 입금하지 않은 주문이 재고를 계속 잡고 있음
- **결정**: 주문 트랜잭션이 옵션 행을 ID 순서로 잠근 뒤(`SELECT … FOR UPDATE`) 재고를 확인하고 뺌. 주문에는 입금 기한(주문일 + 설정 일수의 23:59)을 저장하고, 주기 작업이 기한이 지난 결제 대기 주문을 한 건씩 잠가 상태를 다시 확인한 뒤 취소함
  - 비교한 대안: 입금 확인 때 차감, 조건부 `UPDATE`, 낙관적 락, 별도의 재고 예약 테이블
  - 선택 이유: 실패가 돈이 오가기 전에 드러나고, 고객에게 알릴 수단이 화면뿐이라 입금 뒤의 품절을 수습하기 어려움. 경합이 "드문 충돌"보다 "한 명만 성공하는 경쟁"에 가까워 재시도가 필요한 낙관적 락은 맞지 않음
- **대가**: 기한 동안은 허수 주문이 재고를 잡을 수 있음. 한 회원이 넣을 수 있는 결제 대기 주문의 수는 아직 제한하지 않음
- **검증**: 재고 2개인 옵션에 주문 20건을 동시에 보냈을 때 2건이 성공하고 18건이 재고 부족으로 거절됨. 입금 확인과 자동 취소가 같은 주문에서 겹치면 먼저 잠근 쪽만 반영되고 재고가 한 번만 움직임[* 2026-10-11 로컬 PostgreSQL에서 확인. 입금 확인이 먼저인 경우와 자동 취소가 먼저인 경우를 각각 만들었음]

> 재고 수량을 바꾸는 모든 경로는 같은 트랜잭션에서 재고 이력을 남기고, 옵션마다 이력의 합이 현재 수량과 같음.

### P2. 사진을 올릴 때 세 크기로 변환해 둠

- **문제**: 올린 사진을 그대로 저장해, 120px 썸네일도 상세 화면의 큰 사진도 같은 원본을 받았음. 휴대폰 사진(3~5MB) 12장이 든 목록은 원본 12장을 내려받게 됨
- **결정**: 업로드 요청 안에서 서버가 WebP 세 벌(가로 400·800·1600px)을 만들고, 화면은 `srcset`으로 세 벌을 제시해 브라우저가 표시 폭과 화면 배율에 맞는 것을 고르게 함. 공개된 상품과 글에 쓰인 사진은 하루 동안 캐시를 허용함
  - 비교한 대안: 요청이 올 때 변환, 압축한 한 벌만 저장, 브라우저에서 줄여서 올리기
- **대가**: 사진 한 장의 업로드가 변환 시간만큼 길어짐. 캐시를 허용한 동안에는 사진을 숨겨도 이미 받아 간 쪽에 남음
- **검증**: 4.8MB 사진의 업로드가 2.1초에 끝나고 세 벌이 29KB, 202KB, 793KB로 만들어짐. 운영 사이트의 상품 목록(사진 12장)은 PC에서 119KB, 화면 배율 3인 휴대폰에서 432KB를 받음[* 변환 수치는 4000×3000 크기의 시험용 사진으로 ARM 컨테이너에서 잰 값. 목록 전송량은 2026-10-11 운영 사이트에서 브라우저로 잰 값]

### P3. API 응답의 기본값을 저장 금지로 둠

- **문제**: CDN은 주소가 `.jpg`처럼 끝나면 응답의 종류와 관계없이 저장함. API는 주소의 `;` 뒤를 버리고 처리하므로, `/api/orders/me;a.jpg` 같은 주소를 로그인한 사용자가 열면 그 사람의 주문 목록이 CDN에 저장되고, 같은 주소를 연 다른 사람이 그 응답을 받게 됨(Web Cache Deception). 없는 사진의 404도 4시간 동안 캐시되고 있었음
- **결정**: 요청을 처음 받는 필터가 모든 응답에 `Cache-Control: no-store`를 먼저 적고, 캐시해도 되는 응답만 처리하는 코드가 직접 바꿈. 지금 캐시를 허용하는 응답은 공개 사진 하나임
  - 비교한 대안: CDN 규칙으로만 막기, 오류 응답에만 붙이기, `;`가 든 주소를 거부하기
  - 선택 이유: 원 서버가 지시를 보내면 CDN 설정이 바뀌어도 유지됨. 기본값이 금지이면 새로 만든 응답이 실수로 캐시되지 않음
- **대가**: 방어선이 원 서버 한 겹임. CDN 쪽의 보호 규칙은 아직 켜지 않았음
- **검증**: 고치기 전의 운영 사이트에서 `/api/products;probe1.jpg`가 두 번째 요청부터 CDN에서 응답됨을 확인했고, 배포 뒤에는 같은 형태의 주소가 두 번 모두 `no-store`로 응답되고 CDN을 거치지 않음. 공개 사진은 그대로 캐시됨[* 2026-10-11. 개인 정보가 든 응답으로는 시험하지 않고 공개 상품 목록과 없는 주소로만 확인했음]
