배포는 워크플로를 수동으로 실행해야만 일어나고, 스키마 변경은 조건이 맞지 않으면 DB를 바꾸지 않고 API의 시작을 멈춤.

## 배포 흐름

```mermaid caption="main에 올려도 운영 서버는 바뀌지 않음. 배포 워크플로를 수동으로 실행하면 코드를 서버에 전달하고 서버에서 이미지를 빌드해 바꿈"
flowchart TD
    %% legend: round=시작·끝; diamond=판단
    start([배포 워크플로를 수동으로 실행])
    env{서버에 환경 파일이 있는가}
    stop([중단, 서버는 그대로])
    sync[코드를 서버로 전달]
    build[서버에서 Compose 이미지 빌드와 기동]
    migrate{API 시작: 스키마 변경과 검증을 통과하는가}
    health[상태 확인 주소가 응답할 때까지 대기]
    finish([배포 완료])
    down([API가 시작하지 못해 사이트가 멈춤, DB는 그대로])
    start --> env
    env -->|없음| stop
    env -->|있음| sync
    sync --> build
    build --> migrate
    migrate -->|통과| health
    migrate -->|실패| down
    health --> finish
```

- **검사**: PR과 push에서 웹의 타입 검사, API의 컴파일과 주석 규칙 검사, API의 단위 테스트와 통합 테스트, 빌드를 실행함. 통합 테스트는 PostgreSQL 컨테이너에 마이그레이션을 모두 적용한 뒤 API를 띄워 HTTP로 요청함
- **배포**: 수동 실행으로만 시작함. 환경 파일이 없으면 코드를 전달하기 전에 멈춤. 서버의 환경 파일은 전달 대상에서 빼 덮어쓰지 않음
- **기동**: 서버에서 이미지를 빌드해 컨테이너를 바꾸고, 컨테이너의 상태 확인이 통과할 때까지 기다림(최대 3분)

## 스키마 변경

스키마는 Flyway의 SQL 파일로만 바꾸고, API가 시작할 때 적용함. 엔티티에서 스키마를 자동으로 만들지 않고, 시작할 때 엔티티와 스키마가 맞는지만 검증함.

| 변경 | 중단 조건 | 중단하면 |
| --- | --- | --- |
| 재고에 `CHECK (stock >= 0)` 추가 | 음수 재고가 한 건이라도 있음 | DB는 아무것도 바뀌지 않고 API가 시작을 멈춤. 컨테이너는 이미 새 것으로 바뀐 뒤라 사이트가 멈추므로, 데이터를 고치거나 이전 이미지로 되돌려야 함 |
| 쓰지 않는 재고 예약 테이블 삭제 | 활성 예약이 남아 있음 | 같음 |
| 엔티티와 스키마의 검증 | 열이나 자료형이 다름 | API가 시작을 멈춤 |

입금 기한을 추가할 때는 이미 있던 결제 대기 주문에 "적용일 + 2일의 23:59"를 기한으로 줬음. 주문일 기준으로 계산하면 배포 직후에 오래된 주문이 한꺼번에 취소되기 때문임.

## 배포 뒤 확인

| 확인 | 방법 |
| --- | --- |
| API가 살아 있는지 | 상태 확인 주소 |
| 캐시 기본값이 빠지지 않았는지 | `/api/products;check.jpg` 같은 주소의 응답이 `no-store`이고 CDN이 저장하지 않는지 봄 |
| 사진 변환 도구 | 컨테이너에서 변환 도구의 버전과 시작 로그의 경고를 봄 |
| 재고와 이력 | 옵션마다 이력의 합이 재고와 같은지 조회함 |

## 한계

- 서버 한 대이고 컨테이너를 바꾸는 동안 요청이 끊김. 무중단 배포가 아님
- 이미지를 운영 서버에서 빌드함. 빌드하는 동안 서버의 자원을 씀
- 자동으로 되돌리는 절차는 없음. 이전 이미지로 돌아갈 때, 예약 테이블을 지운 변경처럼 스키마가 이전 코드와 맞지 않으면 테이블을 다시 만들어야 함
- 재고와 이력의 대조는 매시간 돌지만, 어긋남을 알리는 곳이 운영자의 첫 화면과 서버 로그뿐임. 밖으로 보내는 알림은 없음
- DB와 업로드한 사진의 백업을 하지 않음. 서버의 디스크가 손상되면 되살릴 방법이 없음
