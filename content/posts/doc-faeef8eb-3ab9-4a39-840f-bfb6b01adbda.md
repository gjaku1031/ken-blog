예약은 PostgreSQL 안에서 잠금과 제약으로 확정되지만(P1), 확정 문자와 시트 행은 DB 밖에 있어 같은 트랜잭션에 넣을 수 없음. P3은 이 경계에서 외부 결과를 알 수 없을 때 다시 보내지 않고 멈추는 쪽을 택한 결정임.

## P1. 회차 잠금과 멱등 키로 예약·입장을 한 번만 반영

### 문제

같은 예약을 여러 주체가 거의 동시에 바꿀 수 있음.

- 부모가 각자 휴대폰으로 같은 회차를 동시에 예약하거나, 한 사람이 예약 버튼을 연달아 누름
- 입구 스캐너가 응답을 받지 못해 같은 QR 요청을 다시 보냄
- 학부모가 회차를 옮기거나 취소하는 순간 입구에서 같은 예약의 QR을 찍음

검사 후 쓰기(check-then-act)를 트랜잭션 격리만 믿고 하면, 두 요청이 모두 "활성 예약 없음"을 읽고 둘 다 예약을 만들 수 있음. 재전송은 서버 입장에서 새 요청과 구분되지 않아 입장 사건이 두 번 남을 수 있음.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 애플리케이션 선조회만으로 중복 차단 | 동시 요청이 함께 선조회를 통과함. 구현 지침에서 DB 제약 없이 선조회만 쓰는 방식을 명시적으로 배제함[* [NestJS 인수인계서 5.2절](https://github.com/gjaku1031/npr-seminar/blob/92598e6/docs/specs/nestjs-backend-handoff.md)] |
| 회차별 정원 카운터 행을 두고 갱신 | 정원이 있던 설계에서 썼던 방식. 행사장 수용 인원이 충분해 정원을 없애면서 카운터 행이 직렬화 용도로만 남아, 회차 행 잠금으로 대신하고 테이블을 제거함 |
| **회차 행 잠금 순서 + 부분 유니크 인덱스 + 멱등 키 기록 (채택)** | 잠금으로 대부분의 경합을 줄 세우고, 놓친 경합은 DB 제약이 막음. 재전송은 저장한 결과를 그대로 돌려줌 |

변경 경로는 자기가 잠그는 행만 같은 순서로 잠금: 멱등 키 advisory lock → 스캐너 행 → 회차 행(ID 오름차순) → 예약 행 → QR 행. 예약 생성에는 스캐너·QR 행 잠금이 없고, 입장은 다섯 단계를 모두 거침. 회차 이동과 입장은 회차 두 개를 잠그므로 ID 순서를 지키지 않으면 서로 반대 순서로 잠가 교착이 생김. 잠근 뒤에는 예약의 회차를 다시 읽어, 조회와 잠금 사이에 다른 회차로 옮겨진 예약을 입장시키지 않음.

멱등 키는 키와 요청 본문 다이제스트를 결과와 함께 저장함. 같은 키와 같은 본문은 첫 결과를 재생하고, 같은 키에 다른 본문이 오면 409로 거절함. 입장 요청에서는 실제 입장 인원도 본문 다이제스트에 들어가, 인원만 바꾼 재요청이 이전 결과로 조용히 처리되지 않음.

### 대가

- 같은 회차의 예약·입장·이동이 회차 행에서 순서대로 처리됨. 행사 당일 처리량은 측정하지 않았음
- 멱등 기록은 24시간 보관하므로, 그 뒤 같은 키로 다시 보내면 새 요청으로 처리됨
- 재생 응답에는 QR·증명 원문이 없어, 화면이 별도 조회로 다시 받아야 함

## P2. 연락처를 암호문과 다이제스트로만 저장

### 문제

학부모는 계정 없이 연락처로 예약하므로, 연락처를 아는 사람이 남의 예약을 보거나 바꿀 수 없어야 함. 동시에 학생 원장에는 재원생 약 3,000명의 모·부 연락처가 들어오고, 예약 링크와 QR은 문자로 전달되어 URL·메시지·로그에 남기 쉬움.

### 검토한 대안

연락처 원문을 저장하지 않는다는 것은 처음부터 정했음. 고민한 것은 예약 링크를 열 때 어디까지 확인할지였음.

| 대안 | 판단 |
| --- | --- |
| 링크 열람에도 매번 문자 인증 | 같은 성격의 두 링크(확정 문자의 예약 링크, 개인 접근 링크) 중 하나만 인증번호를 요구했음. 열람은 링크와 연락처 확인으로 맞추고, 변경은 문자 인증으로 남김 |
| **암호문·다이제스트 저장 + 일회용 예약 증명 + QR 다이제스트 대조 (채택)** | DB에는 원문이 없고, 인증 통과 사실만 일회용 증명으로 전달함 |

연락처는 AES-256-GCM 암호문, 서버 키로 계산한 HMAC-SHA256 다이제스트, 끝 네 자리로 나눠 저장함. 학생 찾기와 예약 중복 확인은 다이제스트 일치로 하고, 원문은 관리자 명단 표시와 문자 발송 직전에만 복호화함. 문자·시트 outbox의 수신자·본문·스냅샷도 각각 다른 파생 키로 암호화함.[* [연락처 보호](https://github.com/gjaku1031/npr-seminar/blob/92598e6/apps/api/src/common/crypto/phone-protector.service.ts)]

문자 인증을 통과하면 256비트 무작위 예약 증명을 한 번만 돌려주고, DB에는 다이제스트·연락처·용도·만료만 둠. 예약 생성과 변경·취소는 같은 트랜잭션에서 이 증명을 소비하므로 하나의 증명으로 두 번 변경할 수 없음. QR도 다이제스트로 대조하고, 원문은 발급 응답과 본인 확인 후의 복구 조회에서만 내려감. 문자에는 QR 대신 예약 링크만 넣음.

### 대가

- 연락처로 부분 검색을 할 수 없음. 현장에서는 끝 네 자리 후보 최대 20건 중에서 고름
- 암호화·HMAC·QR 키를 서버 설정으로 관리해야 하고, 키를 잃으면 연락처를 복원할 수 없음
- 예약 링크 열람에 인증번호를 요구하지 않으므로, 링크와 연락처를 함께 가진 사람은 예약을 읽을 수 있음. 반복 시도는 예약·연락처·IP·전역 단위 횟수 제한으로 막음[* 링크를 가진 것과 연락처를 아는 것의 두 요소. 변경·취소는 여전히 문자 인증 필요]

## P3. outbox와 회로로 외부 실패를 예약에서 분리

### 문제

예약 하나가 확정 문자, 시트 행, (재원생이면) 학생 원장과 엮여 있음. 외부 서비스마다 실패하는 방식이 다름.

- 문자(Aligo): 요청을 보낸 뒤 연결이 끊기면 발송됐는지 알 수 없고, 요청 중복을 막는 멱등 토큰이 없음
- Google Sheets: 직원이 정렬·편집하면서 행 위치가 바뀌고, 공유 설정이 넓어지면 연락처가 유출됨
- 학생 원천(통통통): 세 캠퍼스가 계정 하나를 공유하고, 로그인 실패가 원천 쪽에 누적됨

예약 요청 안에서 이들을 직접 부르면 외부 지연이 예약을 붙잡고, 예약 커밋과 외부 호출 중 하나만 성공하는 구간이 생김.

### 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 예약 처리 중 외부 직접 호출 | 외부 장애가 예약 실패가 되고, 커밋 전 호출이 성공한 뒤 커밋이 실패하면 예약 없는 문자가 나감 |
| 별도 메시지 큐(Kafka·BullMQ) | 원장과 큐에 함께 쓰는 문제가 다시 생기고 운영할 구성 요소가 늘어남. 구현 지침에서 Kafka는 쓰지 않기로 함 |
| 결과 불명 문자를 자동 재시도 | 이미 발송된 문자가 한 번 더 나갈 수 있음 |
| **트랜잭션 outbox + lease worker + 결과 불명 시 중단 (채택)** | 예약이 커밋되면 발송 작업도 반드시 남고, 외부 호출은 커밋 뒤에만 일어남 |

worker는 `FOR UPDATE SKIP LOCKED`로 행을 집어 30초 lease를 걸고, 외부 호출 직전에 상태를 `SENDING`으로 바꿈. 호출 전에 lease가 만료되면 다시 대기열로 돌리지만, `SENDING` 상태에서 만료되면 `DELIVERY_UNKNOWN`으로 확정하고 다시 보내지 않음. 재시도 가능한 실패는 지수 지연으로 최대 5회까지 시도함.[* [문자 worker](https://github.com/gjaku1031/npr-seminar/blob/92598e6/apps/api/src/modules/sms/sms-worker.service.ts)]

시트는 애플리케이션이 멈췄을 때 현장에서 쓸 대체 명단임. 그래서 PostgreSQL에서 시트로만 씀. 시트에서 고친 값은 DB로 가져오지 않고, 행은 숨긴 표식 열로 찾음. 쓰기 전마다 시트의 공유 설정·로케일·탭 ID·머리글을 다시 확인하고, 링크·도메인·그룹 공유가 하나라도 있으면 쓰지 않고 매핑을 `BLOCKED`로 둠.[* [시트 단방향 동기화 결정](https://github.com/gjaku1031/npr-seminar/blob/92598e6/docs/specs/google-sheets-one-way-sync-20260717.md)]

학생 원천은 실행마다 로그인을 한 번만 시도하고, 시도 표식을 외부 로그인 전에 DB에 커밋함. 로그인이 거부되거나 결과가 불명확하면 회로를 열고, 사람이 원천 쪽 실패 횟수를 확인해 초기화하기 전까지 자동·수동 실행을 모두 거절함. 조회 결과는 staging에 적재·검증한 뒤 해시를 다시 대조해 세 캠퍼스 전체를 한 트랜잭션으로 승격함. 직전 성공 대비 캠퍼스별 행 수가 절반 미만이거나 1.5배를 넘으면 승격하지 않음.[* 직전 성공 조회가 20행 이상인 캠퍼스에만 적용. [동기화 실행](https://github.com/gjaku1031/npr-seminar/blob/92598e6/apps/api/src/modules/student-sync/student-sync-orchestrator.service.ts)]

### 대가

- 문자·시트는 비동기로 반영됨
- `DELIVERY_UNKNOWN` 문자는 사람이 공급자 기록과 대조해야 함. 중복 발송 대신 누락 가능성을 받아들임
- 학생 원천 회로가 열리면 사람이 확인하기 전까지 동기화가 멈추고, 그동안 원장은 마지막 성공본에 머묾

## 참고한 기법

| 결정 | 기법 | 이 프로젝트에서의 적용 |
| --- | --- | --- |
| P1 | 잠금 순서 고정에 의한 교착 회피, 부분 유니크 인덱스, 멱등 키(Idempotency-Key 헤더) | 행 잠금 순서를 모든 경로에서 같게 두고, 활성 예약만 고유 제약으로 막고, 재전송은 저장한 결과를 돌려줌 |
| P2 | 키를 쓴 해시로 검색하는 암호화 필드(blind index) | 연락처는 암호문으로 저장하고, 찾을 때는 HMAC 다이제스트 일치로만 찾음 |
| P3 | 트랜잭션 outbox, lease 기반 작업 소유, 회로 차단기(circuit breaker) | 외부 전송 작업을 예약과 같은 트랜잭션에 남기고, worker가 lease를 잡아 보내며, 학생 원천 로그인이 불명확하면 회로를 열어 자동 재시도를 막음 |
