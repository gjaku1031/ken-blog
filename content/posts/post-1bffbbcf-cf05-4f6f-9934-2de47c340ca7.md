Vowser는 사용자가 기록한 작업 경로를 Neo4j에 저장했음. 개발할 때는 "데이터가 많을수록 그래프 탐색이 빠르다"는 간단한 실험과, 벡터 검색을 같은 DB에서 쓸 수 있다는 점을 보고 골랐음. 그런데 그 실험의 조건과 수치가 남아 있지 않아, 같은 연산을 MySQL로도 구현해 2026년 9월에 다시 쟀음.

> 지금의 경로 구조에서는 모든 연산에서 인덱스를 둔 MySQL이 Neo4j보다 빨랐음. 차이를 가장 크게 만든 것은 DB 종류보다 트랜잭션을 어떻게 묶고 어떤 순서로 조회하느냐였음.

## 무엇을 알고 싶었나

대문의 핵심 문제 P1(사용자 기록을 단계 연결 경로로 저장)에서 고른 저장소가 맞았는지 다시 보고 싶었음. 세 가지를 물었음.

- 경로 등록, 인기 경로 조회, 시각화, 가중치 갱신처럼 지금 쓰는 연산에서 Neo4j가 더 빠른가
- 의도 벡터로 경로를 찾아 전체 단계를 돌려주는 검색에서는 어느 쪽이 빠르고 정확한가
- 지금은 없지만 그래프가 유리할 법한 기능, 즉 여러 경로가 단계를 공유하고 막힌 단계를 돌아가는 대체 경로 찾기에서는 Neo4j가 앞서는가

어느 DB가 빠를지 미리 가설을 세우지는 않았고, 공정하게 비교하는 절차만 실행 전에 정해 둔 탐색적 실험임.

## 어떻게 비교했나

원래 저장 코드의 구조(도메인 → 작업 의도 → 단계 → 다음 단계)를 그대로 따른 합성 경로를 1천, 1만, 3만 개 만들고, 같은 데이터를 두 DB에 넣었음. 경로 깊이와 도메인 쏠림, 읽기와 쓰기 비율도 바꿔 가며 쟀음.

한쪽에 유리하지 않게 몇 가지를 맞췄음. 두 DB 모두 같은 자원 한도에서 한 번에 하나만 띄웠고, 각자 할 수 있는 최적화(Neo4j는 제약과 인덱스, 한 번에 끝나는 Cypher, MySQL은 인덱스와 묶음 쓰기)를 해 두었음. 측정 전에 워밍업을 하고, 세 번 반복하면서 어느 DB를 먼저 돌릴지 순서를 바꿨음. 모든 응답은 미리 계산해 둔 정답과 맞는지 확인했음.[* DB 컨테이너 1 CPU·3GiB, 측정 코드 컨테이너 1 CPU·1GiB. 메모리 설정은 Neo4j가 힙 1GiB와 페이지 캐시 768MiB, MySQL이 버퍼 풀 1GiB. 지연은 드라이버와 localhost 왕복, 결과 조립, 커밋을 포함한 값이며 DB 내부 처리 시간만은 아님. 임베딩 생성과 LLM 호출은 빼고, 의도 검색에는 고정된 합성 벡터를 씀]

### 의도 검색

경로 1천 개와 1만 개, 고른 분포와 쏠린 분포 네 조건에서 상위 3개를 찾는 검색의 중앙값은 아래와 같았음. 도메인 힌트를 주는 경우와 주지 않는 경우를 나눠 쟀고, 이 여덟 조건의 요청 14,400개(진단용 조건까지 합치면 33,600개)에 오류는 없었음.

| 구현 | 힌트 없음 | 힌트 있음 |
| --- | ---: | ---: |
| MySQL + FAISS 벡터 인덱스 | 2.04~2.15ms | 1.85~2.04ms |
| Neo4j, 조회 순서를 고친 버전 | 10.52~12.01ms | 10.76~437.47ms |
| Neo4j, 원래 코드의 조회 순서 | 28.58~29.91ms | 26.51~28.41ms |

조회 순서를 고친 버전은 힌트가 없을 때 원래 버전보다 약 2.5배 빨랐지만, 힌트가 있으면 도메인 안의 모든 경로와 유사도를 직접 계산하는 방식이라 경로가 많고 한 도메인에 몰릴수록 크게 느려졌음(경로 1만 개, 쏠린 분포에서 437ms). 그대로 쓸 수 있는 개선은 아니었음.

원래 순서로도 1위는 190번 모두 맞았음. 다만 2위와 3위까지 순서가 맞은 건 경로 1천 개에서 190번 중 178~190번, 1만 개에서 150~164번이었음. 도메인으로 거르고 개수를 자르는 일이 다시 정렬하기 전에 일어나기 때문임. 경로 3만 개에서는 Neo4j가 벡터까지 포함한 데이터를 넣다가 메모리가 부족해 멈춰서 이 조건은 재지 못했음. 힙을 1GiB로 둔 이 설정에서의 문제이고, 힙을 늘려 다시 재 보지는 않았으므로 Neo4j의 일반적인 한계로 볼 수 없음.

### 그래프가 유리할 법한 기능

여러 경로가 단계를 공유하고, 막힌 단계를 돌아가는 대체 경로를 찾는 기능을 시험용으로 만들어 쟀음. 지금 Vowser에는 없는 기능임. 경로 수, 단계 공유 비율, 갈림길 수를 바꾼 16개 조건에서 38,400개 요청이 모두 정답이었음.

| 구현 | 중앙값 / p95(16개 조건 전체) |
| --- | ---: |
| Neo4j 경로 탐색 | 8.25 / 55.88ms |
| Neo4j 소속 테이블 방식 | 6.21 / 15.72ms |
| MySQL 재귀 쿼리 | 3.76 / 16.55ms |
| MySQL 소속 테이블 방식 | 3.18 / 8.13ms |

같은 방식끼리 조건별로 비교하면 16개 중 대부분(중앙값 14~15개, p95 15~16개)에서 MySQL이 빨랐음. Neo4j가 빠른 조건도 있었지만(경로 1천 개, 공유 50%, 갈림길 2·4개) p95까지 일관되지는 않았음.

## 결과가 말해 주는 것

지금의 경로는 기록마다 단계를 새로 만들어서, 서로 겹치지 않는 사슬이 여러 개 있는 모양임. 그래프 DB가 잘하는 공유 노드나 길이를 모르는 탐색을 거의 쓰지 않으니, 인덱스를 둔 관계형 DB의 단순 조회를 이기기 어려웠음.

속도 차이는 DB 종류보다 구현에서 더 크게 났음. 같은 Neo4j에서도 저장을 묶으면 등록이 약 16배 빨라졌고, 검색 순서를 고치면 힌트가 없는 조건에서 약 2.5배 빨라졌음. 그래프가 유리할 법한 대체 경로 기능에서도 이 규모에서는 앞서는 걸 확인하지 못했음.

그래서 지금 다시 고른다면, 관계형 DB 하나에 경로를 두고 벡터 검색만 따로 인덱스를 붙이는 쪽을 택하겠음. 운영할 DB도 하나 줄어듦. 이 결과에서 생긴 다음 질문은 "단계 공유가 아주 많고 탐색이 깊어지면 Neo4j가 앞서는가"인데, 그 규모는 재지 않아서 답하지 못함.

## 결과를 믿기 어려운 부분

Shadish·Cook·Campbell(2002)의 네 가지 관점으로 점검했음.

- **다른 원인이 섞였을 가능성**: 두 DB를 하나씩만 띄우고 순서를 바꿔 가며 돌려 캐시나 순서 효과를 줄였음. 다만 다른 서비스가 함께 돌던 VM이라 서버가 한가했다고 보장하지는 못함. 대체 경로 실험의 MySQL 소속 테이블 방식은 처음 잴 때 조인 순서가 불리하게 잡혀 있었고, 순서만 고쳐 따로 다시 쟀음. 처음 결과와 바꾼 기록은 남겨 두었음
- **일반화**: 합성 데이터에 요청을 하나씩 보내는 방식이라, 동시에 많은 요청이 올 때나 실제 사용자 경로의 분포는 말할 수 없음. 검색이 얼마나 정확한지는 [Vowser 의도 검색 정확도와 재검색 임계값](/ken-blog/post/post-ccb0e7cb-986a-4f7d-832e-ba4fd69e49e1/)에서 따로 다룸
- **재는 것이 맞나**: DB 파일을 메모리에 두는 tmpfs에 저장해서 실제 SSD의 읽고 쓰는 시간이 빠졌음. 지연은 측정 코드에서 본 왕복 시간이라 DB 자체의 성능 차이와 같지 않음
- **표본 크기**: 조건마다 세 번 반복했고 모든 응답을 정답과 대조했음. 경로 3만 개의 Neo4j 의도 검색은 재지 못해 그 조건의 비교가 없음
