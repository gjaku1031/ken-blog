[0편](/ken-blog/post/post-df978c72-44d3-4e81-b572-8834cd0646c3/)의 확인 질문에 "`Cookie` 헤더는 브라우저가 넣는다"고 적었다. 그런데 로그인은 프레임워크가 알아서 처리해 줘서, 개발자 도구에 보이던 `JSESSIONID`가 정확히 무엇인지는 들여다본 적이 없었다. 서버는 요청마다 따로 받는데 어떻게 방금 로그인한 사람을 알아보는지, 로그인을 흉내 내는 작은 서버를 만들어 확인해 봤다.

## 학습 목표

- HTTP가 요청 사이의 상태를 기억하지 않는다는 것과, 그래서 쿠키가 필요한 이유를 설명할 수 있다
- `Set-Cookie`와 `Cookie`가 오가는 순서와, 세션 ID와 서버 쪽 저장소의 관계를 설명할 수 있다
- `HttpOnly`, `Secure`, `SameSite`가 각각 무엇을 막는지 말할 수 있다

## HTTP는 손님을 기억하지 못한다

HTTP 요청은 하나하나가 독립적이다. 같은 사람이 1초 간격으로 요청을 두 번 보내도, 서버 입장에서 두 요청을 이어 주는 것은 메시지 안에 아무것도 없다. 이걸 HTTP가 무상태(stateless)라고 한다.[* 하나의 TCP 연결로 여러 요청을 보내더라도 마찬가지다. 연결은 언제든 끊기고 다시 열릴 수 있고, 프록시나 CDN이 여러 사용자의 요청을 한 연결로 모아 보내기도 해서 연결을 사람의 표시로 쓸 수 없다]

창구 직원이 손님을 매번 처음 보는 은행을 떠올리면 된다. 로그인한 뒤 "내 주문 목록 주세요"라고 하면 직원은 "누구신데요?"라고 물을 수밖에 없다. 그래서 요청마다 "나는 아까 그 사람이다"를 증명할 무언가를 들고 가야 한다.

## 쿠키와 세션: 옷 보관소의 번호표

옷 보관소에 외투를 맡기면 번호표를 받는다. 찾을 때는 번호표만 내밀면 되고, 번호표에는 내 이름이 적혀 있지 않다. 누구의 외투인지는 보관소 장부가 안다. 쿠키와 세션이 이 구조다.

1. 로그인 요청에서 아이디와 비밀번호가 맞으면, 서버는 짐작할 수 없는 긴 번호(세션 ID)를 만들고 "이 번호 = kim"을 서버 쪽 장부(세션 저장소)에 적는다
2. 응답에 `Set-Cookie: SID=번호` 헤더를 붙인다. "이 번호표를 가지고 있어"라는 뜻이다
3. 브라우저는 이 번호표를 그 사이트 칸에 저장한다. 이게 쿠키다
4. 이후 같은 사이트로 가는 요청마다 브라우저가 알아서 `Cookie: SID=번호`를 붙인다
5. 서버는 번호를 장부에서 찾아 "kim이구나" 하고 처리한다

쿠키는 결국 사이트별로 저장되는 `이름=값` 한 줄이고, 세션은 그 값이 가리키는 서버 쪽 기록이다. 그래서 번호표만 있으면 장부는 그 사람으로 대한다. 번호표를 훔치면 로그인한 사람 행세를 할 수 있다는 뜻이기도 하다.[* 쿠키의 규칙은 RFC 6265가 정한다. Tomcat은 세션 쿠키 이름으로 `JSESSIONID`를 기본으로 쓴다. 장부를 두지 않고 서명한 사용자 정보를 쿠키나 헤더에 직접 담는 방식(예: JWT)도 있지만, 이 글에서는 세션 ID 방식만 다룬다]

## 번호표에 붙는 조건들

`Set-Cookie`에는 값 말고도 "이 번호표를 언제, 어디로 보낼지"를 정하는 속성이 붙는다.

| 속성 | 예 | 정하는 것 |
| --- | --- | --- |
| `Domain` | `Domain=example.com` | 어느 호스트로 보낼지. 없으면 쿠키를 준 호스트에만 보냄 |
| `Path` | `Path=/` | 어느 경로 아래 요청에 보낼지 |
| `Expires` / `Max-Age` | `Max-Age=3600` | 언제까지 보관할지. 둘 다 없으면 브라우저를 닫을 때 지워지는 세션 쿠키 |
| `HttpOnly` | `HttpOnly` | 페이지의 자바스크립트(`document.cookie`)가 읽지 못하게 함 |
| `Secure` | `Secure` | HTTPS 연결로만 보냄 |
| `SameSite` | `SameSite=Lax` | 다른 사이트에서 시작된 요청에도 보낼지 |

`HttpOnly`는 페이지에 끼어든 악성 스크립트가 번호표를 읽어 빼 가는 것(XSS로 인한 세션 탈취)을 막는다. `Secure`는 암호화되지 않은 연결에서 번호표가 그대로 보이는 것을 막는다. HTTPS가 연결에 자물쇠를 채우는 방법은 [8편](/ken-blog/post/post-fe24a8b3-892f-4e3f-aeb6-13437ed47aaa/)에서 다룬다.

### 헷갈렸던 것: `SameSite=Lax`인데 링크로 들어오면 쿠키가 간다

`SameSite`는 요청이 어디서 시작됐는지를 본다. 다른 사이트의 페이지가 내 사이트로 요청을 보내게 만드는 공격(CSRF)을 막으려는 속성이다.

| 값 | 다른 사이트에서 시작된 요청에 쿠키를 보내나 |
| --- | --- |
| `Strict` | 보내지 않음. 다른 사이트의 링크를 눌러 들어와도 보내지 않음 |
| `Lax` | 이미지, `fetch` 같은 하위 요청에는 보내지 않음. 링크를 눌러 페이지를 이동하는 GET에는 보냄 |
| `None` | 항상 보냄. 이때는 `Secure`도 함께 붙여야 브라우저가 받아 줌 |

처음엔 `Lax`면 다른 사이트에서 오는 요청에는 쿠키가 아예 안 가는 줄 알았다. 실제로는 사용자가 링크를 눌러 이동하는 경우는 허용한다. 다른 사이트에서 링크로 들어왔는데 로그인이 풀려 있으면 불편하기 때문이다. 그래서 `Lax`만 믿고 상태를 바꾸는 동작을 GET으로 만들면 안 된다.[* 여기서 사이트(site)는 스킴과 등록 가능한 도메인으로 정해지는 범위라서, `a.example.com`과 `b.example.com`은 같은 사이트다. 스킴, 호스트, 포트가 모두 같아야 하는 출처(origin)보다 넓다. Chromium은 `SameSite`를 적지 않은 쿠키를 `Lax`처럼 다룬다]

## 직접 확인해 보기

로그인을 흉내 내는 서버를 파이썬으로 만들었다. `/login`은 세션 ID를 만들어 딕셔너리(장부)에 적고 두 쿠키를 준다. 세션 쿠키 `SID`에는 `HttpOnly`를 붙이고, 화면 설정용 `theme`에는 붙이지 않았다. `/me`는 `SID`로 장부를 찾아 사용자를 돌려준다. 서버는 받은 요청마다 경로와 `Cookie` 헤더를 출력한다.[* 2026-10-23, Linux VM. 서버는 Python 3.14.4의 `http.server`, 클라이언트는 curl 8.18.0과 Playwright로 띄운 Chromium 153.0.8010.12. 응답의 `Date`, `Server` 줄은 생략했다. 세션 ID는 실행할 때마다 새로 만들어지는 임의 값이다] 서버 코드의 핵심만 줄여 적으면 이렇다.

```text
SESSIONS = {}  # 세션 ID -> 사용자 (서버 쪽 장부)

# /login
sid = secrets.token_urlsafe(16); SESSIONS[sid] = "kim"
Set-Cookie: SID={sid}; Path=/; Max-Age=3600; HttpOnly; SameSite=Lax
Set-Cookie: theme=dark; Path=/; Max-Age=3600

# /me
user = SESSIONS.get(쿠키의 SID)  # 있으면 200 "안녕하세요, {user}", 없으면 401
```

### curl로 번호표 받고 내밀기

```text
$ curl -i http://127.0.0.1:18211/me
HTTP/1.0 401 Unauthorized
Content-Type: text/plain; charset=utf-8
Content-Length: 29

누구신지 모르겠어요

$ curl -i -c jar.txt http://127.0.0.1:18211/login
HTTP/1.0 200 OK
Set-Cookie: SID=XAxA5yx1By08VHq_GTaPEw; Path=/; Max-Age=3600; HttpOnly; SameSite=Lax
Set-Cookie: theme=dark; Path=/; Max-Age=3600
Content-Type: text/plain; charset=utf-8
Content-Length: 13

로그인함

$ cat jar.txt
127.0.0.1	FALSE	/	FALSE	1792792935	theme	dark
#HttpOnly_127.0.0.1	FALSE	/	FALSE	1792792935	SID	XAxA5yx1By08VHq_GTaPEw

$ curl -b jar.txt http://127.0.0.1:18211/me
안녕하세요, kim
```

서버 쪽에서 본 `Cookie` 헤더는 이랬다.

```text
/me | Cookie: None
/login | Cookie: None
/me | Cookie: theme=dark; SID=XAxA5yx1By08VHq_GTaPEw
```

| 출력 | 뜻 |
| --- | --- |
| 첫 `/me`의 401 | 번호표 없이 가면 서버는 누군지 모름 |
| `Set-Cookie` 두 줄 | 서버가 번호표를 건넴 |
| `jar.txt` | curl의 쿠키 보관함. `-c`로 저장하고 `-b`로 꺼내 보냄. `HttpOnly` 쿠키는 `#HttpOnly_` 표시가 붙음 |
| 마지막 `/me`의 `Cookie:` | 저장해 둔 번호표가 요청 헤더로 실려 감 |

curl은 브라우저가 아니라서 `-c`, `-b`를 붙여야 쿠키를 저장하고 보낸다. 브라우저가 "알아서" 해 주던 일을 손으로 해 보니 쿠키가 특별한 게 아니라 응답 헤더로 받고 요청 헤더로 돌려주는 문자열이라는 게 실감 났다.[* `jar.txt`의 앞 세 줄 주석은 생략했다. 숫자 `1792792935`은 만료 시각(유닉스 시간)이다]

### 브라우저에서 `HttpOnly` 확인

```text
document.cookie = "theme=dark"
SID    httpOnly=true  sameSite=Lax path=/
theme  httpOnly=false sameSite=Lax path=/
/me = 안녕하세요, kim
```

Chromium으로 `/login`에 들어간 뒤 페이지 안에서 `document.cookie`를 읽으면 `theme=dark`만 나왔다. 브라우저의 쿠키 목록에는 `SID`도 분명히 있고, `/me` 요청에도 실려 가서 로그인이 유지됐다. 스크립트에게만 숨긴 것이다. `SameSite`를 적지 않은 `theme`도 `Lax`로 나왔다.

### 다른 사이트에서 시작된 요청

`localhost:18212`에 다른 사이트 역할을 하는 페이지를 띄웠다. 이 페이지는 이미지 태그로 `http://127.0.0.1:18211/me?via=img`를 부르고, 같은 주소로 가는 링크(`?via=link`)를 하나 갖고 있다. 먼저 `127.0.0.1:18211/login`에서 로그인한 다음 이 페이지를 열고 링크를 눌렀다.[* 사이트를 판단할 때 IP 주소는 그 자체가 하나의 사이트라서 `localhost`와 `127.0.0.1`은 서로 다른 사이트다]

```text
/me?via=img  | Cookie: None
/me?via=link | Cookie: SID=8liYD5WyGL9G4xXN1Ds6yw; theme=dark
```

이미지 요청에는 쿠키가 하나도 실리지 않았고, 링크로 이동한 요청에는 둘 다 실렸다. 표에서 본 `Lax`의 동작 그대로다.

### 번호표를 훔치면

curl의 `jar.txt`에 있던 `SID` 값을 꺼내, 쿠키 보관함 없이 헤더로 직접 넣어 보냈다. 그다음 원래 주인이 로그아웃하고 같은 값을 다시 보냈다.

```text
$ curl -H "Cookie: SID=XAxA5yx1By08VHq_GTaPEw" http://127.0.0.1:18211/me
안녕하세요, kim
$ curl -b jar.txt http://127.0.0.1:18211/logout
로그아웃함
$ curl -H "Cookie: SID=XAxA5yx1By08VHq_GTaPEw" http://127.0.0.1:18211/me
누구신지 모르겠어요
```

서버는 번호만 보고 판단하니 값을 아는 누구든 kim이 됐다. 로그아웃해서 장부에서 그 번호를 지우자 같은 값이 더는 통하지 않았다. 세션 방식에서는 서버가 장부를 갖고 있어서 번호표를 바로 무효로 만들 수 있다는 뜻이다. 반대로 `HttpOnly`가 막는 것은 스크립트로 읽는 경로 하나뿐이라서, 번호표가 다른 경로로 새어 나가면 막지 못한다.

> 쿠키는 서버가 `Set-Cookie`로 건네고 브라우저가 `Cookie`로 돌려주는 번호표이고, 세션은 그 번호가 가리키는 서버 쪽 장부다. 번호만 알면 그 사람이 되므로, `HttpOnly`, `Secure`, `SameSite`로 번호표가 새는 길을 하나씩 막는다.

## 확인 질문

**1. HTTP가 무상태라는 건 무슨 뜻이고, 그래서 로그인 유지에 무엇이 필요할까?**

<details><summary>답</summary>

요청 하나하나가 독립적이라 서버가 메시지만으로는 두 요청이 같은 사람에게서 왔는지 알 수 없다는 뜻이다. 그래서 요청마다 "나는 아까 그 사람"임을 보여 줄 값이 필요하고, 그 값을 브라우저가 자동으로 실어 보내게 하는 장치가 쿠키다.

</details>

**2. 세션 방식에서 쿠키 안에는 무엇이 들어 있고, 사용자 정보는 어디에 있을까?**

<details><summary>답</summary>

쿠키에는 짐작할 수 없는 세션 ID만 들어 있다. "이 ID = 어떤 사용자"라는 기록은 서버 쪽 세션 저장소(장부)에 있다. 그래서 서버가 장부에서 ID를 지우면 같은 쿠키를 보내도 로그인이 풀린다.

</details>

**3. `HttpOnly`를 붙인 쿠키는 요청에 실려 가지 않을까?**

<details><summary>답</summary>

실려 간다. `HttpOnly`는 페이지의 자바스크립트가 `document.cookie`로 읽지 못하게 할 뿐이고, 브라우저는 요청마다 그대로 보낸다. 실습에서도 `document.cookie`에는 `SID`가 없었지만 `/me` 요청에는 실려 가서 로그인이 유지됐다.

</details>

**4. `SameSite=Lax`인 쿠키는 다른 사이트의 페이지에서 내 사이트로 가는 링크를 눌렀을 때 실려 갈까?**

<details><summary>답</summary>

실려 간다. `Lax`는 이미지나 `fetch` 같은 하위 요청에는 쿠키를 붙이지 않지만, 사용자가 링크를 눌러 페이지를 이동하는 GET에는 붙인다. 그래서 상태를 바꾸는 동작은 GET으로 만들지 않아야 한다.

</details>

**5. 공격자가 내 세션 ID 값을 알아냈다면 서버는 어떻게 대응할 수 있을까?**

<details><summary>답</summary>

서버 쪽 장부에서 그 세션 ID를 지우면 된다. 로그아웃이 바로 그 일을 한다. 실습에서도 로그아웃한 뒤에는 같은 값을 보내도 401이 나왔다. 장부가 서버에 있다는 점이 세션 방식의 장점이다.

</details>
