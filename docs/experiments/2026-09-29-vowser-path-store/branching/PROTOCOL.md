# 실험 3 사전 동결 프로토콜 — 미구현 분기·공유 STEP 프로토타입

2026-09-29 본측정 전 고정. 이 기능은 현재 Vowser 제품에 구현되지 않았다. 원본 `neo4j_service.py`의 선형 `NEXT_STEP*0..20 LIMIT 1` 질의를 분기 기능으로 간주하지 않는다. 원본 agent-server HEAD `d94eaf5f30f734952838528d7045e0eab8891509`, 해당 소스 SHA-256 `153593f35d9d32aad2416dd8efddc63629a1d2b0047a9bcfb74dd3add3a94e58`. 공유 입력 생성기 `shared/data.py` SHA-256 `b65551b2a388dfbe80e811dddfd385e6f5245ebc5d2204f7171270c498e4855e` (현재 최초 동결본; 실행 직전 재확인).

## 입력과 matrix

seed `20260929`. 한 셀의 등록 경로 총수 N은 1,000 또는 10,000이다. `shared.data.path_record`의 정수 path ID, 도메인 30개, 깊이 5/10/20 연결(각각 N/3 내외)을 사용한다. 같은 도메인에서 대체 경로가 생기도록 이 **프로토타입에서만** 공유 입력의 96개 의도를 `task-family-{intent_id % 4}` 네 범주로 투영한다. 원래 intent ID도 함께 보존한다. 인증 상태는 `(path_id // 90) % 2`이며 공유 단계는 같은 도메인·투영 의도·인증 상태 안에서만 합친다. 이 추가 계약은 현재 제품의 sessionId 기반 STEP ID와 다르다. 같은 N의 구조 셀들은 문맥·source path 선택 난수 순서를 공유해 비교 입력을 짝짓는다.

| 경로 수 | 공유율 목표 | 최대 분기(서로 다른 후속 STEP 수) |
|---:|---:|---:|
| 1,000 | 0%, 25%, 50% | 각 비율마다 1, 2, 4 전체 9셀 |
| 10,000 | 0% | 1 |
| 10,000 | 25%, 50% | 각 비율마다 1, 2, 4 전체 6셀 |

총 16셀, 각 셀의 깊이 3종 포함. 10,000경로·공유0%·분기상한2/4는 생략한다. 따라서 규모 10,000에서 공유율0%와 분기상한의 상호작용은 해석하지 않는다. 공유0%에서는 상한이 2/4여도 실제 최대 out-degree는 1일 수 있다. 각 셀의 실제 공유율, STEP 수, 물리/고유 edge 수와 in/out-degree 분포를 따로 보존한다. 50/100 연결은 아래 별도 한계 탐색으로 분리하며 동시성8은 측정하지 않는다.

**공유율 분모:** 전체 `(경로 ID, 단계 순서, STEP ID)` 소속 건수. 이 가운데 둘 이상의 등록 경로에 속하는 STEP의 소속 건수 / 전체 소속 건수. **압축률:** `1 - 고유 STEP 수 / 전체 소속 건수`. 재사용률과 압축률은 다른 값이다. 목표 25/50%는 구조 생성 목표이며 실제 값은 반올림·홀수 군집·공통 인증 단계 때문에 별도로 측정한다.

0%에서는 모든 STEP을 경로별로 둔다. 25/50%에서는 동일 문맥 경로가 마지막 인증 STEP 하나를 공유한다. 상한1은 같은 길이·문맥 경로의 끝 suffix를 더 공유하여 병합만 허용한다. 상한2/4는 같은 길이·문맥 경로를 최대 해당 수로 묶어 prefix를 공유하고 이후 분기한다. prefix/suffix 길이는 `round(목표율 × (depth+1))`을 기준으로 하고 인증 STEP 한 개를 포함한다. 공유 STEP의 URL·selector·action·description도 해당 문맥·단계·군집에 맞게 canonical화하며, 원본의 path ID 포함 URL을 그대로 한 노드에 합치지 않는다. 경로별 `MEMBER(pathId,ordinal,stepId)`와 `NEXT(pathId,ordinal,from,to)`를 명시하므로 공유 노드에서 다른 경로 조각으로 갈아타는 결과를 금지한다. 관계는 물리적으로 경로별 중복 가능하며 distinct 후속 STEP 수와 물리 관계 수를 구분한다.

## 질의·오라클·측정

동일 도메인·투영 의도·인증 상태에서 막힌 STEP ID가 하나도 없는 **등록 경로**를 연결 수, path ID 오름차순 top3로 반환한다. 전체 STEP의 순서·ID·URL·action·selector·description을 반환한다. 네 비교군은 Neo4j `NEXT` 실제 가변 길이 탐색, MySQL indexed adjacency 재귀 CTE, Neo4j membership, MySQL indexed membership이다. 네 군 모두 root 후보 탐색, 막힌 STEP 제외, top3 선정, 전체 결과 반환, 같은 Python 필드 정규화·JSON 직렬화를 요청 시간에 포함한다. **Traversal 군은 membership으로 유효 경로를 먼저 고르지 않는다.** 문맥 root에서 출발해 STEP 차단을 확장 중 검사하고, 경로 ID·ordinal·from/to 연결을 지킨 완주 경로만 top3로 선택한다. Membership 군은 명시 소속으로 막힌 STEP을 필터한 후 저장된 순서로 반환하는 강한 기준선이다. 인덱스·제약·쿼리 원문·EXPLAIN/PROFILE은 보존한다.

셀마다 고정된 200질의: 160개는 대체 경로 사례이며 목표 깊이 5/10/20을 순환해 각각 54/53/53개다. 목표 깊이보다 짧은 등록 경로는 각 경로의 고유 STEP 하나를 차단하고 현재 목표 깊이 경로도 고유 STEP 하나를 차단한다. 이로써 유효 top3가 실제로 세 깊이를 모두 시험한다. 한계 탐색에서는 모든 경로가 해당 고정 깊이이므로 현재 경로 하나만 차단한다. 나머지 20개는 문맥의 모든 등록 경로가 막힌 `none`, 20개는 공통 인증 STEP 차단(공유0%라면 각 경로의 인증 STEP 전부 차단)이다. 기대 답은 저장 전 생성된 전체 path membership 원장으로 독립 계산한다. 작은 smoke 입력에서는 모든 문맥의 모든 source 경로 단일 차단과 문맥별 `none`·인증 차단을 확인한다. 본측정의 모든 질의·모든 모드 결과 해시를 oracle과 대조하고 경로 오염, 막힌 STEP 포함, 누락/순서 오류를 별도 집계한다.

각 셀에서 MySQL만 켜고 적재·전량 검증한 뒤 정지, Neo4j만 켜고 적재·전량 검증한 뒤 정지한다. 이후 round0은 MySQL→Neo4j, round1은 Neo4j→MySQL, round2는 MySQL→Neo4j 순으로 DB 하나만 기동한다. DB 재시작마다 실행 계획·캐시가 소실될 수 있으므로 **매 round·DB 블록에서 두 모드 각각 200질의 warmup 뒤 200질의 본측정**을 한다. 따라서 기본16셀의 warmup은 16×3×2DB×2모드×200=`38,400`, 본측정도 `38,400`, 합계 `76,800` 요청. 원래 1회 warmup/셀·모드 계획의 12,800→38,400 증가는 단일 활성 DB 자원 계약을 지키기 위한 본측정 전 변경이다. round마다 DB 순서와 DB 내 두 모드 순서를 교차한다. 단일 클라이언트, DB 기동·인증 health·연결·적재는 개별 요청 타이머 밖, root 탐색부터 전체 정규화 JSON 생성까지만 측정, SHA/오답 판정은 타이머 밖. 요청당 DB 2초 제한. timeout·오류·오답도 해당 모드의 600 본측정 시도 분모에 남긴다. 각 셀 시작 전 해당 실험 전용 객체만 새로 적재하고 경로 수·인덱스 ONLINE·오라클 해시를 검증한다. 셀별 적재/색인 시간과 저장량도 기록한다. 전체 본측정 60분 상한에 닿으면 남은 셀을 임의 삭제하지 않고 미완료로 기록한다. 결과가 나온 셀만 성공률·지연을 계산하며 미완료 전체를 완주 결과처럼 서술하지 않는다.

자원: **동시에 DB 하나만 활성화**, MySQL 또는 Neo4j DB `1 CPU/3 GiB` + 동일 Python worker `1 CPU/1 GiB` (비교군당 합계 `2 CPU/4 GiB`). localhost 전용 실험 DB, 2026-09-29 `shared/CONTRACT.md` 계약. 각 재기동은 TCP ready 뒤 인증 `SELECT 1`/`RETURN 1` 성공을 최대 90초 재시도하고 warmup 전 수행한다. 다른 두 실험의 본측정 종료·상위 승인 후 본측정 시작. 제품 코드·기존 실험은 변경하지 않는다.

본측정 전 수정 기록: 최초 720경로 스모크 직전 adjacency 질의가 membership으로 먼저 top3를 고른 뒤 복원하는 구조였음을 검토에서 발견하여, 위에서 정의한 **확장 중 차단·완주 후 선정** 쿼리로 바꾸고 스모크했다. 첫 스모크의 Neo root는 6열 index를 사용하지 않아 `NodeByLabelScan`이었다. 이를 4열 문맥 인덱스로 교체한 뒤 `ONLINE` 및 `NodeIndexSeek`를 별도 계획에서 확인했다. 또 최초 200질의는 최단 top3가 항상 깊이5를 반환하는 coverage 결함이 있어 본측정 전에 160 대체 사례를 목표 깊이별 54/53/53으로 층화했다. 마지막으로 공용 자원 계약 검토에서 dual-DB 동시 활성 runner를 제거하고 위 단일 활성 DB·매 재기동 warmup으로 교체했다. 이 변경들은 모두 본측정 전이며 검색/운영 실험 데이터와 무관하다. 이전 스모크 원시 자료는 보존하며 성능 본측정으로 사용하지 않는다. 요청별 `blocked_count`, 목표 깊이, 반환 경로 수·STEP 수를 저장한다. 정상 대체와 `none`·인증 차단의 지연은 분리한다. 더 긴 깊이 사례의 차단 목록이 커지므로 깊이만의 인과 효과로 해석하지 않는다.

운영 실험의 호스트 실행 세션에서 SIGTERM 143이 관측되어 본측정 전 실행 제어를 보강했다. `bash branching/managed.sh start measure` 및 `start measure-stress`는 도구 세션과 분리된 session leader를 띄우고 `results/managed.state`에 PID·시작 tick·로그를 보존한다. `managed.sh status`는 PID 재사용을 구별하며, `managed.sh stop GROUP`은 해당 process group을 종료하고 이 실험 전용 worker 이름 `vowser-eval-v2-br3` 및 활성 DB를 정리한다. orchestrator도 SIGTERM 상태·부분 CSV를 기록하고 정리를 시도한다. **위 60분 상한은 본측정 군마다 경과 검사와 SIGALRM watchdog을 함께 적용**하며 질의·조건·실패 분모는 변경하지 않았다. 스모크도 같은 제어를 사용한다. 실행/정리 로그와 상태 JSON은 보존한다.

수정 후 정합 스모크도 단일 활성 DB로 수행한다. 기본은 720경로·공유50%·상한4에서 모든 문맥의 각 source 경로 단일 차단 및 문맥별 `none`/인증 차단 840사례×4군=3,360조회. 한계는 360경로·100연결·공유50%·상한4에서 고정 200질의×4군=800조회. 스모크 자료는 본측정 latency 집계에 합치지 않으며 각 DB의 BR3/br3 객체는 스모크 종료 직후 정리한다.
