API의 기본 런타임을 Native Image 대신 일반 JVM으로 정하면서, 측정 당시의 1코어·약 4GB 서버에서 JVM이 감당할 수 있는지 확인한 측정. 분류: 탐색적 실험(2026-10-02). 이전 구현에서 같은 코드·1 CPU·1GiB 조건으로 비교했을 때 읽기 요청 120회 후 메모리 중앙값이 JVM 684MiB, Native Image 136MiB였음[* 2026-09 측정, Native Image를 쓰던 이전 구현 기준. [인프라 ADR](https://github.com/gjaku1031/ken-blog/blob/1072a36/docs/ADR/ADR_infra.md)의 과거 Native Image 검증 이력]. JVM이 약 5배의 메모리를 쓰지만 약 4GB 서버에서는 감당할 수 있다고 보고, 리플렉션 설정 유지와 학습 비용이 큰 Native Image 대신 일반 JVM을 택함. 대가는 큰 메모리 사용과 긴 기동 시간.

> 측정한 요청 조합에서 API는 1.5GiB 컨테이너 한도 안에서 OOM과 재시작 없이 유지됐음. 200건/초 구간에서 p95 33.41ms, 호스트 평균 CPU 88.4%, API 메모리 최대 474.5MiB.

## 연구 질문

측정 당시의 1코어·약 4GB 서버에서 일반 JVM API가 메모리 한도 안에서 요청을 처리할 수 있는가. [ken-blog 대문](/ken-blog/post/project-06840552-43a2-4870-83a9-d3e848c71d7e/)의 핵심 문제 P2(제한된 자원에서의 열람 성능)와 연결됨. 도착률과 요청 종류는 실행 전에 정했지만, 통과로 볼 지연·메모리 기준은 기록에 남아 있지 않음.

## 해석

- 측정한 요청 조합에서 API는 1.5GiB 한도 안에서 OOM과 재시작 없이 유지됐고, 메모리 최대는 474.5MiB로 한도의 약 31%였음
- 200건/초에서 호스트 CPU가 88.4%까지 올라, 이 서버에서 이 요청 조합의 여유는 크지 않았음
- 도착률이 오를 때 p95가 단조 증가하지 않았음(10건/초 23.55ms, 100건/초 10.17ms). 요약 결과만으로는 원인을 확정하지 못함

## 타당성과 한계

- **내적 타당성**: 테스트 MySQL이 같은 서버에서 돌았고, CPU는 API만이 아니라 MySQL·OS를 포함한 호스트 전체 값임
- **외적 타당성**: 2026-10-02 당시 이미지와 스냅샷 v2 결과임. 현재 운영 이미지·DB의 성능, 최대 처리량, 장기 메모리 안정성으로 확대하지 않음
- **구성 타당성**: 공개 상태·배지는 당시 API 요청 조합이며, Pages의 HTML 전송이나 브라우저 렌더링 측정이 아님
- **통계적 타당성**: 시나리오마다 30초 관측 한 번이고, 스냅샷 p95는 15회 관측에 한정됨
